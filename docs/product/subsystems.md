# Product subsystem map

Use this map to follow a user's action to the component that owns the work, its
durable state, and its recovery. It describes the implementation, including gaps;
the [principles](principles.md) describe product intent and the
[punchlist](friction.md) records open gaps and their product decisions.

Ownership here means code responsibility, not a team or person. A client can show
a failure while another component owns its cause. Follow both sides before adding
a retry, refusal, banner, or repair action.

Version skew between hub, daemons, clients and remote hubs follows the
direction rules in the [compatibility policy](README.md#compatibility).

## How the product fits together

```mermaid
flowchart TD
    Web[Browser] --> TS[Shared TypeScript client and state]
    Native[Native phone app] --> TS
    TS --> Hub[Hub: routing, hosts, settings, navigation]
    Playdate[Playdate C client] --> Hub
    Playdate --> Transcription[OpenAI Realtime transcription]
    Hub --> Local[Local session daemon]
    Hub --> Remote[SSH attachment to remote hub]
    Remote --> RemoteDaemon[Remote session daemon]
    Local --> Agent[Session engine]
    RemoteDaemon --> Agent
    CLI[Noninteractive CLI] --> Agent
    Agent --> Providers[LLM providers]
    Agent --> Tools[File, shell, MCP, hooks and delegates]
    Agent --> State[Transcript, intent, jobs and delegate journals]
    Agent --> Memory[Host-owned personal and project memory files]
    State --> Views[History projections and indexes]
    Views --> Hub
```

Arrows show responsibility and data flow, not shared memory. Local and remote
daemons have their own state roots. AppWire carries client control, daemon control,
and ordered events; the hub also exposes HTTP surfaces. The installed `evener`
executable provides the commands that launch these processes. See
[architecture](../architecture.md) for module boundaries.

## Clients and interaction

The [Playdate client](playdate-client.md) is a small additional client surface.
Its [separate C repository](https://github.com/prime-radiant-inc/evener-client-playdate) owns paged navigation,
chat projection, scrolling, immediate microphone capture, recoverable audio,
review drafts and persisted mutation identity. Its native Tailscale transport
owns DERP, WireGuard, TCP, native enrollment, authenticated control maps and
device identity recovery. The Hub owns generic short-lived device invitations and browser approvals;
[device pairing](../device-pairing.md) defines the shared QR/acoustic wire format
and encrypted credential delivery. The Hub also owns automatic destination
discovery from the browser origin, listener and network interfaces;
the browser presents that default and lets the operator edit it before creating
an invitation. Ordinary LAN/tailnet setup requires no configuration-file edit.
Mobile settings distinguish the direct phone QR from sound invitations. Sound
setup keeps playback and approval in one flow, with all eight comparison groups
shown as four lines of two. Phone setup offers manual address entry and a QR
invitation through the same approval flow when discovery fails or the phone
needs a different destination.
The parent settings view owns setup dismissal,
keeping the loaded phone pairing link accessible while sound setup loads or fails.
The browser sends invitations and confirms matching codes. Clients own durable
settings and saved work scoped by destination
and authenticated Tailscale peer. S05 AppWire
and S06 Hub routing own its session protocol;
S10 history and S11 durable intent remain authoritative for recorded messages
and accepted input. The device reconnects and hydrates that authority, preserving
its drafts. OpenAI owns transcription; the device connects directly using SDK
TLS, without a Hub or Mac transcription proxy.

## Maintaining the map

Native S03 built-in commands retire edited recovery through a draft-owned
completion marker and S11's exact-source cleanup coordinator. `/steer` and
`/queue` remain message submissions whose source ownership settles only from an
exact resend receipt; command completion is not send evidence. See the
[message recovery contract](message-recovery.md#native-controls-and-recovery).

When a change moves an owner, adds a persistent store, changes a recovery trigger,
introduces a surface, or changes a user-visible boundary, update the affected row
and its owning guide in that change. Keep the user-task table and diagram aligned
with the rows. Link to stable source paths and named responsibilities; avoid line
numbers and duplicated protocol field lists in this map.

The `S`-IDs are stable keys, not a dense sequence: a retired subsystem leaves a
gap (S04 is a retired client surface) and the surviving IDs are never renumbered,
because every other doc and row references them by number. Add a new subsystem at
the next unused ID rather than renumbering.

For a failure path, be able to name the retained intent, the authoritative state,
the smallest affected scope, the component that detects recovery, and the event
that resumes work. If the implementation has no such owner or event, record the
gap in the punchlist rather than describing an intended repair as implemented.
