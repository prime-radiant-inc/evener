# Named Pinned Session Sections — Design Spec

Date: 2026-08-03
Status: Approved
Scope: Serf Hub WebUI session pins

## Summary

Replace the WebUI's single session-level **Pinned** list with user-named pinned sections. Each pinned session belongs to exactly one section. Non-empty sections appear as alphabetical, collapsible peers of **Live** and **Projects** in the sidebar. Users choose or create a section from the session's pin menu.

This design applies only to session pins. Project favorites keep their existing behavior and storage.

## Goals

- Help users organize many current, in-progress sessions.
- Preserve one-step access to pinned sessions in the sidebar.
- Let users create, name, rename, reuse, and delete sections.
- Keep section and assignment state durable across browsers and Hub restarts.
- Preserve the current **Live** view, including its overlap with pinned sessions.

## Non-goals

- Multiple sections or labels on one session.
- Manual ordering of sections or sessions.
- Drag-and-drop assignment or reordering.
- A central section-management screen.
- Named sections for project favorites.
- Synchronizing sidebar disclosure state across browsers.

## User Experience

### Sidebar layout

Each non-empty pinned section appears as a top-level sidebar section between **Live** and **Projects**. The sidebar does not retain a separate **Pinned** umbrella.

Section names sort alphabetically with a case-insensitive comparison. Sessions within each section sort by most recent activity, matching the current favorites list's ordering. A live pinned session appears in both **Live** and its pinned section.

Each section is independently collapsible. The WebUI stores disclosure state in the browser through the rail's existing expansion-state mechanism. Section identity, not its mutable name, keys that state so renaming a section preserves its disclosure state.

Empty sections remain durable but do not appear in the sidebar. They remain available in pin and move menus.

### Pinning an unpinned session

An unpinned top-level session exposes **Pin this session…** in its row menu. Selecting it opens a menu that contains:

1. every existing section, including hidden empty sections, sorted alphabetically;
2. **New section…**.

Choosing an existing section pins the session there immediately.

Choosing **New section…** opens a small name prompt. The WebUI trims surrounding whitespace. An empty result is invalid. If the normalized name matches an existing section case-insensitively, Serf reuses that section and assigns the session to it. Otherwise, Serf creates the section and assigns the session in one server operation.

There is no standalone **Add pinned section** control in the sidebar.

### Moving or unpinning a pinned session

A pinned session exposes **Move pinned session…**. Its menu:

- marks the current section;
- lists every other section alphabetically;
- offers **New section…**;
- offers **Unpin**.

Choosing another section moves the session atomically. Choosing **New section…** follows the same create-or-reuse behavior as the initial pin flow. Choosing **Unpin** removes the assignment but does not delete the section.

A session belongs to at most one section. The API never exposes an intermediate state in two sections during a move.

### Renaming and deleting sections

Each visible section heading has an overflow menu with **Rename** and **Delete**.

Renaming uses the same trimming and case-insensitive matching rules as creation:

- an empty normalized name is rejected;
- a name that differs only by case from the section's own name is accepted as a display-name change;
- a name that matches another section is rejected rather than merging two sections implicitly.

Deleting a non-empty section requires confirmation. The confirmation states that deletion will unpin every session in that section. Confirming deletes the section and all its assignments atomically.

Because empty sections are hidden and the approved scope provides controls only on visible headings, users cannot rename or delete an empty section. They can reuse it from any pin or move menu, which makes it visible again.

## Data Model and Persistence

Introduce two first-class concepts in the Hub's existing SQLite `index.db`:

### `pin_section`

- `id`: opaque, stable section identifier generated by the Hub;
- `name`: trimmed display name;
- `name_key`: case-insensitive normalized key with a uniqueness constraint;
- `created_at` and `updated_at`: Unix timestamps.

### `session_pin`

- `session_id`: canonical top-level session identity;
- `section_id`: foreign key to `pin_section`;
- `assigned_at`: Unix timestamp;
- primary key on `session_id`, enforcing one section per session;
- foreign-key deletion cascades assignments when a section is deleted.

The store performs create-and-assign, move, rename, unpin, and delete-with-members in transactions. Every connection enables SQLite foreign-key enforcement before mutation or query work. Tests must prove that deleting a section cannot leave orphaned assignments.

Section names contain at most 80 Unicode code points after trimming. The API and UI enforce the same limit. Normalization trims surrounding Unicode whitespace and computes a Unicode case-folded comparison key. It does not otherwise rewrite the user's display spelling. SQLite enforces uniqueness on the comparison key, so names such as `Research` and `research` identify one section.

## Existing Favorite Compatibility

The current `favorite` table serves both session and project decisions. Named sections replace only `kind="session"` favorites. Project favorite reads and `POST /api/favorite` with `kind="project"` remain unchanged.

On first use of the new pin-section store, Serf performs an idempotent internal migration:

1. create the section and assignment tables if absent;
2. if any legacy `favorited=true`, `kind="session"` rows exist, create or reuse a section named **Pinned**;
3. classify each legacy session favorite with the existing authority rules, assign valid favorites under their canonical identity, retain dormant favorites under their stored identity, and discard only confirmed-invalid favorites;
4. leave project favorite rows unchanged;
5. delete every `kind="session"` favorite decision, including false decisions, in the same transaction;
6. record the completed migration in the schema version so later startup cannot recreate an assignment that a user removed.

This migration has no user-facing prompt. It preserves the current **Pinned** name as an ordinary section: users may rename it, delete it, or let it become hidden when empty. No permanent fallback section exists.

The WebServer runs this migration only after it has collected the same authority snapshot used by tree revalidation. Existing favorite authority rules determine each legacy row's migration outcome. Confirmed-invalid subagent, fork, cluster, or malformed identities do not become assignments. Missing or incomplete authority is dormant rather than invalid: the migration retains that stored identity so a temporarily unavailable remote favorite survives and reappears when authority recovers.

Deleting one session also deletes its assignment. Project deletion deletes assignments only for sessions actually removed; assignments for skipped live sessions survive. These cleanup paths report pin-store failures through the deletion result's existing decision-error mechanism and do not remove a section that becomes empty.

## API and Wire Contract

### Tree response

Replace the session-oriented `favorites` projection with a first-class collection:

```json
{
  "pin_sections": [
    {
      "id": "opaque-section-id",
      "name": "Client work",
      "sessions": [/* TreeNode values, newest activity first */]
    }
  ]
}
```

`pin_sections` includes only sections with at least one currently renderable authoritative session. A section whose durable members are all temporarily unavailable is hidden until one becomes renderable again; its assignments remain intact. A separate lightweight section-list endpoint supplies all sections, including hidden empty or temporarily unrenderable ones, for menus. This keeps `/api/tree` focused on rendered navigation and avoids shipping empty sidebar groups.

Each `TreeNode` for an assigned session carries `pin_section_id`, including duplicate appearances under **Live** or a project. This lets every copy of the row expose the same move/unpin state without searching groups. The existing `favorite` boolean remains meaningful for project rows only; session UI code migrates to explicit section membership.

### Mutations

Add these contracts:

- `GET /api/pin-sections` returns every section, sorted alphabetically, as `{id, name, member_count}`. `member_count` counts durable assignments, including temporarily unrenderable sessions.
- `POST /api/session-pin` accepts `session_ref` and exactly one of `section_id` or `section_name`. An ID assigns or moves to an existing section. A name atomically creates-or-reuses a section and assigns or moves the session. It returns the canonical section and assignment.
- `DELETE /api/session-pin?ref=<session-ref>` unpins one session and returns whether an assignment existed.
- `PATCH /api/pin-sections/<id>` accepts `name`, renames one section, and returns the canonical section.
- `DELETE /api/pin-sections/<id>` deletes the section and every assignment and returns the deleted durable member count.

Mutation requests use stable section IDs except for the explicit create-or-reuse name path. Every session mutation validates that the requested identity names a real top-level session using the existing favorite validation path. Invalid input returns `400`, an unknown section returns `404`, a rename conflict returns `409`, and a store failure returns `500`.

After a successful commit, the API handler calls `notifyMutation` exactly once. Failed requests and true no-ops emit no notification. The pin store itself does not broadcast, which preserves the current favorite/archive mutation ownership and prevents double notifications. The client still refreshes the tree after success, preserving the rail's current authoritative refresh pattern.

This is a flag-day replacement for session callers: `POST /api/favorite` rejects `kind="session"` with `400` and directs clients to `/api/session-pin`. Project requests continue unchanged. Implementation updates every in-repository session caller and test in the same change.

## Frontend Components and State

Keep the current rail architecture and extend its boundaries rather than introducing a second navigation store:

- `stores/tree.ts` parses `pin_sections` and refreshes them through the existing tree lifecycle and notifications.
- `railNodes.ts` converts each section's sessions into existing session `RailNode` values.
- `Rail.tsx` renders a reusable pinned-section component between **Live** and **Projects** and keys disclosure state by section ID.
- `RailRow.tsx` replaces the binary session favorite action with pin/move menus. Project favorite actions remain unchanged.
- `actions.ts` owns typed section and assignment requests.
- `railPending.ts` projects pin, move, unpin, rename, and delete operations while requests are in flight.

The section picker loads all sections from the durable section-list API, not from visible tree groups, because empty sections are intentionally absent from the tree. The client caches that list for an open picker only: it fetches on every picker open and refreshes after a section mutation. This avoids stale cross-client category choices without adding another long-lived store.

## Data Flow

### Pin to an existing section

1. The user opens **Pin this session…** and chooses a section.
2. The rail adds an optimistic assignment projection.
3. The API validates the top-level session and section, then commits the assignment.
4. The Hub emits a tree-changed notification.
5. The client refreshes the tree and section list.
6. The optimistic projection is removed after authoritative data arrives.

### Create a section while pinning

1. The user enters a section name.
2. The API normalizes the name and finds or creates the section inside a transaction.
3. The same transaction assigns the session.
4. The API returns the canonical section and emits one tree change.
5. The client refreshes and shows the non-empty section in alphabetical position.

### Move, unpin, rename, and delete

These operations use the same optimistic-mutation pattern. Server transactions provide atomic assignment changes. Delete confirmation occurs before the optimistic section removal. A successful delete removes the section and all member assignments together.

## Errors and Concurrency

- API validation errors use clear messages for empty or overlong names, unknown sections, invalid session identities, and rename conflicts.
- A rejected mutation removes its optimistic projection, restores the prior rail state, and shows the existing error toast pattern.
- If another client deletes a target section before assignment, the API returns not found; the picker refreshes instead of silently creating a replacement.
- Concurrent create requests with equivalent names converge through the unique normalized-name constraint. The losing transaction reads and returns the existing section, then assigns the session.
- Concurrent assignments of one session use the session primary key and upsert semantics; the last committed move wins.
- Concurrent rename to an existing name returns conflict. Rename never merges sections.
- Tree refresh failure after a successful mutation leaves the optimistic result only until the request lifecycle ends, then reports the refresh failure through existing tree-store behavior. A later tree notification or retry restores authority.
- Remote source failure does not erase durable assignments. Temporarily unverifiable sessions disappear and reappear under their assigned section as authority recovers.

## Accessibility

- Pin, move, rename, delete, and unpin actions are keyboard reachable through existing row and overflow menu primitives.
- Section headings expose disclosure state with `aria-expanded` and use buttons for collapse/expand.
- Menus mark the current section semantically, not by color alone.
- The delete confirmation names the section and uses the section-list API's durable `member_count`, so temporarily unavailable members are included in the number that will be unpinned.
- Name prompts associate validation errors with the input and preserve entered text after a rejected request.

## Testing

Before changing tests, implementation must follow `docs/testing.md`.

### Store and migration tests

- create schema idempotently;
- create, list, case-insensitive reuse, rename, and delete sections;
- reject empty, overlong, and conflicting names;
- enforce one assignment per session;
- atomically move and delete-with-members;
- preserve empty sections;
- migrate legacy true session favorites into ordinary **Pinned**;
- leave project favorites unchanged;
- make migration repeatable without recreating removed pins;
- preserve remote assignments across temporary authority loss.

### API tests

- list includes hidden empty sections;
- tree includes only non-empty renderable sections;
- sections and sessions have deterministic ordering;
- create-or-reuse and assignment are atomic;
- session validation rejects subagents, forks, clusters, malformed identities, and missing authority under existing rules;
- move, unpin, rename conflict, delete confirmation target, and not-found races return stable statuses and messages;
- successful mutations emit one tree-change notification.

### Frontend tests

- alphabetical top-level section rendering between Live and Projects;
- no standalone add-section control;
- independent persisted disclosure state keyed by section ID;
- picker includes hidden empty sections and **New section…**;
- existing-name entry reuses a section;
- pinned menu marks current section and supports move and unpin;
- visible heading supports rename and delete;
- hidden empty section has no sidebar controls;
- deletion confirmation states that all members will be unpinned;
- live pinned session appears in both locations;
- optimistic success, rollback, and refresh behavior for each mutation;
- project favorite behavior remains unchanged;
- keyboard and accessible-name coverage for new controls.

### End-to-end scenario

Extend the deterministic scripted-provider sidebar scenario to cover:

1. create **Client work** while pinning a session;
2. pin another session into the existing section;
3. create **Research** and verify alphabetical placement;
4. move a session between sections;
5. reload and verify durable assignment and browser disclosure state;
6. unpin the last **Research** session and verify the hidden section remains selectable;
7. reuse **Research** from the picker;
8. delete **Client work**, confirm all members are unpinned, and verify project favorites are unchanged.

Default tests must not require provider credentials, network access, quota, or ambient machine state.

## Acceptance Criteria

The design is complete when:

- a user can pin any valid top-level session into exactly one named section;
- a user can create a section from the pin or move menu;
- entering an existing name reuses that section case-insensitively;
- non-empty sections render alphabetically as collapsible top-level sidebar sections;
- sessions render by recent activity and remain duplicated in **Live** when live;
- empty sections stay durable, remain selectable, and stay hidden;
- visible sections can be renamed or deleted;
- deleting a section confirms and unpins every member atomically;
- state survives reloads and Hub restarts;
- existing session favorites appear in an ordinary **Pinned** section without a prompt;
- project favorites behave exactly as before;
- all mutations recover honestly from validation, persistence, refresh, and concurrency failures.
