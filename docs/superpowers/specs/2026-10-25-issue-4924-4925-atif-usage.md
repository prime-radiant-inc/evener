# Issues #4924 / #4925: ATIF prompt totals and compaction fold copies

Status: frozen after two PAR rounds, 2026-10-25.

This supersedes the `total_prompt_tokens` definition in
`docs/superpowers/specs/2026-10-23-issue-4562-atif-cache-tokens.md`; that
document remains the dated record of the #4562 change. The Usage → Metrics
table in `docs/superpowers/plans/2026-03-02-native-atif-export-design.md` is
the original design's historical mapping; the contract below is current.

## Behavior

`agent/internal/atif/atif.go` exports two figures that disagree with the ATIF
contract and with the session's real spend:

1. **#4924 — prompt totals are cache-miss-only.** ATIF RFC 0001 (and Harbor's
   `FinalMetrics` / `Metrics` models) defines `total_prompt_tokens` as the sum
   of all prompt tokens including cached ones, with `total_cached_tokens` a
   subset and `non_cached_total = total_prompt_tokens - total_cached_tokens` as
   the documented cost split. Harbor's per-step model says the same:
   `prompt_tokens` is "Total input tokens including cached and non-cached" and
   `cached_tokens` is "Subset of prompt_tokens that were cache hits". Evener
   maps `llm.Usage.InputTokens` — cache-miss input only — to both
   `steps[].metrics.prompt_tokens` and `final_metrics.total_prompt_tokens`, so
   `total_cached_tokens` can exceed `total_prompt_tokens` and the RFC's
   subtraction yields a negative non-cached count.

2. **#4925 — compaction fold copies count as steps and spend.** A compaction
   fold re-appends copies of the turns recorded during the fold after its
   markers, stamping `Turn.OriginalOrdinal` (`agent/schema/turn.go:443-446`,
   `agent/session.go:2325-2346`). The exporter iterates every entry and never
   inspects the marker, so each copied assistant turn becomes another
   trajectory step and its usage is added again.
   `internal/apptranscript/usage_total.go` already skips these copies because a
   duplicated line is not a second spend; the exporter has no equivalent guard.

## Contract after the change

Prompt totals are inclusive at both levels, and the final totals are the sums
of the emitted steps:

- `steps[].metrics.prompt_tokens` =
  `llm.Usage.InputTokens + CacheReadTokens + CacheWriteTokens + CacheWrite1hTokens`.
- `steps[].metrics.cached_tokens` = `llm.Usage.CacheReadTokens`, the cache-read
  subset of that step's prompt tokens.
- `final_metrics.total_prompt_tokens` = the sum of the steps' prompt tokens.
- `final_metrics.total_cached_tokens` = the sum of the steps' cache-read
  tokens; it remains a subset of `total_prompt_tokens`.
- `final_metrics.total_completion_tokens` is unchanged in definition (the sum
  of `llm.Usage.OutputTokens`); like every total, it is smaller in a compacted
  session once the fold copies stop being counted.
- `final_metrics.extra.cache_miss_tokens` (new integer, always present) = the
  sum of `llm.Usage.InputTokens`, i.e. the value `total_prompt_tokens` carried
  before this change.

The #4562 keys keep their names and remain always present:

- `final_metrics.extra.cache_read_tokens` = `total_cached_tokens`.
- `final_metrics.extra.prompt_wire_tokens` = `total_prompt_tokens`. It was
  already defined as the prompt-side wire volume; that volume is now the
  standard field's value, so the alias is equal by construction rather than
  removed.

Consequences: `total_prompt_tokens - total_cached_tokens` is
`cache-miss + cache-write + cache-write-1h`, never negative, and it is the
non-cached prompt volume the RFC's cost split asks for. A consumer that needs
the old cache-miss-only figure reads `extra.cache_miss_tokens`.

That identity holds for an adapter that honors `llm.Usage`'s documented
meaning of `InputTokens` (cache-miss only). Google's `parseUsage` still takes
`InputTokens` from `promptTokenCount`, which includes cached content, so for
Gemini the inclusive total counts cached reads twice — the #4923 defect that
#4562 already documented for `prompt_wire_tokens`. Fixing that adapter is out
of scope here; on Gemini runs the inclusive total and the subtraction inherit
the double count.

Fold copies: an entry whose `Turn.OriginalOrdinal` is non-nil produces no step
and contributes no usage to `final_metrics`. Entries without the marker — every
ordinary turn — are projected exactly as before apart from the prompt-metrics
change above. `total_steps` remains `len(steps)`, so it drops the copies too.

### Compatibility / migration note

This deliberately changes exported numbers. In a cached run
`total_prompt_tokens` becomes much larger (it now includes cache reads and
writes), so it is finally consistent with the RFC. Consumers that copied
`total_prompt_tokens` as "cache-miss input" must read
`final_metrics.extra.cache_miss_tokens` instead.
`cache_miss_tokens` and `prompt_wire_tokens` have their old definitions over
the deduplicated turn set, and `prompt_wire_tokens` now equals
`total_prompt_tokens`. In a compacted session all of the prompt, cached,
completion and step totals shrink, because the fold fix removes the duplicate
copies' spend: the old export's `total_prompt_tokens` and
`extra.prompt_wire_tokens` counted those copies, so neither key keeps its old
value there. No top-level field is removed or renamed; the schema version
stays ATIF-v1.7.
`extra.cache_miss_tokens` is always present in a new export, so its presence
is the discriminator between the old cache-miss-only meaning and this
contract.

## Chosen change

In `ConvertTranscriptWithOptions` / `convertAssistantTurn` in
`agent/internal/atif/atif.go`:

1. Build each assistant step's prompt tokens from the four `llm.Usage`
   components (cache reads and both cache-write terms included), keeping
   `CachedTokens` as the cache-read term. Accumulate a separate cache-miss sum
   for the `extra` field.
2. Skip any entry with `Turn.OriginalOrdinal != nil` before the turn-kind
   switch, the same rule `internal/apptranscript` consumers apply. This drops
   the copy from step construction and from the metrics accumulation in one
   place.
3. Build `final_metrics.extra.prompt_wire_tokens` from the accumulated
   inclusive prompt total (it is the same number as `total_prompt_tokens`, not
   the sum of step prompt plus the cached and cache-write terms again), and
   drop the now-redundant cache-write accumulators.

Per-step metrics are corrected along with the final total because they are the
same measurement at two levels: Harbor defines step `prompt_tokens` as
inclusive, and changing only the final total would publish a document whose
`final_metrics` is not the sum of its own steps and whose per-step
`cached_tokens` can still exceed `prompt_tokens`. This is the judgment call the
issue's option 1 leaves open; the alternative (leave steps cache-miss-only)
would preserve a second, unflagged divergence from the format.

## Non-goals

- No provider adapter changes. Google's `parseUsage` taking `InputTokens` from
  `promptTokenCount` (which includes cached content) remains #4923; as the
  caveat above records, Gemini's inclusive total inherits that double count
  and the fix belongs in the adapter, not here.
- No new top-level ATIF fields. Harbor's `FinalMetrics` forbids extra
  non-`extra` fields, so the new name goes in `final_metrics.extra`.
- No change to the gate that decides whether a turn gets a `StepMetrics` block
  (`InputTokens > 0 || OutputTokens > 0`), to `total_completion_tokens`, to
  per-step `extra` contents, or to any other turn kind. As #4562 recorded, no
  supported provider reports cache tokens with both input and output zero, so
  the gate does not drop a prompt contribution in practice; a cache-only
  response is not counted at either level, then or now.
- No restructuring of tool-round pairing across compaction markers. A fold
  that lands between an assistant turn's write and its tool results' write can
  leave the original assistant before the markers and the original results
  after them, with only the assistant's copy between. Before this change the
  copy step absorbed those results; after it the copy is skipped, so the
  original assistant keeps its `tool_calls` without an observation and the
  results are emitted by the existing orphaned-tool-results path with
  `source_call_id` nulled and the original ids preserved in
  `extra.orphaned_source_call_ids`. That is the documented outcome, pinned by
  a test; bridging the results back across the markers is a larger structural
  change this issue does not ask for.
- No change to transcript writing, session compaction, `internal/apptranscript`,
  the ATIF viewer, or Harbor.
- No labels and no merge; the parent owns CI and the merge.

## Verification

1. `agent/internal/atif/atif_test.go`:
   `TestConvertToATIF_FinalMetricsPromptWireVolume` is the cache-heavy case
   (cache-miss, cache-read, cache-write, cache-write-1h across two steps). It
   asserts inclusive step and final prompt tokens, the cached subset, the
   non-negative non-cached split, `extra.cache_miss_tokens`, the #4562 aliases,
   JSON round-trip values, and explicit zero keys on an empty trajectory.
   It failed before the change with `TotalPromptTokens = 1200, want 2050` and
   passes after.
   `TestConvertToATIF_SkipsCompactionFoldCopies` is the fold case: an original
   user/assistant/tool-results round, fold markers, marked copies of the
   assistant and its results, then a real unmarked turn after the fold. It
   asserts 5 steps (not 6), one round of usage for the original, and that the
   unmarked post-fold turn survives with its own usage. The post-fold turn is
   what distinguishes skipping marked copies from dropping everything after a
   marker. It failed before the change with `len(Steps) = 6, want 5`.
   `TestConvertToATIF_SkipsFoldCopyInSplitToolRound` pins the split ordering
   where the original results land after the copy: the original assistant
   keeps its tool calls without an observation, the results reach the
   orphaned-tool-results path with the ids in `extra`, and the copy's usage is
   not counted. It failed before the change because the copy step absorbed the
   results (`Steps[4]` was a paired agent step, not `orphaned_tool_results`).
   `TestConvertToATIF_MultiRound` already carries a cached assistant turn and
   asserted the old cache-miss total; it is updated to the inclusive 270 and
   is part of the same red/green evidence.
2. `agent/internal/atif/conversion_program_fuzz_test.go` (evenerfuzz build
   tag) keeps asserting the generated trajectory's totals, updated to the
   inclusive sum, so the program fuzz stays a real oracle.
3. `go test ./agent/internal/atif/...`, the agent tests that consume the
   export (`go test ./agent -run ATIF`), and `make build`. CI is the source of
   truth for the full suite.
4. Freeze this spec and review it with two independent competing PAR
   reviewers, then review the implementation diff the same way, then run the
   simplify pass before committing.
