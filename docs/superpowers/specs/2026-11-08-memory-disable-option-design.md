# Memory disable option for web and native

Date: 2026-11-08
Status: proposed (naming picked by Jesse, 2026-11-08; awaiting design approval)
Size: small change (roughly 500 lines with tests across hub, web, native)

## Intent and why

Evener sessions bind memory by default: the five native memory tools, personal
and project `MEMORY.md` index projections, core memory guidance in the system
prompt, and the bundled `gardening-memory` skill. The engine already has a
complete per-session opt-out — `--disable-memory` on `evener` and
`evener serve` ([memory](../../product/memory.md) "Per-session opt-out") — but
it is reachable only from the CLI. Jesse wants the same opt-out reachable from
the web UI and the native UI.

What "disable" already means, and continues to mean here (no engine change):
no memory tools registered, no memory index or guidance in context (the "auto
reminders"), no gardening-memory skill offered or loadable, no native memory
file I/O. Stored files are untouched, other sessions keep access, the choice
is sticky across resume and compaction, and a disabled parent dominates its
children.

## Goals

- A Memory launch option settable per session at creation, and savable as a
  global and per-project default, in both clients.
- The pre-session skill catalog stops offering `gardening-memory` when the
  resolved launch disables memory.

## Non-goals

- No live toggle for a running session (documented contract; the engine has no
  mid-session switch).
- No per-session "memory: off" state indicator in either client (offered and
  deferred; would need a new wire field).
- No erasure or filesystem-isolation semantics.
- No CLI rename: the daemon flag stays `--disable-memory`.

## Approaches

1. **A launch option in the existing launch-config system** (chosen). The
   hub's layered launch config (global `launch.toml`, project
   `.evener/launch.toml`, per-launch overrides on `evener/thread/start`)
   already drives both clients' settings UIs from one schema
   (`evener/launch/schema`), and `ToArgs` renders the spawned daemon's argv.
   The web Launch settings form, the spawn pane's Advanced options, and the
   native Launch settings screen all render a new schema option generically,
   with no bespoke UI.
2. Per-launch only (no saved defaults): rejected — a user who wants memory
   off for a whole project or machine must flip it every session.
3. A hub-level kill switch: rejected — no per-project or per-session
   granularity, not editable from either client, and it bypasses the layering
   both UIs are built on.

**Naming (Jesse's pick).** The launch layer, wire and UIs use the positive
spelling: TOML `memory_enabled`, wire `memoryEnabled`, label "Memory", default
On. The daemon flag (`--disable-memory`), `SessionConfig.DisableMemory` and
saved meta (`disable_memory`) keep the negative spelling. The one negation
lives in `launchconfig.ToArgs`: an effective `memory_enabled` of false emits
`--disable-memory`; unset or true emits nothing (the daemon's own default is
enabled). The alternative — `disable_memory` everywhere, matching the flag —
lost on UI readability: every renderer would read "Disable memory: On".

## The pieces

### Backend

- `launchconfig.Layer.MemoryEnabled *bool` (`toml:"memory_enabled"`) in
  cmd/evener-hub/internal/launchconfig/types.go, merging like the other
  pointer scalars (a per-launch true overrides a disabling global default).
- `appwire.LaunchConfigLayer.MemoryEnabled *bool` (`memoryEnabled`) in
  appwire/types_auth_commands.go. The TypeScript type flows through
  `make generate` (appwire-client/typescript/types.gen.ts is generated by
  internal/appwirets); the client schema engine
  (appwire-client/typescript/launchSchema.ts) is generic over options and
  needs no new enumeration.
- Schema entry in launchconfig/schema.go: field `memory_enabled`, wire
  `memoryEnabled`, label "Memory", kind boolean, group Agent, DefaultableLayers
  global + project, PerLaunch true, DriverSupport evener-only,
  BuiltinDefaultBool true (the `sandbox_net` shape). Draft description, final
  copy at implementation: "Evener's cross-session memory. Off starts the
  session with no memory tools, no memory index or reminders in its context,
  and no gardening-memory skill. Stored memory files are kept; a resumed
  session keeps the state it was created with."
- `ToArgs` in launchconfig/args.go emits `--disable-memory` only when the
  effective value is false.
- `freshSpawnSkillAvailability` (cmd/evener-hub/app_spawn_slashcatalog.go)
  stops returning a fixed true and derives `MemorySaveAvailable` from the
  resolved launch (`MemoryEnabled == nil || *MemoryEnabled`). The guard test
  `TestFreshSpawnSkillAvailabilityHasNoLaunchMemoryControl` is rewritten to
  pin the new invariant — it exists to force exactly this derivation once a
  launch memory control arrived. Past threads keep deriving from session meta
  (`pastThreadSkillAvailability`, unchanged).
- Resume is unchanged: `resumeRequestForConfig` carries only `api_log` from
  launch layers today and disable is sticky from session meta, so this option
  shapes new sessions only, matching the documented contract ("Omitting the
  flag on resume preserves it").

### Web (cmd/evener-hub/frontend)

No bespoke UI. The Launch settings form and the spawn pane's Advanced options
render schema options generically, so the Memory row appears in both. The
unset choice names the resolved default ("On (default)" / "Off (default)")
through the existing `resolvedDefaults` plumbing.

### Native (mobile-native)

- LaunchSettingsScreen: automatic, same as web.
- The new-session flow's More options sheet (the curated "few launch settings
  worth touching on a phone") gains a Memory control — segmented Default |
  On | Off — writing `launchOverrides.memoryEnabled`. It renders only when
  the connected hub's launch schema offers the field: against an older hub
  the toggle would otherwise silently do nothing, and silently keeping memory
  on after the user asked for it off is the one lie this feature must not
  tell. (The web is automatically safe: it renders from the schema.)
- `launchSetup.ownedOverrides`, `useLaunchDefaults`' LaunchDefaults pick, and
  MoreOptions' field list gain `memoryEnabled`, so remembered starts and the
  hub-default footers include it.

### Docs (evergreen, same change)

- docs/product/memory.md "Per-session opt-out": the option is settable from
  both clients as the `memory_enabled` launch option; "There is no live
  toggle" stays true; the two spellings and the ToArgs negation are named.
- docs/product/subsystems.md S24 row: name the client surfaces.
- The native spec MoreOptions cites ("spec 11; ruling 14") if it enumerates
  More options fields.

## Testing

Behavior tests only, following each area's existing patterns:

- launchconfig: merge precedence (unset vs set-false vs set-true overriding a
  disabling global), TOML round-trip, ToArgs flag emission and its absence.
- hub: thread/start with `memoryEnabled=false` overrides spawns a daemon whose
  argv carries `--disable-memory` and whose session runs with no memory
  tools; an explicit true over a disabling global launches enabled; the spawn
  slash catalog with a disabling override or global default does not offer
  gardening-memory.
- web: fixture-driven form and spawn tests for the boolean option
  (launchServer.test.tsx, fields.test.tsx, Spawn.test.tsx patterns), and
  collectAdvancedOverrides carrying memoryEnabled into launchOverrides.
- native: MoreOptions sets and clears memoryEnabled and hides against a
  schema without the field; ownedOverrides round-trip through a remembered
  start; newSession passes it on thread/start.
- Engine behavior (a disabled session has no tools, no context, no skill) is
  already covered by agent tests; this design changes no engine code.

## Version skew

Hub older than client: the older hub's `LaunchConfigLayer` has no such field,
so the override is dropped at decode; the native row is gated on schema and
the web renders from schema, so neither client shows a dead toggle. Client
older than hub: nothing new to read. On-disk: `memory_enabled` is a new
optional TOML key an older Evener ignores; no compatibility code, nothing to
remove.
