# Web UI inline output images design

Date: 2026-07-07

## Summary

Serf's web UI should show images inline when an agent produces them. The first version covers three sources:

1. tool results that already contain image bytes, such as `read_file` on a PNG or a screenshot-like tool result;
2. image files written or modified by structured file tools, such as `write_file`, `edit_file`, and `apply_patch`;
3. image files generated by shell commands when the command output names a safe path under the session working directory.

The web UI should render thumbnails under the tool row that produced the image. Users can click a thumbnail to open the existing lightbox and use the existing open-beside control for stable same-origin image URLs.

AppWire should not carry generated image bytes. AppWire should carry only small `outputImages` descriptors that tell the renderer which tool row owns the image and where the browser can fetch it. Image bytes load out of band through hub routes, following the same trust boundary as `/doc/file`.

## Goals

- Show generated screenshots and image files inline in the transcript without requiring the user to open the sidebar or inspect paths manually.
- Keep AppWire payloads small and stable by sending descriptors, not file bytes.
- Reuse the current thumbnail, lightbox, and open-beside image UI where possible.
- Make live sessions and reloaded sessions render the same images.
- Keep path access server-side, session-scoped, and contained by the session working directory.

## Non-goals

- Build a general artifact store for every file type.
- Preview arbitrary binary files, videos, PDFs, or SVGs in v1.
- Infer every possible shell-created image. Shell inference should be conservative.
- Serve files outside the local session working directory.
- Add remote-session file fetching in v1.

## Existing context

The current web UI already has most of the visual pieces:

- `cmd/serf-hub/assets/renderer.js` renders user-message image cards, multi-image sheets, captions, dimensions, lightbox navigation, and open-beside controls.
- `cmd/serf-hub/assets/appwire.js` converts AppWire `ThreadItem` objects into renderer events.
- `cmd/serf-hub/image_serve.go` serves sha-addressed images found in past user-input transcript parts at `/s/<session>/images/<sha>`.
- `cmd/serf-hub/doc_serve.go` serves read-only file panes through `/doc/file?session=<id>&path=<rel>`, resolving paths against the local session cwd with `fspaths.ResolveInRoot`.
- `agent/internal/tool/registry.go` already has `ExecResult.ImageData`, `ExecResult.ImageMediaType`, and `ImageResult` for image-bearing tool results.
- `llm.ToolResultData` already has `ImageData` and `ImageMediaType`, but AppWire projection does not expose tool-result images to the web UI today.

The missing piece is a structured association between a completed tool row and the images that row produced.

## User-visible behavior

When a tool produces one image, the tool row shows one thumbnail below the row's normal command/result text. The thumbnail uses the existing image card behavior: click opens the lightbox; the hover-revealed open-beside control opens the image in a pane when the image URL is stable and same-origin.

When a tool produces several images, the row shows one compact contact sheet below the row. Opening any image enters the same lightbox set, with left/right navigation across the set.

The image preview should not replace text output. If a shell command prints useful output and writes `out.png`, the UI shows both the text preview and the image preview.

If Serf cannot validate or serve an image, it should omit that preview. The tool row remains otherwise unchanged.

## AppWire contract

Add an optional field to `appwire.ThreadItem`:

```go
type ThreadItem struct {
    // existing fields...
    OutputImages []OutputImage `json:"outputImages,omitempty"`
}

type OutputImage struct {
    Source    string `json:"source"`              // tool-result | written-file | shell-path
    Name      string `json:"name,omitempty"`
    MediaType string `json:"mediaType,omitempty"`
    Size      int64  `json:"size,omitempty"`
    URL       string `json:"url,omitempty"`       // same-origin fetch URL for the browser
    SHA       string `json:"sha,omitempty"`       // content hash when known
    Path      string `json:"path,omitempty"`      // display path, preferably cwd-relative
}
```

`OutputImages` is valid only on `commandExecution` items. Clients must ignore it on other item types. The field is additive: old clients ignore it, and old daemons omit it.

The field carries descriptors only. It must not carry raw bytes or base64 data for generated output images.

Use JSON name `outputImages`, matching existing AppWire camel-case style. The frontend event bridge may normalize it to `output_images` internally if that fits existing renderer event conventions.

## Image sources

### Tool-result images

Some tool executions already return image bytes through `tool.ExecResult.ImageData` and `ImageMediaType`. The session should preserve those bytes in `llm.ToolResultData.ImageData/ImageMediaType`, and the AppWire projectors should expose them as `OutputImages` descriptors.

For live display, the descriptor may use a sha-addressed URL whose bytes are available from the current session or transcript scan. For reload display, the descriptor must be reconstructable from persisted `llm.ToolResultData`.

### Written image files

For structured file-writing tools, Serf should inspect explicit target paths after the tool succeeds:

- `write_file`: `file_path`;
- `edit_file`: `file_path` or `path`;
- `apply_patch`: image paths that the patch created or modified, when they can be extracted safely from the patch result or patch metadata.

The resolver should convert absolute paths under cwd to cwd-relative paths, reject paths outside cwd, verify that the file exists, verify that it is regular, sniff a supported image media type, compute size and sha, and emit a `/doc/image` URL.

### Shell-generated image files

Shell output should be scanned for conservative path candidates after the shell command completes. Candidate patterns should include:

- quoted paths with common image extensions;
- `./relative/path.png`-style relative paths;
- bare cwd-relative paths with common image extensions;
- absolute paths that resolve under cwd.

The scanner should cap work per tool call, for example at 20 candidates and 8 accepted images. It should not chase URLs. It should not try to parse prose that does not look like a path.

Every candidate must pass the same resolver as written files. Invalid candidates are ignored.

## Image serving

Add `/doc/image?session=<id>&path=<rel>` for file-backed generated images. It should mirror `/doc/file`'s security model:

1. require `GET`;
2. require a local session id and a relative path;
3. resolve the path against the session cwd with `fspaths.ResolveInRoot`;
4. reject path escapes with 403 and missing/non-regular files with 404;
5. sniff and allow only supported image media types;
6. set `Content-Type` to the detected media type;
7. set conservative cache headers keyed by mtime/size or content sha.

For transcript-backed tool-result images, generalize the existing sha route or add a sibling route that can find image bytes in both user-input image parts and tool-result image fields. The descriptor should use a same-origin URL with a content hash, so browser caching remains safe.

Supported media for v1: PNG, JPEG, GIF, and WebP. Exclude SVG in v1. SVG is text but can carry active content and should not be treated as an ordinary image until Serf has a sanitization policy.

## Backend data flow

### Live tool completion

1. Tool execution completes.
2. The session builds `ToolCallEndData` and includes enough image evidence to create descriptors:
   - tool-result image bytes/media type, if present;
   - tool name and arguments for structured write tools;
   - full output text for shell path candidate extraction.
3. `internal/appprojector` creates a `commandExecution` item with `OutputImages` descriptors.
4. AppWire sends `item/completed` with the descriptor list.
5. The browser fetches image bytes from descriptor URLs when the thumbnail loads.

### Reload and history

1. `internal/apptranscript` projects persisted `llm.ToolResultData` into `commandExecution` items.
2. `cmd/serf-hub/app_threadread.go` supplies the hub-specific resolver for transcript-backed image bytes and file-backed paths.
3. The projected item includes the same `OutputImages` descriptor shape as live projection.
4. The browser renders the same thumbnail UI as the live path.

## Frontend data flow

1. `cmd/serf-hub/assets/appwire.js` passes `item.outputImages` from `commandExecution` items into `TOOL_CALL_END` renderer payloads.
2. `renderer.js.finalizeToolCall` calls a new helper, for example `renderToolOutputImages(state, data.output_images || data.outputImages)`.
3. The helper resolves each descriptor to `{src, name}` using `descriptor.url` first, then `descriptor.sha` only when the route is known.
4. It appends one image card or one image sheet under the tool row.
5. It reuses `buildSingleImageCard`, `buildImageSheet`, `openImageLightboxSet`, and `attachImageOpenBeside` with tool-specific wrapper classes.

The helper must make image content count as a non-empty tool body, so `toolBodyIsEmpty` does not remove the disclosure control when images are present.

## Error handling and safety

- Do not expose raw local absolute paths in fetch URLs.
- Do not render an image descriptor without a same-origin URL or sha route the browser can fetch.
- Do not read or serve paths outside the local session cwd.
- Do not serve directories, symlinks that escape cwd, devices, or other non-regular files.
- Do not serve SVG in v1.
- Do not fail the tool row if image discovery fails.
- Do not show warnings for ignored shell candidates in the main transcript. They would create noise. Debug logs or tests can assert why candidates were rejected.
- Cap file size. Use the existing 8 MiB image attachment limit as the v1 default unless implementation finds a stronger local convention.
- Cap the number of candidates and rendered images per tool call.

## Testing plan

### Go tests

- AppWire schema encodes and decodes `ThreadItem.OutputImages` without affecting existing items.
- Candidate extraction finds conservative shell image paths and ignores URLs, prose, and non-image extensions.
- Path resolution rejects traversal, out-of-cwd absolute paths, missing files, non-regular files, oversize files, and SVG.
- `/doc/image` serves valid cwd-contained PNG/JPEG/GIF/WebP files with correct content type and refuses invalid paths.
- Live `EventToolCallEnd` projection attaches `OutputImages` for tool-result image bytes.
- Replay projection reconstructs `OutputImages` for persisted tool-result images.
- Structured write tool projection attaches descriptors for valid image target paths.

### JavaScript tests

- A completed tool row with one `outputImages` descriptor renders one thumbnail.
- A completed tool row with several descriptors renders one image sheet.
- Clicking a tool output thumbnail opens the existing lightbox set.
- A stable same-origin URL gets an open-beside affordance.
- Missing or invalid descriptors do not throw and do not create empty expand controls.

### Integration and E2E tests

Use scripted providers and local temp files. Default tests must not depend on network access, provider credentials, or ambient machine state.

## E2E scenario cards

| Card | Covers | Falsification |
| --- | --- | --- |
| read-image-tool-result-inline | A tool result that carries image bytes, such as reading a PNG screenshot, renders a thumbnail below that tool row. | After the tool completes, the transcript shows only text output or a path, with no clickable image thumbnail under the producing tool row. |
| written-image-inline-after-reload | A structured file-writing tool writes an image under the session cwd, the web UI shows it inline, and a page reload still shows it. | The image appears live but disappears after reload, or reload shows the image detached from the producing tool row. |
| shell-generated-image-path-inline | A shell command writes an image under cwd and prints its path; the web UI shows the image inline under the shell row. | The shell row contains the path text but no thumbnail for the generated image. |
| unsafe-image-path-ignored | A shell command prints an out-of-cwd image path or traversal path; the web UI does not preview it. | The UI fetches or displays an image from outside the session cwd. |
| output-image-lightbox-and-pane | A rendered output image opens in the lightbox on click and offers open-beside when it has a same-origin stable URL. | Clicking the thumbnail does not open the lightbox, or the open-beside control is missing for a valid same-origin image URL. |

## Implementation notes

Prefer one shared backend resolver for all file-backed sources. The caller should pass the session id, cwd, candidate path, source kind, and display name. The resolver should return either an `OutputImage` descriptor or a typed rejection reason for tests and debug logging.

Prefer a separate scanner for shell output. The scanner should produce candidate strings only. It should not stat files or decide safety.

Keep the frontend small. The renderer should trust only descriptor URLs generated by the backend and reuse existing image-card builders. It should not parse paths from shell text.

## Open decisions resolved in this spec

- AppWire carries descriptors, not generated image bytes.
- File-backed images load through a `/doc/image`-style route, parallel to `/doc/file`.
- Tool-result image bytes can still be served through sha-addressed transcript lookup because those bytes already live in transcript data.
- SVG is excluded from v1.
- Shell inference is included in v1 but must be conservative and server-validated.
