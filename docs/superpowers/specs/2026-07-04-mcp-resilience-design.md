# MCP Resilience — Design (v3)

Date: 2026-07-04 (v2: round 1, C 10 / D 11 — D wins; v3: round 2, I 7 / J 9 — J wins; 14 distinct, all folded)
Status: Draft — awaiting Jesse's spec review
Workstream: 5 of 6 from the 2026-07-03 web-UI UX diagnostic ("Linear MCP was 400-ing" with no clarity)

## Problem — three stacked defects

1. **One bad server kills the whole session before it exists.** `mcp.NewManager` treats any per-server failure — transport build, connect (manager.go:62-65), or tool discovery — as fatal: it calls `mgr.Close()` (closing every *healthy* server already connected) and returns nil. That error propagates through `initMCP` → `NewSession`, so the `*Session` never constructs; `serf serve` exits before binding its listener; the hub forwards the MCP error buried in 64KB of stderr as an HTTP 500. One 30s batch budget, serial connects, no retry. **The plugin-path fatality is narrower than v2 claimed (round-2 I2/J2):** a plugin's `.mcp.json` *file* errors and malformed inline JSON are already *silently swallowed* (plugin.go:121, :130 — documented as known gaps, subagent-runtime-contracts.md:94-95); the one fatal plugin path is a well-formed inline `mcpServers` map whose entries fail `ParseServerMap` (empty name, unset `${VAR}`; plugin.go:131-136 → Load/LoadAll abort). **And the silence is its own defect:** `mcpconfig.Discover` likewise swallows the entire global/project layer on one parse error or unset `${VAR}` (config.go:255-272; expansion is fatal-per-file at :181-186) — a typo in `~/.config/serf/mcp.json` silently removes every global server with zero diagnostics (round-2 I4/J8).
2. **Server-reported tool errors render as success.** Channel A (transport error): `err != nil` → `IsError: true`. Channel B (the server reports `CallToolResult.IsError` — how a Linear 400 arrives per-spec): folded into a plain `"[MCP Error] …"` string, `IsError` hardcoded `false` on the registry's fallback branch (registry.go:532-533) — collapsed green "ok", error text invisible.
3. **Health exists nowhere honest.** No reconnect, no notification handlers; `Servers()` replays the startup snapshot forever. The settings probe is orphaned twice over (computed-and-discarded; no status-code check — a 400 reads "available"). The wire home (`SerfMCPServerInfo`) carries no health field and threads through `{Name, Tools}`-only carriers.

## Decisions (Jesse, 2026-07-04)

1. **Minimal lazy reconnect in scope**: call-driven, one attempt per server per 30s, no background loops, no tool-list re-discovery.
2. OAuth out (static `headers` + env expansion is the Linear workaround).
3. v2 decide-and-state: startup-failed servers are terminal in v1 ("retry server" from settings = named fast-follow); **Channel-B never marks a connection broken** — but it **does stamp the server's `Error` field** (round-2 J4, below); restored sessions re-emit startup warnings deliberately.
4. v3: **`degraded` means connection-level failure only** — the SDK's error taxonomy is three-way (`ErrConnectionClosed` vs `ctx.Err()` vs JSON-RPC errors; sdk transport.go:206-236), and only the first is transport death (round-2 J1). A user interrupt or a model arg-error must never tear down a healthy connection.

## Design

### Non-fatal, parallel, per-server startup

Connects run in parallel under per-server 10s timeouts and a parent context tied to session construction. Result assembly spans two stages: `NewManager` returns connect-stage results; `RegisterTools` returns per-server register outcomes, continuing past failures; `initMCP` merges. Determinism: connect results re-sort to config order before registration; MCP-vs-MCP collisions resolve first-in-config-order. **Rollback removes only the names the losing server successfully registered — never the colliding name itself** (round-2 I3: `Remove` is name-keyed, and name-sanitization lets distinct servers emit identical tool names — `foo-bar` and `foo_bar` both produce `foo_bar__*` (manager.go:189) while `Merge` dedupes by server name only — so a blunt remove-all-of-the-loser's-names would delete the *winner's* registration). **The definition surface is rebuilt from the registered set** (round-2 I1): `s.mcpTools` currently takes `mgr.ToolDefinitions()` verbatim (session_init.go:1177) and feeds the system prompt unguarded (session_prompts.go:96) — without this, a `failed(register)` server's tools would be advertised to the model as callable while the registry rejects them.

**Warnings ride the deferred-diagnostics path**: MCP failures collect into `pendingMCPWarnings`, flushed in `emitSessionStartEnvelope` after SESSION_START via `emitDiagnosticWarning` — rendering everywhere without firing the Notification hook. **They carry an MCP diagnostics classification** (round-2 J6): `diagnostic.Classify` has no MCP branch today, so a connect failure would get the generic "check the Serf session log" hint and an MCP 401 would match the *provider-credentials* matcher ("unauthorized", diagnostic.go:171) — actively misleading. A `SourceMCP` classifier branch maps command-not-found / connection-refused / auth / bad-handshake to actionable hints, and the warnings set their Source so `FromFields` never falls through to misclassification — **in both diagnostic packages** (the agent-side `agent/internal/diagnostic` *and* the root-module `internal/diagnostic` the projector re-classifies with at appwire_projection.go:404; plan-drafting surfaced that the hub-side re-classification would otherwise re-introduce the provider misdirection at the web surface).

**Config-load honesty (round-2 I4/J8)**: swallowed layer errors become visible — a global/project `mcp.json` that fails to parse or expand produces a `pendingMCPWarnings` entry naming the file and error (the layer is still skipped; non-fatal). **The plugin fold, retargeted (round-2 I2/J2)**: the fatal inline-`mcpServers` `ParseServerMap` path degrades to a **plugin-level** `failed(config)` diagnostic — per-server rows are unbuildable when the map didn't parse, so the warning names the plugin and error, the plugin's MCP layer is skipped, and its other contributions (hooks, skills, prompts) load normally. The already-swallowed file/inline-JSON gaps get the same visible warning. CLI `--mcp-config` and `--mcp` inline specs stay fatal (explicit user input). With this, no MCP path can kill a spawn *and* no MCP config failure is silent.

### Severity fix (bug, TDD)

Channel B returns through the error path → `IsError: true` → red ✕ and visible error body. Model-facing change stated: the tool result reaches the model as an error-typed `tool_result` (llm/generate.go:336) where it previously read as success — desired, pinned by a turn-loop test.

### Lazy reconnect

Closures capture the connection (not the session pointer) and read `c.session` under the per-conn mutex; `conn` retains its `ServerConfig` and **a redial transport factory** — the only transport injection today is positional-at-startup (manager.go:51-52), so without a per-conn factory seam the reconnect tests cannot use the hermetic in-memory fakes and the redial cannot be constructed at all for fakes (round-2 J5). **A conn goes `degraded` only on `errors.Is(err, ErrConnectionClosed)`** (Decision 4); `ctx.Err()` and JSON-RPC errors return as ordinary tool errors against a healthy conn. **The backoff clock starts at zero** — a conn broken for the first time redials on the very next call, and the triggering call **retries once against the swapped session** (round-2 J9: otherwise the e2e's "next call reconnects" is non-deterministic and the user pays one extra failed call per recovery). The dial is bounded by the 10s per-server timeout. **The displaced session is closed after a successful swap** (round-2 J7: nothing else can ever reap it — `Close()` iterates *current* sessions — so each reconnect would otherwise leak a zombie child or HTTP session for the process lifetime). **Swap and `Close()` operate under the same per-conn mutex with a closed flag checked under that mutex after every dial** (round-2 I6: the v2 close-signal context alone left a pointer race between `Close()`'s unlocked iteration and a concurrent swap, and a leak window for a dial that outran the signal). Recovery lines ride `emitDiagnosticWarning` — same path and hook semantics as the startup warnings (round-2 I7). Startup-failed servers remain terminal (no tools → no trigger); stated and asserted.

### Honest health, rendered

- **Wire**: `Status`/`Error` thread the enumerated carrier chain (mcpconfig.ServerInfo → server.MCPServerInfo → appwire.SerfMCPServerInfo + both converters), populated via a `Servers()` reworked to read live per-conn state under the mutexes. Vocabulary: `connected` / `degraded` / `failed`. **`Error` carries the last failure of *any* kind, including Channel-B application errors on a `connected` server** (round-2 J4): the originating incident — initialize succeeds, every `tools/call` 400s — must not read as fully healthy; diagnostics render "connected · last error: … (2m ago)". The status value itself never changes on Channel B (Decision 3). Protocol doc regenerated. **`docs/subagent-runtime-contracts.md` is a named deliverable** (round-2 I5): its "fail-fast / no partial-availability" paragraph (:63-65) and silent-gap notes (:94-95) describe the exact behavior this spec inverts.
- **Probe**: parallel, 3s cap, per-row env errors, real initialize for http/sse, command-present for stdio — **with its limits stated on the surface** (round-2 J4): initialize-OK cannot certify per-tool success (the 400-ing-Linear case shows `available` while calls fail — the `Error` field above is what tells that truth), and stdio command-present cannot certify connectability. Labeled "as probed from the hub" with the daemon-env divergence noted.
- **Settings**: server list + status column (name, transport, probe status, last error); source-layer column dropped (global-file-only discovery); `mcpstatus` dies.

## Error handling

Zero healthy servers = healthy session. Reconnect never blocks beyond one bounded attempt + one retry; close and swap serialize on the per-conn mutex; late dials discard and close their session. Probe failures classify per-row. Warning flush is non-fatal. All manager state reads take the conn mutexes.

## Contract changes (tests that deliberately flip)

Flip: `TestIntg_InitMCP_ConnectError` / `RegisterToolsError`; `TestIntgMCP_NewManager_TransportBuildError` / `ConnectError` / `ListToolsError`; `TestMCPManager_BuiltinCollision` / `ToolNameTooLong`. Stays fatal-pinned: `TestIntg_InitMCP_DiscoverError` (config-parse). New: healthy-survive-sibling spy; plugin inline-`ParseServerMap` degradation (the correct fatal path — the v2 test targeted the already-swallowed file path and would have passed with no change, pinning nothing).

## Out of scope

MCP OAuth; `tools/list_changed`; background health polling; startup-failed revival (fast-follow); per-server enable/disable UI; subagent MCP inheritance; spawn-stderr cleanup (WS6).

## Testing

- Manager: parallel result matrix via the **redial-factory seam** (hermetic in-memory fakes for every stage incl. reconnect — the seam is what makes closure-liveness and `-race` tests runnable at all); config-order determinism; healthy-survive-sibling spy; rollback removes only the loser's own registered names (the winner's colliding tool survives — the I3 regression); `ToolDefinitions()`/`s.mcpTools` exclude failed-register servers (system prompt matches the callable set — the I1 regression); reconnect — closure reaches the NEW session, **degraded only on ErrConnectionClosed (ctx-cancel and JSON-RPC errors do not break the conn)**, zero-initialized backoff (first post-break call redials immediately), triggering call retries once post-swap, displaced session closed (leak test), close-vs-swap under one mutex (`-race`), Channel-B stamps `Error` without status change.
- Severity: both channels end-to-end; model-facing error-typed tool_result; jstest error-marker.
- Warnings: flush after SESSION_START, no Notification hook, restore re-emits; **MCP classifier** — connection-refused / command-not-found / 401 get MCP hints, and the 401 no longer matches the provider matcher; global-layer parse failure and plugin inline-map failure each produce a visible warning while the session constructs.
- Probe: 200 available / 400 unreachable / refused unreachable; per-row env error; parallel bound; stdio labeling.
- e2e card — **three servers** (round-2 J3: one server cannot be both startup-failed and rendering-red): good; startup-failed (warning + terminal + probe-unreachable); connected-but-Channel-B-erroring (red render + `Error` populated + status still connected). Then kill + restart the good server → next call reconnects (immediately — zero-initialized backoff).
