# MCP Resilience — Design (v2)

Date: 2026-07-04 (v2 after adversarial round 1: C 10 / D 11 — D wins; 18 distinct findings, all folded)
Status: Draft — awaiting Jesse's spec review
Workstream: 5 of 6 from the 2026-07-03 web-UI UX diagnostic ("Linear MCP was 400-ing" with no clarity)

## Problem — three stacked defects

1. **One bad server kills the whole session before it exists.** `mcp.NewManager` treats any per-server failure — transport build, connect (manager.go:62-65), or tool discovery — as fatal: it calls `mgr.Close()` (closing every *healthy* server already connected, manager.go:174-183) and returns nil. That error propagates `initMCP` (session_init.go:1150-1179) → `initSessionState` (:597-599) → `NewSession`, so the `*Session` is never constructed; `serf serve` exits before binding its listener (serve.go:249 vs :260). The hub sees "process exited before rendezvous" and forwards the MCP error buried in up to 64KB of raw subprocess stderr as an HTTP 500 (spawn.go; web_spawn.go:60). One 30s context budget covers all servers combined (session_init.go:1163); connects are serial, attempted exactly once. **The same fatality is reachable through a third-party plugin's malformed `.mcp.json`** (round-1 D2): `discoverPluginMCPConfigs` err → `Load`/`LoadAll` abort (plugin.go:227-229, 245) → `initPlugins` → "plugin initialization" fatal (session_init.go:575).
2. **Server-reported tool errors render as success.** MCP failures split into two channels in `tool.Registry.ExecuteCall` (registry.go:446-534). Channel A (transport error): `err != nil` → `IsError: true`. Channel B (the server itself reports `CallToolResult.IsError` — exactly how a well-behaved Linear server wraps an upstream 400): `mcpResultToString` folds it into a plain `"[MCP Error] …"` string that falls to the registry's final branch where **`IsError` is hardcoded `false`** (registry.go:532-533). The web renders MCP calls with the bodyless default renderer, so a Channel-B failure shows a collapsed green "ok" with the error text invisible; the TUI likewise.
3. **Health exists nowhere honest.** A dead server's tools stay registered for the session's life — no reconnect, no notification handlers (manager.go:43-46), `Servers()` replays the startup snapshot forever (manager.go:158-171). The settings probe (`mcpstatus.ProbeMCPStatus`) is orphaned twice over: computed on every settings render and discarded (mcp.html has no status reference), and for http/sse it calls any response "available" without reading the status code (mcp_status.go:57-61). The wire has a natural home — `SerfMCPServerInfo` on the diagnostics sidecar — but it carries no health field, and the value threads through a chain of `{Name, Tools}`-only carriers (below).

## Decisions (Jesse, 2026-07-04)

1. **Minimal mid-session reconnect is in scope**: lazy, call-driven, one attempt per server per 30s, no background loops, no tool-list re-discovery.
2. Carried: OAuth for MCP servers is out (static `headers` + env expansion is the documented Linear workaround).
3. v2 (from round 1, decide-and-state): **startup-failed servers are terminal in v1** — they registered no tools, so the call-driven trigger can never fire for them (round-1 C1); the honest path is status + warning + a named fast-follow ("retry server" from settings), not silent hope. **Channel-B errors do not mark a connection broken** — the transport is healthy; a reachable-but-400-ing server must neither reconnect-storm nor flap. **Restored sessions re-emit startup warnings deliberately** (round-1 D11) — each warning describes *this* process's connect attempt, and current status may differ from the prior run's.

## Design

### Non-fatal, parallel, per-server startup

Connects run in parallel, each under its own 10s timeout (replacing the 30s batch budget) and a parent context tied to session construction. **Result assembly spans two stages, stated explicitly (round-1 C8/D3):** `NewManager` returns the manager plus connect-stage results (`{Name, Status: connected|failed, Stage: transport|connect|discover, Err}`); `RegisterTools` — which owns the registry and today aborts on the *first* collision (manager.go:129-131) — is reworked to return per-server register outcomes, continuing past failures with per-server rollback via the registry's existing `Remove`; `initMCP` merges both into the final per-server result set. **Determinism under parallelism (round-1 C9):** connect results are re-sorted to config order before registration, so MCP-vs-MCP name collisions resolve first-in-config-order (loser = `failed(register)`), and `Servers()`/tool ordering stay stable across restarts. Core-tool collisions and over-long names likewise become that server's `failed(register)`.

**Warnings ride the deferred-diagnostics path, not inline `emit` (round-1 C3/D4).** `initMCP` runs before the SESSION_START envelope, and the codebase already solves this exact problem: init-time diagnostics collect into a pending list and flush in `emitSessionStartEnvelope` *after* `EventSessionStart`, via `emitDiagnosticWarning` — which renders on every surface but deliberately does **not** fire the user's Notification hook (session_events.go:16-33, 62-73: inline `emit(EventWarning)` would spam the hook once per failed server at every startup, and would order the notification before `thread.started` at the projector). MCP failures join a `pendingMCPWarnings` list flushed exactly like `pendingHookWarnings`. Restore re-emits per Decision 3.

**Plugin configs (round-1 D2):** a plugin whose `.mcp.json` fails to parse degrades to per-plugin failure — its servers land as `failed(config)` results with a warning; the session constructs. CLI `--mcp-config` parse failures and malformed `--mcp` inline specs stay fatal (explicit user input fails fast); a missing global/project `.mcp.json` stays non-fatal. With this, no MCP path can kill a spawn.

### Severity fix (bug, TDD)

The MCP Exec closure returns Channel B through the error path: `if result.IsError { return nil, errors.New(mcpResultToString(result)) }` → registry error branch → `IsError: true` → red ✕ and visible error body on web/TUI. **This is also a model-facing change, stated (round-1 D9):** the tool result now reaches the model as an error-typed `tool_result` (`ToolResultNamed(…, r.IsError)`, llm/generate.go:336) where it previously read as success — the desired behavior (models should see failures as failures and may now retry), pinned by a turn-loop test expectation.

### Lazy reconnect

**Closure mechanics, stated (round-1 D1 — as v1 wrote it the feature was inert):** today each Exec closure captures the session pointer by value at registration (`sess := conn.session`, manager.go:135-140), so swapping a field can never reach it. The rework has closures capture the *connection* (`c := &m.conns[i]`) and read `c.session` under the per-conn mutex on every call; `conn` is extended to retain its `ServerConfig` and transport construction so a redial is possible at all (today the client is a `NewManager` local). A Channel-A failure marks the conn broken (`degraded`); the next call to that server's tools, if ≥30s since the last attempt, redials once — **bounded by the same 10s per-server timeout (round-1 D6; no per-call timeout exists anywhere in the call path, so an unbounded dial would hang the turn)** — success swaps the session under the mutex and emits a recovery line; failure stamps the backoff clock. **Close-during-dial (round-1 C10):** the manager exposes a close signal (context) that aborts in-flight dials, and a dial completing after close discards and closes its session — a pre-dial check alone is a TOCTOU that leaks a subprocess or stalls shutdown. Channel-B never marks broken (Decision 3). Startup-`failed` servers are terminal in v1 (Decision 3); the e2e card asserts this honestly.

### Honest health, rendered

- **Wire — the full carrier chain, enumerated (round-1 C6/D7):** `Status`/`Error` thread through four types and two converters: `mcpconfig.ServerInfo` (config.go:27-30) → `agent` DetailedStatus (via a reworked `Servers()` that reads live per-conn state **under the per-conn mutexes** — the manager holds mutable state now, and `DetailedStatus`/appwire reads run on other goroutines (round-1 D5)) → `server.MCPServerInfo` (server/server.go:36, copied at serve.go:569-571) → `appwire.SerfMCPServerInfo` (copied at appwire_runtime.go:514-516). Status vocabulary: `connected` (live), `degraded` (broken, awaiting its reconnect window), `failed` (never connected — terminal in v1). Both TUI diagnostics renderers grow one status token. **`docs/appwire-protocol.md` is generated ("go generate ./appwire") and gets regenerated as a deliverable (round-1 D10).**
- **Probe**: new public `agent/mcpprobe` wrapping the internal transport machinery: http/sse run a real MCP initialize (+ tool count) under a 3s timeout — a 400 fails honestly; stdio stays a command-present check labeled truthfully. **Probes run in parallel** (round-1 D8 — serial × 3s would multiply settings-render latency by server count; aggregate bound ≈ slowest single probe). **Env-expansion honesty (round-1 C2):** expansion uses the hub's environment, and a missing `${VAR}` is a *per-row* config error — never a pane failure (today `LoadFile`'s expansion is fatal on the first unset var, config.go:181-186, which would blank the whole pane); the status column is labeled "as probed from the hub," with the daemon-env divergence limitation stated (a server authenticated by daemon-side env can probe unreachable from the hub).
- **Settings**: Settings → MCP servers gains the server list + status column — name, transport, probe status. The **"source layer" column is dropped** (round-1 C7): settings discovery reads the single global config file (web_settings.go:462-481) and no type carries layer provenance; project- and plugin-contributed servers surface in session diagnostics instead, stated. The hub's `mcpstatus` package dies; the `web_types.go:64` vocabulary drift dies with it.

## Error handling

Session start with zero healthy servers is a healthy session. Reconnect never blocks a call beyond one bounded attempt; close aborts in-flight dials and discards late sessions. Probe timeouts and per-row env errors classify per-row, never hang or blank the pane. Warning flush failures are non-fatal. All manager state reads (status, tool defs) take the conn mutexes.

## Contract changes (tests that deliberately flip — corrected, round-1 C4/C5)

Flip to pin graceful degradation: `TestIntg_InitMCP_ConnectError` / `RegisterToolsError` (agent/cov_intg_mcp_test.go), `TestIntgMCP_NewManager_TransportBuildError` / `ConnectError` / `ListToolsError` (agent/internal/mcp/cov_intg_manager_test.go), **plus `TestMCPManager_BuiltinCollision` and `TestMCPManager_ToolNameTooLong`** (manager_test.go:232-235, 271-274 — they assert the fatal `RegisterTools` error return being removed). **`TestIntg_InitMCP_DiscoverError` stays pinning fatal** — it exercises a malformed inline spec through `mcpconfig.Discover` (cov_intg_mcp_test.go:164-172), which this spec explicitly keeps fail-fast; v1's flip list contradicted its own config-fatality rule. New: a "healthy servers survive a sibling's failure" spy test; per-plugin degradation for broken plugin `.mcp.json`.

## Out of scope

MCP OAuth; `tools/list_changed` and mid-session tool-list refresh; background health polling; startup-failed-server revival ("retry server" from settings = named fast-follow); per-server enable/disable UI; subagent MCP inheritance; the generic spawn-stderr clarity cleanup (WS6).

## Testing

- Manager: parallel-connect result matrix across all stages incl. register outcomes merged by initMCP; config-order determinism (registration + collision winner under adversarial completion order); healthy-survive-sibling spy; per-server timeout isolation; reconnect — **a registered tool call reaches the NEW session after swap (the closure-liveness test v1's design would have failed)**, broken→backoff→bounded-dial→status transitions, close-during-dial aborts and leaks nothing, Channel-B does not mark broken; `-race` over status reads concurrent with reconnect writes.
- Severity: both channels `IsError: true` end-to-end; Channel-B body carries "[MCP Error]"; the model-facing error-typed `tool_result` expectation; jstest error-marker render for namespaced tools.
- Warnings: collected and flushed after SESSION_START via the diagnostic path — ordering asserted at the projector (no `NotifyWarning` before `thread.started`), and the Notification hook does NOT fire; restore re-emits.
- Plugin: malformed plugin `.mcp.json` → session constructs, plugin's servers `failed(config)`, warning present.
- Probe: http 200 → available; **http 400 → unreachable (the regression)**; refused → unreachable; stdio present/missing labeling; missing `${VAR}` → per-row config error, pane renders; parallel aggregate bound.
- Surfaces: Status/Error across all four carriers + both converters; TUI renderer lines; settings column template test; regenerated protocol doc.
- e2e card: session with one good + one 400-ing server → starts, warns after SESSION_START, good tools work, failing call renders red, settings shows unreachable, **the 400-ing (startup-failed) server stays terminal for the session** — then kill + restart the good server mid-session → next call reconnects.
