# Split `execenv/local.go` and unify file-op dispatch (design record)

Measured on origin/main today. W1-07 has not landed yet (no W1-0x commit past W1-09 touches execenv).

## Summary

`agent/execenv/local.go` is 3,647 lines. It has 123 funcs, 84 `LocalExecutionEnvironment` methods and a 31-field struct (local.go:70-250). Those sizes match the audit; execenv has not moved since. The file mixes six jobs: scratch and sandbox-layer lifecycle, environment probes, file tools, list/glob/grep, process launchers, and path/env helpers.

The security-relevant mess is the file-op dispatch. Every file op picks one of three arms by hand: sandboxed layer, granted scratch layer, or plain filesystem. Eight sites repeat that choice: `ReadFileAndBytesCtx` (local.go:1591), `WriteFile` (:1742), `EditFileWithCtx` (:1804), and `ReadFileRawCtx`, `WriteFileRaw`, `RemovePath`, `RenamePath` in `mutator.go` (:261-346). `WriteFile` and `WriteFileRaw` differ only in tool name, perm and message. The arms are not uniform (reads skip `requireLiveSandboxRootForRelative`, edit adds `checkWritable` first, `ReadFileRawCtx` calls `resolveWrite` for a read, `RenamePath` has two endpoints). Each difference may be deliberate, and nothing pins them in one place.

There are also two near-identical grep walks (`grepNativeSkipping` local.go:2721-2870 and `sandboxFS.grepNative` securepath_browse_fdops_unix.go:188-364), three list-dir walkers, three process launchers sharing setup, and a ~300-line gitignore cost estimator the code itself calls "best-effort, not a proof" (gitignore.go:351-360, issue #1971).

End state: `local.go` under about 800 lines, one path-target helper behind the eight file-op sites, one grep walk body, and the other responsibilities in named files. Net about -600 lines, plus about 3,000 lines moved. Worth it because this is the sandbox boundary: a denial fix today needs eight edits, and drift between arms is how a hole opens (the recent #4703, #4680, #4726 fixes each touched several arms).

## Proposed structure

All in package `execenv` (one package, so no import-direction changes and no exported API change). Files, not packages, because the methods share the unexported `sandboxFS` and the struct.

| File | Owns |
|---|---|
| `local.go` (~500) | struct, constructor, `With*`, `Initialize`, `Cleanup`, `WorkingDirectory` |
| `local_scratch.go` | scratch and sandbox-layer lifecycle (:70-1130), the two locks and their fields |
| `local_probe.go` | `Platform`, `OSVersion`, `LoginShellPATH`, probe capture (:1329-1560) |
| `local_files.go` | `fileTarget`, read/write/edit/exists, `FileMutator` methods moved from `mutator.go` |
| `local_edit_match.go` | fuzzy match helpers `findFuzzyMatch`..`wordSet` (:1890-2015) |
| `local_search.go` | list, glob, grep entry points and the rg arm |
| `local_exec.go` | `ExecCommand`, `ExecArgv`, `StreamCommand`, `DetachCommand`, venv/PATH injection |
| `local_paths.go` | `resolve*`, `ensure*`, `pathWithinRoot`, `filteredEnv*` |

Boundary rules:
- State stays on `LocalExecutionEnvironment`. Files split by method group, not by new types, in the first pass. A `scratchState` struct (fields + `sbMu`/`scratchMu`) is a later, separate decision (Question 1).
- `fileTarget(tool, path, mode)` returns the chosen layer (`*sandboxFS` or nil), the resolved absolute path, and a `release` func. It owns the order of checks per arm and takes mode `read|write`. It encodes today's differences as explicit branches, not as a unified rule: reads skip `requireLiveSandboxRootForRelative`; edit calls `checkWritable` after it; `ReadFileRawCtx` keeps `resolveWrite` on the plain arm. `RenamePath` calls it twice and keeps its cross-scratch refusal.
- One grep walk body takes a small `grepWalkFS` input (the `fs.FS`, a `masked(abs) bool` func that is nil off-sandbox, and a named-file handler). The two entry points build their inputs and call it. The named-file difference stays as an injected handler because it is real drift (off arm windows an over-cap file, sandbox arm uses `grepNamedFile`).
- Process launchers share one `prepareLaunch(workingDir, env)` that does `resolveCommandWorkingDir` + `injectLocalVenvPath(commandEnvironment(...))`. The `lookPathInEnv` step stays in exec and detach only (not stream).
- No new exported symbol. The 12 optional interfaces are untouched except deleting `ReadFileAndBytes` and `EditFileWith` (not interfaces; plain methods).

## Risks and containment

- Sandbox hole from a mis-merged arm (PR 8). Contained by the parity table landing first and by one site family per commit. The refactor keeps each arm's check order literal inside `fileTarget`; it does not unify them.
- Lock-order or lifetime regression in scratch code (PR 4). Pure move of whole methods and fields together; no lock changes. The existing `sandbox_scratch_lease_unix_test.go`, `sandbox_teardown_drain_test.go` and `sandbox_lifecycle_program_fuzz_test.go` run in CI.
- Merge conflicts with in-flight execenv fixes (execenv saw 8 fix PRs in the last few days). Moves go first and ship quickly, one block per PR, so later fixes land in the new files. Each move PR is checked with the name-only diff gate against main (memory: history-rewrite gate).
- Pure-move PRs hiding a change. Use `git diff --color-moved=dimmed-zebra` and a script that compares sorted function bodies before and after; zero body changes allowed.
- Platform build tags. Unix-only files (`*_unix.go`) keep their tags; PR 5 and PR 9 must be built for darwin and windows (`GOOS=darwin go vet ./agent/execenv`, same for windows) because the sandbox arm is unix-only and the off arm is not.
- Grep unification surfaces a latent difference (PR 9). The pair test catches it first; each difference is a named decision, not a silent change.
- Test doubles. PR 6 only touches tests that call two methods; no fake changes.

## Questions for Jesse

1. Should the split stay files-only inside `execenv`, or do you want a `scratchState` type carrying the two locks and their fields (more type work, but it is where the verifier says the real cost lives)? I recommend files-only first, revisit after PR 8.
2. Keep or delete the ripgrep arm (`rg_capture.go`, `buildRipgrepArgs`)? Deleting makes grep always native: simpler and same confinement as sandboxed sessions, but slower on large trees. Needs your call (product and performance).
3. Keep or replace the gitignore cost estimator? Options: keep as is (and fix the comments), or charge the real compiled program size (the follow-up #1971 names), or cap rule-line length and count and drop the estimator. It defends memory use against a hostile `.gitignore`, so this is a safety tradeoff.
4. Fold the Ctx and budgeted forms (`ReadFileCtx`, `EditFileCtx`, `GlobWithBudget`, `ListDirectoryWithBudget`, and so on) into `ExecutionEnvironment`? That removes 5 to 6 optional interfaces but rewrites about 18 test doubles and changes a public interface. Default: leave them.
5. Is it fine to sequence PRs 7 to 11 after W1-07 lands, or should the behavior-preserving refactors go first? I recommend moves (1 to 5) now, refactors after W1-07.

## Rejected alternatives

- New sub-packages (`execenv/scratch`, `execenv/search`). The pieces share unexported `sandboxFS` and the struct, so a package split would force exporting internals. Files give the same navigability with no API change.
- One `fileTarget` that unifies every arm's checks. The verifier showed the arms differ on purpose; unifying would change denial behavior in the sandbox. Keep differences explicit.
- Splitting `local.go` before writing the parity table. Moves are safe on their own, but the dispatch refactor is not, so the table gates PR 8 only.
- Merging `RenamePath` into the single-path helper. Two endpoints and the cross-scratch refusal make it a poor fit.
- Deleting the capability interfaces now. Test doubles depend on capability-absent branches; production has one impl but the branches are test-live.
