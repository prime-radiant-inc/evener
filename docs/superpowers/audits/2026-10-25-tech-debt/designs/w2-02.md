# Watch skeleton dedupe: fire funnel, teardown transaction, configure (design record)

## Summary

The watch code in `agent` repeats the same lock-protected skeletons in several places. Today (origin/main, 2026-10-26): `agent/job_watch.go` is 6,390 lines, `agent/jobs.go` 2,094, `agent/jobs_activity.go` 1,989. Three things repeat:

- Four match sites run the same "offer to the breaker, then build a send or a notification, then count the delivery" sequence.
- Three teardown paths run the same "mark rejecting, persist, then roll back or detach" sequence.
- `configureWatchWithHooks` is a 217-line function (`job_watch.go:764-980`).

Smaller debt sits beside them: two shallow-or-partial `JobRecord` clone helpers, a pass-through `validateWatchSendTarget`, and a duplicated `id`/`watchID` field.

The audit promised about -700 lines. After the verifier's corrections and Wave 0 landing, I measure the real saving at about -150 to -200 lines. The value is that each skeleton gets one owner, so the next change to the breaker or teardown rules lands in one place. The risk is high because all of it runs under `jm.mu`. So the plan is small PRs, each guarded by tests that exist before the refactor.

Two items from the audit are already done on main: the dead `abandonRunningJob` is gone, and `Session.FollowUp` is not in scope here. Two audit items do not survive scrutiny and I recommend dropping them: collapsing the two `deliverStableWatchSend` branches, and a single teardown value that hides three failure policies.

## Current structure

All paths are on origin/main.

**Fire sites** (`noteConditionFireLocked`, `job_watch.go:1945`, guarded by `job_watch_condition_fire_guard_test.go`):
- `onSessionEvent`, call at `:3174`. Records sends, then clears over-budget watches, then enqueues. The cleared notification rides with the event's batch. Has an event-specific identity fix for `job.notification` watches.
- `feedJobOutputWithProvenance`, call at `:3473`. Enqueues, records sends, then clears. Breaks out of the match loop when a match crosses the budget.
- `fireAttachScan`, calls at `:3585` (send branch) and `:3599` (notify branch). Each has its own lock pair, and each clears over-budget after unlock.
- Not part of the funnel, and to be left alone: `fireProgressTick` (periodic ticks never trip the budget), `runTerminalCatchup`, `completeExpired`.

The part that is truly shared per site is small: `noteConditionFireLocked`, then `if cfg.send != nil` snapshot else build notification plus `countWatchDeliveryLocked`. The builders differ per site (self-influence classification, provenance, event identity), and the unlock tails differ in order. A helper that takes a builder closure saves little.

**Teardown paths**:
- `clearWatch` (`job_watch.go:1639`). Marks configs rejecting, persists with `appendWatchTeardownBatch`, on error rolls back via `rollbackWatchConfigSnapshotsRejecting` and `rollbackWatchConfigsRejecting` and returns the error. On success detaches, removes terminal snapshots, forgets empty detached configs.
- `autoClearWatchOverBudgetNotification` (`:2018`). Same mark and persist, but rollback is `rollbackWatchBudgetTeardown`, which also resets `budgetTripped`. Failure returns `(zero, false)`. Success runs `detachOverBudgetWatch`, which lifts rejecting inside the same critical section.
- `abandonRunningJobs` (`jobs.go:844`). Uses `appendAbandonSnapshots`, which can apply part of the batch. On failure it removes the applied snapshots, rolls back, and swallows the error into a notification.
- `jm.appendTeardown` and `jm.appendAbandonSnapshots` are injectable fields on `jobManager` (`jobs.go`), used in six test files. Persist-failure tests are therefore possible today.

The three failure policies are different on purpose (return error, return false, notify). Only the mark and rollback pairing is common.

**Configure**: `configureWatchWithHooks` (`:764-980`) has one production caller, `configureWatch` (`:761`), which passes an empty `watchConfigureHooks{}`. Both hooks (`beforeTargetRevalidate`, `afterDetachedTeardown`) are used only by `job_watch_core_config_fuzz_test.go:231,252`, to force two races. `job_watch_timer_identity_test.go:214-263` is an AST guard that looks the function up by name and counts calls inside its body. `validateWatchSendTarget` (`:1249`) forwards to `validateWatchSendDeliveryTarget(target, _ watchArgs)`; the only test caller besides `:679` and `:822` is `cov_s1_watch_validate_test.go:30`.

**Clone helpers**: `cloneJobRecord` (`jobs.go:2088`) is a shallow `*rec` copy with six uses in `jobs.go` plus `jobs_nested.go`, `job_shell.go`, `session_tools_jobs.go`. `cloneActivityRecord` (`jobs_activity.go:1027`) deep-copies three pointer fields only. `cloneFoldJobs` and `cloneFoldOrdered` (`jobstore/store.go:945,968`) deep-copy seven fields with the body pasted twice. Important: `agent/clone_aliasing_fuzz_test.go:29` records that `cloneActivityRecord` leaves `StructuredResult` (an `any` holding decoded JSON) shared while jobstore's `cloneEvent` deep-copies it, and calls this "a product question about who mutates a projected record".

**Send-rail state**: ten maps and sets on `jobManager` (`jobs.go:81-130, 211-217`), all guarded by `jm.mu`. `deliverStableWatchSend` has two branches that return different values and keep different failure bookkeeping.

## Proposed structure

No new package. Everything stays in `package agent` and in `jobstore`. W2-01 will have split `job_watch.go` by concern first, so the helpers land in the file W2-01 names for their concern (condition fire, teardown, config). If W2-01 has not landed, apply the same edits in `job_watch.go` and let the merge follow.

- `jobstore`: `(*JobRecord).Clone()` owns the deep copy of every pointer, slice, map and `any` field. `cloneFoldJobs` and `cloneFoldOrdered` call it.
- `agent`: one `fireConditionLocked(cfg, build)` style helper per the decision below, or nothing (Q1).
- `agent`: a small `watchTeardown` value holding `targets` and `detachedCfgs`, with `markRejectingLocked()` and `rollback()`. Each of the three sites keeps its own persist call, failure policy and success tail.
- `agent`: `configureWatchWithHooks` becomes a short orchestrator over a few named steps (`validateWatchArgs`, `installWatch`, and a restore or replace step as the code suggests). The hooks parameter stays. The AST guard is updated to follow the new function names.

Boundary rules: helpers named `*Locked` keep the "caller holds `jm.mu`" contract and never take the lock. A helper never calls `appendEvent` while holding `jm.mu`. State stays on `jobManager`; no new struct owns locked state unless Q2 is approved.

## Risks and containment

- **Lock ordering and critical sections.** Helpers named `*Locked` do not lock. PRs 6 and 8 are split one site per commit so a revert is small. `detachOverBudgetWatch` keeps its single critical section for detach plus unmark.
- **Order drift at wake time.** The three sites enqueue, record and clear in different orders, and the order decides what the model sees in its first wake. PR 7 pins each order before PR 8 touches it. The helper does not own the tail.
- **Rollback losing state.** The budget path must reset `budgetTripped`, and the abandon path must remove already-applied snapshots. PR 5 asserts both before PR 6.
- **Clone depth change.** PR 2 may make activity listings deep-copy `StructuredResult`. That is a cost and safety change, not a visible one. Q3 asks before doing it.
- **Merge conflicts.** `job_watch.go` has 259 commits of history. Land PRs 3 to 9 after W2-01 and rebase quickly. PRs 1, 2, 5, 7 touch tests or `jobstore` and can go earlier.
- **Guard tests.** `job_watch_condition_fire_guard_test.go` (writes to `conditionFires` only inside the helper) and the timer-identity AST guard must be updated in the PR that moves what they scan, never later.
- **Docs.** `docs/job-control.md` changes only if lifecycle prose changes. I do not expect any. Call out in each PR description that no behavior changed.

## Rejected alternatives

- **One `watchTeardown` value that runs the whole transaction.** It has to model three failure policies, so it becomes a callback soup. Share only mark and rollback.
- **One flush helper for all fire sites including progress ticks, catch-up and expiry.** Those sites do not use the breaker on purpose.
- **Collapsing the two `deliverStableWatchSend` branches.** They return different values and keep different retry bookkeeping. Wait until per-branch concurrency tests exist.
- **Splitting `watchConfig` into three role types.** About -50 lines of value against 132 test literals to rewrite.
- **Replacing hooks with real synchronization in the race tests.** No cheap way found; keep the hooks.
