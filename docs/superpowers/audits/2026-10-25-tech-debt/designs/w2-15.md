# Split `stores/threads.ts` and the transcript repository (design record)

Roadmap entry W2-15. Findings: web-stores-1, -3 (step 2), -5, -6, -9, -16. Measured on origin/main at 7887662c9f (2026-10-26).

## Summary

`cmd/evener-hub/frontend/src/stores/threads.ts` is 8,899 lines (audit said 8,990; W0-27 removed about 90). It holds 194 top-level functions, 85 module-level `let`/`new Map|Set` singletons, the zustand store body (`threadsStore`, :7135-8262, about 1,130 lines) and a hand-maintained reset (`resetThreadsStoreForTests`, :8771-8899, 129 lines) that clears those singletons one by one. 173 files import it and 117 import the reset. Two modules already had to work around it: `liveControls.ts:63-65` says threads.ts cannot import it without a cycle, and `tasksPanel.ts:1-9` documents a lazy reach-back.

The end state is a thin `threads.ts` that composes the store and its actions, plus about eight owner modules, each holding its own state and its own reset. Dependencies run one way: owner modules never import `threads.ts`. The payoff is reviewable diffs (68 commits touched threads.ts since 2026-09-01), no import cycles, and a reset that is the sum of small resets. Net deletion is small (about -500); the value is moves (about 8,000 lines).

`transcriptRepository.ts` (3,108 lines) is a smaller problem than the audit said. `SessionEntryCache` already lives in its own `sessionEntryCache.ts` (1,805 lines), so the "1,805-line class inside the repository" part of web-stores-16 is done. What remains is `TranscriptRepository` itself (class at :367-3108, about 2,700 lines, ~95 methods). I propose leaving it alone in this entry (question 3).

## Proposed structure

Rule: an owner module imports only appwire-client, other leaf owners listed below it, and shared utilities. It never imports `threads.ts`. If it needs a store read or the live client, `threads.ts` passes a getter at wiring time (the same shape `tasksPanel.ts` wants). Each owner exports `reset...ForTests()` next to its state; `resetThreadsStoreForTests` calls them in a fixed order.

Leaf first (bottom of the list has no store dependency):

1. `threadsErrors.ts`: `ConflictError`, `StopCanceledError`, `mapConflict`, `isStorageTimeout`, `isStorageFailure`, `appendFrameTime` + constants, `olderTranscriptPageKey`. Pure.
2. `recoveryFence.ts`: `isRecoveryFenced`, `isResumeOnly`, `isSendResumes`, `resumeOnlyModel`, `sendResumesModel`, `sendDrivenModel`, `localFenceSignals`, `hasBlockedUnknown`, `hasQueuedNonSend`. Pure functions over a model. This is the predicate `liveControls.ts` needs, so the cycle comment goes away.
3. `cacheLifetime.ts`: cache epoch, channel, `markCacheSessionsDeleted`, `clearCachedSessions`, `countCachedSessions`, `subscribeCacheWrites`, `applyCacheGapRule`, and `refCounts`-style lifetime ownership (:5292-5390, :8263-8600).
4. `entryTranscriptRoutes.ts`: region 700-1640, owner of `productionEntryRoutes`, `entryRouteRetirements`, `olderPageGenerations`.
5. `mutationRuntime.ts`: region 1988-2790 (pins, undelivered ids, dispatch scheduling, runtime creation). Owner of `mutationRuntime`, `pinnedMutationRefs`, `dispatchableMutationRefs`.
6. `stopFence.ts`: region 2793-3285 (stops, shutdown gates, resume swap, retarget). Reads `mutationRuntime.ts`.
7. `mutationEnqueue.ts`: composer intent, direct vs durable enqueue, retry/edit/remove/recovery actions (4095-5100 and 3285-3620).
8. `hydration.ts`: after W1-46, one hydration path with explicit differences, pending hydration, notification replay, owned retries, `refreshTrackedThread`/`refreshWatchedThread` taking an options object.
9. `threads.ts` keeps: `threadsStore` creation, action bodies (grouped by small slice-creator functions in the same file), client wiring (`handleReady`, `rewireClient`, `requireClient`), `useThreadsStore`, and the reset sequence. Target under 2,500 lines.

Public surface: panes keep importing the names they import today. Two options in question 1.

Test seams: `...ForTests` exports move to `stores/testing/` (the directory already exists) as each owner is cut out. Seams with a behavior test that cannot reach the failure otherwise stay as exports on the owner module.

Shim removal: `hostRouting.ts` importers (35) and `mutationDispatcher.ts` importers (3) import `@evener/appwire-client` directly. `mutationOutbox.ts` stays for its type aliases unless the aliases are also inlined (question 2).

## Risks

- **Module-load wiring order.** `threads.ts` does work at import time (unwire callbacks, cache channel, residency lazy-creation). PR 3 adds the load-order test before any state moves. Each later PR keeps wiring in `threads.ts`.
- **Hidden shared singleton.** A moved function reads a `let` that stayed. TypeScript catches the name; it does not catch two owners each keeping a copy. The reset-completeness test in PR 5 and the existing 36 suites cover it.
- **Reset ordering.** `resetThreadsStoreForTests` has comments about generation bumps and `getInitialState()` that encode real ordering (:8800-8830). It stays in `threads.ts` and calls owner resets in the same order; no reset mechanism is introduced (question 4).
- **Cycles.** The one-way rule is enforceable. PR 3 proposes no new tooling; reviewers check imports, and `tsc` fails on a real runtime cycle only through `undefined` at load, so each PR runs the load-order test.
- **Merge churn.** 68 commits since 2026-09-01 touched this file. Keep each PR a single region, rebase often, merge serially.
- **Importer churn.** 173 importers. Moves keep exported names; option 1 of question 1 controls how many import lines change.
- **Product behavior.** No PR changes recovery, fence, or retry behavior. The message-recovery contract tests in the existing suites are the guard, run in CI per memory rule (tests in CI, not local).

## Questions for Jesse

1. After a symbol moves out of `threads.ts`, do importers change to the new module, or does `threads.ts` re-export it? Re-export keeps diffs small and is a shim of the kind step 1 deletes. Direct import touches more files per PR (up to 173 for `putThreadModel`-style names) but leaves no shim. I recommend direct import.
2. The 1,408-line and 1,330-line web tests of `MutationDispatcher` and `MutationOutbox` (web-stores-9): move them into `appwire-client/typescript/state/mutation`, or keep them in the web tree? The package has no dispatcher or outbox test today.
3. Leave `TranscriptRepository` (2,700 lines) alone in this entry, since `SessionEntryCache` is already split? I recommend yes and revisiting only if a later feature fights its size.
4. Reset mechanism: keep an explicit call list in `resetThreadsStoreForTests` (my plan), or add a small registry that owners self-register into? The registry is a new mechanism; AGENTS.md's simplicity rule and your 2026-08-30 note argue against it.
5. Is it acceptable to land step 8 only after W1-46, or should hydration move first as two functions and be unified inside the new module?

## Rejected alternatives

- **One big split PR.** Unreviewable at 8,000 moved lines, and the module-load order risk has no bisect point.
- **Keep threads.ts as a barrel re-exporting every owner.** Recreates the shim pattern the audit asks to delete and hides the dependency direction.
- **Zustand slices for the whole store.** The actions share the closure singletons; slicing the store first would force the same ownership decisions with less safety. Slice-creator helpers appear only in step 7, inside the file.
- **Reset registry now.** A new mechanism for a 129-line list that shrinks as owners take their own.
- **Split `TranscriptRepository` here.** Large, high risk, and not blocking any threads.ts extraction.
