# Hub and CLI composition roots (design record)

Source: ROADMAP W2-10, verified findings hub-root-rest-1, -7, -10, -14, internal-misc-cmds-3, -4, x-error-handling-slop-1. Code read on origin/main at 7887662c9f (2026-10-26).

## Summary

Three startup functions are each one giant body. `runMain` in `cmd/evener-hub/main.go` is 776 lines (253-1028). `runServeWithDeps` in `cmd/evener/serve.go` is 1,597 lines (401-1997). `run` in `cmd/evener/run.go` is 403 lines (114-516). `serve` and `run` declare 36 of the same flags twice, with identical defaults and drifted help text. Five hub subcommands each re-parse flags with their own `fs.Visit` copy. The tool-fluency runner carries copies of the CLI's launch helpers.

End state: `runMain` reads as a list of named construction phases, and each phase hands back its own cleanup so the `defer` order stays literal. `serve` and `run` register their shared flags from one definition. The helper copies in tool-fluency are gone. Splitting the hub `main` package is not part of this plan (question 1).

Why it is worth it: these functions are where startup, recovery and shutdown order live. Today nobody can review a change to one phase without reading 700 to 1,600 lines. Estimated net change is about -800 lines, with most of the value in reviewability.

W0-07 and W0-08 have landed (commits c44a1dd760, 7f13df5327). They did not touch these functions. W1-32 (handler skeleton) has no commit on main yet. It edits `app_rpc.go`, which this plan does not touch, so the dependency is only about ordering reviews.

## Proposed structure

Hub (all stay in package `main`, same files unless noted):
- `main.go` keeps `Run`, `mainDeps`, `runMain` as a short sequence. New file `hub_startup.go` holds the phase functions and the small `hubRuntime` struct they share (config, endpoint, state roots, stores, `web`, `sshManager`, `background`).
- Phase shape: `func (r *hubRuntime) openStores(...) (cleanup func(), err error)`. `runMain` calls each phase and runs `defer cleanup()` on the next line. The defer stack is the same list in the same order, written where a reader can see it. No cleanup registry, no new type.
- Phases, by the order they run today: `acquireProcessLock`, `startDiagnostics` (pprof, trace), `openStores`, `openListener`, `connectHosts` (registry, SSH manager, hostops store), `buildWeb` (the `WebConfig` literal), `wireNavigationInvalidation` (the single onChange site), `startBackground`, `publishEndpoint`, `announce`.
- Subcommand flag helper: one `parseConfigFlags(fs, opts)` in a new `cli_flags.go` that returns the explicit/present pair via `fs.Visit`. `attach`, `endpoint`, `login-url`, `restart` and `parseHubOptions` call it. `login-url` calls `readAuthToken` and wraps the error as `ErrLoginURLToken`.
- Launch-check: one `runEvenerLaunchCheck(ctx, binary, env, extraArgs...) ([]byte, error)` in `spawn.go` that owns default binary, timeout, redaction and refusal wrap. The two callers keep their own decode.

Evener CLI:
- New `cmd/evener/launch_flags.go`: `type launchFlags struct` holding the 36 shared values, with `registerLaunchFlags(fs) *launchFlags`. One help string per flag. `newRunFlagSet` and `runServeWithDeps` each add only their own flags after it. Each keeps its own ErrorHandling and usage printer.
- `cmd/evener/launch_setup.go`: the nine once-each helpers become `resolveLaunchSettings(lf *launchFlags, ...) (launchSettings, error)` so the validation prelude exists once. `serve` and `run` still build their own `SessionConfig` literals (question 3).
- `runServeWithDeps` is split only at its clean joins: flags (above), `prepareServeSession` (:487-820: signals, plugins, state dir, profile, session create), `serveRuntime` struct owning the closure state at :860-1540 with the closures as methods, `serveHTTP` tail (:1910-1997). The retirement and bridge closures move to `serve_retirement.go` and `serve_bridge.go` as methods on the same struct.
- `cmdutil` gains `ApplyFastCheapModel`, `ParseSandboxNet`, `ConfigureSandbox`, `ProvisionSandbox` (with `PickFreshSessionID` folded in) and `InitialProfile`. `cmd/evener` and tool-fluency both call them. `cmdutil` already imports `agent`, `llm` and `appwire`, so no new edge appears.

Boundary rules:
- `cmdutil` imports nothing from `cmd/*`. The hub package imports nothing from `cmd/evener`. Tool-fluency imports `cmdutil` only.
- Phase functions take explicit inputs and return outputs. They do not read package-level mutable state beyond what `runMain` reads today (`hubBootID`, `hubBoundAddr`, `hubLaunchEntrypoint` globals stay where they are and are listed in the PR 4 description).
- `mainDeps` stays the only test seam for the hub. `serveDeps` stays for serve.

## Risks and containment

- Shutdown order regresses. Contained by PR 5 landing first and by keeping `defer` literal next to each phase call. The two conditional defers (message search, trace) become phase-returned cleanups that are always non-nil (a no-op when the resource did not open).
- Error-path double close. Today's error returns call `hubListener.Close()` by hand and also defer it. Phases keep one close per path; PR 5 includes a failure-after-listen case.
- Help text drift treated as test oracle. PR 7 compares usage strings between the two flag sets for equality, which tests sharing, not wording. No hardcoded phrase.
- `serve` closure state shared across clusters. PR 9 moves clusters as methods on one struct with the fields unchanged, so lock and ordering discipline is copied, not redesigned.
- Merge conflicts with W2-13 (`Config`, host knobs, `WebConfig` literal) and W2-11 (`newHubRelayFunctions` neighbors). Contained by keeping PR 6 off `Config` and `WebConfig` field lists. Land PR 6 before W2-13 starts touching the `WebConfig` literal, or have W2-13 rebase onto `buildWeb`.
- Tool-fluency is a separate build target. PR 2 builds it in CI and keeps its tests, which already import `cmdutil`.

## Questions for Jesse

1. Should the hub `main` package be split at all? My recommendation: no, now. The cheapest seam (`hubconfig`, 934 lines) moves 1.7% of the package, conflicts with W2-13 (which rewrites `Config` and drops the `host_*` knobs), and buys one thing: `sshconn`'s test stops importing package `hub`. If yes, which seam goes first? I would wait until W2-13 lands, then do `hubconfig` as a pure move.
2. Is it fine for the unified flag help text to change the `evener serve --help` wording to the longer `run` wording? It is user-visible text on a daemon flag set that only the hub and scripts invoke.
3. Do you want the two `SessionConfig` literals (`serve.go:686`, `run.go:354`) unified into one builder? I left them separate. They share about 25 fields but differ in lifetime context, ownership, and resume handling. Unifying them is a bigger and riskier change than this plan.

## Rejected alternatives

- One big "split runMain" PR. Rejected: no way to bisect a shutdown-order regression.
- A cleanup registry (`runtime.AddCleanup(fn)`). Rejected: it hides the order that a `defer` line shows, and it adds a seam nothing else needs.
- Generating the flag sets from a table or struct tags. Rejected: two flag sets with 13 differing flags do not justify a mechanism. A shared registration function does the job.
- Splitting the hub `main` package into many packages now. Rejected: 193k test lines resolve unexported names. About 64k moved lines, and the verifier (hub-root-rest-10) said it is not a standalone PR.
- Lint thresholds (`funlen`/`gocyclo` with baseline) from x-error-handling-slop-1. Deferred, not rejected: add after these three functions are under the threshold, as a separate small PR.
