### High

- **Stale GET leaves `hubLoading` permanently true, blocking future writes** — `appwire-client/typescript/keybindingsStore.ts:673` (stale branch at `:675`; thunk at `:937`)
  `applyHubOverrides` only resolves the function-valued `extra` (thunk) when the payload is not stale (`payload.revision < state.revision`). On the stale branch it skips the thunk entirely, but `hubLoading: false` lives inside that thunk. The previously plain-object `extra` always cleared it; now `hubLoading` stays `true` indefinitely, so `patchOverrides` refuses with `UNAVAILABLE_MESSAGE` (and sets `hubError`) and `rebaseDraft` throws, even though the hub is fine. The new test at `keybindingsStore.test.ts:278` exercises this stale path but never asserts `hubLoading`, so the regression is latent.
  **Fix**: Separate the unconditional `hubLoading`/`hubError` reset from the deferred `settledWrite` side effect. On the stale branch, publish `hubLoading: false` as a plain object without invoking `settledWrite`, or have `refreshFor` clear `hubLoading` when `applyHubOverrides` returns `false`.

### Medium

- **Post-rename settle leaves `draftConflict: true` with `draft: null`, blocking next save** — `appwire-client/typescript/keybindingsStore.ts:1217`–`:1220` (with `:725` and `:1177`)
  The post-rename success path calls `settleWrite(applied, checkpoint, false, { saving: false, writeUncertain: false })` without `draftConflict`, relying on `applyHubOverrides`' own `draftConflict: staleDraft(state.draft, payload.revision)`. At that moment `state.draft` is still the proposal (pre-write revision) while `payload.revision` is the confirmed revision, so `staleDraft` returns `true`. `settleWrite` then publishes `draft: null` without clearing `draftConflict`, violating the invariant `draftConflict === staleDraft(draft, revision)` and surfacing as `snapshot.keybindings.conflict === true` (`mobile-native/src/nativePreferences.ts:134`). A subsequent `saveDraft(rules)` throws `"Review the current shortcuts before saving your changes."` (`:1188`) despite a successful write and no draft to review. The confirmed-reply caller passes `draftConflict: newerExternal` (`:1286`) to avoid exactly this; the post-rename caller has the same "draft still present during apply" condition.
  **Fix**: Derive `newerExternal` from `getState().revision > applied.revision` and pass `draftConflict: newerExternal` (matching the confirmed-reply path), or clear `draftConflict` in `settleWrite`'s final publish when the checkpoint was released.

- **`UnreadableDraftError` maps to `storageUnavailable`, aborting hub load and blocking `discardDraft`** — `appwire-client/typescript/keybindingsStore.ts:605`
  The restore path treats `UnreadableDraftError` identically to a port failure (`storageUnavailable`), aborting the hub load and blocking `discardDraft` despite the distinct-record doc indicating a bad record should be discardable.
  **Fix**: Handle `UnreadableDraftError` separately in the restore path — allow the hub load to proceed and permit discarding the bad record.

- **`removeIf` returns `void`, so discard treats a concurrent replacement as success** — `appwire-client/typescript/draftCheckpointPort.ts:16`
  `removeIf` is a compare-and-remove operation but returns no outcome. `discardDraft` and `settleWrite` therefore clear in-memory draft state while a concurrently replaced record remains durable — the refusal is silently swallowed.
  **Fix**: Return the removal outcome from `removeIf` → `discardClassified` → `discardStoredDraft`; on refusal, reload and publish the replacement or surface a storage conflict instead of clearing the draft.
