## Summary

The two commits extract mobile's connection lifecycle into a new `useHubConnection` hook built on the package's shared `createConnectionStore` (D28 native half), and then close a stale-client race during hub switches.

- `hubConnection.ts` owns the token fetch, client construction, `onStateChange`-driven error reporting, and exposes `{ client, state }`. The package store now handles wiring/mirroring client state and swap safety; the hook no longer keeps its own `session`/`state` React state.
- The new `connectedFor` ref records which hub a client was actually opened for, and is written in the same synchronous step as `store.setState({ client })`. During the render that already names a newer `activeId` but whose effect has not yet run (so the store still holds the previous hub's client), the gate `connectedFor.current === activeId` returns `null` instead of surfacing the old client.
- `hubConnection.test.tsx` exercises the idle/connect/ready/closed transitions, the hub-switch race, attempt-bump teardown, and unmount listener release with a fake client over the real store.

I traced the ordering of cleanup, effect re-runs, ref writes, store publishes, and `useSyncExternalStore` re-renders, including React's synchronous-notification and StrictMode cases. The store's swap-safety (`core.ts`) detaches and identity-guards the outgoing client's listener, so the removed `setState(next)` in the hook's listener is faithfully replaced; the extra `store.setState({ client: null })` in cleanup is what releases the store's own listener on unmount. The gate is conservative (it can only hide a client, never reveal the wrong one), and every place `connectedFor` changes is paired with a store write that forces a render. The package subpath import resolves through tsconfig paths, the vitest alias, and Metro's generic subpath resolver (covered by `metroResolver.test.ts` reading the exports map), and `ConnectionProvider` retains no now-unused imports.
