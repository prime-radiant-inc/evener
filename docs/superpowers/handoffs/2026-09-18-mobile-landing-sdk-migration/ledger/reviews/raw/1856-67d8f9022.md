## Summary

The series moves the pending-turns "projection fence" out of the web store (`cmd/evener-hub/frontend/.../pendingTurnsStore.ts`) into the shared SDK as `createMutationProjectionFence` in `appwire-client/typescript/state/mutation/projection.ts`, exported from `state/mutation/index.ts`. The extracted version changes the shape of a refresh result: instead of computing the winning target set at read resolution and applying it immediately, `refresh()` returns `{ snapshot, apply() }`, where `apply()` re-checks the generation floor at call time so an `advance()` (live commit) or newer refresh landing after resolution can still out-rank it. It also (per the reverted/redone commits) keeps a failed refresh's raised generation rather than rolling it back, and adds unit tests for the ordering rules.

## Findings

**Medium — `apply()` does not re-check the all-targets generation floor**

File: `appwire-client/typescript/state/mutation/projection.ts`, `apply()` at lines ~131–138 (compare with the resolution-time check at line 121).

The re-check only compares the per-target generation:

```ts
if (refreshGenerations.get(target) !== generation) accepted.delete(target);
```

A newer *specific* refresh or an `advance()` for the target updates `refreshGenerations`, so it is caught. But a newer *all-targets* refresh only advances `allTargetsRefreshGeneration` at `refresh()` start (line 102); it does not touch `refreshGenerations` unless/until it resolves. So if a newer all-targets refresh starts after this refresh resolved but its read rejects before the caller calls `apply()`, the per-target generation still equals `generation` and the older snapshot is accepted. That directly contradicts the invariant this series tests ("a newer refresh that fails still raises the generation floor for an older in-flight refresh"), and because the superseding refresh failed, nothing overwrites the stale projection until the next successful read — the exact stale re-projection the fence exists to prevent.

Suggested fix: re-run the full floor check in `apply()`, e.g.

```ts
for (const target of accepted) {
  if (generation < Math.max(allTargetsRefreshGeneration, refreshGenerations.get(target) ?? 0)) {
    accepted.delete(target);
  }
}
```

(For accepted targets `refreshGenerations.get(target) === generation`, so this reduces to rejecting when a newer all-targets refresh started.) Add an all-targets counterpart to the existing "newer refresh that fails" test.

---

**Low — `reset()` restarts generation numbers, so a stale pre-reset `apply()` can alias a post-reset refresh**

File: `appwire-client/typescript/state/mutation/projection.ts`, `reset()` at lines ~152–158 (`refreshGeneration = 0;` at line 155), interacting with `apply()` at line 136.

`apply()` decides validity by equality against `refreshGenerations`, but `reset()` clears the map and restarts the counter at 0. A refresh that resolved before a reset keeps its captured generation; after the reset, later refreshes are numbered from 1 again and can reuse that same number. If a post-reset refresh happens to be assigned the stale result's generation for the same target, that stale result's `apply()` sees `get(target) === generation` and accepts, projecting a pre-reset (pre-client-swap) snapshot. `refresh()` already captures `epoch` and can return `false`, but the returned object never exposes the epoch and `apply()` doesn't consult it, so nothing guards the resolve→apply window. (This window doesn't exist in the original store, which applied synchronously inside the same continuation.)

Suggested fix: have `apply()` also verify `refreshEpoch === epoch` (capture `epoch` from the enclosing `refresh` scope), and/or stop resetting `refreshGeneration` to 0 so generation numbers stay monotonic and can never alias across a reset.
