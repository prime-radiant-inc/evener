## Summary

The series does three SDK-migration fixes in the shared `appwire-client` package plus the hub frontend and mobile consumers:

1. **Reasoning export** — moves `joinedReasoningParagraphs` from the hub's `reasoningFormat.ts` into the package (`reducer.ts`), exporting it from the package index; the hub file now re-exports it so `ThinkBlock.tsx` keeps one import site.
2. **Image folding + warning text** — adds regression tests and comments pinning the "empty input-image list means absence, not removal" rule (one-way `mergeItemImages`), shares `isActiveItem` via `itemFailure.ts`, bounds/route-tests the raw warning-frame fallback (`rawWarningFrame`, code-point-safe truncation), and makes `warning` rows render `""` text when only `title`/`hint` exist (web reads `item.warning`; mobile gains `warningFallbackText`). 3. **Ask resolution** — `liveAskQuestions` now gates on the wire's `ThreadModel.askPending` and treats interrupt/user-steer steering items as resolution boundaries alongside plain user messages.

The final aggregate is coherent and the new tests exercise meaningful behavior (item-scan boundaries, the wire gate, explicit image removal vs. absence, surrogate-safe truncation). I found one behavioral concern.

---

**Medium — early return on `askPending` silently drops the transcript-derived fallback for threads whose snapshot omits the flag**

File: `appwire-client/typescript/deriveAskQuestions.ts:106` (`if (!model.askPending) return [];`), interacting with `reducer.ts:823` (`askPending: thread.evener.askPending ?? false`).

The wire type itself documents that this field is absent (decoding as `false`) "on old daemons and source-backed threads that omit the field" (`appwire/types.go`'s `EvenerThread.AskPending` comment). Before this change `liveAskQuestions` ignored `askPending` entirely and derived the live set from the transcript, so such a thread with a completed, unanswered `ask_user` item still rendered the answer dock. After this change `askPending === false` (including "absent") short-circuits before the scan, so the dock never appears for those threads — the user sees the pending question's transcript row but has no way to answer it.

The tradeoff is deliberate and does fix a real bug (a *past* session, whose `Evener.AskPending` is intentionally hardcoded false at `cmd/evener-hub/app_threadread.go:774`, could otherwise show a bogus dock), so the concern is specifically the tri-state collapse: hydrate cannot distinguish "the server says nothing is pending" from "this producer never sent the field". If answering a question on a source-backed/older-daemon session is a supported scenario, this is a user-visible loss of function; if it is not, the constraint should be documented at the return so the next reader does not treat the wire bool as universally authoritative.

Suggested fix: preserve absence at hydrate (e.g. `askPendingKnown` alongside `askPending`, or a nullable model field) and fall back to the positional scan only when the value is unknown, rather than whenever it is false. If the drop is intentional, add a comment at `deriveAskQuestions.ts:105` naming the old-daemon/source-backed case explicitly, since the current comment only explains why re-derivation is undesirable.

## Review Findings
- **Severity**: Medium
  - **Location**: `appwire-client/typescript/reducer.ts:1697`
  - **Problem**: The warning fold copies unchecked `params.title` and `params.hint` into `ItemModel.warning`. The new projector guard only fixes `itemSummary`; `WarningItem` still renders those values using truthiness, so an object or array title/hint from a malformed frame can crash React with “Objects are not valid as a React child,” while numeric values render despite `hasWarningText` treating them as absent.
  - **Fix**: Normalize `title`, `hint`, and `source` to strings at the reducer boundary, or apply the same string/non-blank guard in `WarningItem` before rendering.

---

- **Severity**: Low
  - **Location**: `appwire-client/typescript/reducer.ts:1206`
  - **Problem**: `rawWarningFrame` serializes the entire unknown frame and expands every code point with `Array.from` before slicing. The 2000-code-point bound limits stored text, but a large warning still creates an O(frame-size) temporary allocation; with the transport’s 128 MiB frame limit, this can amplify memory pressure before truncation.
  - **Fix**: Take a bounded UTF-16 prefix first, then expand and truncate that prefix by code point, or use an iterator that stops after 2000 code points.
