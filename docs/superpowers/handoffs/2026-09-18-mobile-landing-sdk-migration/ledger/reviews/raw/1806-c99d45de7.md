## Summary

The series unifies how a pending `ask_user` question is resolved between the live session and a restored one. It introduces `turnResolvesAskBoundary` (shared by `deriveRestoredState`/`deriveRestoredAskPending`), excludes human-note steering from resolving a pending ask, adds a `SteeringCarrier` tag to `schema.TurnFailureInfo` (set for a carrier whose own steer fails to append or whose skill selection fails), clears `askPending` before `EventSteeringInjected` is published, and adds substantial tests plus a `beforeSteeringInjectedPublish` test seam. The mechanics of the tag, the shared boundary, and the emit ordering look correct.

## Issues found

**Medium — the human-note exclusion is bypassed on the production carrier path, so saving a note still resolves a pending ask live and diverges from restore**

`steeringSourceAnswersAsk` (agent/session_tools_ask.go:115-117) deliberately excludes `SteeringKindHumanNote`, and `clearAskPendingForResolvingSteer` / `turnResolvesAskBoundary` honor that. But a human note is delivered by `SetHumanNote` → `wakeForPendingSteering` → `ProcessPendingUserInput`, which claims the carrier and calls `ProcessInputKind(..., EntryUserInput)` (agent/session_client_mutation_queue.go:265-284). That enters `processOneInput`, which clears the pending set unconditionally on entry, before `acceptSteeringCarrierInput` ever runs:

```go
// agent/session_lifecycle.go:1801
// Pending asks resolve with this accepted turn (spec §5.2) ...
s.askPending = nil
```

The entry gate `if len(s.askPending) > 0 && kind != EntryUserInput` (session_lifecycle.go:1155) admits EntryUserInput, so a note wake reaches this clear. Consequently, with a question pending, `SetHumanNote` → live run leaves `askPending` empty and reports no pending ask on the wire — exactly the behavior `TestAskUser_HumanNoteDuringPendingAskDoesNotResolveIt` (agent/session_ask_test.go:1701) asserts must not happen. That test only calls `acceptSteeringCarrierInput` directly, skipping `processOneInput`'s entry clear, so it passes while the real path is still broken.

The concrete harm is a live/restore disagreement: live silently dismisses the question, but after a daemon restart `deriveRestoredAskPending` scans past the non-decisive human-note `TurnSteering`, reaches the `ask_user` `TurnToolResults`, and re-derives the question as pending (`SessionAwaiting`), flipping the client's ask state back on. This is the same class of desync the series set out to remove, on the most likely path for "user saves a note while a question is pending" (the session is idle/awaiting, so the note always arrives via this wake carrier rather than mid-round).

Suggested fix: make the entry clear conditional for the carrier case — e.g. in `processOneInput`/`acceptUserInputWithSkillSelection`, when `queuedClientMutationFromContext(ctx).SteeringCarrier` is set and the steer it is about to drain is a `SteeringKindHumanNote`, leave `askPending` intact (the mid-round predicate already knows this distinction). Then add a regression test that drives `ProcessPendingUserInput` (not `acceptSteeringCarrierInput`) with a queued human note while an ask is pending, asserting both `askPendingCount() == 1` live and that the restored session still reports the question.
