## Summary

The commit narrows the "a turn resolves the pending ask" boundary so that only user-sourced steering that actually answers the question clears `askPending`. It:

- Adds `steeringSourceAnswersAsk` and uses it both for the live mid-round clear (`clearAskPendingForResolvingSteer`, called as a steer lands) and for a new entry-clear guard in `processOneInput`, so a human-note carrier no longer clears the pending ask on acceptance.
- Moves the clear ahead of `EventSteeringInjected` so the server's ask-facet refresh never observes a stale `askPending=true`.
- Adds `testOnly.beforeSteeringInjectedPublish` and three live tests (human note does not resolve; mid-flight answering steer does resolve and reaches the model; clear precedes publish).
- Adds `schema.TurnFailureInfo.SteeringCarrier` and tags the two carrier-TurnFailure shapes so a restore can treat them as a resolution boundary too, with `emitSteeringCarrierTurnFailure` / `recordFailedSteeringSelection` plumbing and a claim-drain marker.

The live behavior changes look correct and match the stated intent.

---

**Severity: medium** — `TurnFailureInfo.SteeringCarrier` is written but never read; restore still re-derives a pending ask after a carrier failure, contradicting the code's own documented contract.

- `agent/schema/turn.go:144-170` declares the field and states "restore must read either case as resolving too", naming `deriveRestoredAskPending`/`deriveRestoredState` and `turnResolvesAskBoundary`.
- `agent/session.go:575` and `agent/session_tools_ask.go:132` also reference `turnResolvesAskBoundary` — no such symbol exists anywhere in the repository.
- The actual restore consumers, `deriveRestoredState` (`agent/session_tools_ask.go:350`) and `deriveRestoredAskPending` (`agent/session_tools_ask.go:409`), have no `case schema.TurnFailure` and never inspect `turn.Error.SteeringCarrier`; likewise `recordTurnFailure`/`emitSteeringCarrierTurnFailure` only ever set the flag.

What goes wrong: for a carrier failure that resolved the ask live, history ends `… TurnToolResults(ask_user ack) , TurnFailure{SteeringCarrier:true}`. Live, `processOneInput` set `askPending=nil` at acceptance; on restore the backward scan skips the unhandled `TurnFailure`, reaches the non-error `ask_user` tool result, and rehydrates `askPending` — so `session_init.go:1437-1445` installs a phantom pending question that live had already resolved. For the selection-failure shape the steer is retired (`recordFailedSteeringSelection` marks it failed), so nothing will ever re-deliver it and clear the phantom ask; the holds keyed on `askPending` (entry gate refusing non-user wakes, goal arm-don't-kick, `Compact` guard) stay engaged, blocking autonomous work until a new user turn. If the restore half is genuinely deferred to a follow-up commit, the schema/session comments must not assert present-tense restore behavior, and the field is dead persisted data in this commit.

Suggested fix: implement the reader — treat a `TurnFailure` whose `Error.SteeringCarrier` is true as decisive in `deriveRestoredAskPending` (resolving the ask, returning `nil, false` or the appropriate state) and in `deriveRestoredState`, or add the referenced `turnResolvesAskBoundary` helper and call it from both scans; the renamed/stale comment references should be corrected either way.
