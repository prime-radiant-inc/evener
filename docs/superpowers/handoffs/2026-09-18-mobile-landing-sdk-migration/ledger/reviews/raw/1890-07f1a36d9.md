## Summary

The two commits harden marketplace error reporting and reorder `RemoveMarketplace`:

- `4d46014` adds `saveFailed`, `storeChangeRollbackFailed`, and `cloneRemovalFailed` helpers in `marketplaces.go` and routes every marketplace metadata save (and the save/rollback failures around `AddMarketplace`/`EditMarketplace`) through them, so the raw `atomicWriteFile`/`os.RemoveAll`/`os.Rename` error text — which names this machine's absolute plugin-store path — only goes to `m.stderr()` and the RPC caller gets a scrubbed message. It preserves `errStoreBetweenNames` through the scrub so migration recovery can still detect the half-renamed state. A large `marketplaces_path_scrub_test.go` exercises each path, and the migration test's assertion is updated for the new scrubbed text.
- `07f1a36` reorders `RemoveMarketplace` so `known_marketplaces.json` is saved before the clone is removed. A save failure is now a plain refusal (marketplace stays registered, clone untouched), and a clone-removal failure after the save is reported as an error stating the marketplace is already unregistered. The fuzz coverage test is updated to expect that error.

The reordering and the `errStoreBetweenNames` plumbing look correct, and the new tests are non-tautological (they force real `*fs.PathError`s and assert mode/listing behavior).

---

**Severity: medium** — the scrub is not applied to every store-write failure reachable over the same RPC surface, so the goal of “store write failures never name the store path” is only partially met.

Files/locations:
- `internal/plugins/marketplace_migration.go:442` (`writeRenameMarker`)
- `internal/plugins/marketplace_migration.go:541` (`saveMigrationRecord`)
- Related residue: `internal/plugins/install.go:183`, `:284`, `:308`, `:343` (raw `m.saveRegistry` returns)

What goes wrong: these are the same `marketplaceAtomicWriteFile`/`SaveRegistry` primitives that `saveFailed` was added to scrub, and they are reached in the very flow the new test `TestMigrationTriggeredSaveFailureNamesNoPath` covers. `migrateMarketplaceNames` writes the rename marker and the migration record *before* calling `saveRename`; those helpers return the raw `atomicWriteFile` error (`creating temp /home/<user>/.config/evener/plugins/...`), and `migrateMarketplaceNames` wraps it with `%w` and returns it through `lockStore` → `loadMigratedMarketplaces` → `ListMarketplaces`/every store-locking verb → the hub RPC, with no `saveFailed` in between. Likewise `Install`/`Upgrade`/`Remove`/`SetEnabled`/`SetAutoUpgrade` return `m.saveRegistry` errors untouched, which are `SaveRegistry` → `atomicWriteFile` errors naming the absolute `installed_plugins.json` path. So a client can still receive the absolute plugin-store path in an error, which is exactly what this change set intends to prevent. The new tests only inject failures into the marketplaces file, so this branch is untested and unnoticed.

Suggested fix: route the marker/record writes and the install registry writes through the same scrub helper (`saveFailed`/a shared `scrubStoreError`) before they reach an RPC caller, and add failure injection for the marker/record files and for `saveRegistry` in the install paths (asserting no absolute path in the returned error).
