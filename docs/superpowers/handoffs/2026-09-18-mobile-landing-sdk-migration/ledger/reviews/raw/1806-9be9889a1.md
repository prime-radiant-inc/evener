## Summary

The two commits tighten the ask-resolution boundary between the live session and restore-time derivation. `turnResolvesAskBoundary` factors out the single "decisive turn" predicate shared by `deriveRestoredState` and `deriveRestoredAskPending`, so the two scans can no longer drift. It adds two new decisive shapes that the live runtime already treats as resolving:

- a `TurnSteering` carrying `SteeringKindInterrupted` or `SteeringSourceUser` (the interrupt branch clears `askPending` directly; a drained user steer now clears it mid-round via `clearAskPendingForResolvingSteer`), and
- a `TurnFailure` tagged with the new `SteeringCarrier` flag, used for the one carrier path whose acceptance already cleared `askPending` but which persisted no steering/user turn (append failure, or a selection failure that the carrier's own claim was draining).

`recordTurnFailure` gained a `steeringCarrier` parameter threaded through `emitTurnFailure`/`emitSteeringCarrierTurnFailure`, and a per-drain claim slot (`steeringCarrierClaimClientMutationID`) lets `recordFailedSteeringSelection` tag only the steer a claimed carrier is actually draining. Tests cover interrupt (same-round and later-round), user steer, both carrier failure paths, and the deliberate non-resolution of an unrelated (untagged) `TurnFailure`.

I traced the live and restore sides for each new boundary and they agree in the scenarios the tests pin. I found no functional defect in the code logic.

---

**Severity: low** — `agent/schema/turn.go:144-160` (and `agent/session_events.go:270-281`, `agent/session_tools_ask.go:288-292`)

The new documentation for `SteeringCarrier` says it marks "the one TurnFailure shape ... a steering carrier turn whose own steer failed to append" and cites only `carrierSteerUndelivered`; `emitSteeringCarrierTurnFailure`'s doc asserts "The ONLY caller is acceptSteeringCarrierInput's carrierSteerUndelivered case". But `recordFailedSteeringSelection` (session_queue.go:1327) also sets `SteeringCarrier: true` when the steer being drained is the carrier's claimed steer, and the new test `TestAskUser_RestoreResolvesAcrossFailedSteeringSelectionCarrier` depends on exactly that. Compounding this, `turnResolvesAskBoundary`'s comment (session_tools_ask.go:288-292) lists "a failed steering-selection prepare" as an example of an unmarked, non-resolving `TurnFailure`, directly contradicting what the code now does for a carrier-claim selection failure.

What goes wrong if not fixed: a future maintainer reading these comments can conclude the tag belongs only to the append-failure path, remove the `steeringCarrierClaimDrain` plumbing from `recordFailedSteeringSelection`, and reintroduce the exact restore divergence this commit fixes (live cleared `askPending`, restore re-derives it), with the comments themselves endorsing the change.

Suggested fix: update the three comments to say the tag covers both carrier shapes — the steer's append failure (`carrierSteerUndelivered`) and the carrier-claim's own steer selection failure (`recordFailedSteeringSelection` when the claim slot matches) — and reword `turnResolvesAskBoundary`'s parenthetical from "a failed steering-selection prepare" to "a non-carrier (inline) failed steering-selection prepare", since a carrier-claim selection failure *is* tagged and resolving.
