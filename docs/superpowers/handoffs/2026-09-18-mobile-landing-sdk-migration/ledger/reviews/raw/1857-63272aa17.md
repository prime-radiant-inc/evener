## Summary

This series moves the durable-read "projection fence" out of the web's `pendingTurnsStore.ts` and into the shared AppWire package as `createMutationProjectionFence` in `appwire-client/typescript/state/mutation/projection.ts`, exporting it (and its `MutationPersistencePort`/`MutationPersistenceSnapshot`/`MutationProjectionFence`/`MutationProjectionRefresh` types) through the `state/mutation` subpath.

The fence centralizes the generation/epoch ordering that decides which of a refresh's targets its durable snapshot may still replace: specific and all-targets refreshes share one monotonic counter, `advance` records a live commit's generation without a read, and `reset` bumps an epoch that voids in-flight reads (even though generation numbers restart). The key new behavior is that `refresh` now returns a `MutationProjectionRefresh` with a re-checkable synchronous `apply()` instead of a decided target set, so a live commit's `advance` (or a newer refresh) landing after the read resolves but before the caller projects still out-ranks the older snapshot. The web now binds `readMutationPersistence` directly as the port, uses `projectionFence.advance(...)` on commits, `projectionFence.epoch()` for submission bookkeeping, and `projectionFence.reset()` for tests; its local duplicate `replaceTargetRecords` and generation globals are deleted.

Tests for the fence cover fresh single-target and all-targets acceptance, read failure, reset invalidation, `advance` out-ranking a slow all-targets read per-target, post-resolution `advance`, all-targets-raises-floor-at-start, reset/epoch reuse, a failed newer refresh still raising the floor, and a commit after a failed refresh. The re-check predicate in `apply()` is monotonic within an epoch (floors only rise; epoch mismatch returns empty), so it can only narrow, never widen, the resolution-time decision, and the web calls it synchronously immediately before `setState`.
