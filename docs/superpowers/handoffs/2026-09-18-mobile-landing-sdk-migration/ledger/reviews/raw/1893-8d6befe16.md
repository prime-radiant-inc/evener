- **Severity**: Low
- **Location**: `appwire-client/typescript/reducer.ts:1054` and `:1092`
- **Problem**: Field-value and property-name truncation use UTF-16 `slice(0, 2000)`, which can split a surrogate pair and leave a lone surrogate in the pruned value. The surrounding `rawWarningFrame` was specifically written with `Array.from` to avoid that exact outcome at the final bound.

## Summary

######## member 2 (pi default)
## Summary

The series hardens `rawWarningFrame` in `appwire-client/typescript/reducer.ts`, which renders the JSON envelope of a message-less warning frame into `item.text`. Previously it called `JSON.stringify(params)` on the whole (up to 128 MiB) wire frame and only bounded the *output* afterward, so a transport-sized malformed frame made `JSON.stringify` walk/allocate proportional to the full frame. The diff adds `prunedForStringify`: a depth/node-budgeted walk that truncates strings, caps arrays/objects at 50 items/keys, caps nesting at 6 levels, and caps the whole walk at 500 nodes before the value ever reaches `JSON.stringify`. The accumulator is `Object.create(null)` so a wire key literally named `__proto__` becomes a real own property instead of tripping the prototype setter. One commit also removes a dead `Array.isArray` disjunct in the depth cap. Tests cover long strings, deep nesting, many keys, key-name length, and `__proto__`.

The aggregate diff does achieve the stated goal: the frame is bounded *before* `JSON.stringify` walks it, and the `__proto__` data-loss bug is fixed correctly (`Object.create(null)` has no inherited `__proto__` accessor, so the assignment is an ordinary own-property create; `JSON.stringify` serializes own enumerable keys of null-prototype objects normally).

## Issues

**Low — the total-node-budget guard has no effective test, and its stated test is bounded by a different guard**

`appwire-client/typescript/reducer.test.ts` (the `"bounds a many-key object…"` test, ~lines 4700–4761) is described as covering `RAW_WARNING_FRAME_MAX_NODES` (`reducer.ts:1039`), but its input is a single object with 100,000 keys, which is fully bounded by `RAW_WARNING_FRAME_MAX_OBJECT_KEYS` (50) before the node budget is ever reached. The test passes unchanged if the node budget is removed. `RAW_WARNING_FRAME_MAX_NODES` is the only guard against wide-but-shallow frames (e.g. 50 keys each holding a 50-key object ≈ 2,500 nodes, well within the per-object/array/depth caps and well under 128 MiB). If a future change weakens or drops the budget, every existing test still passes while such a crafted frame again makes `JSON.stringify` walk/allocate far more than intended — reintroducing exactly the memory issue this series fixes. Suggested fix: add a case whose node count exceeds 500 only via branching under the per-object/array caps (e.g. 50 keys → 50-key objects) and assert the stringified output stays small.

---

**Low — the new string/key truncation can split a surrogate pair, unlike the final output bound the code deliberately protects**

`reducer.ts:1051-1053` (`value.slice(0, RAW_WARNING_FRAME_MAX_FIELD_CHARS)`) and `reducer.ts:1096-1097` (`key.slice(0, RAW_WARNING_FRAME_MAX_FIELD_CHARS)`) slice by UTF-16 unit, so a multi-megabyte string (or key) whose 2000th unit is a high surrogate is cut mid-pair. The very next step, `JSON.stringify`, escapes the resulting lone surrogate as a literal `\uXXXX` sequence, so the fallback can render an escape artifact at the boundary. The surrounding code and the existing `"never splits a surrogate pair at the truncation boundary"` test go out of their way to avoid exactly this at the final bound (`Array.from(...)` at `reducer.ts:1105`). Concrete harm is cosmetic (a visible `\ud8xx` fragment rather than a clean truncation), not a crash — hence low. Suggested fix: truncate strings/keys with the same code-point-aware helper used for the final bound (or accept it explicitly if the artifact is deemed acceptable).
