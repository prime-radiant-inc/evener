**Severity: medium** — `appwire-client/typescript/reducer.ts:1270`

`prunedForStringify` bounds depth, array length, key count, string length, and total nodes, but still materializes every property of an object up front:

```ts
for (const [key, val] of Object.entries(value).slice(0, RAW_WARNING_FRAME_MAX_OBJECT_KEYS)) {
```

`Object.entries(value)` allocates one `[key, value]` pair per own enumerable key *before* `.slice(0, 50)` discards all but the first 50. The node budget cannot help here because the enumeration happens inside a single node's handling. A malformed, message-less warning frame (e.g. `{threadId, ref, warning: {k0: "v", …, k10M: "v"}}`) reaches `rawWarningFrame` (team/ref present, no usable `message`/`title`/`hint`), and `Object.entries` then builds an array with millions of entries — hundreds of MB of transient allocation on top of the already-parsed 128 MiB transport frame, enough to OOM the web bundle or the native app. This is exactly the vector the surrounding comment claims to have closed ("the whole walk cut off after … regardless of shape"), and the new test "bounds a many-key object" only spies on `JSON.stringify`, so it does not observe the `Object.entries` allocation.

Suggested fix: enumerate without allocating the full entry array, e.g.

```ts
let taken = 0;
for (const key in value) {
  if (!Object.prototype.hasOwnProperty.call(value, key)) continue;
  if (taken++ >= RAW_WARNING_FRAME_MAX_OBJECT_KEYS || budget.remaining <= 0) break;
  // ...same key/value handling
}
```

(`Object.keys` has the same O(N) allocation, so a bounded `for…in`/manual counter is needed.) Add an allocation-observing test (e.g. spy on `Object.entries`, or assert on the frame shape) so this vector stays closed.
