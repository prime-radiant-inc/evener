## Summary

The series completes the #1731 image-folding and warning-text work across the shared SDK, web renderer, mobile store, and mobile canonical projection. The functional changes are:

- The mobile live item handler now sources companion-attachment rows from the reducer's folded `ItemModel` (via `findFoldedItem`/`itemAttachments`) instead of the raw wire item, so the reducer's "an empty/absent input-image list means unchanged" rule is honored on the live path the same way `mergeItemImages` already honored it.
- Warning params are normalized once (`hasWarningText`/`rawWarningFrame`/`foldWarningParams`) into string-or-absent `text/title/hint/source`, with the raw-frame fallback bounded by code points; the reducer, `WarningItem`, `transcriptProjector.itemSummary`, the mobile live failure row, and the mobile canonical fallback all consume the fold.
- Mobile reasoning projection now prefers a growing `reasoningSummaries` join over a stale seed for active items, and `item.text` over a stale seeded summary for settled items.
- `itemIdentityMatches` is widened to a structural signature and exported so the mobile store can reuse the package's identity rule.

The new behavior is well covered by the accompanying reducer/projector/store/native tests, and I found no correctness, security, or regression issues in the core paths.

---

**Severity: low** — `mobile/src/state/conversation.ts:2542-2543`

The comment "An empty image list removes it" now contradicts the code three lines below it, which was changed in this series to route through the folded model precisely so an empty input-image list does *not* remove the row. The statement remains true only for output images (`MergeOutputImages`' non-nil-empty rule); for input images it is the opposite. If left, a future maintainer could "restore" the removal behavior the tests here deliberately removed.

Suggested fix: reword to distinguish the two rules, e.g. "an empty output-image list removes it; an empty input-image list is not a removal."

---

**Severity: low** — `mobile/src/conversation/project.ts:533, 540-548`

`warningFallbackText` is only consulted when `item.text` is falsy (`item.text || warningFallbackText(item) || item.output`), so a warning that carries both a message and a `title`/`hint` loses the title and hint in the canonical projection. Concrete effect: for `{ title: "Provider warning", message: "rate limit", hint: "slow down" }`, `projectConversation` produces an activity whose only output is `"rate limit"`, while the web renderer and this series' live failure row (`mobile/src/state/conversation.ts`'s warning case) show the title and the hint as well — the same divergence the function's own comment says it exists to avoid. Today this path is only reached for warning items injected into a model (as the added `project.test.ts` case does), since warnings are not transcript-persisted, but it is the exact shape the planned canonical-projection switch will use.

Suggested fix: for `item.type === "warning"`, compose the output from all non-blank parts (`text`, `title`, `hint`) rather than short-circuiting on `item.text`, or add a dedicated warning branch mirroring the live row's `[text, hint].filter(hasWarningText).join(" — ")`.
