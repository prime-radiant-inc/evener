######## member 2 (pi default)
## Summary

The series closes an information-disclosure gap (#1700): failure errors returned to the hub/RPC caller could carry this machine's absolute plugin-store path (`atomicWriteFile` names its temp/destination, `os.RemoveAll`/`os.Rename` return `*fs.PathError`/`*os.LinkError` with absolute paths). It introduces `saveFailed`, `rollbackFailed`, and `storeChangeRollbackFailed` helpers that log the raw error to `m.Stderr` and return a scrubbed message naming only the marketplace and (for saves) the store file's basename, applies them across `ensureFetched`, `AddMarketplace`, `RemoveMarketplace`, `RefreshMarketplace`, and both `EditMarketplace` save branches, and reorders `RemoveMarketplace` so the metadata save lands before the clone removal (a clone-removal failure is now surfaced, not swallowed). It also adds a path-scrub test suite and updates the coverage fuzz test for the new clone-removal-error behavior. The second commit fixes `EditMarketplace`'s `fail` closure so a successful rollback returns the (scrubbed) cause directly rather than joining it with nil rollback errors.

The core change is correct: paths are scrubbed, the raw errors are still logged, `errors.Is` checks for refusals (`ErrMarketplaceNotFound`, `ErrMarketplaceExists`, `ErrInvalidName`, `ErrMarketplaceSourceInStore`) are all on errors returned before any save, and the `RemoveMarketplace` reordering removes a real data-loss window (clone deleted but metadata save failing left the marketplace registered against a deleted clone).

## Findings

**Low** — `internal/plugins/marketplaces.go:269` (`saveFailed`), used at `marketplaces.go:506-507`

`saveFailed` hardcodes `marketplacesFileName` in its message. In the rename branch, `saveRename` (`marketplaces.go:624`) saves the registry first, so when `installSaveRegistry` fails the scrubbed error tells the caller that `known_marketplaces.json` failed when it was actually `installed_plugins.json`. Previously the raw error named the registry file, so this is a regression in diagnostic accuracy: an operator following the client-facing error looks at the wrong store file (the raw error is only in the hub log). Suggested fix: pass the file name (basename) into `saveFailed`, or have `saveRename` label which file failed before the caller scrubs.

---

**Low** — `internal/plugins/marketplaces.go:269` and `506-507`

`saveFailed` builds its result with `fmt.Errorf` and no `%w`, so it drops the wrapped error identity. The one wrapper that matters is `saveRename`'s `errStoreBetweenNames` (`marketplaces.go:630-632`), set when the marketplaces save fails *and* the registry restore also fails. In that state the store is left half-renamed (marketplaces file records the old name, registry keys the new one), and `EditMarketplace`'s `fail` closure, when its own outer rollback succeeds, returns `m.saveFailed(name, err)` — so `errors.Is(err, errStoreBetweenNames)` is false even though that is exactly the condition the sentinel documents. EditMarketplace writes no rename marker, so nothing else records the half-state. Concrete harm is limited today (no current caller of `EditMarketplace` inspects the sentinel), but the sentinel's documented contract is silently broken for this path and future recovery/doctor logic keyed on it would miss the state. Suggested fix: preserve the sentinel while scrubbing (e.g. re-attach `errStoreBetweenNames` in `fail` when `errors.Is(err, errStoreBetweenNames)`, or return `errors.Join(scrubbed, sentinel)`).
