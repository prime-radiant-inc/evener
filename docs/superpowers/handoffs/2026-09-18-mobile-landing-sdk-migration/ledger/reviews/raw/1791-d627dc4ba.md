## Summary

This 29-commit series continues an SDK migration for the keybindings draft editor. The aggregate diff:

- Introduces `appwire-client/typescript/draftCheckpointPort.ts`: a generic `DraftPort<Checkpoint>` (`load`/`save`/`removeIf`/`replaceIf`) plus `createDraftRepository`, which normalizes checkpoints through a `decode` on both directions, tracks a "classification" identity (raw bytes most recently read/written) so `discardClassified`/`replaceClassified` never act on a record the store never saw, and surfaces a stored-but-undecodable record as `UnreadableDraftError`.
- Migrates `keybindingsStore.ts` onto that repository, adds `draftUnreadable`, a `settleWrite` helper that unifies the post-rename/confirmed/conflict settle paths (adopting a checkpoint replaced under the writer), a `directWrite` claim that fences the two write paths against each other, and routes `lostHub` through the generation fence.
- Adds the store-free `discardStoredDraft` (+ `isReadableKeybindingDraft`) for hosts with no live store, and native plumbing: `parseDraftBytes`, a `replaceIf`-capable backend, an offline discard path in `NativePreferencesProvider`, and an unreadable-draft affordance on the keybindings screen.
- Consolidates test fakes (`memoryDraftStorage`, `fakeDraftBackend`) and adds extensive coverage in `draftCheckpointPort.test.ts`, `keybindingsStore.test.ts`, and `nativePreferenceDrafts.test.ts`.

The store/repository logic, the raw-identity tracking, the settle/adopt behavior, and the two-write-path fencing are consistent with the tests shown; I found no logic, security, or data-loss defect in the keybindings paths.

---

**Severity: low** — `mobile-native/src/nativePreferenceDrafts.ts:29` (with `NativePreferencesProvider.tsx` `backend.get`, line ~65)

`parseDraftBytes` is a shared helper used by `backend.get` for *both* draft keys, but its JSON-`null` handling was designed for the keybindings port's discardability. `return parsed === null ? raw : parsed;` makes a stored `"null"` come back as the string `"null"` instead of `null`. Previously `backend.get` did `JSON.parse(value)`, so a `"null"` record reached `nativeTranscriptDrafts.load` as `null` and `TranscriptDraftRepository.load` returned `null` (absent). Now `load` returns the string `"null"`, `validateCheckpoint` throws, and `restoreTranscriptDraft`'s catch (`mobile-native/src/nativePreferences.ts:543`) publishes `storageUnavailable: true` — permanently, because `refresh()` only retries `restoreTranscriptDraft` and it throws on every pass, `refreshTranscript` is skipped, and `discardTranscriptDraft` is itself gated on `storageUnavailable`. The transcript domain has no `draftUnreadable`/discard escape hatch, unlike keybindings, so the section is locked.

The trigger is narrow — the app's own `set` path always writes a checkpoint object via `JSON.stringify`, so a stored `"null"` comes only from external/corrupt storage — but the consequence is a permanent, in-app-unrecoverable lockout introduced purely by sharing `parseDraftBytes` with the transcript backend. Suggested fix: scope the raw-`null` preservation to the keybindings backend (e.g. call `parseDraftBytes` only in the keybindings port's `load`, or have the transcript `load` map a non-null non-object back to `null`), so transcript keeps treating a `"null"` record as absent.

---

**Severity: low** — `appwire-client/typescript/draftCheckpointPort.ts:63`

`discardStoredDraft` reports `"absent"` both when nothing was stored and when `removeIf` refused to remove the value it just read (`return storage.removeIf(value) ? "removed" : "absent";`). The doc comment defines `"absent"` as "there was nothing stored to discard", but a `false` from `removeIf` means the port could not name the record — the record is still there. `NativePreferencesProvider.discardUnreadableKeybindingsDraft` treats every outcome alike and clears the unreadable notice, so a refusal (e.g. a byte-aware backend whose stored bytes are not the canonical re-encoding of what `get` parsed) clears the "could not be read" state while the unreadable record survives; the notice then reappears on the next restore. The synchronous path makes a true concurrent race impossible, so this is narrow, but distinguishing the two cases (or having the provider only clear the notice on `"removed"`/`"refused"`) would keep the UI truthful.
