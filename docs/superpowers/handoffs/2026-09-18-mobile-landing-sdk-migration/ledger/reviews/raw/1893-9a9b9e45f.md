######## member 2 (pi default)
## Summary

The two commits add `prunedForStringify`, a bounded, lazy pre-pass in `appwire-client/typescript/reducer.ts` that shrinks an untrusted `WarningParams` object *before* `JSON.stringify` sees it, so a transport-sized (up to 128 MiB) malformed warning frame can no longer make that single serialization walk the whole graph. It truncates strings (2000 UTF-16 units), caps arrays/objects at 50 entries, caps nesting at 6, enforces a 500-node total budget, prunes over-long property names, and uses a guarded `for...in` instead of `Object.entries` so it doesn't allocate one pair (and read one value) per key. Tests were added covering the string, depth, many-key, property-value-access, and property-name vectors. The final code matches the stated intent, and the previously existing small-frame and surrogate-pair tests still hold because the field-level cap doesn't fire on those inputs.

## Issues

**Low — `pruned[boundedKey] = ...` mishandles a `"__proto__"` key**
`appwire-client/typescript/reducer.ts:1083`

`pruned` is a plain `{}`, so assigning the literal key `"__proto__"` does not create an own property: it invokes `Object.prototype`'s `__proto__` setter. A warning frame coming from Go's `encoding/json` (which will happily encode a map key named `__proto__`) has that field silently dropped from the rendered fallback, and when its value is an object the freshly built result's prototype is replaced with wire data (no global pollution — the object is local and only fed to `JSON.stringify`, whose `toJSON` lookup cannot find a function in parsed JSON). Concrete harm is limited to losing that one field in the diagnostic text, but it's avoidable. Suggested fix: build the accumulator with `Object.create(null)` (no `__proto__` setter), or `Object.defineProperty(pruned, boundedKey, { value, enumerable: true, configurable: true, writable: true })`.

---

**Low — the 500-node total budget (`RAW_WARNING_FRAME_MAX_NODES`) has no test that actually exercises it**
`appwire-client/typescript/reducer.ts:1039` (constant) / `reducer.ts:1050` (budget check); tests in `appwire-client/typescript/reducer.test.ts:4726` onward

The budget is the only thing bounding a *broad, shallow-of-depth* structure: with the per-object cap (50) and depth cap (6) alone, a nested array such as `[[[ ... 50 items ...]]]` expands to ~50⁶ nodes before the depth cap can stop it. Yet none of the added tests can reach it — the many-key test is stopped by `RAW_WARNING_FRAME_MAX_OBJECT_KEYS` (the `taken >= 50` break happens first), the deep-nesting test by the depth cap, and the oversized-string/name tests by the field cap. So a regression that removed the `budget.remaining <= 0` early return (or decremented it in the wrong place) would pass the whole suite while reintroducing the exact O(frame-size) blow-up the series exists to prevent. Suggested fix: add a test that passes e.g. a 50×50×50 nested-array `extra`, spies on `JSON.stringify`, and asserts the pruned output stays within the node/character bound (and that it completes rather than expanding the full tree).

---

No high- or medium-severity issues found; the prune is depth-, breadth-, string-, node- and key-length-bounded, cycle-safe (depth cap), and the largest possible pruned serialization remains a small constant fraction of the transport limit.
