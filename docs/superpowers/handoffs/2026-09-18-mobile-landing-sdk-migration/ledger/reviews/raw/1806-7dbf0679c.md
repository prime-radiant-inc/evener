## Summary

The series hardens the ask_user resolution boundary. It (1) makes `processOneInput`'s entry clear kind-aware so a human-note steering carrier does not clear a pending ask, (2) moves `clearAskPendingForResolvingSteer` before the `EventSteeringInjected` publish so the server's ask-facet refresh can't observe stale pending state, (3) factors the shared decisive-turn predicate `turnResolvesAskBoundary` so `deriveRestoredState` and `deriveRestoredAskPending` can't drift, reading durable journal provenance for kindless legacy steering turns, and (4) tags the carrier-failure `TurnFailure` shapes as `SteeringCarrier` so restore treats them as resolution boundaries. It also adds substantial tests (interrupt same-round, user steer, human note, failed carrier append, failed carrier skill selection, unrelated failure, event ordering, panic cleanup).

## Findings

**Medium — A failed human-note carrier is tagged `SteeringCarrier`, so restore resolves an ask that was never resolved**

`agent/session_lifecycle.go:2762` (with `agent/session_events.go:269-286`)

`acceptSteeringCarrierInput` unconditionally calls `s.emitSteeringCarrierTurnFailure(...)` on the `carrierSteerUndelivered` path, which persists `TurnFailureInfo.SteeringCarrier = true`. `turnResolvesAskBoundary` (`agent/session_tools_ask.go:356-357`) treats any such turn as a resolution boundary, returning `SessionIdle` / an empty pending set.

But the reason the tag is supposed to be valid is that the carrier's acceptance already cleared `askPending` (`session_lifecycle.go:1813`, guarded by `carrierAnswersAsk`). For a **human-note** carrier, `steeringCarrierClaimAnswersAsk` returns `false` (`session_tools_ask.go:113-122`), so the entry clear is deliberately **skipped** — `askPending` remains set. If that carrier's own steer then fails to append, the live session still reports the ask as pending, while a session restored from that transcript derives `SessionIdle` with no pending ask (the tagged `TurnFailure` short-circuits the backward scan before it reaches the `ask_user` ack). The live and restored answers to "is a question pending?" diverge, and the restored session drops the user's unanswered question from the wire-authoritative `AskPending` flag (`deriveRestoredAskPending` returns `(nil, false)`).

The existing `TestAskUser_RestoreResolvesAcrossFailedSteeringCarrier` only covers an *answering* steer (entry clear ran), so the human-note variant is not caught.

Suggested fix: only tag the failure as a resolution boundary when the carrier actually resolved the ask. For example, compute the answering decision once in `acceptSteeringCarrierInput` (e.g. `s.steeringCarrierClaimAnswersAsk(identity)`) and call `emitSteeringCarrierTurnFailure` when it is true, `emitTurnFailure` otherwise; mirror the same guard in `recordFailedSteeringSelection`'s `SteeringCarrier: s.steeringSelectionFailureIsCarrierClaim(...)` tag for consistency. Add a regression test that drives a `SetHumanNote` carrier whose steer append is refused (the `refuseSteerAppends` helper), then restores and asserts the ask is still pending and the state is `SessionAwaiting`.
