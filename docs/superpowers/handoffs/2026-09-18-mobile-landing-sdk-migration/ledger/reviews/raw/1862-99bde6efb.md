## Summary

This series completes two related pieces of #1731. Piece 2/3 reworks image and warning handling in the shared `appwire-client` reducer and its consumers:

- Input-image lists now treat an empty/absent list as "unchanged" (`imagesToItemImagesForSession` returns `undefined`), so `mergeItemImages`/`mergePageItem` carry prior images forward instead of erasing them, while output images keep their explicit-removal semantics. Mobile's live path now reads attachments from the reducer-folded item (`findFoldedItem`/`itemAttachments`).
- Warning frames are folded through one validated shape (`foldWarningParams`): `title`/`hint`/`source` become string-or-absent, blank normalizes to absent, text falls back to a bounded, pruned rendering of the raw frame, and every string is capped by code point. Web (`WarningItem.tsx`), the transcript projector, and mobile's failure-row/reasoning/warning-fallback paths all read that shape.

Piece 3/3 addresses ask resolution: `liveAskQuestions` is gated on the wire-authoritative `ThreadModel.askPending`, and its positional boundary now recognizes interrupts and user-sourced (non-`human-note`) steering as resolutions. Tests were updated to stamp `askPending` on the frames/thread models that carry an unanswered ask.

## Findings

**Medium** — `appwire-client/typescript/reducer.ts:1270` (`prunedForStringify`)

`for (const [key, val] of Object.entries(value).slice(0, RAW_WARNING_FRAME_MAX_OBJECT_KEYS))` materializes `Object.entries(value)` in full *before* slicing. The stated purpose of the prune is to stop `JSON.stringify` from walking a transport-sized (up to 128 MiB) malformed warning frame; a flat object with millions of keys makes `Object.entries` walk the whole object and allocate a `[key, value]` pair array per key, roughly doubling the allocation and risking an OOM/crash on the client — the exact class of allocation the surrounding commit rounds were closing. The node budget and the per-object key cap do not prevent this because the enumeration happens first.

Concrete harm: a hostile/malformed warning frame with one giant flat object defeats the bound the tests claim to enforce (the "bounds a many-key object" test only measures `JSON.stringify`'s output length, not the `Object.entries` allocation).

Suggested fix: iterate without materializing the key list, e.g. `let count = 0; for (const key in value) { if (!Object.hasOwn(value, key) || count++ >= RAW_WARNING_FRAME_MAX_OBJECT_KEYS || budget.remaining <= 0) break; ... }`, keeping the existing value/key-length/budget guards.

---

**Low** — `mobile/src/state/conversation.ts:761` (`findFoldedItem`)

Every `item/started` and `item/completed` now scans every item of every turn (`for (const turn of conv.turns) for (const candidate of turn.items)`) to find the folded model item. `conv.turns` is the reducer model and is not subject to the 500-row `capItems` bound applied to `conv.items`, so on a long-lived thread it grows with the session while lifecycle notifications arrive twice per tool call, making attachment resolution O(total items) per frame (quadratic over a session). The reducer already resolves the owning turn cheaply (`findItemTurnId`'s `turnId` hint → `activeTurnId` → scan), and `params.item.turnId` is available here.

Suggested fix: resolve the turn first (prefer `params.item.turnId`, then `conv.activeTurnId`) and scan only that turn's items, falling back to the full scan only if neither yields the item.
