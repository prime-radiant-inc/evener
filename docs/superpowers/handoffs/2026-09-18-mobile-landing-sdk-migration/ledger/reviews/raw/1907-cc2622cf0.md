## Summary

The three commits tighten how the pending-ask boundary is decided on both the live and restore paths:

- **`cc2622c`** releases the steering-carrier claim id via `defer` so a panic mid-drain can't leak it.
- **`fe2ec08`** threads steering provenance (the client-mutation journal's kind/method, scoped by `divergenceTurn`) into `deriveRestoredState`/`deriveRestoredAskPending`, factors a shared `turnResolvesAskBoundary`/`roundEntryResolvesAskBoundary`, and adds a `SteeringCarrier` flag on `TurnFailure` as a resolution boundary.
- **`2f23354`** stops a human-note carrier from clearing `askPending` on entry (`steeringCarrierClaimAnswersAsk`), tags carrier failures only when the claimed steer answers, and moves the mid-round steer clear before `EventSteeringInjected` publishes.

The logic is broadly coherent and the boundary is now shared between the two restore walkers. I found two issues, one a now-false invariant the drain ladder still depends on, and one provenance gap in the new steering boundary.

---

**Severity: medium** — `agent/session_lifecycle.go:1399` (with the conditional clear at `agent/session_lifecycle.go:1809-1813`)

The drain-ladder capture reads `awaiting := s.State() == SessionAwaiting` and its justifying comment (lines ~1381-1397) asserts the equivalence "`s.State() == SessionAwaiting` iff `askPendingCount() > 0` here", explicitly because "processOneInput unconditionally resets ... `s.askPending` to nil at entry ... for every accepted entry kind". That premise is no longer true: the entry clear is now skipped whenever `carrierAnswersAsk` is false. For a human-note steer while a question is pending, `askPending` stays non-empty but the carrier's round ending in a communicate ack still calls `finishProcessingAtBoundary(ctx, SessionIdle)` with `askedThisRound == false` (`deliverIfCommunicated`, session_tool_round.go:527). At the capture, `s.State()` is therefore `SessionIdle` while `askPendingCount() == 1`.

What goes wrong: `selectDrainNextAction` receives `Awaiting: false`, so its awaiting hold (which "overrides every other rung") does not apply, and the very scenario this change is meant to preserve — an unresolved question — can still let the loop run a `runNotification` or `armGoalGate` turn (i.e. the agent acts past the unanswered question). The restore side now correctly reports Awaiting+pending for this shape (`TestAskUser_RestoreDoesNotResolveAcrossASuccessfulHumanNoteCarrierCompletion`), so live and restored disagree at the boundary the commit is trying to unify.

Suggested fix: derive the capture from the pending-ask set rather than the state, e.g. `awaiting := s.State() == SessionAwaiting || s.HasPendingAsk()` (or have the non-resolving carrier round preserve the awaiting boundary), and update the now-false equivalence comment.

---

**Severity: low** — `agent/session_tools_ask.go:370-378` (`turnResolvesAskBoundary` / `steeringSourceAnswersAsk`) vs `agent/session_notes_rpc.go:931-936` (`steeringKind`)

`steeringKind()` only recovers note origin from a recorded kind or a `notes/human/set` method; unlike `isHumanNoteSteer`, it does not fall back to the write-path text shape when both are absent. `turnResolvesAskBoundary` therefore sees a kindless human-note turn as `steeringSourceAnswersAsk(user, "") == true` and treats it as an answering steer.

What goes wrong: on a normal restore the session's own journal supplies the record and this is fine. But for a forked child whose inherited prefix is scanned with `nil` origins (`steeringOriginBoundary`), a legacy pre-kind-stamping human-note turn becomes an answering steer: `deriveRestoredState` returns `SessionIdle` and `deriveRestoredAskPending` returns an empty set, whereas the parent session (which stamped the kind live) kept the question pending. That is a live/restore divergence for exactly the class of record the round-4/5 work is fixing.

Suggested fix: for a kindless, provenance-less user-sourced steering turn, reuse the same text-shape evidence `steeringOrigin.isHumanNoteSteer` already documents as the sole marker (or have `steeringKind()` apply that fallback), so the new boundary doesn't classify it as an answer.
