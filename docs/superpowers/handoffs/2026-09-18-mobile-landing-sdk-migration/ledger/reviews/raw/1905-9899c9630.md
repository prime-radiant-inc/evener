## Summary

The two commits implement the **live** half of ask-boundary gating for steering:

- `clearAskPendingForResolvingSteer` clears a pending ask mid-round when a drained steer actually answers it (`SteeringSourceUser` and not `SteeringKindHumanNote`), instead of waiting for the next accepted-turn entry.
- `processOneInput`'s entry clear is now conditional: for a steering-carrier identity it consults the client-mutation journal (`steeringCarrierClaimAnswersAsk`) so a human-note carrier does not resolve the ask; an unknown/lost journal record fails closed.
- `TurnFailureInfo.SteeringCarrier` is added and set by the two carrier failure shapes (`acceptSteeringCarrierInput`'s undelivered case and `recordFailedSteeringSelection`'s selection-failure case), for the restore scan stacked on this change.
- The drain-ladder gate now treats `askPendingCount() > 0` as awaiting, and `consumeSteeringMessage` moves the clear ahead of `EventSteeringInjected` while keeping admit/unpark after it.
- Behavioral tests cover both failure-tag shapes, the human-note non-resolution path, the unknown-provenance fail-closed case, event ordering, and the follow-up gate.

### Low — Fail-closed journal check is bypassed on the delivery path
**File:** `agent/session_queue.go:1267` and `agent/session_queue.go:1280` (via `clearAskPendingForResolvingSteer`, `agent/session_tools_ask.go:100`)

`steeringCarrierClaimAnswersAsk` was hardened (round-1 Low) to fail closed when the journal record is missing, so a carrier with unknown provenance does not answer the ask. But that guarantee only covers the entry-clear and the failure tag. When such a steer is actually drained, `consumeSteeringMessage` builds `t.SteeringKind` from the same missing journal record (`clientSteeringFromSnapshot` → `origin.steeringKind()` → `""`) and then calls `clearAskPendingForResolvingSteer(t)`, where `steeringSourceAnswersAsk("user", "")` returns `true`. So a human-note steer whose journal record is lost still clears the pending ask on delivery, contradicting the stated "does not answer / fails CLOSED" contract for exactly that case.

What goes wrong: with an inconsistent store (`PendingExecutions` present, `Journal` entry absent) a note-save restores as an answering steer, silently resolving an unanswered question live while the entry-clear had deliberately refused to; the restore side (the next stacked change) reading the same missing provenance would also disagree.

Suggested fix: make the delivery-path clear require positive provenance for client-mutation steers too — e.g. thread the entry decision (`carrierAnswersAsk`) into `acceptSteeringCarrierInput`/`consumeSteeringMessage`, or have `clearAskPendingForResolvingSteer` skip clearing for a client-mutation steer whose journal record is absent — so the two clear points cannot independently disagree.
