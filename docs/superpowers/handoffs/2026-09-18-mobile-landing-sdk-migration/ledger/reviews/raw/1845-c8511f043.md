## Summary

This 52-commit series is a large SDK migration/refactor that lands one shared checkpointed-draft stack and one new hub-defaults store in `appwire-client/typescript`, then updates the native app to consume it:

- **New shared modules**: `draftCheckpointPort.ts` (a byte-aware draft port + repository with `removeIf`/`replaceIf` conditional write semantics and `discardStoredDraft`), `checkpointedDraftEditor.ts` (`assertDraftDiscardable`, `persistCheckpointedDraft`, `discardCheckpointedDraft`), `settingsHubGeneration.ts` (generation wiring + payload retirement + lost-hub write settle), and `transcriptDisplayStore.ts` (per-layout hub defaults store with a direct write).
- **`keybindingsStore.ts`** was rebuilt on those primitives: `draft` is now a `KeybindingsDraft` carrying a ready-generation stamp, unreadable records surface as `draftUnreadable` and are discardable without a live hub, the two write paths share one write token with a synchronously reserved `directWrite` claim, and settle paths were unified through `settleWrite`.
- **`readyGenerationFence.ts`** gains `awaitingFirstPayload`/`firstPayloadApplied` and `lostHub`.
- **Mobile native** gets a shared `fakeDraftBackend`, `parseDraftBytes`/`matchesStoredBytes`, store-free unreadable-draft discard, and a `draftUnreadable` projection plus recovery action.

The new tests exercise the repository's compare-and-swap races, generation staleness, settle/refusal-adoption paths, and both stores' fence matrices; the intent of the series (extract shared plumbing, then build the transcript store on it) is achieved.

**Low** — `settleUnsettleableWrite` is exported and unit-tested but has no production caller, and the module header's claim that the lost-hub settle is "byte-identical"/shared between stores is false.

File: `appwire-client/typescript/settingsHubGeneration.ts:66` (and the header claim at lines ~8–12); the inlined replacement is `appwire-client/typescript/keybindingsStore.ts:741` (`settleLostHubWrite`).

What goes wrong: `keybindingsStore` deliberately does not call the shared helper because its settle must also publish `draftConflict` (the helper's generic `SettingsHubWriteFields` lacks it), so the extracted function is only ever exercised by `settingsHubGeneration.test.ts` and is dead in production. A future settings store (the transcript store's promised checkpointed editor, piece 12) that imports `settleUnsettleableWrite` as "the" shared lost-hub settle will silently drop its own per-store field exactly as keybindings would have, and the header comment asserting the two implementations are byte-identical will mislead a maintainer reasoning about keybindings' behavior.

Suggested fix: either have `settleUnsettleableWrite` accept an `extra` partial (like `retireSettingsHubPayload` does) so keybindings can pass `{ draftConflict: true }` and the helper becomes the single production path, or remove the helper until a second consumer exists and correct the header to say the lost-hub settle is currently store-owned.
