## Review Findings

**Severity**: Medium  
**Location**: `keybindingsStore.ts:636-648, 1405-1422`; `NativePreferencesProvider.tsx:37-40`  
**Problem**: An unreadable persisted draft is treated as `storageUnavailable`, preventing hub refresh, while `discardDraft()` is also blocked by `assertEditable()`. Native `JSON.parse` failures are swallowed before the draft port can remove the raw record, leaving users permanently unable to access keybinding settings.  
**Fix**: Distinguish unreadable records from storage failures, allow a discard-only recovery path, and preserve malformed native bytes for removal.

---

**Severity**: Medium  
**Location**: `draftCheckpointPort.ts:44-47`  
**Problem**: `discardStoredDraft()` blindly removes whatever record is present. If an unreadable record is replaced by a valid draft before removal, the valid replacement can be deleted; a failed compare-and-remove is also indistinguishable from an empty store.  
**Fix**: Accept a readability predicate and return distinct `removed`/`absent`/`refused` outcomes, re-reading after a failed compare.

---

**Severity**: Medium  
**Location**: `NativePreferencesProvider.tsx:30-33, 47-55`  
**Problem**: The native backend compares stored JSON bytes directly with `JSON.stringify(value)` after parsing the stored value. Equivalent records with different whitespace, key order, or numeric formatting fail `removeIf`/`replaceIf`, causing successful saves or discards to leave stale drafts behind.  
**Fix**: Compare canonical parsed values or preserve and compare the original raw bytes consistently.

## Summary

## Summary

This 28-commit series extracts and generalizes the keybindings draft checkpoint machinery into a new `draftCheckpointPort` module (`DraftPort`, `createDraftRepository`, `discardStoredDraft`, `UnreadableDraftError`), makes `removeIf`/`replaceIf` return a boolean so a settle can detect a checkpoint that another writer replaced under it, introduces the `lostHub`/`settleLostHubWrite` distinction between a support flap and supersession, adds a `replaceIf` to the native preference backend, and adds a generation-scoped `directWrite` reservation so the checkpointed and direct write paths cannot fence each other out. The aggregate behavior is coherent and the new tests exercise the new branches (replacement adoption, refusal of blind classification, stale replies, support-flap settles, no-port fallback).

I found one substantive gap.

---

**Severity: medium** — `appwire-client/typescript/keybindingsStore.ts` (`discardDraft` → `assertEditable`, ~line 1181/1407), `appwire-client/typescript/draftCheckpointPort.ts:35-52`, `appwire-client/typescript/index.ts:133`

The new `discardStoredDraft`/`discardStoredKeybindingDraft` is documented as the way to clear an unreadable draft, and its docstring states "a host with a live store uses discardDraft, which also publishes the state." But with a live store an unreadable checkpoint puts the store in `storageUnavailable: true` (`restoreDraft`'s catch at keybindingsStore.ts:646-649), and `discardDraft()` calls `assertEditable()` first, which throws `UNAVAILABLE_MESSAGE` whenever `state.storageUnavailable` is true. `refreshOverrides()` cannot clear it either: it retries `restoreDraft`, the decode throws again, and it returns before the GET. The exported `discardStoredKeybindingDraft` has no production call site anywhere in the repo (only `index.ts` and tests reference it), and the native UI disables both Save and Discard on `domain.storageUnavailable`. So a persisted keybinding checkpoint that this build cannot decode (e.g. a shape change from another/newer build — exactly what `UnreadableDraftError` and the new removal helper exist for) leaves the user permanently unable to edit, save, or discard keybindings; the bad record can never be removed through any reachable path.

Suggested fix: wire `discardStoredKeybindingDraft` into the native recovery flow (call it with the `KeybindingDraftStorage` and then rebuild/refresh the store), or relax the `storageUnavailable` leg of `assertEditable`/`discardDraft` so a discard is permitted when the only problem is the unreadable record, and add a test that exercises discarding a `corrupt()`ed store through the store itself.
