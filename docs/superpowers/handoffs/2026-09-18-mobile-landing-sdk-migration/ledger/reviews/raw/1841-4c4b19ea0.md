## Summary

The series migrates the keybindings draft editor off its bespoke repository onto two extracted, reusable primitives:

- `draftCheckpointPort.ts` — a generic `DraftPort<Checkpoint>` plus a `createDraftRepository` that compare-and-swaps every write against the last record it classified (`save`/`removeIf`/`discardClassified`/`replaceClassified`), and a store-free `discardStoredDraft` for clearing an unreadable record with no live store.
- `settingsHubGeneration.ts` — the ready-generation begin/end wiring, payload retirement, and lost-hub write settle extracted from `keybindingsStore`, now used by the store via a `lostHub` fence method.
- The draft is now a first-class `KeybindingsDraft` carrying its own `generation`, so a hub replacement that reports a coincidentally identical revision is still detected as a conflict via `staleDraft`.
- The native side adds tagged `StoredNullRecord`/`UnparseableDraftBytes` bytes handling, canonical (key-order-insensitive) byte comparison in `matchesStoredBytes`, atomic `replaceIf`, and an offline "discard unreadable draft" recovery path (`NativePreferencesProvider`, `KeybindingPreferencesScreen`).

The change is unusually well covered: the new CAS paths, generation stamping/staleness, unreadable-record recovery, offline discard outcomes, and settle-vs-supersede distinctions all have targeted tests.

---

**Severity: medium** — `appwire-client/typescript/draftCheckpointPort.ts:169` (`createDraftRepository.save`, the `else { storage.save(decoded); }` branch)

`save()` only compare-and-swaps when `classification` is a real record; when it is `"absent"` (or `null`) it writes unconditionally. The comment asserts "Nothing classified yet, or classified as absent, has no existing record to race against here," but that is exactly the window the same diff demonstrates elsewhere: the test *"discardClassified is a no-op after load() observes empty storage, even when another writer saves afterward"* constructs a writer that saves **after** this repository classified the store as empty, and `discardClassified` correctly refuses to touch it. The `save()` path has no such protection and will silently overwrite that record.

Concrete harm: two windows (or two app instances) share one storage key. Window A starts with no draft (`load()` → absent), window B edits and persists a draft, then window A edits — `persistDraft` → `save()` unconditionally clobbers B's just-written draft with no refusal, and neither side sees an error. This is the same class of lost-write the rest of `save()`/`replaceClassified` was added to prevent, and it defeats the series' stated atomicity guarantee precisely in the "first draft" case.

Suggested fix: give `DraftPort` a create-if-absent operation (or extend `replaceIf`/a new `saveIfAbsent` so `expected === null` means "only if no record"), and use it for the absent branch so a record appearing after the absent classification turns into a `false` refusal the caller already handles (as `persistDraft` does for any other refusal). The native and in-memory ports both need updating; the current `matches()` already returns `false` for a missing key, so the primitive is expressible at the backend.
