## Summary

The commit makes the ask-dock's "is anything pending" decision read the wire's `ThreadModel.askPending` instead of re-deriving it from transcript shape, and extends the transcript scan's resolution boundary from "last plain user message" to "last resolution item" (a user message, an `interrupted` steer, or a user-sourced steer that is not a `human-note`). Test fixtures are updated to carry `askPending: true`, new unit tests cover the steering/interrupt/human-note boundaries and the wire gate, and the qualification script is updated. The `isResolutionItem` predicate mirrors `layoutRoles.ts`'s existing `source === "user" && steeringKind !== "human-note"` condition, and the added boundary cases line up with the server's `clearAskPending` call sites in `agent/session_lifecycle.go` (interrupt at :1271, accepted user turn at :1804).

---

**Severity: medium** — `appwire-client/typescript/deriveAskQuestions.ts:110`

The new unconditional early return `if (!model.askPending) return [];` makes the dock entirely dependent on a field that is documented as absent (decoding to `false`) on peers that predate it. `appwire/types.go:760-763` states: "AskPending is true while an ask_user question is unanswered. Additive: absent on old daemons and source-backed threads that omit the field, decoding as false," and `reducer.ts:619` hydrates it with `thread.evener.askPending ?? false`. The hub–daemon pair is explicitly reachable in ordinary operation ("daemons outlive the hub that spawned them, so an operator who rebuilds and restarts the hub has one" — `appwire/types.go:22-24`), and `omitempty` fields are deliberately invisible to the exact protocol-version handshake.

Before this change, `liveAskQuestions` rendered the dock from the transcript alone, so a v5 daemon that omits `askPending` still produced a working ask dock. After this change, that same transcript yields `[]` on every call, so the dock (the composer's answering surface and mobile's question rows via `mobile/src/conversation/project.ts:328`) silently never appears even though a completed, unanswered `ask_user` call is present. The prior "re-derive is buggy" concern is real for the `true`→`false` transition, but the `false` case is exactly where absence and a real clear are indistinguishable in a plain `bool`.

Suggested fix: either bump the protocol version so the field is guaranteed present, or keep the transcript scan as the source of "which questions" while letting `askPending` only veto (i.e. treat a missing/unknown value as "fall back to the scan") rather than short-circuiting every render. As written, the change trades a class of stale-`true` bugs for a hard feature regression against any peer that omits the field.
