## Summary

The series is a security/quality hardening pass that stops absolute plugin-store filesystem paths from reaching RPC callers. Raw write/rename/rollback errors are now logged to the hub's stderr sink and the caller receives a scrubbed message that names only the store file (`known_marketplaces.json`, `installed_plugins.json`, `rename-marker.json`, `marketplace-migration.json`), preserving sentinel identities (`errStoreBetweenNames`, `errRenameRollbackIncomplete`, `ErrMarketplaceUnregisteredCloneRemains`) through `%w`. It also reorders `RemoveMarketplace` so the unregistration save lands before clone deletion, and types the resulting "unregistered but clone remains" outcome. Extensive tests were added for the new scrubbing boundaries.

The implementation is generally coherent and the sentinel-preservation branches are correct. Two wire-reachable move/rename error paths were missed.

---

**Medium** — `internal/plugins/marketplaces.go:481` (call site lines 498–500): `EditMarketplace`'s `fail` closure returns `err` unscrubbed when both rollbacks succeed, but the `moveMarketplace` call passes it a raw error.

`moveMarketplace`'s own `fail` returns `fmt.Errorf("renaming marketplace clone: %w", err)` where `err` is an `*os.LinkError` from `marketplaceRename` (`os.Rename`) whose `Error()` text is `rename <absolute old> <absolute new>: ...`. On failure `moveMarketplace` returns a nil `undo`, so in `fail` both `undoSwap()` (swappedIn empty) and `runUndo(nil)` are nil, hitting the newly added `return MarketplaceRef{}, err` at line 481 with the raw path. A rename failure (EACCES, ENOTEMPTY, EXDEV, a symlinked destination) over the hub RPC therefore leaks this machine's absolute plugin-store path — exactly what `markerAfterFailedMove` was added to prevent on the migration path. No test forces `marketplaceRename` to fail through `EditMarketplace` (the new scrub tests force `marketplaceAtomicWriteFile`/`saveRegistry`/`marketplaceRemoveAll`), so this is uncovered. Fix: scrub `moveMarketplace`'s error before returning it from `fail` (e.g. route it through a helper akin to `markerAfterFailedMove`, or wrap it with a path-free message and log the raw error), and add a test that makes `marketplaceRename` fail during an `EditMarketplace` rename.

---

**Medium** — `internal/plugins/marketplace_migration.go:271-272` and `:303-304`: `recoverMarkedRename` passes raw move-helper errors through `fail(err)`.

The same `moveMarketplace` / `movePluginCachesToNewName` rename errors reach the caller here without scrubbing. `recoverMarkedRename` is invoked from `lockStore` (`locks.go:83`), which `ListMarketplaces`/`List` reach, so a recovery whose clone/cache rename fails (or whose `pathPresent`/`marketplaceDirsAreItsOwn` stat fails) returns absolute paths to the RPC caller. The series scrubbed the save/rollback branch of this very function (and introduced `markerAfterFailedMove` for the fresh-migration equivalent of these same move failures), but the move branches were left raw, so the recovery path is inconsistent with both. Fix: scrub the move-helper error at these two call sites the same way `markerAfterFailedMove` does (log raw, return a path-free message preserving `errRenameRollbackIncomplete` where applicable), and cover a recovery whose forward rename fails.
