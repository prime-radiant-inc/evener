## Summary

This 66-commit series extracts the keybindings store's checkpointed-draft machinery into shared, generic modules (`draftCheckpointPort.ts`, `checkpointedDraftEditor.ts`, `settingsHubGeneration.ts`) and its ready-generation wiring into `readyGenerationFence.ts` (`awaitingFirstPayload`, `lostHub`), then builds a new `transcriptDisplayStore.ts` on those primitives. Along the way it fixes a long list of draft-editor race/uncertainty bugs: atomic compare-and-swap saves (`replaceClassified`/`replaceIf`), adopting a checkpoint replaced under a write, settling `draftConflict`/`draftUncertain` consistently, never locking the section on an unreadable record, generation-stamping drafts so a hub replacement at the same revision is still caught, a shared `memoryDraftStorage`/`fakeDraftBackend` test double, native byte-identity matching (`parseDraftBytes`, `matchesStoredBytes`), and an offline store-free "discard unreadable draft" path. The aggregate diff is coherent and heavily tested; I found no high-severity logic, security, or data-loss defects.

## Issues

---
**Severity: medium**

**File:** `appwire-client/typescript/keybindingsStore.ts:726` (with `:1100`)

On a *genuine* port failure, `restoreDraft`'s catch returns `draftUnreadable: unreadable`, i.e. it forces `draftUnreadable` to `false` even when the previous state classified the record as unreadable. The surrounding comment says a genuine port failure is "left alone", but `draftUnreadable` is the one field it clears.

Concrete harm: a user with an unreadable stored draft (`draftUnreadable: true, storageUnavailable: true`) triggers a transient `Storage.load()` throw on the next `refreshOverrides`. `restoreDraft` now publishes `storageUnavailable: true, draftUnreadable: false`; `refreshOverrides` then returns early at line 1100 (`storageUnavailable && !draftUnreadable`). The section is now locked: `assertEditable` refuses on `storageUnavailable`, and `assertDiscardable` (the whole point of the fix this series ships) refuses because `draftUnreadable` is false — so the one recovery action, "Discard unreadable draft", disappears until a later restore happens to succeed. The offline probe in `NativePreferencesProvider` deliberately does the opposite ("left at whatever it last was rather than guessed at"), so the live store is inconsistent with its own offline twin.

Suggested fix: in `restoreDraft`'s genuine-failure branch, omit `draftUnreadable` from the returned partial (so `setState` preserves the previous value) instead of returning `draftUnreadable: unreadable`:

```ts
const unreadable = error instanceof UnreadableDraftError;
return {
  storageUnavailable: true,
  ...(unreadable ? { draftUnreadable: true, draftError: DRAFT_RESTORE_FAILED_MESSAGE,
                     draft: null, writeUncertain: false, draftConflict: false }
                 : { draftError: DRAFT_RESTORE_FAILED_MESSAGE }),
};
```

---
**Severity: low**

**File:** `mobile-native/src/NativePreferencesProvider.tsx:52` / `:114` / `:238` (and `KeybindingPreferencesScreen.tsx:183-208`)

`offlineStorageUnavailable` is computed, tracked in state, and published on the `Preferences` context, but nothing in the repository ever reads it. As a result the offline discard's genuine-port-failure path is silently swallowed: `discardUnreadableKeybindingsDraft` catches the storage throw at lines 184-187, sets `offlineStorageUnavailable(true)`, and returns `null`. `clearsErrorAfterOfflineDiscard(null)` is `false`, so the screen neither clears the prior error nor sets a new one — and the screen's own `catch` (which writes "The change could not be completed…") never fires because the provider never throws. The user taps the recovery button, nothing changes, and no message tells them why. The field's own doc comment says it exists precisely to distinguish this case.

Suggested fix: surface the failure — e.g. have the screen treat `preferences.offlineStorageUnavailable` (when `draftUnreadable` is shown) as a disabled/error state, or return a distinct result from `discardUnreadableKeybindingsDraft` so the screen can set its error message instead of relying on a `catch` that cannot be reached.
