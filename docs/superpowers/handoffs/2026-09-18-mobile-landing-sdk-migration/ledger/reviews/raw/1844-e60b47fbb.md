######## member 2 (pi default)
## Summary

The series extracts three shared settings-hub primitives out of `keybindingsStore.ts` — a generic draft port/repository (`draftCheckpointPort.ts`, with a byte-aware `removeIf`/`replaceIf` compare-and-swap), a checkpointed draft editor (`checkpointedDraftEditor.ts`), and ready-generation/payload-retirement wiring (`settingsHubGeneration.ts`) — and switches the keybindings store onto them. Along the way it adds draft compare-and-swap on save/settle, a `draftUnreadable` state and store-free/unreadable-record recovery path (including a native offline discard), a ready-generation stamp on drafts to catch cross-hub staleness at equal revisions, `lostHub`/`settleUnsettleableWrite` handling, and a shared in-memory draft fake. The changes are heavily covered by new unit tests for each primitive and updated store tests.

The aggregate diff is coherent and the extracted logic matches the pre-extraction behavior in the paths I traced. I found two residual gaps, both narrow.

---

**Severity: medium** — `appwire-client/typescript/draftCheckpointPort.ts:174` (`save`, the `else` arm)

`save()` conditionally compare-and-swaps only when `classification` names a record; when the repository has classified storage as **empty** it calls `storage.save(decoded)` unconditionally, overwriting whatever is there. The comment claims an absent classification "has no existing record to race against", but that is only true at the instant of classification: after `load()` observed empty storage (or after a successful `discardClassified`/`removeIf`, which sets `classification = "absent"`) a concurrent writer can create a record before this repository saves, and the blind save destroys it. Concrete harm: the concurrent writer's draft is silently lost, which is exactly the class of overwrite the series set out to close ("persistDraft's save() compare-and-swaps against the classified record instead of overwriting it"). No test covers this arm with an external writer present. Suggested fix: express create-if-absent in `DraftPort` (e.g. a `replaceIf` that succeeds only when no record exists, or a dedicated `create`) and use it for the absent arm, or re-read and CAS against whatever is found.

---

**Severity: low** — `mobile-native/src/NativePreferencesProvider.tsx:185` and `mobile-native/src/KeybindingPreferencesScreen.tsx:204`

A genuine storage failure (`Storage.getItemSync` throws) during the offline discard is caught and recorded only in `offlineStorageUnavailable` (`return null`), but nothing consumes that field — it is defined on `Preferences`, set here, and passed through the context provider, yet no screen reads it (`grep` finds only its definition/assignment). Because `discardUnreadableKeybindingsDraft()` returns `null` rather than throwing, the screen's `catch` never runs, and `clearsErrorAfterOfflineDiscard(null)` is false, so no error is set and no clearing happens. Concrete harm: when the storage read/write fails, tapping "Discard unreadable draft" updates nothing the user can see — the notice stays up and no message explains why, so the action reads as a dead button. Suggested fix: surface `offlineStorageUnavailable` in the screen (disable/annotate the action, or set the component-local error) so the failure is visible.

## Review Findings
- **Severity**: High
- **Location**: `appwire-client/typescript/draftCheckpointPort.ts:166`
- **Problem**: Once storage is classified as absent, `save()` performs an unconditional write. Another writer can create a checkpoint after that classification but before this save, and this repository silently overwrites it.
- **Fix**: Add an atomic create-if-absent operation, or define `replaceIf(null, next)` as that operation, and use it for the absent classification. Add a two-repository test where both observe empty storage before one saves.

---
- **Severity**: Medium
- **Location**: `appwire-client/typescript/keybindingsStore.ts:1050`
- **Problem**: When settling a replaced checkpoint during a refresh, `restoreDraft(getState())` evaluates conflict against the pre-apply revision. Because `resolved` is spread after `applyHubOverrides` computes conflict against the new payload, a replacement based on the old revision can be marked current after the hub has moved.
- **Fix**: Adopt the replacement using the authoritative payload revision, such as `restoreDraft({ loaded: true, revision: payload.revision })`, or recompute conflict from the resolved draft after applying the payload.

---
- **Severity**: Medium
- **Location**: `mobile-native/src/KeybindingPreferencesScreen.tsx:98`
- **Problem**: A stale domain snapshot suppresses the provider’s fresh offline unreadable-draft signal whenever `domain` exists, including while disconnected. If a record becomes corrupt after disconnection, the recovery action does not render.
- **Fix**: Prefer the offline probe when `preferences.connected` is false, while continuing to use the live domain while connected. Add a provider/screen integration test for corruption discovered after disconnection.

---
- **Severity**: Medium
- **Location**: `mobile-native/src/NativePreferencesProvider.tsx:183`
- **Problem**: A genuine offline storage failure is conflated with “no hub” by returning `null`, and the screen never consumes `offlineStorageUnavailable`; the failed discard is therefore silent. A failed read for a new hub can also retain the previous hub’s unreadable flag.
- **Fix**: Return a distinct storage-failure outcome or rethrow to the screen, render `offlineStorageUnavailable`, and clear or scope `offlineDraftUnreadable` by hub when a new hub’s read fails.

---
- **Severity**: Low
- **Location**: `mobile-native/src/nativePreferenceDrafts.ts:171`
- **Problem**: `draftUnreadableAfterDiscard` requires `outcome === "refused"`. If the old record is removed or absent and a concurrent writer leaves a new unreadable record before the second read, the notice is cleared even though the current record is unreadable.
- **Fix**: Base the decision on the authoritative second read, effectively returning `current === "unreadable"`, and test the removed/absent-then-unreadable replacement race.

## Summary
The change generalizes checkpointed draft storage, settlement, and ready-generation handling, then uses those primitives to add native unreadable-draft recovery and generation-aware keybinding conflict tracking.
