######## member 2 (pi default)
## Summary

The commit makes three native "ready-only" screens (Hub settings, Plugins, Providers) survive a transient connection flap instead of being replaced by a full-screen "Reconnect" wall. It does this by:

- Extracting `ConnectionStatus` into its own module so test-reached screens don't pull `screens.tsx`'s navigation graph.
- Adding a `fatal` flag to `useHubConnection` (protocol-mismatch closes only), propagated through `ConnectionProvider`.
- Adding `connectionDisplay`/`useConnectionDisplay`, which picks `none` (ready), `banner` (flap after something was shown, content stays mounted), or `wall` (never-ready or fatal).
- Adding `lastClient` fallbacks in Hub settings/Plugins so the child stays mounted through the brief client-null window of a manual retry.
- Tests for the pure decision, the hook, and the Providers screen transitions.

The display decision, fatal propagation, and retry-gap handling look correct, and the Providers path refreshes on reconnect through `useCredentialStore`'s `connectionChanged`. One functional gap remains.

---

**Severity: medium** — `mobile-native/src/PluginsScreen.tsx:101,123-124` and `mobile-native/src/HubSettingsScreen.tsx:142,160-163` (contract claim at `mobile-native/src/connectionDisplay.ts:6-9`)

**What goes wrong:** A transport flap keeps the *same* `AppwireClient` object — only its `state` moves `ready → reconnecting → ready` — so `useMemo(..., [client])` never rebuilds the Plugins/Hub-overview stores, and the screens stay mounted through the flap. When the banner clears, neither store re-reads:

- `createPluginsStore` recovers only through `connectionChanged` (`appwire-client/typescript/state/extensions/storeLifecycle.ts`), and nothing on native calls it — the only native caller of `connectionChanged` is `credentialStore.ts`. `fetchPlugins()` runs once per `model`, from the mount effect at `PluginsScreen.tsx:123-124`.
- `createHubOverviewStore` has no reconnect recovery at all (`hubOverview.ts`: "callers decide when to fetch() or refresh()"), and `useFocusEffect` at `HubSettingsScreen.tsx:160` does **not** re-run on a flap because its deps (`model`, `upgrade`) don't change while the screen stays focused.

Before this change, a flap hit `state !== "ready"` and unmounted the child, so the remount re-issued the reads. Now the stale pre-flap list/overview is displayed with no automatic refresh, directly contradicting the doc comment's promise of "auto-refreshing once ready again through the store's own reconnect recovery rather than any manual 'refresh to see the latest' affordance." Concretely: if a plugin was installed/removed or hub settings (e.g. version, storage) changed while the phone was away, the user acts on outdated rows — e.g. trying to remove a plugin that is already gone, or trusting a stale hub version — until they manually pull to refresh.

**Suggested fix:** drive the native reconnect recovery explicitly. For Plugins, call the lifecycle's `connectionChanged(client, state)` (e.g. from the screen, which already has `state`) so `storeLifecycle` re-reads once ready again, or re-mount/refetch on the `reconnecting → ready` transition. For Hub settings, call `refresh()` when the connection transitions back to `ready` (there is no `connectionChanged` on the hub-overview store). The new `ProvidersScreen.test.tsx` exercises this class of transition for Providers only, so wiring the same assertions for Plugins/Hub settings (using the existing `renderNative.testkit`) would pin the fix.
