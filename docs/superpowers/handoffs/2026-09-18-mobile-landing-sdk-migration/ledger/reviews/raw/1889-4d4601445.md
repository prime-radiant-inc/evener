######## member 2 (pi default)
## Summary

The commit makes marketplace store-write failures opaque to RPC clients: it adds `saveFailed` (logs the raw error server-side, returns a scrubbed message naming only the store file) and `storeChangeRollbackFailed` (same for the case where the undo also fails), then routes every `saveMarketplaces`/`saveRegistry` failure in `ensureFetched`, `AddMarketplace`, `EditMarketplace`, `RefreshMarketplace`, and `saveRename` through them. It preserves the `errStoreBetweenNames` sentinel so the migration's marker logic still works, and adds a test file asserting no absolute path leaks for save and rollback failures. The existing `saveRename` message was replaced, and the one test asserting on it was updated.

## Issues

**Medium** — `RemoveMarketplace` still returns the raw `saveMarketplaces` error, so a write failure there still names the absolute store path on the wire.

`internal/plugins/marketplaces.go:316` (`return m.saveMarketplaces(mk)`) is the only remaining `saveMarketplaces` caller in this file that the commit did not wrap, while its sibling `RefreshMarketplace` (`:993`) and `ensureFetched` (`:166`) were wrapped in the same change. `saveMarketplaces` returns `atomicWriteFile`'s error, whose text names the destination and temp file directly. That error flows unchanged through `hubPluginsController.RemoveMarketplace` → `marketplaceRefusalToWire` → the `evener/marketplace/remove` RPC result. Concrete harm: a client triggering a remove under a failing/read-only store receives this machine's absolute plugin-store path, exactly the leak #1700 is about and that the rest of this commit eliminates.

Suggested fix: `if err := m.saveMarketplaces(mk); err != nil { return m.saveFailed(name, marketplacesFileName, err) }`.

---

**Medium** — primary directory-rename/move failures in `AddMarketplace` and `EditMarketplace` still reach the caller raw, so the "never names the store path" goal is only met for save and rollback failures.

In `EditMarketplace`'s reworked `fail` closure (`internal/plugins/marketplaces.go:436-449`), when `swapErr == nil && undoErr == nil` it now returns `err` untouched. `err` there can be a raw `swapInClone` (`:487`, e.g. `installing fresh clone: %w` over an `*os.LinkError` carrying both absolute paths) or `moveMarketplace` (`:462`, `renaming marketplace clone: %w`) error. `AddMarketplace` has the same hole at `:224` (`return MarketplaceRef{}, err` after `swapInClone`). These reach the client through `EditMarketplace`/`AddMarketplace` in `app_plugins.go`, which pass non-sentinel errors straight through. Concrete harm: a rename the filesystem refuses during a re-source/rename leaks the absolute clone/cache paths over `evener/marketplace/edit` or `/add` — the same class of leak the commit scrubs when the rollback happens to fail, making the protection dependent on whether the undo succeeded rather than on the error's sensitivity. The commit's own `storeChangeRollbackFailed` doc concedes `os.Rename` output carries the store path.

Suggested fix: scrub the cause on the success-rollback branch too — e.g. have `fail` run `err` through a path-stripping helper (a `causeFailed`/generic "operation failed; see the hub's log for detail" wrapper, logging the raw error first) instead of `return MarketplaceRef{}, err`, and do the same for `AddMarketplace`'s `swapInClone` return. Add a test that injects a `marketplaceRename` failure (not a save failure) and asserts no absolute path in the returned error, mirroring the existing rollback tests.
