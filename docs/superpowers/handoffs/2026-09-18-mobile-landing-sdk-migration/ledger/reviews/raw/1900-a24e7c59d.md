######## member 2 (pi default)
## Summary

The series extracts the checkpointed-draft editor's storage port and repository into a new shared module (`appwire-client/typescript/draftCheckpointPort.ts`), replacing the keybindings-only `draftRepository` with a generic `createDraftRepository`/`DraftPort` that adds atomic `insertIfAbsent`/`replaceIf` compare-and-swaps, a `draftUnreadable` state for present-but-undecodable records, a store-free `discardStoredDraft` with a remove/absent/refused result, and a `readyGenerationFence.lostHub` split between a lost-hub write and a superseded one. On native it widens `deleteIf` to report whether it removed, adds `insertIfAbsent`/`replaceIf` to the backend, and adds `parseDraftBytes`/`matchesStoredBytes`/`classifyDraftRead`/`readDraftOutcome` plus a shared test backend. Tests are heavily expanded around the CAS, adoption, and settle paths. The goal is achieved within the pure-TypeScript SDK layer; the native differential handling is not actually wired into the production backend, as detailed below.

---

**Severity: medium**

File: `mobile-native/src/NativePreferencesProvider.tsx:39`

`backend.get` still returns `JSON.parse(value)` directly, so the tagged `StoredNullRecord`/`UnparseableDraftBytes` markers that `parseDraftBytes` (`nativePreferenceDrafts.ts:46`) produces are never created in production. The new module's own docs assert the opposite ("Parses a draft record's stored bytes the way a backend's own get() must", and `nativePreferenceDrafts.ts:173-181`: "A stored JSON `null` comes back from the shared backend.get() as STORED_NULL_RECORD"), and `nativePreferenceDrafts.test.ts` stands in for the real backend with a fake whose `get` calls `parseDraftBytes`, so the tests pass against a backend that does not exist.

What goes wrong: with a corrupt persisted keybinding draft, `createDraftRepository.load()` calls `storage.load()` → `backend.get` → `JSON.parse` throws a raw `SyntaxError` *before* the decoder/`UnreadableDraftError` path and before `classification` is set. `restoreDraft`'s catch sees a non-`UnreadableDraftError`, so it publishes `storageUnavailable: true` while leaving `draftUnreadable: false`; `refreshOverrides` then retries `restoreDraft`, fails forever, and returns before the hub read — the section is locked with no "discard unreadable draft" recovery, the exact case the feature exists to fix. Likewise `discardStoredDraft`/`discardClassified` cannot clear the record (`load()` throwing isn't caught there). A stored JSON `null` is also indistinguishable from "no record" rather than the present-but-unreadable record the tests expect.

Fix: import `parseDraftBytes` into `NativePreferencesProvider.tsx` and use it in `get`:
```ts
get(key: string): unknown {
  const value = Storage.getItemSync(key);
  return value === null ? null : parseDraftBytes(value);
},
```
This makes `nativeKeybindingDrafts` yield `UnreadableDraftError`/`draftUnreadable` for corrupt bytes and `nativeTranscriptDrafts` keep its stored-null-as-absent meaning.

---

**Severity: medium**

File: `mobile-native/src/NativePreferencesProvider.tsx:32-34`

`matches` compares `Storage.getItemSync(key) === JSON.stringify(value)`, not the byte-aware `matchesStoredBytes(Storage.getItemSync(key), value)` from `nativePreferenceDrafts.ts`. `draftBackend.testkit.ts:3-5` and the `rawBytesBackend` in `nativePreferenceDrafts.test.ts` explicitly claim the real backend "runs on stringified values via matchesStoredBytes/canonicalJson"; it does not.

What goes wrong: `deleteIf`/`replaceIf` are the CAS used by `discardClassified`, `settleWrite`, and the repository's `save`/`removeIf`. Even once `get` is fixed (previous finding), a `StoredNullRecord`/`UnparseableDraftBytes` identity passed back to `deleteIf` stringifies to `{"kind":"unparseable","raw":"{not json"}` while storage holds `{not json`, so the removal always returns false — the unreadable record can never be discarded (it reads as a spurious refusal and the store re-adopts the same corrupt bytes). For well-formed records, any stored bytes not byte-identical to `JSON.stringify(parsedValue)` (key-order differences from another build, whitespace, non-canonical number/escape forms) also fail the compare, turning a legitimate CAS into a false "another writer replaced it" refusal.

Fix: implement `matches` as
```ts
function matches(key: string, value: unknown): boolean {
  return matchesStoredBytes(Storage.getItemSync(key), value);
}
```
