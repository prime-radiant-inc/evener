## Review Findings

- **Severity**: High  
  **Location**: `mobile-native/src/mutationOutboxStorage.ts:135-145`  
  **Problem**: The generated `clientMutationId` is stored only on the record, not added to `record.payload`. The dispatcher sends that payload directly, so native mutation requests lack the ID required for daemon correlation and receipts.  
  **Fix**: Persist `payload: { ...intent.payload, clientMutationId }`, matching the IndexedDB implementation.

---

- **Severity**: High  
  **Location**: `mobile-native/src/mutationOutboxStorage.ts:124-145, 182-208`  
  **Problem**: Sequence allocation and multi-table transitions use separate autocommit statements. A crash or SQLite error can leave a sequence gap, both source and destination rows, or an incomplete transfer.  
  **Fix**: Wrap each compound operation in a SQLite transaction/savepoint with rollback handling.

---

- **Severity**: Medium  
  **Location**: `mobile-native/src/mutationOutboxStorage.ts:176-185`  
  **Problem**: `settleReceipt` only checks `mutation_outbox`. Receipts arriving after a record has moved to optimistic or recovery storage return `false` and leave stale durable rows behind.  
  **Fix**: Inspect all three tables and apply the same source-selection and cleanup behavior as the IndexedDB adapter.

---

- **Severity**: High  
  **Location**: `mobile-native/src/mutationOutboxStorage.ts:107`  
  **Problem**: The default ID generator directly calls global `crypto.randomUUID()`, but React Native does not guarantee a Web Crypto global; this project already provides `expo-crypto` for native UUIDs. Enqueueing can therefore throw at runtime unless every caller supplies an override.  
  **Fix**: Use the native `expo-crypto` source or require and safely invoke an injected ID generator.

---

- **Severity**: Low  
  **Location**: `mobile-native/src/mutationOutboxStorage.ts:123`  
  **Problem**: Empty or whitespace-only `targetRef` values are accepted and durably queued, although the existing IndexedDB adapter rejects them; such records cannot be routed by the dispatcher.  
  **Fix**: Reject `!intent.targetRef.trim()` before allocating a sequence.

## Summary

The commit adds a native SQLite mutation-outbox write adapter, but it currently fails to propagate mutation IDs, lacks atomic durability guarantees, mishandles cross-table receipt settlement, and assumes unavailable native crypto globals.

######## member 1 (codex default)
## Review Findings
- **Severity**: High
- **Location**: `mobile-native/src/mutationOutboxStorage.ts` (`enqueueIntent`, `settleReceipt`, `transferToRecovery`)
- **Problem**: Each multi-row mutation is 2+ separate sync statements with no transaction (sequence upsert then outbox insert; optimistic/recovery insert then outbox delete). A crash between statements leaves a sequence gap or the same `client_mutation_id` resident in two tables, breaking the oracle's single-transaction handoff the file header claims to mirror.
- **Fix**: Wrap each method's statements in one SQLite transaction (`BEGIN`/`COMMIT`, rollback on throw) so sequence allocation, receipt handoff, and recovery transfer are all-or-nothing.
---
- **Severity**: Medium
- **Location**: `mobile-native/src/mutationOutboxStorage.ts` constructor default `() => crypto.randomUUID()`
- **Problem**: Bare global `crypto.randomUUID()` has no fallback and throws where the host offers no `randomUUID`, contradicting the port's own `createSecureUUID` fallback pattern; `mobile-native/package.json` already ships `expo-crypto` but this adapter never uses it.
- **Fix**: Default the id source through `createSecureUUID` with an explicit `SecureRandomSource` (e.g. `expo-crypto`'s `randomUUID`/`getRandomValues`) instead of dereferencing the global directly.
---
- **Severity**: Medium
- **Location**: `mobile-native/src/mutationOutboxStorage.ts` `settleReceipt`
- **Problem**: Only consults the outbox table and deletes only there, while the oracle settles from outbox, recovery, or optimistic and retires the sibling copies; a receipt for a recovery/optimistic-resident id wrongly returns `false` and can leave stale duplicates behind.
- **Fix**: Look up all three tables as the source and delete the outbox/recovery copies (and the optimistic copy when the receipt carries no `input` display), matching `mutationOutboxIndexedDB.ts` `settleReceipt`.
---
- **Severity**: Low
- **Location**: `mobile-native/src/mutationOutboxStorage.ts` `delete`, `markAttempted`, `markUnknown`
- **Problem**: Read-modify-write via `SELECT` then `UPDATE`/`DELETE` doubles I/O and races; a concurrent writer can interleave between the check and the write.
- **Fix**: Issue a single conditional `UPDATE`/`DELETE` and decide the boolean from the statement's affected-row count instead of a prior `SELECT`.
---
- **Severity**: Low
- **Location**: `mobile-native/src/mutationOutboxStorage.test.ts`
- **Problem**: No test covers the aborted-handoff/aborted-transfer atomicity invariants the oracle explicitly tests, so the non-transactional bug above passes the suite.
- **Fix**: Add failure-injection tests asserting a failed `settleReceipt` leaves the outbox record with no optimistic duplicate, and a failed `transferToRecovery` leaves the outbox durable with no recovery row.
## Summary
Adds the native SQLite write path with correct happy-path contracts but without the oracle's transactional atomicity, multi-table settlement, or portable id fallback.


######## member 2 (pi default)
## Summary

This commit adds the write half of the native mutation outbox: `MutationOutboxSQLite`, a synchronous SQLite-backed adapter implementing six of the package's 13 `MutationOutboxStorage` calls (`enqueueIntent`, `markAttempted`, `markUnknown`, `settleReceipt`, `settleApplied`, `transferToRecovery`), plus a `node:sqlite`-backed test suite. It is deliberately unwired until D25d-1b adds the read half. Intent is clear from the commit message and the file's own header, so intent-alignment was checked.

---

**Severity: high** — `enqueueIntent` never writes `clientMutationId` into the persisted payload.

File: `mobile-native/src/mutationOutboxStorage.ts:135-144` (record construction); the test bakes this in at `mobile-native/src/mutationOutboxStorage.test.ts:82`.

`enqueueIntent` spreads `...intent`, so `record.payload` is exactly the caller's payload. The dispatcher sends `record.payload` verbatim as the RPC params (`appwire-client/typescript/state/mutation/dispatcher.ts`, `#attempt` → `client.request.call(client, method, record.payload)`), and `appwire.ValidateMutationParams` requires `clientMutationId` on every retry-safe method (`appwire/protocol.go:230-239`), returning `"clientMutationId is required"` otherwise. The web oracle fills this gap inside storage: `MutationOutboxIndexedDB.enqueueIntent` writes `payload: { ...intent.payload, clientMutationId }`, and its oracle test asserts the restored payload contains `clientMutationId: "mutation-1"`. Because the id is generated inside `enqueueIntent` (`this.#createMutationId()`), no caller above the adapter can supply it. Result once wired: every native mutation is rejected on shape alone, never dispatches, and `restoreProvenAbsent` (D25d-1b) cannot replay the original mutation identity from the payload.

Fix: create the id first, then build the record with `payload: { ...intent.payload, clientMutationId }`, and update the test expectation to include it.

---

**Severity: medium** — `settleReceipt` only consults the outbox table, unlike the port oracle.

File: `mobile-native/src/mutationOutboxStorage.ts:176-186`.

The web oracle reads `outboxRecord ?? recoveryRecord ?? optimisticRecord` and removes the record from all three tables (and updates an existing optimistic record). Native reads only `TABLES.outbox`, returns `false` when the record is absent from it, and never touches `optimistic`/`recovery`. Concrete case: tab A is dispatching a record while tab B moves it to recovery (`transferToRecovery`) or it has already been receipt-settled into optimistic; tab A's authoritative receipt then calls `settleReceipt`, which returns `false` and leaves the stale recovery/optimistic row in place instead of retiring it as the oracle contract specifies. It generally self-heals on the next `reconcileIdentities`/`settleApplied`, hence medium rather than high.

Fix: follow the oracle — resolve `outbox ?? recovery ?? optimistic` as the source and delete from every table that holds it (preserving the `pending`-input → optimistic promotion).

---

**Severity: low** — default `createMutationId` assumes an unguarded global `crypto.randomUUID`.

File: `mobile-native/src/mutationOutboxStorage.ts:107`.

`options.createMutationId ?? (() => crypto.randomUUID())` calls a bare Web Crypto global. The package this adapter implements explicitly refuses to assume one (`secureUUID.ts`: "a host with neither … still gets an id out of createSecureUUID rather than a throw … never this package's to assume"), and every other native call site uses `expo-crypto`'s `Crypto.randomUUID` or a host-supplied `SecureRandomSource` rather than the global. On a JS runtime where `globalThis.crypto` is missing or lacks `randomUUID`, enqueue throws and no mutation can be persisted. Currently unreachable because the class is not yet constructed, but it is the default a future wiring would inherit.

Fix: default to `createSecureUUID` (imported from `@evener/appwire-client/state/mutation`) with an explicit host source, or require `createMutationId` and pass `expo-crypto`'s `randomUUID` at the wiring site.
