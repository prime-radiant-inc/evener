## Summary

This six-commit series (pieces 2/3 and 3/3 of #1731) makes three coordinated changes across the shared AppWire TypeScript client, the hub frontend, and the mobile/native apps:

1. **Ask resolution is now wire-authoritative.** `liveAskQuestions` gates entirely on `ThreadModel.askPending` and treats an interrupted steering item or a user-sourced steering item as a resolution boundary (`isResolutionItem`), so the client no longer re-derives "is anything pending" from transcript shape. Fixtures/tests throughout the web and mobile suites were updated to carry `askPending` on hydrate and on `thread/status/changed`.
2. **Image folding for input images.** Empty/absent input-image lists now mean "unchanged" rather than "removed"; the mobile live store resolves attachments from the already-folded model item (`findFoldedItem` + exported `itemAttachments`) instead of the raw wire item, and the reducer documents the input-vs-output asymmetry (`omitempty` vs `omitzero`).
3. **Warning text folding.** A single `foldWarningParams`/`hasWarningText` shape validates title/hint/source, bounds the raw-frame fallback (truncate strings, cap arrays, cap depth, bound code-point expansion), and every consumer (web `WarningItem`, transcript projector, mobile failure row/canonical projector) reads that shape instead of raw `params`. Reasoning deltas are now projected on mobile from `reasoningSummaries` when `item.text` is empty.

The changes are internally consistent and well covered by the added tests. I found only minor issues.

**Low — pre-stringify prune does not bound object breadth, so the "bounded walk" guarantee is incomplete**

File: `appwire-client/typescript/reducer.ts:1245-1265` (`prunedForStringify`, especially the `Object.entries(value)` loop at `:1259`)

`prunedForStringify` caps string length, array length, and nesting depth, but never caps the number of keys on an object. A malformed warning frame that is a single wide object (e.g. `{"extra":{"k0":0,"k1":0,…}}` with hundreds of thousands of keys) is still fully walked and copied by `Object.entries`/the `pruned` record, and then fully walked again by `JSON.stringify`. That is O(frame size) work and allocation, exactly the class of cost the comment at `:1232-1244` and the commit's stated goal ("bounds the frame before JSON.stringify walks it, not just its output") set out to eliminate. The added test `an oversized warning frame's fallback bounds the frame before JSON.stringify walks it` only exercises one huge string field, so it passes while leaving this path unguarded.

Suggested fix: cap the number of keys copied (e.g. iterate `Object.entries(value)` up to a fixed small count, or break once the pruned representation exceeds a byte budget), and add a test with a wide, shallow object rather than only a single long string.

---
