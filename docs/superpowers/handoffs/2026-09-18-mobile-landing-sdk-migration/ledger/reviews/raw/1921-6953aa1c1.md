## Summary

Both commits are test-only (#1879). The first adds `root.sendersWG.Wait()` to `assertRetirementEvidenceEligible`, the shared helper used by dozens of retirement tests, so that the in-flight async session namer (which registers itself on `sendersWG` and reports an `autonomous` blocker until `finishSessionNamer` releases it) settles before eligibility is read. It also adds two deterministic-style regression tests. The second commit closes two gaps round 1 missed: the same wait added directly to `TestRetirementSafetyDetachedLifetime` before its raw `c.TryClaim(true)` (line 171), plus a second regression test mirroring that raw-claim path. All changes are consistent with the stated goal of eliminating the `"settled owner not eligible"` flake; the ordering in `finishSessionNamer` (`pending--`, then `release()`, then `DonesendersWG`) makes `sendersWG.Wait()` a correct way to observe that the namer's blocker is gone.

No production code is touched.

---

**Severity: low** — `agent/session_retirement_evidence_test.go:1429-1437` (`TestRetirementEvidenceEligibleAwaitsInFlightNamer`)

The test's comment claims that removing the helper's `sendersWG.Wait()` "makes the first read observe an immediate Fatal instead … proves by construction rather than by timing." That is not guaranteed. The first observation is a non-blocking `select` with a `default`, and the helper runs in a freshly spawned goroutine. If the goroutine has not been scheduled when the main test reaches that select, `default` is taken and `close(release)` runs. With the `Wait` removed, the helper's `TryClaim` then races the namer's post-release settlement; if the namer releases its blocker first, the helper succeeds and the test passes even though the fix was reverted. Only the fixed path (Wait blocks on the parked namer) is truly deterministic. Concrete harm: the regression guard can silently pass on a revert, reintroducing the very flake this commit fixes.

Suggested fix: make the failing path deterministic before releasing the namer — e.g. have the helper goroutine signal a "reached the claim point" channel (or perform the claim attempt in a per-test select with a rendezvous) so the main goroutine closes `release` only after the helper has provably had the opportunity to settle, and then asserts it did not.

---

**Severity: low** — `agent/session_retirement_evidence_test.go:1461-1519` (`TestRetirementDetachedLifetimeEligibilityAwaitsInFlightNamer`) and `agent/session_retirement_evidence_test.go:171`

The commit message and the new test's doc comment describe this as the deterministic regression for the second occurrence, i.e. the raw `c.TryClaim(true)` in `TestRetirementSafetyDetachedLifetime` that round 1 did not cover. The new test, however, does not exercise that call site: it re-implements the wait (`root.sendersWG.Wait()`) inside its own goroutine and then claims. Removing the added `root.sendersWG.Wait()` at line 171 leaves every test in the file passing (the underlying condition is a non-deterministic race), so the round-2 fix has no coverage. Concrete harm: the second gap can be reintroduced without any test failing, which is exactly the failure mode the commit says it is closing.

Suggested fix: drive the real code path — e.g. extract the "settle the namer, then `TryClaim`" sequence from `TestRetirementSafetyDetachedLifetime` into a helper that the new regression test and that test both call, so the assertion references the same call site that was fixed.
