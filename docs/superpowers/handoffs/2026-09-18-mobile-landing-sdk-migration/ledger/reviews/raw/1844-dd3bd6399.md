## Summary

The series extracts two shared modules from `keybindingsStore` (`draftCheckpointPort.ts`, `checkpointedDraftEditor.ts`) plus the settings-hub generation/retirement core (`settingsHubGeneration.ts`), and threads them back into the store. On top of that it reworks the checkpointed draft editor: drafts now carry a non-persisted ready-generation stamp so a hub replacement that coincidentally reuses a revision is still flagged stale; writes track identity via a `rawFrom` WeakMap so byte-aware ports can compare exactly what was written; `discardClassified`/`replaceClassified` replace blind load-then-remove/save; unreadable records become a first-class `draftUnreadable` state with a store-free discard path (SDK + native), and both write paths share one write token with a synchronous `directWrite` reservation. Tests are correspondingly expanded, and the native backend now reports delete/replace results and classifies unparseable stored bytes as an unreadable record.

The core logic is internally consistent: the identity/classification tracking, the `settleWrite`/`applyHubOverridesSettling` ordering, `savingAtReadStart` fencing, `lostHub` vs `superseded`, and the generation-stamp-on-first-payload rule all line up with their tests and comments. I found one state-projection divergence on the native offline path.

---

**Severity: low** — `mobile-native/src/NativePreferencesProvider.tsx:168-189` (`discardUnreadableKeybindingsDraft` → `setBound`)

On a `"refused"` outcome that is refused *because the replacement record now decodes as valid*, the store-free path updates only `draftUnreadable`, `storageUnavailable`, and `error` in the bound snapshot; it leaves `draft` (and `conflict`/`writeUncertain`) at their previous values. The live-store path (`discardCheckpointedDraft` → `restoreDraft`) instead adopts the replacement, so the two paths diverge exactly where the comment claims they agree ("the same fields restoreDraft would publish on a live store"). Concretely: a concurrent writer replaces an unreadable record with a valid draft; while offline the user taps "Discard unreadable draft"; `discardStoredDraft` returns `"refused"`, the unreadable notice disappears, but the snapshot still reports the old `draft: null`, so the valid on-disk proposal is invisible (no "Changes saved on this phone"/review UI) until a live model republishes on reconnect. No data is lost, and the state self-heals when a model reconnects, hence low.

Suggested fix: after computing `draftUnreadable`, when the outcome is `"refused"` and the record is readable, also populate the snapshot's `draft` (and clear `conflict`/`writeUncertain`) from the now-readable checkpoint, mirroring `restoreDraft`'s fields — or explicitly document in the field comment that the offline projection intentionally omits the adopted draft rather than claiming parity with `restoreDraft`.

- **Problem**: `save()` unconditionally overwrites the stored record, and `editDraft`, `saveDraft`, and `rebaseDraft` all reach it. Another writer that replaces the classified record before those calls persist will have its draft silently lost, despite the compare-and-swap handling used during cleanup and settlement.
