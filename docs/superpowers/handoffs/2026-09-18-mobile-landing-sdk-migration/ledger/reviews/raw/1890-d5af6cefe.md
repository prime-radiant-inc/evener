## Summary

This series hardens the Go plugin store's error surface and the `RemoveMarketplace` ordering:

- `saveRegistry` and `saveMarketplaces` now scrub the raw `*fs.PathError` (which names the machine's absolute plugin-store path) at the single shared write boundary, log the raw error server-side, and return a message naming only the JSON file (`installed_plugins.json` / `known_marketplaces.json`). All marketplace callers (`ensureFetched`, `AddMarketplace`, `RefreshMarketplace`, `RemoveMarketplace`, `EditMarketplace`, `saveRename`, `SeedDefaultMarketplaces`) wrap that scrubbed error with the marketplace name via `saveFailed`/`storeChangeRollbackFailed`.
- `EditMarketplace`'s `fail` closure now distinguishes a clean rollback (return the scrubbed cause) from a failed one (`storeChangeRollbackFailed`), preserving `errStoreBetweenNames` through `errors.Is` in both branches so migration marker decisions still work.
- `RemoveMarketplace` reorders to save metadata first, then delete the clone. A clone-removal failure after the save lands is reported as a new typed `ErrMarketplaceUnregisteredCloneRemains`, and a lookup miss is documented/tested as never touching disk. Tests cover each read/write/rollback branch and assert no absolute path reaches the caller.

The logic in the diff is sound. The reordering preserves the store lock; the `fail`-closure evaluation order (`undoSwap` before `runUndo`) is unchanged; `errRenameRollbackIncomplete` cannot reach `storeChangeRollbackFailed` (a `moveMarketplace` failure assigns `undo = nil` and leaves `swappedIn == ""`, so the closure returns the cause directly), and `errStoreBetweenNames` is re-attached where needed. No high or medium issues found.

**Severity: low** — `internal/plugins/marketplace_migration_test.go:2694`

`TestMarketplaceNameMigration_ARecoveryThatRollsBackRemovesTheMarker` previously asserted the recovery error carried the injected save cause (`strings.Contains(err.Error(), "boom")`) to prove the rollback error was joined from a real, non-nil cause. After scrubbing, that assertion was replaced with `strings.Contains(err.Error(), marketplacesFileName)`. Because `saveFailed` injects `fileName` into its message unconditionally (it does not include the cause except for the `errStoreBetweenNames` sentinel), this assertion now passes even if the underlying save error were nil or dropped. The check becomes trivially true by construction, so a future regression that loses the real cause would go undetected.

Suggested fix: capture the raw cause where it is actually observable — point `m.Stderr` at a `bytes.Buffer` in this test and assert the log contains `"boom"` (the value `saveRegistry`/`saveMarketplaces` logs before scrubbing), while keeping the existing wire-error/marker assertions. That exercises the real behavior (raw detail is logged, scrubbed detail is returned) rather than a message fragment the helper emits regardless of the cause.
