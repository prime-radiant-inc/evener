## Summary

Commit `25de246` extracts the mutation-projection ordering logic from the web's pending-turns store into a package-level `createMutationProjectionFence` (plus `MutationProjectionRefresh`/`MutationProjectionFence` types) under `appwire-client/typescript/state/mutation/projection.ts`, and exports it from the mutation barrel. The fence assigns monotonically increasing generations to refreshes (one target or all targets), records "live commit" generations via `advance`, and returns the subset of targets a resolved snapshot may still replace, using `reset`/`epoch` to invalidate work across client swaps. `1897417` is an empty retarget commit. New unit tests in `projection.test.ts` cover acceptance, all-targets, read failure, reset invalidation, `advance` ordering, and `epoch`. The change is intentionally package-only (no production consumer wired yet), so intent is achieved.

## Issues

**Medium** — A rejected read permanently advances the generation floor, so it can suppress a concurrent successful refresh.

`appwire-client/typescript/state/mutation/projection.ts:78-81` assigns `allTargetsRefreshGeneration`/`refreshGenerations[ref]` *before* the read, and the `catch` at line 106 returns `false` without rolling those assignments back. Because the pre-assigned generation is still the maximum floor when a slower, older, but *successful* read resolves, the success gets discarded:

- All-targets refresh `g1` starts.
- A specific refresh of `ref-a` starts as `g2`; its port read rejects.
- The all-targets `g1` read succeeds and resolves. At line 99, `1 < max(allTargetsRefreshGeneration=1, refreshGenerations["ref-a"]=2)` is true, so `ref-a` is deleted from `targets` and its fresh snapshot is never applied.

Without the failed read, the `g1` snapshot for `ref-a` would have been accepted. The result is a silently dropped update for `ref-a` (stale pending-turn/recovery state) until some later refresh happens to run; a rejected all-targets read can similarly suppress an older in-flight specific refresh. The top-of-file comment only promises not to discard the *last durable projection*; it does not cover this case, and the behavior is an artifact of consuming a generation for a read that produced nothing.

Fix: on the failure path, roll the assignment back when it has not been superseded, e.g. capture the previous value before assigning and, in `catch`, restore it only if the current value still equals the generation this refresh assigned:

```ts
const previous = ref === undefined ? allTargetsRefreshGeneration : refreshGenerations.get(ref);
// ... assign ...
try { ... } catch {
  if (ref === undefined) {
    if (allTargetsRefreshGeneration === generation) allTargetsRefreshGeneration = previous ?? 0;
  } else if (refreshGenerations.get(ref) === generation) {
    refreshGenerations.set(ref, previous ?? 0); // or delete when there was no prior entry
  }
  return false;
}
```

(Rolling back only under the equality check avoids undoing a newer refresh/`advance` that landed during the read, which is why the ordering must stay assigned during the read.)
