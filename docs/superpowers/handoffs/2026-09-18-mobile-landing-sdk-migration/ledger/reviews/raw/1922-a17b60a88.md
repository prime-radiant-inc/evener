## Review Findings

- **Severity**: Medium  
  **Location**: `mobile-native/src/connectionDisplay.ts:80`, `mobile-native/src/PluginsScreen.tsx:142-149`  
  **Problem**: When a retry creates a new client in `connecting`, `useRenderClient` immediately switches to it. The child store remounts and issues its initial request before the client is ready, causing rejected requests, blank content, and potentially stale upgrade errors.  
  **Fix**: Keep rendering the previous client until the replacement reaches `ready`, or gate initial fetch/reconciliation effects on readiness.

---

- **Severity**: Medium  
  **Location**: `mobile-native/src/MarketplaceBrowser.tsx:73-80`, invoked from `mobile-native/src/PluginsScreen.tsx:215-225`  
  **Problem**: The marketplace store is now retained across reconnects but never receives `connectionChanged`. Its marketplace list and catalog cache therefore do not refetch after a passive connection flap.  
  **Fix**: Pass connection state into `MarketplaceBrowser`, call `model.connectionChanged` on every transition, and gate its refresh/mutation controls while disconnected.

---

- **Severity**: Medium  
  **Location**: `mobile-native/src/ProvidersScreen.tsx:308-310`, `371-405`, `437-495`  
  **Problem**: Most provider operations remain enabled while disconnected: editor saves, credential writes, credential tests, default changes, credential clearing/logout, and instance removal. These invoke AppWire requests that reject unless the client is ready.  
  **Fix**: Include `!ready` in all wire-operation controls and pass it into `ProviderEditor`’s disabled state.

## Summary

The change preserves several mobile screens across connection flaps, but leaves marketplace recovery, provider readiness gating, and retry-time client replacement incomplete.

## Summary

The series makes ready-only mobile screens (HubSettings, Plugins, Providers) survive a transport flap instead of dropping to a full-screen "wall": a shared `connectionDisplay.ts` derives `wall`/`banner`/`none` from the connection state, `hubConnection.ts` now exposes a `fatal` flag (protocol mismatch) so those screens still wall on a non-retryable close, and the retained children stay mounted behind a `ConnectionStatus` banner whose mutation controls are disabled while not `ready`. Plugins/HubSettings also get reconnect recovery (`useReconnectRecovery` / `store.connectionChanged`), a last-known-client fallback through the brief null gap of a manual retry, and new unit tests for the display logic plus screen-level banner/fatal tests.

The design is coherent and the new `connectionDisplay` logic is well covered. One gap stands out.

---

**Severity: medium** — "gate mutations on ready" is applied inconsistently, so newly-retained screens still accept mutations during a flap.

With the old code, `state !== "ready"` unmounted the whole child, so no mutating control in these screens was reachable during a flap. After this change the children stay mounted behind the banner, but several mutating controls are not gated on `ready`:

- `mobile-native/src/ProvidersScreen.tsx`: only the OAuth sign-in action got `disabled={state.busy || !ready}` (≈line 425). The other write actions still use only `state.busy || state.data?.writesRefused` — "Add provider instance" (≈line 213), `ProviderEditor disabled` (≈line 285), "Test credentials" (≈line 394), "Save key"/"Save credential JSON" (≈line 366), "Make default" (≈line 430), "Clear stored key" (≈line 460). `ProviderInstances.busy` (mobile-native/src/providerInstances.ts:88) does not track readiness, so none of these disable during `reconnecting`.
- `mobile-native/src/PluginsScreen.tsx`: the installed-list controls were correctly gated (`busy || !ready`), but the `<MarketplaceBrowser …>` call site (≈line 212) is never told the readiness; `MarketplaceBrowser`'s Install / Add marketplace / Remove / Refresh source actions are disabled only by `busy` (MarketplaceBrowser.tsx:177–221, 271, 490).

What goes wrong: during `reconnecting` (the exact scenario the banner introduces), those controls remain enabled. Tapping one calls the store, which calls `client.request(...)`, and `AppwireClient.request` rejects immediately when the state isn't `ready` (`appwire-client/typescript/client.ts:391`). The user gets a failure message ("The operation could not be confirmed…", "Could not confirm the change…") for an operation that never went on the wire — and, on Plugins, the identical controls right next to it (the installed list's switches and Remove/Upgrade buttons) are correctly disabled, so the screen contradicts itself.

Suggested fix: thread the existing `ready` value into `MarketplaceBrowser` (or pass a `disabled`/`readOnly` prop) and OR it into every write control's `disabled`, and add `|| !ready` to the remaining Providers mutation/refresh actions listed above (and to `ProviderEditor`'s disable input), matching the pattern the same commit already applied to the OAuth action.
