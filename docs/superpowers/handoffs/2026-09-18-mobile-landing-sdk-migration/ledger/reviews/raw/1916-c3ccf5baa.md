## Summary

The series adds `mobile-native/src/mutationOutboxStorage.ts`, the write half of the native implementation of the package's `MutationOutboxStorage` port over a synchronous SQLite handle, plus a `node:sqlite`-backed test that mirrors the web oracle (`MutationOutboxIndexedDB`) per-method contracts. Round 1 added `enqueueIntent`, `markAttempted`, `markUnknown`, `settleReceipt`, `settleApplied`, `transferToRecovery` and the savepoint/`fromRow` plumbing; round 2 replaced the default id source with expo-crypto's `SecureRandomSource`, made `settleReceipt` consult the recovery table, and added trigger-based atomicity tests. Behavior otherwise matches the oracle: gap-free per-target sequencing, the pending-input-carrying-record-becomes-optimistic rule, the `onlyAttempted` guard, and insert-before-delete with rollback.

The implementation is faithful to the oracle. I found only latent/low-severity divergences, listed below.

---

**Severity: low**
`mobile-native/src/mutationOutboxStorage.ts:237` (with `:118` and `:301`)

`settleReceipt` builds the accepted optimistic record by spreading the source (`this.insert(TABLES.optimistic, { ...source, state: "accepted" })`). When the source is a `MutationRecoveryRecord` (the path added in round 2, exercised by "settleReceipt consults recovery..."), `insert` persists that record's `recovery_kind`/`recovery_reason`, and `fromRow` (line 118) then re-attaches `recoveryKind`/`recoveryReason` to the optimistic record. The web oracle constructs the accepted record field-by-field and deliberately omits these.

What goes wrong: once D25d-1b's `getOptimistic`/`listOptimistic` exist, a record with `state: "accepted"` will also report `recoveryKind: "rejected"`. Any consumer that branches on `recoveryKind` (rather than `state`) will treat an accepted-but-unreflected optimistic mutation as a refused one, e.g. surfacing recovery controls for a submission that succeeded.

Suggested fix: build the optimistic record explicitly from the port's fields (as the oracle does), or have `insert` write `NULL` for `recovery_kind`/`recovery_reason` whenever the target table is `mutation_optimistic`.

---

**Severity: low**
`mobile-native/src/mutationOutboxStorage.ts:286` (called from `enqueueIntent` at `:181`)

`insert` uses `ON CONFLICT (client_mutation_id) DO UPDATE SET state = excluded.state, attempted = excluded.attempted`. For `enqueueIntent` the web oracle uses `objectStore.add(record)`, which throws on a duplicate key. Native silently updates only two columns and then returns a `record` whose `payload`/`attachments`/`intentSequence`/`createdAt` do not match what is actually stored.

What goes wrong: if `createMutationId` ever yields a colliding id (an injected deterministic generator, or the package's documented non-crypto fallback under adversarial conditions), the first mutation's stored payload is preserved while its `state`/`attempted` are clobbered, and `enqueueIntent` reports the second intent as if it were persisted; the underlying mutation is lost and the returned record disagrees with the row. Web would instead reject the duplicate at the storage boundary.

Suggested fix: use a plain `INSERT` for `enqueueIntent` (letting the primary-key constraint reject a collision) or extend the `DO UPDATE` to refresh every mutable column so storage matches the returned record.

---

**Severity: low**
`mobile-native/src/mutationOutboxStorage.test.ts:143` (test "markAttempted flips a submitting record's attempted flag and refuses a non-submitting one")

The test name promises refusal of a non-submitting record, but the only false case asserted is `markAttempted("missing")`, which exercises the "no row" path, not the `AND state = 'submitting'` guard. The new mutation still only flips `attempted` for a record in the `submitting` state.

What goes wrong: a regression that dropped the `state = 'submitting'` clause would still pass, and attempt evidence could be recorded for a record already classified `blockedUnknown`, weakening the "commit attempt evidence before transport" invariant the method exists for.

Suggested fix: after enqueue, `markUnknown(id, "blockedUnknown")`, then assert `markAttempted(id)` resolves `false` and the row's `attempted` stays `0` (observable behavior, not a source-text check).
