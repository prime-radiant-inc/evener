## Review Findings
- **Severity**: Medium
- **Location**: `mobile-native/src/mutationOutboxStorage.ts:311`
- **Problem**: `restoreProvenAbsent` lists then updates in a loop with no savepoint, while the oracle (`mutationOutboxIndexedDB.ts`) and every other compound write in this file (`enqueueIntent`, `settleReceipt`, `settleApplied`, `transferToRecovery`) use a transaction. A throw mid-loop leaves a partial restore.
- **Fix**: Wrap the list-filter-update in `this.transaction("mutation_outbox_restore_absent", ...)` like the other writers.
---
- **Severity**: Medium
- **Location**: `mobile-native/src/mutationOutboxStorage.ts:236`
- **Problem**: `settleReceipt` builds the optimistic record as `{ ...source, state: "accepted" }`. When `source` is a recovery record this carries `recoveryKind`, `recoveryReason`, and `attempted` into the optimistic table; the oracle explicitly constructs an accepted record without recovery fields.
- **Fix**: Construct the accepted record explicitly from only `version`, `clientMutationId`, `originClientId`, `intentSequence`, `createdAt`, `targetRef`, `threadId`, `method`, `payload`, `attachments`, `optimisticDisplay`, `composerText` plus `state: "accepted"`.
---
- **Severity**: Medium
- **Location**: `mobile-native/src/mutationOutboxStorage.ts:336`
- **Problem**: `insert` uses `ON CONFLICT DO UPDATE SET state, attempted` only, so a conflicting `clientMutationId` keeps stale `payload`, `optimistic_display`, `composer_text`, and `recovery_*` columns. The oracle uses IndexedDB `put`, which fully overwrites the record.
- **Fix**: Update all persisted columns on conflict, or delete-then-insert / `INSERT OR REPLACE` to match full-overwrite semantics.
## Summary
Native SQLite outbox mirrors the IndexedDB contracts but diverges on restore atomicity, optimistic-record shape, and conflict-overwrite semantics.

## Summary

The series adds `mobile-native/src/mutationOutboxStorage.ts`, a native implementation of the package's `MutationOutboxStorage` port over a synchronous SQLite handle (expo-sqlite in production, `node:sqlite` in tests), plus `mutationOutboxStorage.test.ts`. Commit 1a lands the write path (`enqueueIntent`, `markAttempted`, `markUnknown`, `settleReceipt`, `settleApplied`, `transferToRecovery`) with savepoint-wrapped compound writes; 1b adds the read path (`listTargetRefs`, `getOutbox`/`getOptimistic`/`getRecovery`, `listOptimistic`, `nextDispatchable`, `restoreProvenAbsent`). The implementation mirrors the web oracle (`mutationOutboxIndexedDB.ts`) for sequencing, receipt settlement, recovery transfer, blocked-unknown gating, and proven-absent restoration, and the tests drive a real SQLite engine including fault-injection triggers for the two atomic handoffs.

I checked each of the 13 port methods against the web oracle, the SQL placeholder/column alignment, the savepoint rollback paths, the `changedRows` bigint/number handling, the id-source default (`createSecureUUID` over expo-crypto, never a bare Web Crypto global), and the `fromRow` round-trip for every table. I did not find a defect with concrete harmful impact. Divergences I considered and discarded as non-harmful or documented/out-of-scope: the native adapter omits the web's `notes/human/set` recovery-superseding inside `settleReceipt`/`settleApplied` (explicitly scoped out in the file header and not part of the port; no native consumer exists yet), `insert`'s `ON CONFLICT DO UPDATE` makes `enqueueIntent` idempotent rather than rejecting a duplicate id (unreachable with `createSecureUUID`), and a recovery-sourced optimistic handoff retains `recoveryKind`/`recoveryReason` columns (inert—no package reader inspects those on an optimistic record).

No issues found.
