## Summary

This series extracts the checkpointed-draft machinery from `keybindingsStore.ts` into a shared, generic `draftCheckpointPort.ts` (`DraftPort`, `DraftRepository`, `discardStoredDraft`, `UnreadableDraftError`), then makes unreadable stored drafts recoverable: the live store exposes `draftUnreadable` and permits discard over it, and the native app adds a store-free offline discard path (`discardStoredKeybindingDraft`) plus a cold-start probe. Along the way it adds compare-and-swap `replaceIf`/`save` semantics to the repository, tags stored-null/unparseable bytes distinctly on the native backend, canonicalizes the byte comparison, and tightens write fencing (`directWrite` reservation, `lostHub`, `savingAtReadStart`). The final aggregate matches that goal and the port tests are extensive.

I found one reachable functional gap in the native UI wiring and two smaller completeness issues. The core port/repository logic looks sound.

---

**Severity: medium** — `mobile-native/src/KeybindingPreferencesScreen.tsx:98-100`

```ts
const draftUnreadable = domain
  ? domain.draftUnreadable
  : preferences.offlineDraftUnreadable;
```

The screen makes `domain.draftUnreadable` authoritative whenever *any* snapshot exists, so the independently-computed `preferences.offlineDraftUnreadable` is silently ignored. But `bound`/the snapshot persists across a disconnect (`NativePreferencesProvider` never clears it, and `selected = bound?.hubId === hubId ? bound : null`), while the live store does not re-read the draft when offline. If a record becomes unreadable after the connection drops (or after the store's last read) and the probe effect detects it, `offlineDraftUnreadable` becomes `true` but `domain.draftUnreadable` stays `false` — the recovery action does not render, and the user has no way to clear the unreadable record until they reconnect, which is exactly the offline case the commit series is adding the action for.

Fix: treat the offline signal as an additional source, e.g. `domain?.draftUnreadable || preferences.offlineDraftUnreadable` (and keep the live domain's value authoritative only for the positive case).

---

**Severity: low** — `mobile-native/src/NativePreferencesProvider.tsx:213-224`

The `setBound` snapshot update on an offline discard writes only `draftUnreadable`, `storageUnavailable`, and `error`. The comment claims these are "the same fields restoreDraft would publish on a live store", but `restoreDraft` also publishes `draft` (and `writeUncertain`/`draftConflict`). When `discardStoredKeybindingDraft` returns `"refused"` because a concurrent writer replaced the unreadable record with a *readable* one, the notice is correctly cleared but `snapshot.keybindings.draft` remains `null`, so the replacement draft the store-free path just discovered is not shown (the "Changes saved on this phone" block stays hidden) until a reconnect re-runs the live store's `restoreDraft`. The discard's own re-read already has the data; it should update `draft` (and `writeUncertain`/`draftConflict`) from `current`/the restored record rather than leaving stale `null`s.

---

**Severity: low** — `mobile-native/src/NativePreferencesProvider.tsx:130-135` and `:237-238`

`offlineStorageUnavailable` is computed and published on the context, but nothing consumes it. Because a genuine port failure deliberately leaves `offlineDraftUnreadable` "at whatever it last was", the "Discard unreadable draft" action keeps rendering over a dead port; pressing it calls `discardUnreadableKeybindingsDraft`, which swallows the throw, returns `null`, and (via `clearsErrorAfterOfflineDiscard(null)`) shows no feedback at all. The failure is therefore invisible and the button silently no-ops. Either consume the flag to disable/suppress the action (or surface an error), or drop the field.

######## member 3 (codex default)
## Review Findings
- **Severity**: High
  **Location**: `appwire-client/typescript/draftCheckpointPort.ts:155`
  **Problem**: `save()` writes unconditionally when classification is `null` or `"absent"`. Two repositories can both classify the same empty store, after which the second save silently overwrites the first; a repository that never loaded can also overwrite an existing record.
  **Fix**: Add an atomic create-if-absent port operation, or define an explicit absence identity for `replaceIf`, and make repository saves CAS against that classification rather than calling unconditional `storage.save()`.

---

- **Severity**: Medium
  **Location**: `appwire-client/typescript/keybindingsStore.ts:679`
  **Problem**: A genuine storage-read failure sets `draftUnreadable` to `false`, erasing the discard recovery after an earlier unreadable record and leaving the editor blocked by `storageUnavailable`.
  **Fix**: Omit `draftUnreadable` from the partial state for non-`UnreadableDraftError` failures; set it to `true` only for unreadable records.

---

- **Severity**: Medium
  **Location**: `mobile-native/src/nativePreferenceDrafts.ts:171`
  **Problem**: `draftUnreadableAfterDiscard()` clears the unreadable notice whenever the outcome is `"removed"` or `"absent"`, even when the follow-up read finds a new unreadable record. The provider also leaves the old notice when removal succeeded but the follow-up read fails.
  **Fix**: Derive the notice from the current read; when that read is unavailable, clear it for `"removed"`/`"absent"` and preserve it only for `"refused"`.

---

- **Severity**: Medium
  **Location**: `mobile-native/src/NativePreferencesProvider.tsx:177`
  **Problem**: A storage failure during the offline discard is swallowed and returned as `null`, the same value documented for “no hub,” so the screen reports no error and `offlineStorageUnavailable` is never rendered.
  **Fix**: Re-throw storage failures so the screen’s existing catch renders an error, or return a discriminated result that distinguishes “no hub” from “discard failed.”

## Summary
This change centralizes checkpointed draft storage behind compare-and-swap semantics and adds native unreadable-draft recovery plus shared write-token fencing.
