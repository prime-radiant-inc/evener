## Summary

The series extracts the pending-turns "projection fence" (the generation bookkeeping that decides which durable-read snapshot may still replace a target's records) out of the web's `pendingTurnsStore.ts` into the shared `appwire-client` package as `createMutationProjectionFence`, switches the web to consume it, and reworks the fence to hand callers a re-checkable `apply()` step instead of a target set fixed at read-resolution time. `replaceTargetRecords` and the port type are exported from the package, and the web's duplicate local copy and module-level generation globals are deleted. A failed refresh deliberately does **not** roll back its generation (the rollback fix was reverted; tests now pin this), and `apply()` re-checks the generation floor so a live commit's `advance` landing after the read resolves still out-ranks the stale snapshot. The aggregate diff achieves that goal, and the package test file adds targeted coverage for the ordering cases (single vs. all-targets, failed refresh, reset, apply-after-resolve).

One correctness gap in the new fence:

---

**Severity: medium** — `apply()` omits `allTargetsRefreshGeneration` from its re-check, so an all-targets refresh that starts after a single-target read resolves (and then fails) no longer fences that older snapshot, contradicting the fence's own stated generation rule.

`appwire-client/typescript/state/mutation/projection.ts:129-138` (compare with the resolution-time check at line 121)

The resolution-time decision uses `generation < Math.max(allTargetsRefreshGeneration, refreshGenerations.get(target) ?? 0)` (line 121), but `apply()` only re-checks `refreshGenerations.get(target) !== generation` (line 136). `refreshGenerations` is not touched by an all-targets refresh until *its own* read resolves, and `allTargetsRefreshGeneration` is bumped the moment one *starts*. So this sequence escapes the fence:

1. `refresh(port, "ref-a")` (gen 1) resolves; `candidates = {ref-a}`, accepted, `refreshGenerations.set("ref-a", 1)`. Caller defers `apply()`.
2. A newer all-targets `refresh(port)` (gen 2) starts — `allTargetsRefreshGeneration = 2` — and its read rejects.
3. Caller runs the gen-1 `apply()`: `refreshGenerations.get("ref-a") === 1`, so `ref-a` is accepted and the stale snapshot is projected.

The test at line 142 ("a newer refresh that fails still raises the generation floor…") establishes that a newer refresh is supposed to raise the floor even when it fails, and the module comment at line 10 states an all-targets refresh's generation "counts against every target's own floor exactly as a specific refresh's does." Here a failed all-targets refresh does not fence, because the floor check that would catch it exists only at read-resolution time, and the whole point of `apply()` is to re-decide after that. Concrete harm: the fence projects data a newer all-targets read has already superseded, and if that newer read fails the stale records survive instead of being discarded (the state the failed-refresh test exists to prevent). This is not reachable through the current web caller, whose `apply()` runs synchronously in the same microtask as `refresh()` resolution (so no newer refresh can start in between) — but `MutationProjectionFence` is now a reusable package API that explicitly hands callers a `snapshot`/`apply` pair to invoke "at the moment the caller calls it," so the invariant should hold at apply time regardless of caller timing.

Suggested fix: make `apply()` use the same floor expression as the resolution-time check:

```ts
apply: () => {
  const accepted = new Set(candidates);
  for (const target of accepted) {
    if (generation < Math.max(allTargetsRefreshGeneration, refreshGenerations.get(target) ?? 0)) {
      accepted.delete(target);
    }
  }
  return accepted;
},
```

This is a no-op for an all-targets refresh's own `apply()` (its `generation` equals `allTargetsRefreshGeneration`), so it only restores the missing fence. Add a package test mirroring the failed-specific-refresh test but with an all-targets second refresh: resolve a single-target refresh, start an all-targets refresh whose read rejects, then `apply()` the first and assert the target is absent.

## Review Findings
- **Severity**: High
  - **Location**: `appwire-client/typescript/state/mutation/projection.ts:133`
  - **Problem**: `apply()` only rechecks the per-target generation. It ignores both `refreshEpoch` and `allTargetsRefreshGeneration`, so an already-resolved refresh can still apply after a reset (where generation numbers are reused) or after a newer all-targets refresh has raised the global floor, including when that newer refresh fails.
  - **Fix**: Reject a target in `apply()` when `refreshEpoch !== epoch`, `generation < allTargetsRefreshGeneration`, or the current per-target generation differs. Add tests for an old refresh surviving a reset before `apply()` and for a failed newer all-targets refresh invalidating an older resolved refresh.
