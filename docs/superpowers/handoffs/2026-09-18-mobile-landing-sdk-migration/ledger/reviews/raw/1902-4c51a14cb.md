######## member 2 (pi default)
## Summary

The series migrates the keybindings draft editor onto a shared, generic `createDraftRepository`/`DraftPort` in the AppWire client, adding atomic `insertIfAbsent`/`replaceIf` compare-and-swap so concurrent writers can't silently clobber a checkpoint (closing #1884). It gives the port an `unknown` identity parameter, adds unreadable-record classification (`UnreadableDraftError`, `draftUnreadable`), a store-free `discardStoredDraft` recovery path, a native draft backend that tags stored-null/unparseable bytes, an offline probe, and a large test suite. The changes for atomic settle/adoption look internally consistent and well covered.

## Findings

### High — `draftUnreadable` is written into a snapshot type that does not declare it, and is never projected
**File:** `mobile-native/src/NativePreferencesProvider.tsx:218` (and `mobile-native/src/nativePreferences.ts:17-27`, `keybindingsDomain`)

`setBound` builds `snapshot.keybindings` with a `draftUnreadable` property, but `PreferenceState<T>` has no such field and `keybindingsDomain` never maps `state.draftUnreadable`. Two concrete consequences:

1. `NativePreferencesProvider.tsx` no longer typechecks: `{...previous.snapshot.keybindings, draftUnreadable, ...}` is an object literal with an excess property against `PreferenceState<ConfirmedKeybindings>` (TS2353). The `check` step (`tsc --noEmit -p tsconfig.check.json`) is part of `make test-native` (see `make/testing.mk:64`), so the native gate fails.
2. Even at runtime the value is unreliable: the store subscription republishes `keybindings: keybindingsDomain(state)`, which drops `draftUnreadable`, so the provider's manual patch only survives until the next store publish. The comment at lines 49-52 (“Superseded by `snapshot.keybindings.draftUnreadable` the moment a model publishes”) therefore references a field that does not exist, and the live-model unreadable state is never available to a consumer.

**Suggested fix:** add `draftUnreadable: boolean` to `PreferenceState`, initialize it in `initialDomain`, and map `draftUnreadable: state.draftUnreadable` in `keybindingsDomain` (then the manual snapshot patching at 218 can be removed and `offlineDraftUnreadable` becomes purely the pre-model fallback).

---

### Medium — the store-free discard recovery is exposed but unreachable
**File:** `mobile-native/src/NativePreferencesProvider.tsx:64,271-273`, `nativePreferenceDrafts.ts:169`

The provider adds `offlineDraftUnreadable`, `offlineStorageUnavailable`, and `discardUnreadableKeybindingsDraft`, and `clearsErrorAfterOfflineDiscard` is exported and unit-tested, but nothing in the app calls any of them: `KeybindingPreferencesScreen` (the only keybindings-settings consumer) never reads the provider’s new fields, and the existing “Discard changes” action only renders when `domain.draft` is truthy. For a stored record this build cannot decode, `domain.draft` is null and `storageUnavailable` is true, so `busy` disables the section and no discard control is rendered. The section is permanently locked with no way to invoke `store.discardDraft()` — precisely the failure the new comment at lines 49-52 warns about (“A host must offer that discard, or the section is locked with no way out”), and the intent of the p6a/p6b commits.

**Suggested fix:** render the unreadable-draft state (from `snapshot.keybindings.draftUnreadable` once projected, or `offlineDraftUnreadable` before a model exists) in `KeybindingPreferencesScreen`, with an action calling `discardUnreadableKeybindingsDraft`/`model.discardKeybindingsDraft`, and use `clearsErrorAfterOfflineDiscard` to decide whether to clear the component’s local error.

---

### Low — the follow-up read can throw outside any guard
**File:** `mobile-native/src/NativePreferencesProvider.tsx:208`

`decodeKeybindingDraftFields(storage.load())` performs a fresh synchronous port read with no try/catch, unlike the `readDraftOutcome` call immediately before it and the `discardStoredKeybindingDraft` call before that. If that second read hits a genuine `Storage` failure, the exception escapes `discardUnreadableKeybindingsDraft` into the caller’s event handler instead of degrading to `offlineStorageUnavailable`. The window is small (a read succeeded moments earlier), but the inconsistency means the one path that can throw is the one that isn’t handled.

**Suggested fix:** wrap the second read in the same failure handling (reuse `readDraftOutcome`, or catch and set `offlineStorageUnavailable`).
