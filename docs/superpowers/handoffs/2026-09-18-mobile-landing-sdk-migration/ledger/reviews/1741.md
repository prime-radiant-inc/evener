## roborev: Combined Review (`f0e1b58`)

**Verdict:** One blocking regression (`hubLoading` stuck on stale refresh) plus a post-rename `draftConflict` leak and two minor type/semantics issues.

## High

**Stale refresh leaves `hubLoading` stuck true** — `appwire-client/typescript/keybindingsStore.ts:685-692, :962`

A stale GET reply skips the function-valued `extra` thunk, but that thunk is also the only place `refreshFor` clears `hubLoading`. The stale guard at `:685` was changed to only apply plain objects (`if (typeof extra !== "function" && ...) setState(extra)`), so when a `changed` notification or in-flight write bumps `state.revision` past the GET's payload while the GET is outstanding, `applyHubOverrides` skips the thunk and returns `false` without clearing `hubLoading`. The settings UI then stays stuck loading (`hubLoading || !loaded`, `cmd/evener-hub/frontend/src/panes/settings/sections/keybindings.tsx:489`), `editable` is permanently false (`:476`), and `patchOverrides`/`rebaseDraft` reject as unavailable (`keybindingsStore.ts:1072, :1374`) until some unrelated event triggers another refresh. The race is not hypothetical: a `changed` broadcast arriving during startup or manual refresh with a higher revision produces it, and the notification path applies state directly without triggering a follow-up refresh.

*Fix:* Clear `hubLoading` independently of the settlement side effects — split `extra` into a plain object (`{hubLoading:false}`) and a separate deferred side effect the stale guard skips, or check `applyHubOverrides`'s return value in `refreshFor` and publish `{ hubLoading: false }` on the stale path without invoking `settledWrite`. Extend the existing stale-reply test (`keybindingsStore.test.ts:343`) to assert `hubLoading` is `false` after the stale reply.

## Medium

**Post-rename save leaves `draftConflict` stuck true** — `appwire-client/typescript/keybindingsStore.ts:1224`

A successful post-rename save applies a newer revision (marking the in-memory draft stale), then removes the draft, but the final publish does not clear `draftConflict`. This leaves `draft === null` with `draftConflict === true`, so a subsequent `saveDraft()` is incorrectly rejected with "Review the current shortcuts before saving your changes."

*Fix:* Clear `draftConflict` when the checkpoint is successfully removed after a settled non-external write, preserving existing conflict state for newer-external, storage-error, and refusal paths. Assert `draftConflict: false` in the post-rename success test.

## Low

**`invalidDraft()` conflates error types** — `appwire-client/typescript/keybindingsStore.ts:323`

`invalidDraft()` throws `UnreadableDraftError` for both stored-checkpoint decode failures and user-input `keybindingRules` validation, conflating storage-unreadable with invalid user input.

*Fix:* Keep `UnreadableDraftError` only for `draftCheckpoint` decode; use plain `Error` for `keybindingRules` validation failures.

**Unconstrained `WeakMap` generic** — `appwire-client/typescript/draftCheckpointPort.ts:89`

`rawFrom: WeakMap<object, unknown>` with `checkpoint as object` throws if `Checkpoint` is ever a primitive; the generic is unconstrained.

*Fix:* Constrain with `Checkpoint extends object` or guard non-object checkpoints before `WeakMap` access.
