## Summary

This series moves plugin-store write notifications from per-handler manual calls (`notifyMarketplaceUpdated`/`notifyPluginUpdated`) to a post-commit hook. `plugins.Manager` gains a `StoreChanged{Plugins,Marketplaces}` accumulator marked by the two write primitives (`saveRegistry`, `saveMarketplaces`), captured and cleared by `lockStore`'s wrapped release, and delivered to an `OnStoreChanged` callback after the file lock is released. The hub wires that callback to broadcast on every `Manager` it constructs (plugins controller, auto-upgrade manager, seed, GC, command-list), removes the now-duplicated manual notify calls, and routes plugin resolution through a per-server `WebConfig.PluginResolveManager` closure instead of an unwired throwaway manager. Tests cover migration-triggered writes, no-op vs. writing sessions, rollback, concurrent sessions, and exactly-once behavior. The aggregate diff achieves its goal: every primitive-level store write is reported once per lock session, and the manual notify paths are gone, so there is no double-broadcast.

## Low

- **`cmd/evener-hub/app_plugins.go:35-38`** — Misleading mutex comment.
  The comment justifies `hubPluginsController` holding no mutex by claiming `Manager`'s `StoreChanged` state "is only ever touched while the same flock is held, so it needs no mutex of its own either." That is exactly the claim the rest of the series refutes in `internal/plugins/paths.go:25-33` and `internal/plugins/store_changed.go:80-88`, which add `storeChangedMu` precisely because flock provides no Go happens-before edge and the package's own `lockAcquirer` seams can be stubbed to a no-op. A future maintainer reading this comment could delete `storeChangedMu` on the belief that the file lock suffices, reintroducing the unsynchronized `pendingStoreChanged`/`onStoreChanged` accesses the mutex prevents (lost/duplicated report or a race the `-race` gate only catches under stubbed locks or direct field access).

  **Suggested fix:** Reword the comment to say Manager already guards its `StoreChanged` state with its own mutex, and that is why no *controller*-level mutex is needed here — retaining the accurate conclusion while correcting the rationale.
