## Verdict: Server-side ask-boundary unification is solid, but client-side derivation diverges — two medium gaps and one weak test remain.

### Medium

**Client-side ask derivation diverges from server after user-sourced / interrupted steering**

`agent/session_tools_ask.go:301-304` · `appwire-client/typescript/deriveAskQuestions.ts:56-72` · `appwire-client/typescript/reducer.ts:1686` · `agent/session_ask_test.go:1477-1560`

The server now clears `askPending` for user-sourced and interrupted `TurnSteering` turns (`clearAskPendingForResolvingSteer`, `turnResolvesAskBoundary`), but the client's `liveAskQuestions`/`lastUserMessageIndex` still treats only `type === "userMessage"` items as the resolution boundary. User-sourced steering turns are projected as `type: "steering"` with `Source: "user"` (`internal/apptranscript` `ProjectTurn`, pinned by `apptranscript_test.go:216-234`; same shape on the live reducer path).

Result: after a user steers (a non-answer) while an ask is pending, the server considers the question resolved and lets the model proceed, but the web client keeps the ask dock open and the answer prompt live — the exact live/derived divergence the commit's comments (`session_tools_ask.go:86`, `275-283`) claim to have eliminated. The comments reference a `deriveAskQuestions.ts` `isResolutionItem: SteeringSourceUser` that does not exist anywhere in the repo. This gap predates the commit for new-turn steers but is extended to mid-round steers here, with parity asserted but not established.

- **Fix**: Extend `liveAskQuestions` to treat a user-sourced `steering` item as a boundary (with updated tests), or correct the comments to state the client boundary is still only `userMessage` and parity is a known follow-up.

**`SteeringCarrier` persisted in Go transcript schema but not projected through AppWire**

`agent/schema/turn.go:144-160`

`SteeringCarrier` is persisted only in the Go transcript schema and is not projected through the wire/client model. A failed carrier produces an item-less failed turn that the client cannot identify as resolving the ask, leaving the ask dock inconsistent after reload.

- **Fix**: Propagate the carrier-resolution signal through the wire/client model, or otherwise make item-less carrier failures an explicit client-side resolution boundary.

### Low

**`TestAskUser_RestoreResolvesAcrossInterrupt` does not exercise the new `SteeringKindInterrupted` clause**

`agent/session_ask_test.go:1477-1560` (with `agent/session_tools_ask.go:302`)

The interrupt is produced by a second `ProcessInput` ("actually, hold on"), which appends a `TurnUserInput` turn before the model call is cancelled. The backward scan hits that `TurnUserInput` first and returns `SessionIdle` via the pre-existing `TurnUserInput` case; the test passes identically if the new `SteeringKindInterrupted` condition is deleted. The clause is only decisive when the interrupted turn was a non-user entry (e.g. a notification/goal/steering-carrier wake after an ask ack) — the case where, without it, restore would scan past the interrupt marker and re-derive a pending ask from earlier `ask_user` results.

- **Fix**: Add a case that reaches the interrupt marker without an intervening `TurnUserInput` (e.g. drive a notification-entry round to an ask ack, then cancel that turn) and assert the restore yields `SessionIdle` with empty `askPending`.
