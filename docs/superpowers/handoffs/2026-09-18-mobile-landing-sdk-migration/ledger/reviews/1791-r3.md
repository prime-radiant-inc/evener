## roborev: Combined Review (`6552236`)

**Verdict:** Unreadable-draft recovery is well-built at the store layer but the mobile discard button can silently no-op while offline, and two discard paths race on record identity.

---

## High

### Offline discard silently does nothing when the model is retained after disconnect
`mobile-native/src/KeybindingPreferencesScreen.tsx:185-188` (guard at `:110`)

All four reviewers flagged this. After a connection drop the client object is *not* disposed, so `preferences.model` stays non-null while `preferences.connected === false`. The handler takes the model branch and routes the discard through `run()`, whose guard at `:110` (`if (!scope.connected || !model || ...) return;`) returns immediately. The store-free fallback (`discardUnreadableKeybindingsDraft()`) is never reached, so tapping Discard does nothing — no error, no clearing — and the user is locked out of editing shortcuts until reconnect. This defeats the advertised store-free recovery that `assertDiscardable` deliberately permits offline.

**Fix:** Branch on connectivity — e.g. `if (model && preferences.connected) { run(() => model.discardKeybindingsDraft()); return; }` and fall through to the store-free path when offline — or bypass `run` entirely and call `model.discardKeybindingsDraft()` directly with scoped error handling.

*(Three reviewers rated this Medium; one rated High. Placed at High because it fully breaks a user-facing recovery feature.)*

---

## Medium

### Delete-without-identity race can remove a newer valid checkpoint
`appwire-client/typescript/draftCheckpointPort.ts:41-47`, `mobile-native/src/NativePreferencesProvider.tsx:129`

`discardStoredDraft` reloads the current value and then deletes it without retaining the original record's identity. If a concurrent writer replaced the unreadable record with a valid checkpoint between display and discard, the reload fetches that newer draft and deletes it as if it were the unreadable one. The live-store path explicitly refuses and reclassifies in this same race, but the stateless fallback path does not.

**Fix:** Retain and compare against the originally classified raw identity, or refuse the discard when the current value decodes as a valid checkpoint. Return a distinguishable removed/absent/refused result so the UI can preserve replacement data.

### Post-discard snapshot/error state not fully refreshed
`mobile-native/src/NativePreferencesProvider.tsx:134,141`

Two related gaps in the no-model discard path:
- The snapshot update is gated on `if (removed)`. When `discardStoredDraft` returns `false` (nothing stored, or a concurrent writer already replaced the record), the stale snapshot keeps `draftUnreadable: true`, so the prompt and the now-dead button persist until the next reconnect rebuilds state.
- A successful discard clears only `draftUnreadable` and `storageUnavailable`; the projected `error` still holds the draft-restore failure, and the screen neither clears its local error before the fallback nor handles a `false`/`null` return, leaving stale or missing feedback.

**Fix:** Update the snapshot whenever the discard call completes without throwing — not only when `removed` is true — and clear the draft-specific error in the screen before the operation, reporting refused/absent outcomes distinctly while preserving any real hub error.

## Low

### Stored JSON `null` coalesces to "no record" and is never recoverable
`mobile-native/src/NativePreferencesProvider.tsx:42-48`, `mobile-native/src/nativePreferenceDrafts.ts:47`

A stored JSON `null` parses to `null` and coalesces to "no record," so it never becomes `draftUnreadable` and cannot be discarded through the recovery path.

**Fix:** Distinguish an absent key from a stored JSON `null` using a presence sentinel or a raw-value-preserving backend API.

### Fallback action disabled by stale `loading` state
`mobile-native/src/KeybindingPreferencesScreen.tsx:184`

The fallback is gated on `domain.loading`. If the model is disposed while a refresh is in flight, the retained snapshot can keep `loading: true` indefinitely, permanently disabling a storage-only operation that `assertDiscardable` intentionally permits during a read.

**Fix:** Do not gate this local discard on stale hub loading, or clear transient `loading` when the model goes away (and in the successful no-model snapshot update).

---

**Summary:** The change adds shared checkpoint persistence, atomic compare-and-swap settlement, and unreadable-draft recovery across the SDK and native preferences flows. The store-level logic (settle/adoption, uncertain-write recovery, discard re-classification, write fencing) is coherent and well-tested. The actionable issues are concentrated in the mobile discard wiring and the stateless delete path.
