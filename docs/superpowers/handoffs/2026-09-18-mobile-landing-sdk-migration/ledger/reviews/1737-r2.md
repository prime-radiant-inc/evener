## roborev: Combined Review (`10beda5`)

## PR Review: Unified Ask Resolution & Native Projections

**Verdict:** Three substantive issues need fixing — two restore/live state mismatches and a broken package qualification gate — plus an unwired native helper layer.

---

### High

**Carrier skill-selection failure lets restore resurrect a cleared ask**
- `agent/session_queue.go:1205`, `agent/session_lifecycle.go:2750-2761`, `agent/session_tools_ask.go:305-309`
- A steering-carrier turn is accepted as `EntryUserInput`, so `processOneInput` clears `askPending` unconditionally at entry (`session_lifecycle.go:1804`). When the steer's skill selection fails, `injectDrainedSteering` records an *untagged* `TurnFailure` via `recordFailedSteeringSelection` (`session_queue.go:1297-1302`, builds `TurnFailureInfo{Message: ...}` with `SteeringCarrier` false), and `carrierSteerFailed` returns `errSteeringCarrierStoodDown` with no tagged marker. Live `askPending` is `0`, but restore skips the untagged failure, reaches the earlier `ask_user` ack, and re-derives the ask as pending — re-arming entry gate, goal engine, and Compact guard. The series' `SteeringCarrier` tag only covers `carrierSteerUndelivered`.
- **Fix:** Tag the `TurnFailure` as `SteeringCarrier` when `recordFailedSteeringSelection` is invoked from a carrier turn, or have `carrierSteerFailed` persist a tagged boundary before standing down. Add an integration test driving a bad-skill steer through the real carrier `ProcessInput` path with a pending ask, asserting live and restored `askPending` agree. *(Reported by Reviews 3 & 4.)*

**`askedThisRound` capture before steering drain creates live/restore mismatch and undispatched steer**
- `agent/session_lifecycle.go:2227`
- Capturing `askedThisRound` before `injectPostToolSteering` combines with the new mid-round clear: a user steer resolves the ask, but `deliverIfCommunicated` still treats the round as asking, ends it in `SessionAwaiting`, and the incorporated steer is no longer runnable for a follow-up model request. Restore then sees the user steering boundary and derives `SessionIdle` — creating both a live/restore state mismatch and a potentially undispatched steer.
- **Fix:** Recompute the ask delta after the steering drain so a resolving steer lets the current round continue, or separate "the round posted an ask" from "an ask is still pending" and explicitly dispatch the incorporated steer. Test that a post-tool user steer reaches another model request and that restored state matches live state. *(Reported by Review 4.)*

### Medium

**`askPending` gate breaks package qualification and hides questions for old daemons**
- `appwire-client/typescript/deriveAskQuestions.ts:106`, `appwire-client/typescript/scripts/qualify-package.mjs:62,66,69`
- The new gate `if (!model.askPending) return [];` treats `undefined` as authoritative. Two consequences:
  - **Gate break (guaranteed):** The qualifier's hand-written smoke calls pass `{ turns: [{ items: [askItem] }] }`, so `model.askPending` is `undefined` and the early return yields `[]`. `liveAskQuestions(...)[0].key` (line 62) throws `TypeError: Cannot read properties of undefined`; assertions on lines 66–69 also fail. `make test-api-package` (part of `make merge-approval-gate` and CI) was not updated.
  - **Old-daemon regression:** `EvenerThread.askPending` is optional for old daemons, and hydration defaults absence to `false`, so reconnecting to an older daemon with an unanswered `ask_user` call silently hides the question — where the previous transcript-based derivation still displayed it.
- **Fix:** Update the three qualifier calls to pass `askPending: true` (matching `deriveAskQuestions.test.ts`'s `model()` default), and either make the gate `if (model.askPending === false) return [];` or preserve whether `askPending` was present on the wire and fall back to transcript derivation when unknown. *(Reported by Reviews 1 & 3.)*

**Native truncation/cap helpers not wired into the production store**
- `mobile/src/conversation/project.ts:942`, `mobile/src/state/conversation.ts:481`
- The new "centralized" truncation and cap helpers (including the orphan-attachment cap and broader row bounds) are not used by the production store; `conversation.ts` still has parallel implementations including the older narrow `truncateItem` and a simple `capItems`. Consequently the new bounds do not affect the actual store path. `capItems` (`project.ts:1103`) has no consumer anywhere in the tree and is dead code duplicating the store's private `capItems`.
- **Fix:** Move the helpers to a shared module, update the store to use them, delete the duplicate state implementations, and cover the actual store path. *(Reported by Reviews 3 & 4.)*

### Low

**`boundQuestion` comment contradicts code; truncated labels could pass client validation**
- `mobile/src/conversation/project.ts:1020-1027`, `mobile-native/src/questionAnswers.ts:11-17`
- The contract comment says the composed answer "does NOT read either bounded copy — it asks the model for the canonical refs (`pendingQuestions`, through `liveAsksFor`)." But `pendingQuestions` actually reads `conversation.items` and returns each `kind === "question"` row's `questions` — i.e. exactly the projection that `boundQuestion` would cut (`label`/`detail` are truncated). `composeQuestionAnswers` then validates selections against those same truncated labels (`question.options.some(o => o.label === label)`), so a truncated label could pass client validation and be sent to the server as a choice the agent never offered. Today this is latent because `conversation.ts`'s `truncateItem` does not touch `question` rows; it becomes wrong the moment the stated migration swaps in `project.ts`'s `truncateItem`.
- **Fix:** Either have `pendingQuestions` derive from canonical refs (`liveAsksFor`/`liveAskQuestions`) before bounding is applied to rows, or correct the comment and ensure question rows are never bounded. *(Reported by Review 3.)*
