## roborev: Combined Review (`90477a0`)

## Verdict: Unifies pending-ask resolution across restore and client projections, but leaves carrier-failure restoration, live/restore state divergence, and several mobile wiring gaps that should be addressed before merge.

### High

- **Steering-carrier skill-selection failure resurrects a resolved ask on restore**
  - `agent/session_queue.go:1302`, `agent/session_tools_ask.go:301-314`, `agent/session_lifecycle.go:2750-2761`
  - A claimed steering carrier whose skill selection fails still clears `askPending` at turn entry, but `recordFailedSteeringSelection` persists an ordinary `TurnFailure` without the `SteeringCarrier` marker. Restore skips that unmarked failure and reconstructs the previously pending `ask_user`, so a restart resurrects a question the live session already resolved.
  - **Fix:** Pass carrier context into steering consumption/failure recording and set `Error.SteeringCarrier` only for carrier-originated selection failures (a shared resolving boundary), then add a restore test through the real carrier path.

### Medium

- **Live and restore derive different `SessionState` after a mid-round steer resolves an ask posted in that round**
  - `agent/session_lifecycle.go:2233`, `agent/session_tools_ask.go:306`, `session_tool_round.go:523-545`
  - `askedThisRound` is captured *before* `injectPostToolSteering` drains the steer, so a round that posts `ask_user` and has a user steer drained in its post-tool window ends live as `SessionAwaiting`, while restore hits the new `TurnSteering` branch and returns `SessionIdle` (attention-status-model v5 tier flip). `askPending` is empty on both sides, but the status diverges.
  - `TestAskUser_InjectPostToolSteeringClearsPendingAskForAnAcceptedUserSteer` exercises exactly this run but never asserts `State()`, so the divergence is unpinned.
  - **Fix:** Align the two derivations—either compute `askedThisRound` after a resolving steer clears the ask, or have restore treat a user steer immediately following an ask in the same round as still awaiting—and add a state assertion to the steer test.

- **Live warnings differ in type, styling, and identity from the same warning after re-projection**
  - `mobile/src/conversation/project.ts:559-591`, `mobile/src/state/conversation.ts:2813-2830`
  - The canonical projector renders warnings as `notice` items, but the live store still appends a `failure` row, so live warnings look different from the re-projected version of the same warning.
  - **Fix:** Route live warning rows through the same warning projection as hydrated models.

- **Stale question rows remain in `conversation.items` after `askPending` is cleared**
  - `mobile/src/state/conversation.ts:2845`
  - The store's default notification path only publishes the updated model; `evener/steering/injected` and `thread/status/changed` can clear `askPending`, but the previously projected question row stays until an unrelated rehydrate.
  - **Fix:** Reproject rows from the updated model (or request a coalesced rehydrate) when steering or `askPending` changes affect questions, and add a store-level integration test for interrupt/user-steer resolution.

- **Shared truncation and orphan-aware cap logic is not wired into the production mobile store**
  - `mobile/src/conversation/project.ts:1050`, `mobile/src/state/conversation.ts`
  - The store still uses its private, narrower `truncateItem` and simple `capItems`, so question/failure/notice text and orphaned attachments aren't actually protected by the new shared code.
  - **Fix:** Wire the store to the shared `truncateItem`, `capItems`, and identity helpers, then remove the duplicated private implementations.

### Low

- **Persisted question-draft signature changed shape with no migration, silently discarding saved drafts**
  - `mobile-native/src/questionAnswers.ts:78`, `draftRepository.ts:288-304`, `draftRepository.ts:93-99`
  - `questionsIdentity` now emits a `{key, digest}` array, but old rows hold full question objects, so the per-key comparison never equals and `readQuestions` returns `{}`. A user with partially answered questions who updates the app loses those draft selections (transcript unaffected).
  - **Fix:** Key the comparison on the question `key` alone, version/invalidate the `question_drafts` table on this shape change, or normalize stored rows to the new shape once on read.

- **`turnResolvesAskBoundary`'s `decisive` return can never be true with `resolves == false`, making callers' `continue` branches unreachable**
  - `agent/session_tools_ask.go:301-315`, `:366-372`, `:430-436`
  - The function only returns `(true, true)` or `(false, false)`, so both callers' `continue` paths are dead. The misleading two-value contract invites a future "not decisive but resolving" case that would silently skip the `continue`.
  - **Fix:** Return a single `bool` (resolves) and let callers `continue` on `false`, or document/enforce the invariant with a tri-state if a third case is intended.

- **Warning with `title`/`hint` but no message stores the entire raw frame as `item.text`**
  - `appwire-client/typescript/reducer.ts:1689`
  - Renderers then show the title/hint twice and expose the routing envelope (`threadId`, `ref`) in the body.
  - **Fix:** Use the raw-frame fallback only when message, title, and hint are all blank; otherwise use the effective message or an empty body and let structured title/hint render normally.

- **Memoization test asserts on wall-clock time, making it host-dependent**
  - `mobile-native/src/questionAnswers.test.ts:400-423`
  - The test computes `performance.now()` deltas and asserts `repeatsMs < max(firstCallMs * 10, 5)`, which can flake under scheduler pauses or a loaded CI runner (AGENTS.md requires deterministic default tests). The property under test—a memo hit performs no rehash—is better asserted by counting `questionHash`/`JSON.stringify` invocations with a spy.
  - **Fix:** Test memoization through an injected/counted hash function, or drop the timing assertion and keep deterministic correctness tests.
