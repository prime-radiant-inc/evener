## roborev: Combined Review (`93edcf7`)

## Verdict: One high-severity issue with a mid-round steer silently never reaching the model, plus a carrier-failure restore regression and a broken package qualification script.

## High

- **User steer consumed mid-round never reaches the model**
  `agent/session_lifecycle.go:2233` (capture) vs `agent/session_lifecycle.go:2245` (`injectPostToolSteering`)

  Capturing `askedThisRound` before `injectPostToolSteering` causes an accepted user steer queued during an `ask_user` round to be consumed and marked incorporated, then the round immediately ends at the ask boundary. No later carrier can claim the steer, so it reaches the transcript but is never sent to the model — the user's input is silently parked until another external input. The new test only asserts the steering turn and `askPending`; it does not verify a second model request reads the steer. The move also breaks the invariant documented at `agent/session_lifecycle.go:1377-1397` (`SessionAwaiting` iff `askPendingCount() > 0`): after the move `SessionAwaiting` is set with `askPendingCount() == 0`, so the `if !awaiting` guards wrongly skip the follow-up pop and steering-carrier claim. Before the move, `askedThisRound` was computed after the drain (false), so the loop continued to a second round that read the injected steer — matching `injectPostToolSteering`'s own comment that steering is injected "before the next model call" (`agent/session_tool_round.go:445-455`).
  **Fix**: Capture `askedThisRound` after the drain (the resolving steer legitimately cancels the "asked" signal), or skip draining a steer in a round whose own `ask_user` ends the turn and leave it for the carrier rung. Either way, ensure a user steer consumed mid-round is followed by a model request that reads it, and add an observable test asserting the steer reaches the next model request.

## Medium

- **Untagged `TurnFailure` from failed steering-carrier selection resurrects a cleared `askPending` on restore**
  `agent/session_lifecycle.go:2750-2761`, `agent/session_queue.go:1297-1303`, `agent/session_tools_ask.go` (`turnResolvesAskBoundary`)

  `processOneInput` clears `s.askPending` at entry for every accepted turn (`session_lifecycle.go:1803`), including a steering-carrier turn. If that carrier's drained steer fails skill preparation, `recordFailedSteeringSelection` appends an untagged `TurnFailure`, so live ends `SessionIdle` with no pending ask. On restore, that untagged failure is skipped as non-decisive and the earlier `ask_user` `TurnToolResults` is found, re-deriving a pending ask — a reload reopens a question the live session had closed. The new `TestAskUser_RestoreDoesNotResolveAcrossAnUnrelatedTurnFailure` drives `consumeSteeringMessage` directly and asserts the live count stays 1, which bypasses the `processOneInput` entry clear and therefore doesn't exercise (or reveal) the real production state.
  **Fix**: Thread carrier-consumption context into `recordFailedSteeringSelection` and tag only carrier-produced selection failures with `SteeringCarrier` (keeping mid-round selection failures unmarked), or persist/restore the actual cleared flag instead of re-deriving it from an ambiguous turn shape. Add a restore test driven through a real user steering carrier.

- **New `askPending` gate on `liveAskQuestions` breaks the package qualification script**
  `appwire-client/typescript/deriveAskQuestions.ts:106` (new `if (!model.askPending) return [];`) combined with `appwire-client/typescript/scripts/qualify-package.mjs:62,66,69`

  The smoke calls construct a model with no `askPending` key, e.g. `client.liveAskQuestions({ turns: [{ items: [askItem] }] })[0].key`. With the gate, `model.askPending` is `undefined`, so the function returns `[]`; `[][0]` is `undefined` and `.key` throws `TypeError`. This is the same file `npm run qualification` executes, so `make test-api-package` fails outright. The change updated the vitest helpers (`askDock.test.ts`, `deriveAskQuestions.test.ts`) but missed this hand-written consumer smoke test.
  **Fix**: Pass `askPending: true` in the three `liveAskQuestions` calls (and re-check the dependent `reconcileBatches`/`createAskDockStore` assertions).

## Low

- **`turnResolvesAskBoundary`'s `decisive` result is never true while `resolves` is false**
  `agent/session_tools_ask.go:289-303`

  The function only ever returns `(true, true)` or `(false, false)`, so both callers' `if resolves { return ... } continue` branches (`:357-362`, `:432-437`) are dead, and the doc's framing of a "decisive but non-resolving" case is misleading. Either drop the second return value or document that it is currently always equal to the first.

- **Dangling test reference in a new comment**
  `agent/session_ask_test.go:1760-1762`

  The comment cites `TestCommunicate_ClientSteeringDuringToolExecutionRunsBeforeTheNextRequest` as establishing the ordering, but no such test exists anywhere in the repo. Point at the real coverage or drop the claim.

- **New comments encode review-round history and brittle line references**
  `agent/session_tools_ask.go:272`

  Several new comments encode review-round history and source-line references rather than the durable invariant, contrary to the repository's WHAT/WHY comment rule. Rewrite them around the persisted semantic boundary without round numbers, temporal "this round" language, or line-number references.
