## roborev: Combined Review (`c179f70`)

## Verdict: Series extracts reusable draft-checkpoint port and hardens write settlement, but leaves several checkpoint-race and validation gaps.

### Critical
None.

### High

- **`appwire-client/typescript/keybindingsStore.ts:1198`** — Draft settlement ignores compare-and-remove refusals. If another writer replaces the checkpoint while a PATCH, authoritative refresh, or discard is pending, successful-save cleanup can hide the replacement by publishing no draft, while uncertain/conflict/newer-external paths can overwrite it through unconditional `persistDraft`. Make `removeIf` and `discardClassified` report whether they acted, add an atomic replace operation for settled rewrites, and reload/adopt the current checkpoint on refusal. Cover replacement races during successful saves, uncertain refreshes, known rejections, and discards.

- **`appwire-client/typescript/keybindingsStore.ts:1071`** — `patchOverrides` can start while `saveDraft` is in flight because its gate omits `saving` and `writeUncertain`. It claims the shared write token, making the checkpointed reply appear superseded, but never clears `saving`, leaving the editor permanently stuck mid-write. Reject `patchOverrides` while `state.saving || state.writeUncertain` before claiming the write token, and test a direct write attempted during a checkpointed save.

### Medium

- **`appwire-client/typescript/draftCheckpointPort.ts:85-87, 114-117`** — Loading an empty store clears `hasLastClassified`, so `discardClassified()` performs a fresh load. If another writer creates a draft afterwards, discard can delete that newer draft. Track an empty load as a classified absence and make discard a no-op when the classified value was empty.

- **`appwire-client/typescript/draftCheckpointPort.ts:96`** — `save()` updates `lastClassified` but does not update the `rawFrom` entry for the same checkpoint object previously returned by `load()`. A later `removeIf()` on that reference passes the pre-save raw bytes to a byte-aware port, which can refuse to remove the record `save()` just wrote. Update `rawFrom` for the input checkpoint after a successful save, and test load → same-reference save → `removeIf()` with a raw record containing extra fields.

### Low

- **`appwire-client/typescript/keybindingsStore.ts:1244-1258`** — The post-rename rejection path accepts any structurally valid `applied` payload, unlike normal replies, which reject `loadError` or revisions below the requested revision. A malformed or version-skewed error can be reported as a successful settled save. Apply the same semantic validation as the normal response path before settling; otherwise preserve the uncertain checkpoint.

- **`appwire-client/typescript/keybindingsStore.ts:1180-1182`** — The `settleWrite` JSDoc says the post-rename caller deliberately omits `draftConflict` so `applyHubOverrides`'s `staleDraft` check decides it, while the confirmed-reply caller forces it. In reality, both callers force `draftConflict: newerExternal` — the post-rename call at ~1255-1259 passes it, and the inline comment explains this is required so `staleDraft` doesn't misread the write's own confirmed revision as a conflict (asserted by the "post-rename durable failure during saveDraft" test). If a future maintainer follows the stale doc and removes `draftConflict` from the post-rename call, `staleDraft(state.draft, applied.revision)` will compute `true` for the ordinary success case, reintroducing the bug this series fixed. Update the doc to state both callers force `draftConflict: newerExternal` and drop the "post-rename caller deliberately omits" clause.

### Notes

The extraction of shared draft and generation-fencing infrastructure, the generic `draftCheckpointPort`/`draftStorage`, and the settle/fence hardening are otherwise correct and well-tested. Reviewers confirmed byte-identity behavior, fence semantics, module reachability, and removal of old importers.
