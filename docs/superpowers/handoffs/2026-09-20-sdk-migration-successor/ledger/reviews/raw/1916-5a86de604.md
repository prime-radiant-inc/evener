## Summary

The series adds the write half of the phone's `MutationOutboxStorage` port (`mobile-native/src/mutationOutboxStorage.ts`) over a synchronous expo-sqlite-shaped database interface, plus a comprehensive test file that mirrors the web IndexedDB oracle's write-side contracts using `node:sqlite`.

The final implementation:
- Persists records into three tables (`mutation_outbox`, `mutation_optimistic`, `mutation_recovery`) whose membership encodes state, with a `mutation_sequence` table for per-target sequencing.
- Allocates the intent sequence with a single atomic `INSERT … ON CONFLICT … DO UPDATE … RETURNING` instead of a separate read-then-write, closing the cross-handle race (the round-4 failing-first test exercises this via a deterministic reentrant call on one connection).
- Wraps every compound operation in a `SAVEPOINT`/`ROLLBACK TO`/`RELEASE` matching `draftRepository.ts`, so a duplicate id, a failed handoff, or a failed transfer rolls the whole operation back.
- Encodes an absent `optimisticDisplay` as JSON `null` (satisfying the `NOT NULL` column) so a later receipt can still retire the record.
- Uses `expo-crypto`'s synchronous `randomUUID`/`getRandomValues` through `createSecureUUID` rather than assuming a Web Crypto global.

I verified the signatures against the `MutationOutboxStorage` port in `appwire-client/typescript/state/mutation/outbox.ts`, the record types in `records.ts`, the IndexedDB oracle's semantics, the dependency manifests (`expo-crypto ~57.0.2`, `expo-sqlite ~57.0.2`), the vitest/tsconfig resolution for `@evener/appwire-client/state/mutation`, and the savepoint idiom already used in `draftRepository.ts`. The query parameters are all bound, table/transaction names are constants, and `fromRow`'s parse paths are safe for the declared `NOT NULL` columns. The omitted shared-notes recovery-superseding behavior is a documented, deliberate scope reduction, and `mobile-native` has no `notes/human/set` call sites, so it is not a live defect.
