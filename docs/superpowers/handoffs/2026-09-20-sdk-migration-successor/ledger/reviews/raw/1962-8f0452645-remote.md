## Summary

This series completes the "#1806 piece 2" restore-side ask-boundary work. The live session already resolves a pending `ask_user` question on several boundaries (a plain user reply, an accepted user steer, an interrupt, a steering-carrier failure). The series makes the restore scan (`deriveRestoredState` / `deriveRestoredAskPending`) agree with those live boundaries by:

- factoring the boundary into one shared predicate (`turnResolvesAskBoundary`) and one provenance helper (`steeringAnswersAsk` / `steeringOriginBoundary`);
- reading durable client-mutation-journal provenance so a kindless legacy human-note steer is not misread as an answering steer, and scoping that provenance to the child's own turns for forked/compacted histories;
- accumulating pending questions across non-resolving rounds (matching `ask_user`'s live append semantics) using `roundEntryResolvesAskBoundary` to skip bookkeeping turns;
- settling live terminal/failure boundaries (`finishProcessingAtFailureBoundary`, `awaitingOrHasPendingAsk`) to the same awaiting-vs-idle state restore derives, so `WireState` doesn't report a session with a live question as idle.

The implementation is internally consistent: the shared `turnResolvesAskBoundary` guarantees `deriveRestoredState` and `deriveRestoredAskPending` cannot disagree on the decisive turn, and I could not construct a history where one returns idle while the other returns a non-empty pending set. The refactor of `escapeHistoryWithSessionProvenance` to `steeringOriginBoundary` is behavior-preserving for the `inherited <= 0` and `inherited >= len` cases.

**Low — `TestAskUser_RestoreUsesJournalProvenanceForAKindlessLegacyHumanNoteTurn` does not actually exercise journal provenance**

`agent/session_ask_test.go:2052-2057`. The test sets up a kindless, user-sourced legacy note whose journal record is `{method: clientMutationMethodNotesHumanSet}`, then asserts the ask stays pending. But the turn's text is `"human updated their whiteboard: watch the ingest path"`, which already matches the write-path prefix that `steeringOrigin.isHumanNoteSteer` falls back to when *both* `kind` and `method` are empty. Consequently the test passes even if `origins` is ignored entirely (e.g. pass `nil`): `steeringOriginForTurn` returns `{kind:""}`, `isHumanNoteSteer` reads the prefix, and the note is still classified as non-resolving.

What goes wrong if not fixed: the test's stated bug (RoboRev #1907's "`steeringKind()` used directly, so a kindless journal record with no reachable provenance reads as an answering steer") is not pinned. A regression that drops the journal lookup in `turnResolvesAskBoundary`/`steeringOriginForTurn` would only be caught for the text-shape path (covered by the sibling test), not for the journal-provenance path this test claims to cover, so a future edit could silently reclassify a legacy note as an answering steer and resolve an unanswered ask on restore.

Suggested fix: make the provenance load-bearing in the fixture. Use a note text that does *not* begin with `humanNoteSteerPrefix` (e.g. the text as it would appear if the prefix were added only at model-render time), so the only evidence left is the journal record's `notes/human/set` method; with `origins` supplied the ask stays pending, and with `origins` nil the classification flips. Alternatively, assert the discriminating pair (`deriveRestoredAskPending` with `origins` vs. with `nil`) in one test.
