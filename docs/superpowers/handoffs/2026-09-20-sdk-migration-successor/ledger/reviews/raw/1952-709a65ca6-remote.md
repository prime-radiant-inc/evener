## Summary

The series introduces a per-screen connection-display policy for the native app so that ready-only screens (Providers, Plugins, Hub Settings) survive a transport flap instead of being replaced by a full-screen wall. `useHubConnection` now exposes a `fatal` flag (protocol-mismatch closes only), a new `connectionDisplay.ts` derives `"none" | "banner" | "wall"` from state + per-screen `everReady` + `fatal`, `ConnectionStatus` is extracted into its own module, and Plugins/Hub Settings keep a last-known client so the list stays mounted during a manual retry's brief client-clear gap. Tests cover the display policy, the `fatal` transitions, and ProviderScreen's banner/wall behavior.

## Findings

**medium** — Plugins and Hub Settings do not refresh their data after a passive reconnect, contradicting the feature's own contract and regressing the old remount behavior.

`mobile-native/src/PluginsScreen.tsx:123-129` (`<Plugins>` mounts its store and calls `fetchPlugins()` only when `model` changes, i.e. when the `client` identity changes) and `mobile-native/src/HubSettingsScreen.tsx:160-164` (`useFocusEffect` calls `refresh()`/`reconcileAfterReconnect()` with deps `[model, upgrade]`, both keyed on `client` identity).

Before this change, a passive flap set `state` to `"reconnecting"`, the screen returned the wall, and the child unmounted; the reconnect remounted it with a fresh model/effect and re-read the hub. The new banner branch (`PluginsScreen.tsx:71`, `HubSettingsScreen.tsx:50`) keeps the child mounted for the whole `reconnecting → ready` transition, and on a passive reconnect the `AppwireClient` instance does not change, so neither effect re-runs. Unlike the credential store (`ProvidersScreen.tsx:88-90`, which does call `connectionChanged` and re-reads on ready), the native Plugins store never receives `connectionChanged` — `grep` shows only `credentialStore.ts`/tests call it — and `createHubOverviewStore` is an explicit fetch-once cache with no push invalidation. Concrete harm: after a network flap the plugin list and hub settings show pre-flap data indefinitely, and the “upgrade may have been installed, reconnect and verify” flow no longer auto-verifies — `reconcileAfterReconnect` is only reachable via refocus or the manual “Refresh running version” button, whereas the previous remount performed it automatically. This directly contradicts `connectionDisplay.ts`’s doc (“auto-refreshing once ready again through the store's own reconnect recovery”).

Suggested fix: drive the stores from the connection state rather than mount identity — call `model.connectionChanged(renderClient, state)` for the plugins store (its lifecycle already re-reads an established list when the connection is ready again), and add an effect keyed on the transition to `"ready"` in `HubSettings` that calls `model.getState().refresh()` and `upgrade.reconcileAfterReconnect()`.
