The series makes a marketplace removal that unregisters the marketplace but fails to delete its clone a typed, applied-with-litter outcome instead of an ordinary failure. It adds the `ErrMarketplaceUnregisteredCloneRemains` sentinel and `ErrorMarketplaceUnregisteredCloneRemains` WireError code/data, reorders `Manager.RemoveMarketplace` so the metadata save lands before the clone is removed (a save failure leaves the clone untouched; a clone failure after the save is reported as litter), classifies the outcome at the hub (with `Applied` carrying the fresh list, or `AppliedUnavailable`) and at the CLI, and adds TUI reconciliation: apply `Applied` directly when present, otherwise fence the removal and fetch a fresh list. ## Issues found

**Severity: medium** — `cmd/evener-tui/hub_update_config.go:517-528`

When the reconciliation read itself fails, the removal fence is never released, permanently blocking every subsequent marketplace removal until the TUI restarts.

In `handleMarketplaceMutateResult`, the `marketplaceCloneRemainsUnavailable` branch sets `marketplaceReconcilePending = true` (keeping `marketplaceRemovePending`) and issues `CmdMarketplaceReconcileList` exactly once. If that reconcile list comes back with `msg.Err != nil` (the same store read failure persisting, the 5s `pluginsQuickTimeout` elapsing, lock contention, etc.), `handleMarketplaceListResult` has no error branch:

- the generation guard at line 517 does not fire (the generation matches),
- the clear block at line 520 is skipped because `msg.Err != nil`,
- the error is merely forwarded to the panel, with no command returned.

Nothing ever re-issues a reconcile, and any later untagged list (`CmdMarketplaceList` uses generation 0, issued on panel open, the command palette, and plugin-updated notifications) is discarded by the same generation guard, so `marketplaceReconcilePending` never clears. Because `marketplaceRemovePending` is still set, `handleMarketplaceRemove` (line 597) also rejects every new removal, including of unrelated marketplaces. The user is stuck with a stale list and no way to remove anything short of restarting the TUI. There is no test for the reconcile-failure path, which is why this is not caught.

Suggested fix: in `handleMarketplaceListResult`, when the tagged reconcile result carries an error, clear the fence (`marketplaceRemovePending = ""`, `marketplaceReconcilePending = false`) so the user can retry, or increment the generation and re-issue `CmdMarketplaceReconcileList`; alternatively let an untagged successful list settle the fence. Add a test exercising `handleMarketplaceListResult` with `ReconcileGeneration == marketplaceReconcileGeneration` and a non-nil `Err`, asserting the fence is released.
