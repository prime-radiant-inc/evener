## Summary

The commit series hardens the "ask boundary" so that a restored session re-derives an `ask_user` pending set that agrees with what the live session did. The core changes:

- Introduces a single `turnResolvesAskBoundary` predicate (user input, resolving user steer/interrupt, or a `SteeringCarrier`-tagged `TurnFailure`) shared by `deriveRestoredState` and `deriveRestoredAskPending`, replacing the previously separate live predicate `steeringSourceAnswersAsk`.
- Adds `roundEntryResolvesAskBoundary`, which walks back past assistant/tool-result and bookkeeping turns to the round's real entry, so a non-resolving carrier round (a human-note update) no longer has its own generic completion treated as resolving the ask.
- Makes `deriveRestoredAskPending` accumulate `ask_user` questions across non-resolving rounds (oldest-round-first) to match `ask_user`'s live append semantics.
- Threads steering provenance (`steeringOrigins`) and the fork `divergenceTurn` boundary through restore, so a kindless legacy human-note turn is recognized and a child's own journal cannot reclassify an inherited parent turn.
- Adds `finishProcessingAtFailureBoundary` so provider/retry-budget/tool-cap failures preserve a still-pending ask instead of settling `SessionIdle`, and adds `awaitingOrHasPendingAsk` to sample state and the pending set under one lock.

I traced the backward-scan/accumulation logic against the live append order, the divergence scoping (`steeringOriginBoundary`), the fork-provenance cases, the carrier failure tagging, and the multiple call sites of the changed signatures. The refactors preserve prior semantics (including the `escapeHistoryWithSessionProvenance` boundary cases), the accumulation ordering matches live, and the boundary decisions stay consistent between the two derivation functions and the live clears.
