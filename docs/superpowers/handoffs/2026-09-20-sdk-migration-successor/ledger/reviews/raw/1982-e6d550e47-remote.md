## Summary

The series reworks `mergeOlderItemPage` in `appwire-client/typescript/reducer.ts` so older-page turns are coalesced transitively by identity, placed relative to positioned "anchor" fragments and retained runs with a monotonic gap assignment, and so the tool call/result fold (`mergeToolCallsByCallId`) tracks the *source page* of each item's fields. A new `ToolItemMergeContext` records a provenance tree per item at every identity-match edge, and field precedence is applied per field (fresh results → fresh calls → older results → older calls → the call's own field). The accompanying tests exercise transitive coalescing, placement invariants, and field-provenance cases. The implementation matches the stated intent, and I did not find a correctness, security, or regression defect in the new logic.

One testing gap:

---

**Severity: low** — `appwire-client/typescript/reducer.test.ts:2944` and `:2950` (helper `countIdentityReadsForMerge`, ~`:2887`)

Both "linear provenance work" guards are vacuous: `countIdentityReadsForMerge` attaches a counting getter to `id` on the `agentMessage` items, but every code path that reads `id` gates on `callId` first (`reducer.ts:536` `collectToolCandidates` does `if (!item.callId) continue;`, and `isToolCallId(item.id)`/`isToolResultId(...)` are only reached for items with a `callId`). The message items have no `callId`, and with `data: []` the one fresh turn never enters `turnsMatch`/`turnsShareItemIdentity` (the initial `groups` array is empty in `coalesceTurnFragments`). So `reads` is `0` for both `smaller` and `larger` in both tests, and `expect(larger).toBeLessThanOrEqual(smaller * 3 + 16)` (and `... + 40`) is trivially true regardless of what the implementation does.

What goes wrong if not fixed: the tests advertise a guard against reintroducing quadratic identity work in the provenance/collection path, but they never observe a single identity read, so a genuinely quadratic regression would pass CI unnoticed.

Suggested fix: make the counted items actually participate in the matching/collection path — e.g. give the getter-bearing items a `callId` (and ensure a call/result candidate is collected), or spread the items across repeated turns that force `turnsMatch`/`itemIdentityMatches` to compare them — then assert the count grows within the intended bound. Verify the count is non-zero for the smaller input (an explicit `expect(smaller).toBeGreaterThan(0)`) so the guard cannot silently become vacuous again.
