## Summary

The commit fixes a state-leak bug in `transcriptDisplayStore`: when a ready generation was directly replaced while a `get` was still in flight, the old code only cleared `loaded` (and only when it was already true), leaving `hubLoading` stuck at `true` because the superseded reply returns early at `if (!stillMine()) return`. The change detects a replacement (`fence.generation >= 0` before `beginReadyGenerationCore()`), and calls `retirePayload()`, which supersedes any in-flight read/write and resets the in-flight flags (`loaded`, `hubLoading`, `saving`/`writeUncertain`) while preserving the confirmed `hub` map. A regression test confirms the cached defaults survive and `hubLoading` is cleared both immediately after replacement and after the stale read resolves.

I traced the fence/generation helpers (`readyGenerationFence.ts`, `settingsHubGeneration.ts`) and the FakeClient handler semantics; the replacement condition is evaluated before `begin()` bumps the generation (so the first `begin` doesn't retire, and a post-`end()` begin doesn't double-retire), the old read is already fenced by the generation change, and `retirePayload` is idempotent. The write-side fields it resets are currently always-false in this store, so no write state is lost.
