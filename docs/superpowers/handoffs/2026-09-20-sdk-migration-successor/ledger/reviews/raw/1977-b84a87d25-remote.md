## Summary

The series moves pending-`ask_user` resolution from turn entry to a durability point. Previously `processOneInput` unconditionally cleared `s.askPending` when a turn was accepted (except for non-answering steering carriers). Now the entry clear only fires for a claimed steering carrier that answers the ask, and ordinary user input clears only after its `USER_INPUT` turn has been admitted through a synced transcript write. Supporting changes:

- `appendUserInputTurnRefusingPoison` now routes through `appendTurnAfterTranscriptWrite` with `writeTranscriptSyncedLocked`, so a write that records nothing (clean rollback, closed writer, partial line) is returned instead of being warn-and-continued, leaving the ask pending.
- `clearAskPending` is added to the already-incorporated client-mutation path, the recovered-start recovery path (only when the user record was actually written), and after a successful direct/claimed append.
- `MaxTurns` refusal now settles through `finishProcessingAtFailureBoundary` so a surviving pending ask reports `SessionAwaiting`, matching `deriveRestoredState`/`deriveRestoredAskPending`.
- Tests add coverage for MaxTurns, environment-persist, transcript-append, closed-transcript, retained-record adoption, and recovered-start variants, and repair two durability fixtures broken by the synced direct write.

The logic is consistent with restore semantics: every path that clears the ask either durably recorded a resolving `USER_INPUT`/`TurnFailure{SteeringCarrier}` turn or was already incorporated. I found no high-severity correctness, security, or data-loss issue.

**Severity: low** — `agent/session_lifecycle.go:2364` (new error return) via `processInputKindWithProvenance` error tail

`appendUserInputTurnRefusingPoison` now returns the raw error for a clean-rollback write failure (previously it warned and continued). That error propagates out of `acceptUserInputWithSkillSelection`, and the drain loop's generic failure tail calls `s.terminateGoalOnError(processCtx, err)` before `finishProcessingAtFailureBoundary`. `terminateGoalOnError` sets an active goal to `goal.StatusBlocked`, which persists until `/goal clear` or a new `/goal`. So a transient transcript write failure (e.g. disk full with a successful rollback) on an ordinary user input now permanently blocks a running goal, where before the input was processed with only a warning. If blocking the goal on any failed turn is the intended policy this is fine; otherwise, consider classifying a pre-admission transcript-write failure so it does not take the goal-blocking path (only `finishProcessingAtFailureBoundary`), while still preserving the pending ask.
