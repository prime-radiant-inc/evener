## Summary

The series reworks `plugins.Manager.RemoveMarketplace` so the unregister **save lands before** the clone is deleted, fixing the old data-loss window where a failed save left the marketplace registered against an already-deleted clone. A failure removing the clone after the save is now a distinct, typed applied-with-litter outcome (`ErrMarketplaceUnregisteredCloneRemains`), surfaced at the manager, the hub RPC boundary (a `WireError` carrying `ErrorMarketplaceUnregisteredCloneRemains` with `Data.Applied`/`Data.AppliedUnavailable`), and the CLI (nonzero exit with a message that the entry was removed but files remain). Tests cover save-failure (clone preserved), clone-removal failure (typed outcome, no path leak), retry-after-litter (`ErrMarketplaceNotFound`), and lookup-miss non-destructiveness (`""`, `".."`, `"../x"`).

Both reorder and typing look correct: the protection check is still computed from the pre-removal registry, the store lock is held across save + sweep, the sentinel wraps cleanly through `errors.Is`, and no path leaks into any client-facing error. I found two wiring/observability gaps.

---

**Low — the applied-with-litter client contract is not consumed by any UI client**

- `appwire/types.go:3577-3588` documents that "Clients should reconcile from Applied instead of treating the removal as rejected," mirroring `KeybindingsPostRenameData`, which the TS client actually consumes (`appwire-client/typescript/keybindingsStore.ts:1233`).
- But the marketplace clients still treat any rejection as failure and never look at `Data.Applied`:
  - web/native: `appwire-client/typescript/state/extensions/marketplaces.ts:223` → `MarketplaceSheet.tsx:259-276` toasts `Remove marketplace failed: ...`,
  - TUI: `cmd/evener-tui/hub_update_config.go:526-531` sets `m.err` and skips applying the list.
- Concrete harm: on a clone-removal failure the user is told removal failed even though it applied (the message does name the litter, mitigating it). The list itself is eventually corrected by the `evener/marketplace/updated` broadcast/refetch, so the impact is a misleading failure report plus `Applied`/`AppliedUnavailable` being dead payload until a client reads it.
- Suggested fix: mirror `rejectionPayload` for `marketplaceUnregisteredCloneRemains` in the TS store (apply `data.applied` when present, skip the failure toast / mark `appliedUnavailable`) and reconcile similarly in the TUI's `handleMarketplaceMutateResult`; or explicitly document that UI clients deliberately ignore the typed outcome.

---

**Low — the reconcile-list failure is discarded without any server-side trace**

- `cmd/evener-hub/app_plugins.go:294-298`: `if applied, listErr := c.listMarketplaces(ctx); listErr != nil { data.AppliedUnavailable = true }` drops `listErr` entirely. There is no log call, unlike the manager, which logs its raw error to `m.Stderr` before scrubbing (`internal/plugins/marketplaces.go:317`).
- Concrete harm: when a client receives `appliedUnavailable: true`, nothing anywhere records *why* the snapshot could not be built, so an operator cannot distinguish a transient lock timeout from a real store fault. This is the second failure in the same request, and it is exactly the kind of diagnostic the rest of this codebase preserves.
- Suggested fix: log `listErr` to the manager's stderr (or a controller logger) before setting `AppliedUnavailable`.

## Review Findings
**Severity**: Medium
**Location**: `appwire-client/typescript/state/extensions/marketplaces.ts:223`
**Problem**: The shared marketplace client still treats every remove rejection as a failed mutation. The new `marketplaceUnregisteredCloneRemains` WireError is discarded by the generic mutation path, so `Data.Applied` is never applied; web reports “Remove marketplace failed” and native reports `WRITE_FAILED` even though unregistration landed. If the follow-up list read is unavailable or the update notification is missed, the client can retain stale marketplace state and encourage a retry that returns not-found.
**Fix**: Recognize this `evenerErrorInfo` in the shared store, commit `applied` through the same fenced-list path, issue a list refresh when `appliedUnavailable` is true, and expose the leftover-clone condition as a warning rather than a generic failed removal. Add shared-store and web/native host tests.
---
**Severity**: Medium
**Location**: `cmd/evener/plugincmd_test.go:148`
**Problem**: The new CLI test calls the full `runPlugin` startup path without isolating `HOME`, `XDG_CONFIG_HOME`, or `XDG_STATE_HOME`. `EnsureUserConfigDirs` can therefore create real user configuration directories and fail based on ambient legacy `~/.serf` or `~/.evener` data, making the default test nondeterministic and mutating the developer machine.
**Fix**: Point `HOME`, `XDG_CONFIG_HOME`, and `XDG_STATE_HOME` at temporary directories before invoking `runPlugin`, preferably deriving the injected plugin root from the isolated config tree.
---
**Severity**: Low
**Location**: `cmd/evener-hub/app_plugins_test.go:600`
**Problem**: Both permission-based hub tests skip on `os.Getuid() == 0`, but Unix permission checks use the effective UID. A root-effective process is not skipped and the permission setups may not force the intended failures; the reverse case causes an unnecessary skip.
**Fix**: Use `os.Geteuid() == 0` in both tests, matching the CLI test.
---
**Severity**: Low
**Location**: `cmd/evener/plugincmd_test.go:148`
**Problem**: The test claims to verify remaining clone files but never checks that the clone directory survived. A future regression could remove the clone while still returning the typed litter error and still pass the test while giving misleading cleanup instructions.
**Fix**: After `runPlugin`, assert that `clone` still exists as a directory.
## Summary
The change makes marketplace unregistration durable before clone cleanup and propagates a path-scrubbed applied-with-litter outcome through the manager, hub, and CLI.
