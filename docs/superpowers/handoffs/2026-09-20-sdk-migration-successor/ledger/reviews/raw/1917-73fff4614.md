## Summary

The commits add `mobile-native/src/mutationOutboxStorage.ts`, an expo-sqlite implementation of the package's 13-method `MutationOutboxStorage` port (write path from D25d-1a, read path from D25d-1b), plus a 541-line Vitest suite that exercises it against a real `node:sqlite` database. The implementation allocates per-target sequences with a single atomic `INSERT … ON CONFLICT … RETURNING`, wraps compound writes in `SAVEPOINT`/`ROLLBACK TO` transactions, and mirrors the web oracle's per-method contracts (`cmd/evener-hub/frontend/src/stores/mutationOutboxIndexedDB.ts`). The work is not yet wired into any production call site; the tests are the only consumer.

The implementation is careful and the tests correctly falsify the failure modes they claim to (handoff atomicity, sequence-collision rollback, restore rollback, missing Web Crypto global). One behavioral divergence from the oracle remains.

---

**Severity: medium** — `mobile-native/src/mutationOutboxStorage.ts:263` (`settleReceipt`) and `:307` (`settleApplied`)

The web oracle runs a `#discardSupersededNoteRecovery` step inside both settlement transactions (`mutationOutboxIndexedDB.ts:187`, `:231`, `:244-260`). When a `notes/human/set` mutation is authoritatively applied, it deletes any earlier recovery row with the same `targetRef` and a lower `intentSequence` — so a refused note that was later corrected and accepted disappears from the recovery surface. The native adapter omits this entirely; its header comment (lines 14-17) justifies the exclusion by saying note-superseding is something "the port [doesn't] declare," but the port *does* declare `settleReceipt`/`settleApplied`, and this cleanup is part of their settlement semantics, not a separate method.

Concrete harm: once native notes reach the outbox (the dispatcher already routes `notes/human/set` generically at `dispatcher.ts:159`), a user who gets a note rejected on a thread and then successfully writes a newer note will keep seeing the stale "rejected" recovery card for the superseded text — the durable row is never retired. This is latent today only because no mobile-native code path enqueues a human note.

Suggested fix: add a `discardSupersededNoteRecovery(source)` helper that, when `source.method === "notes/human/set"`, deletes `mutation_recovery` rows with the same `target_ref` and `intent_sequence < source.intentSequence`, and call it inside both `settleReceipt` and `settleApplied` before their deletes, matching the oracle. A test seeding a lower-sequence note recovery row and then settling a later accepted note would fail today and pin the behavior.
