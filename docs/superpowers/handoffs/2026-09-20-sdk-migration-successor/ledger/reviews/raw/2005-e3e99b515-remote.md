## Summary

The three commits make the interrupt marker a durability-gated boundary. Previously the outer drain loop resolved a pending `ask_user` (`clearAskPending`), settled `SessionIdle`, emitted the interrupted steering event, and opened the autonomous drain *before* writing the interrupt marker — and the marker was written through the non-durable `recordTurn` path, so it always landed in history. Now the loop first calls `appendSteeringTurnDurablyForOwner`; only on success does it clear the ask, settle `Idle`, emit `EventSteeringInjected(interrupted)`, and allow the drain. On failure the turn falls through to the pending-aware failure boundary (`finishProcessingAtFailureBoundary`), which keeps the ask live and settles `Awaiting`, and `endInputAtTurnFailure` reports `turn_failed`. Two premodel/round-boundary cancellation sites in `processOneInput` no longer settle the boundary themselves, so the outer handler can make that decision. Two tests cover clean rollback (pending preserved, restore agrees) and retained-unsynced adoption.

The core change is coherent and the two new tests exercise observable state across restart. I found one reachable divergence the gating newly enables.

**Severity: medium** — `agent/session_lifecycle.go:1305-1307` (the `clearAskPending()` now gated on `markerAccepted`), interacting with `agent/session_events.go:712` and `agent/session_tools_ask.go:389`.

`turnResolvesAskBoundary` treats **any** `TurnSteering` with `SteeringKindInterrupted` as resolving the ask, and its doc comment states this is valid because "the interrupt branch calls clearAskPending directly." That invariant held before this change because the interrupt branch always cleared the ask. It no longer holds when the durable marker write is rejected.

There is a second, non-durable interrupt marker: when a model call is cancelled after the stream already produced a partial, `handleModelError` calls `settleInterruptedRound`, which persists the salvaged draft and then appends `interruptSalvageSteering` with `SteeringKindInterrupted` via `appendSteeringTurn` → `recordTurn` (`session_events.go:712`). That write is buffered, not synced, and lands in `s.history` unconditionally. If the later durable main marker write fails (the exact failure the new test injects, e.g. an fsync error followed by a successful rollback), the live session keeps `askPending` and settles `Awaiting`, but the transcript still contains the salvage `SteeringKindInterrupted` turn (flushed on `Close`).

Concrete harm: after the interrupted-but-salvaged round with a failed main marker, the live wire state says `Awaiting` with the question pending, while `RestoreSessionFromMeta` scans the salvage marker, returns `SessionIdle`, and rebuilds an empty pending set — the pending question silently disappears on restart, exactly the live/restore divergence the series set out to eliminate. The new failure test cancels before the first model call, so it never produces a salvaged partial and does not catch this.

Suggested fix: make the ask-resolution predicate depend on the admitted marker, not the kind alone — e.g. give the salvage explanation a distinct kind that does not resolve the ask (updating `turnResolvesAskBoundary` accordingly), or record that the durable interrupt marker was the admitted one and only treat that as the boundary. Add a failure test that streams a partial before cancellation so the salvage-marker interaction is covered.
