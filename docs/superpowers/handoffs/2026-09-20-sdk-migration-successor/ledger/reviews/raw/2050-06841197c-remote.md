## Summary

The commit handles the last uncovered outcome in the hub's marketplace-removal path. `RemoveMarketplace` already distinguished "unregistered, but clone cleanup failed" (litter, with a snapshot in `Data.Applied`) from a plain refusal. The remaining case was the success path: `c.mgr.RemoveMarketplace` succeeds (unregister saved, cleanup done), but the subsequent `c.listMarketplaces` read used to build the response fails. Previously that raw error fell through `appserver.WireError`, becoming an `InternalError` that (a) reads as "removal failed" and (b) could carry the absolute plugin-store path from the `*fs.PathError`. The change:

- Adds `ErrorMarketplaceRemoveApplied` and `MarketplaceRemoveAppliedData` (no `Applied` field, `AppliedUnavailable: true`) so a client can tell a no-litter applied removal from a failed one.
- Adds a `hubPluginsReconcileAfterAppliedRemove` test seam, then re-lists into a local; on failure it logs the read error (including any path) to the hub's stderr and returns a typed `CodeInternalError` wire error naming the marketplace.
- Adds `TestPlugins_Marketplace_RemoveSuccessListReadFailureStaysApplied`, which forces a real permission-denied read after the removal applied, asserts the typed discriminant/message hygiene, and verifies the removal stayed applied (retry yields `InvalidParams` not-found).

The implementation matches the stated intent, the read failure is genuine (the re-list goes through `Manager.ListMarketplaces` → `loadMarketplaces`, which returns permission errors rather than swallowing them), the returned error round-trips through `appserver.WireError`'s `errors.As` path, and the `os.Stderr` logging style matches existing hub logging conventions. The deferred client binding is explicitly scoped to follow-up issues, and the new behavior strictly improves on the prior path (no path leak, typed outcome).
