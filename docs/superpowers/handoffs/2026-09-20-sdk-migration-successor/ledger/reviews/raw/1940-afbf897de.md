## Summary

The series reorders `Manager.RemoveMarketplace` so the unregistration save lands **before** the fetched clone is deleted. A failure removing the clone after the save is now reported as a distinct typed sentinel (`ErrMarketplaceUnregisteredCloneRemains` → `ErrorMarketplaceUnregisteredCloneRemains`), with the hub returning a `WireError` whose `Data` carries the post-removal marketplace list (`Applied`) or an `AppliedUnavailable` marker, and the CLI exiting non-zero with a "clone remains on disk" message. It also documents/guards the lookup-miss path (no filesystem mutation on a miss) and updates the tests and the fuzz-coverage expectation. The reorder itself is a genuine correctness improvement (previously a failed save after a successful clone deletion left the registry pointing at a deleted clone), and the scrub tests cover the new paths.

**Severity: medium**

**Location:** `appwire/types.go:3580-3582` (contract) / `cmd/evener-hub/app_plugins.go:287-304` (producer); no consumer added in `appwire-client/typescript/state/extensions/marketplaces.ts:223` or `cmd/evener-tui/internal/launchconfig/plugins_client.go:135-140`.

**Issue:** The new error payload is documented as "Clients should reconcile from Applied instead of treating the removal as rejected", but neither in-repo client consumes it. `hubPluginsController.RemoveMarketplace` returns `CodeInternalError`, and both clients funnel every error into a mutation failure: the frontend's `mutate` rejects and `MarketplaceSheet.handleConfirmRemove` pushes `Remove marketplace failed: …`, and the TUI's `MarketplaceMutateResultMsg` surfaces the error prominently. So on a clone-removal failure the removal *has* applied (and the store broadcast has already refetched the list), yet the user is told the removal failed. Before this diff the litter was a warning-only and the operation returned nil, so this is new contradictory feedback introduced by surfacing the typed outcome.

**Concrete harm:** A user (or any RPC client/automation) sees "Remove marketplace failed" and may retry. The retry then returns `ErrMarketplaceNotFound` (hub `InvalidParams`), compounding the confusion, and any client that aborts on error will not adopt the applied list even though the server state changed.

**Suggested fix:** Have the marketplaces store detect the discriminator like keybindings does (`rejectionPayload` in `keybindingsStore.ts:423`): when `error.evenerErrorInfo === "marketplaceUnregisteredCloneRemains"` and `appliedUnavailable` is false, resolve the mutation using `error.data.applied` (and when unavailable, trigger a refetch instead of rejecting), so the removal is treated as applied. The same handling belongs in the TUI's `CmdMarketplaceRemove` path.

**Location:** `cmd/evener-hub/app_plugins.go:295-299`

**Issue:** When the reconcile read used to build `Applied` fails, the error (`listErr`) is discarded without any logging; only `AppliedUnavailable` is set. The manager logs the clone-removal failure, but not this second failure, which can be an independent fault (the code and its comment explicitly call it "a fresh read that can fail on its own account").

**Concrete harm:** If the reconcile read fails for a reason other than the clone-litter fault (e.g. the registry file became unreadable), an operator has no server-side record of why clients received `AppliedUnavailable`, making the failure hard to diagnose.

**Suggested fix:** Log `listErr` through the same server-side log path used for other scrubbed failures (the manager's `m.stderr()`/hub log) before marking `AppliedUnavailable`, keeping it out of the wire message.
