## Summary

The series completes the native `MutationOutboxSQLite` adapter (D25d-1) by adding the seven read methods the `MutationOutboxStorage` port declares (`listTargetRefs`, `getOutbox`, `getOptimistic`, `listOptimistic`, `getRecovery`, `nextDispatchable`, `restoreProvenAbsent`), with tests mirroring the web `MutationOutboxIndexedDB` oracle, and then makes the class declare `implements MutationOutboxStorage<A>` so the compiler enforces full port conformance. The read semantics match the web oracle: per-target sequence ordering, `nextDispatchable` blocked only by an earlier `blockedUnknown` on the same target, and `restoreProvenAbsent` reopening only `blockedUnknown` records the authoritative snapshot omits, wrapped in the existing savepoint for atomicity. The signatures all match the port, and the tests exercise each read method plus a rollback case for the restore loop.

I found no functional, security, or regression defects in the production code. The two items below are low-severity.

---

**Severity: low** — `mobile-native/src/mutationOutboxStorage.test.ts:506-519`

The `restoreProvenAbsent` test conflates target scoping with the authoritative-ID check, so it does not actually cover the `WHERE target_ref = ?` filter that `restoreProvenAbsent` relies on (`mutationOutboxStorage.ts:375`). `named` is both on another target and present in `authoritativeIds`, so an implementation that ignored `targetRef` entirely (e.g. `this.list(TABLES.outbox)` without the ref) would still produce `[omitted]` for the first call and `[]` for the second (because `omitted` was already reopened to `submitting` by then), and the test would pass. If the target filter ever regressed, a restore for one thread would reopen `blockedUnknown` records belonging to other threads and re-dispatch mutations the authoritative snapshot had already accounted for elsewhere. Suggested fix: add a `blockedUnknown` record on a second target that is *not* in `authoritativeIds`, and assert it stays `blockedUnknown` after `restoreProvenAbsent(TARGET, new Set())`.

---

**Severity: low** — `mobile-native/src/mutationOutboxStorage.ts:396-397`

The inline comment still describes the read half as pending: "shared plumbing D25d-1a's write methods above call (D25d-1b's read methods, stacked on this, reuse insertValues/get/list too)". Now that 1b has landed (and the top-of-file comment was updated to say the port "landed as two stacked PRs"), this line is stale and will mislead a reader into thinking the read methods are not yet present. Suggested fix: reword to describe both halves as landed, matching the file header.
