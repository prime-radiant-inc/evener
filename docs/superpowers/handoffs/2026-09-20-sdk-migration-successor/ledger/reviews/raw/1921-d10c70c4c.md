## Summary

The commit series addresses a flaky-test race tracked as #1879: when a test calls `RetirementController.TryClaim` immediately after a session's first turn, the async session namer goroutine (launched by `launchInitialPromptNamer`, which is not joined before `ProcessInput` returns) may still hold the `"autonomous"` retirement blocker, so the claim intermittently comes back blocked. The fix centralizes a `sendersWG.Wait()` before eligibility claims in a new `retirementClaimAfterFirstTurn` helper used by both `assertRetirementEvidenceEligible` and the raw eligibility check in `TestRetirementSafetyDetachedLifetime`, and adds a `synctest`-based regression (`TestRetirementClaimAfterFirstTurnAwaitsInFlightNamer`) that holds the real namer in flight, proves the claim goroutine stays parked on the wait, then proves it succeeds after release. It also adds the `testing/synctest` import and explanatory comments.

I verified:
- `sendersWG.Wait()` is durably blocking inside a `synctest` bubble because the namer's `Add(1)` happens inside the bubble (`session_namer.go:324`), and `t.Cleanup`/`root.Close` run inside the bubble per `testing/synctest` semantics.
- The regression is deterministic: with the wait removed, `TryClaim` completes and fills the buffered `resultCh`, which `synctest.Wait()` observes and the test fails on; with the wait, the goroutine is durably blocked and the channel stays empty.
- Waiting for all senders (namer and subagent runs) before asserting eligibility is aligned with the existing test idiom (`root.sendersWG.Wait()` already precedes most of these assertions), and parked detached processes are not registered on `sendersWG` (`recordDetachedProcess` only records the receipt), so the detached-lifetime test cannot deadlock on the still-running process.

The final aggregate diff achieves the series' goal, and the new test exercises real observable behavior rather than restating constants.
