## Summary

The series is a preparatory refactor on the offline-draft branch. It (1) extracts the live store's checkpoint→draft-fields projection into a shared, exported `decodeKeybindingDraftFields` in `appwire-client` and reuses it inside `restoreDraft`; (2) replaces the string-tagged `StoredNullRecord`/`UnparseableDraftBytes` sentinels in `nativePreferenceDrafts.ts` with `unique symbol` brands so stored JSON can no longer be mistaken for a marker; (3) adds a `RawStringStorage`-backed `rawStringDraftBackend` plus `readDraftOutcomeWithValue`, and rewrites the native draft tests to use them. Tests cover the new projection, the brand collision cases, key-order-insensitive removal, and single-read classification.

## Issues

**Medium — the tests claim to exercise production's backend, but production still uses its own divergent copy**

`mobile-native/src/nativePreferenceDrafts.test.ts:28` states that `rawStringDraftBackend` "is the same function production calls over it, not a parallel reimplementation," and the doc on the function (`mobile-native/src/nativePreferenceDrafts.ts:138`) says it "lets tests exercise the same code production uses." Neither is true at this commit: `NativePreferencesProvider.tsx` still defines its own module-scope `backend` (lines 30–62) and never imports `rawStringDraftBackend`; `rawStringDraftBackend`'s only callers are the tests.

That matters because the two implementations are not equivalent:

- The tested backend resolves identity with `matchesStoredBytes`/`canonicalJson` (key-order- and whitespace-insensitive), which is what the new test at `nativePreferenceDrafts.test.ts:150` ("removes a stored record … with a different key order") verifies. Production's `matches` is `Storage.getItemSync(key) === JSON.stringify(value)` — byte-exact — so a checkpoint serialized with different key order (e.g. by a different app version) refuses `deleteIf`/`replaceIf` in production despite the suite reporting that scenario covered.
- The tested backend's `get` uses `parseDraftBytes`, returning `UnparseableDraftBytes` for malformed bytes so the store can classify the record `draftUnreadable`. Production's `get` uses a bare `JSON.parse`, which throws instead, so a malformed native record surfaces as `storageUnavailable`, not the unreadable-record state (and its discard recovery).

Concrete harm: the new tests give false confidence that the key-order and malformed-record behavior applies to the shipping backend, and the duplication the shared function was added to eliminate is still present, so the two can drift further unnoticed.

Suggested fix: have `NativePreferencesProvider` build its backend with `rawStringDraftBackend(Storage, () => Crypto.randomUUID())` and delete the inline object, or, if wiring is deferred, correct the test/function comments and add coverage that exercises the actual provider backend.
