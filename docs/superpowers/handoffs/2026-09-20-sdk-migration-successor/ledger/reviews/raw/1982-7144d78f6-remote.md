## Summary

The four commits rework how `mergeOlderItemPage` folds a tool call and its result when an older transcript page is merged into the live model. The old code built a `resultByCallId` map from the *final* merged turns, so a result item that had already absorbed fields from a call could hand those inherited fields (or the wrong freshness) to the fold. The new code:

- tags every pre-merge item with a `"fresh"`/`"older"` source in a `WeakMap`, and records a membership tree at each identity-match edge in `mergePageItems` (`recordMergedToolItem`),
- derives per-callId call/result candidates from that provenance (`collectToolCandidates`/`appendToolItemCandidates`) instead of from final IDs,
- selects each result-bearing field via `preferredToolField` with source priority `fresh.results → fresh.calls → older.results → older.calls → item`,
- preserves traversal order through the membership tree and routes items whose `callId` was omitted through their resolution.

The added tests cover fresh-vs-older precedence, same-source ordering, aliases, omitted-callId routing, and duplicate fragments. The implementation is internally consistent and the traced cases behave as the tests assert.

---

**Medium** — `reducer.ts:572` (`status: field("status")` in `mergeToolCallsByCallId`; helper `preferredToolField` at `reducer.ts:523-533`)

`preferredToolField` resolves every field with a plain "last defined value wins" rule, including `status`. That bypasses `mergePageItem`'s `statusRank` (lines 586-589, 620), which exists precisely so a later, *less settled* duplicate cannot revert a completed item to `inProgress`. Because provenance trees contain the original fragments (not the already-ranked merged item), the ranked status produced by `mergePageItem` is discarded and the newest fragment's raw status is used instead.

Concrete trigger (no older page needed, just `mergeOlderItemPage(model, { data: [] })`):

- `t1`: call `item_tool_1_0`, callId `X`
- `t2`: result `item_tool_result_2_0`, callId `X`, `status: "completed"`
- `t3`: result `item_tool_result_2_0` (same identity), callId `X`, `status: "inProgress"`

`t2`/`t3` coalesce and `mergePageItem` keeps `completed` via `statusRank`. `collectToolCandidates` then stores `fresh.results = [resultCompleted, resultInProgress]`, and `preferredToolField` returns the *last* one, so the folded item ends up with `status: "inProgress"`. The pre-change code read `result.status` off the already-ranked merged result item and produced `completed`.

Harm: a completed tool call can be rendered as still running (spinner instead of settled output/failure state) whenever same-identity fragments arrive with a later, less-settled status — exactly the case the `statusRank` guard was written for. The new tests only exercise status precedence across sources (`fresh` vs `older`), where the source-priority behavior is intentional, so this is uncovered.

Suggested fix: derive `status` with the rank rule within the winning source rather than plain last-wins (e.g., a `preferredToolStatus` that scans the chosen source's candidates and keeps the most-settled status, preserving `failed`/`completed` over `inProgress`), while keeping the existing source ordering so a fresh call's `inProgress` still beats an older result's `completed` as test 2 requires.

---

**Low** — `reducer.test.ts:2944-2955` (`countIdentityReadsForMerge` at 2916-2943)

The two "work linear as history grows" tests are tautological: the instrumented `id` getters are attached only to the `agentMessage` items, but `mergeOlderItemPage` never reads the `id` of a message item (no `callId`, so `mergeToolCallsByCallId`'s `item.callId &&` short-circuits and `collectToolCandidates` continues before touching `id`). With older data `[]` and a single fresh turn, coalescing performs no `turnsMatch` either. Every tool item is a plain object whose `id` is not counted, and the tool count is identical in the `smaller` and `larger` runs (one pair), so both measured values are `0` and both assertions (`0 <= 0 * 3 + 16` / `+ 40`) are true by construction.

Harm: the guards claim to protect the "no quadratic provenance work" property the new comment calls out, but cannot fail regardless of how the merge scales — a future quadratic change to `collectToolCandidates`/`appendToolItemCandidates` would pass and could hang the UI while paging long histories.

Suggested fix: attach the counting getter to the tool items too and scale the number of tool call/result fragments (or distinct calls) with history size, so the measured count actually varies with the work being guarded.
