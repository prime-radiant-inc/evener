## Summary

The series reworks `finishProcessingAtRestoredFailureBoundary` so that an interrupt whose marker write was rejected settles the session from the durable transcript rather than the live in-memory history. It adds a shared `transitionProcessingAtBoundaryLocked`, holds `attentionMu` across the transcript read and state/`askPending` publication, and maps the immutable full-transcript fork divergence into resumed-history coordinates (compaction offset + orphan-repair insertions) exactly as restore does. A new test file covers the durable rollback case, the publication ordering, and the compacted-fork provenance mapping.

The core logic is internally consistent: the divergence remap mirrors `session_init.go`'s restore-time remap byte-for-byte, and the lock nesting (`attentionMu → s.mu`) follows the codebase-wide order.

---

**Medium** — `agent/session_state.go:362-364` (with `agent/session_tools.go:973` and `agent/session.go:2084`)

The boundary is derived from the transcript read at this instant, but the very turn that failed its transcript write is *not* transient: `appendCanceledToolResults` records the round through `appendTurnWithTranscriptMessage` → `recordTurn`, which appends the live turn to `s.history` **and** calls `logPairPersistedLocked` *before* attempting the write. On a clean failure nothing lands on disk, but the pair stays in `s.history` and `persistedAppendLog`. `publishFoldTransaction` re-appends every pair in that log after its compaction markers (`session_compaction.go:240`). So the next compaction makes that tool-results turn durable — including a **non-error** `ask_user` result (`ask_user`'s Exec returns `askUserAckText, nil` before the cancel).

Consequence: the rejected-marker path here settles live to `SessionIdle` with `askPending` empty (what `TestAskUser_RejectedInterruptUsesDurableBoundary` pins), but after any later fold a restart derives from the re-persisted turn: `deriveRestoredState` sees the non-error tool result and returns `SessionAwaiting`, and `deriveRestoredAskPending` sees the decisive ask round and repopulates `askPending`. The live session and a post-fold restart therefore disagree about whether a question is pending — precisely the live/restore divergence the function exists to eliminate. The previous history-based derivation did not have this problem, because `s.history` contained the phantom turn and agreed with the eventual durable state.

Suggested fix: pick one source of truth. Either exclude failed-write pairs from the recovery set (drop the pair from `s.history`/`persistedAppendLog` when the write recorded nothing), so the transcript read here really is the eventual durable state; or keep deriving provenance/state from the history-plus-pair-log view so the boundary does not change after a fold. A test that settles this boundary, then drives a fold, then restores, would pin whichever behavior is chosen.

**Low** — `agent/session_state.go:363`

`deriveRestoredAskPending`'s `isAskRound` return is discarded. Restore (`session_init.go:1432-1434`) emits an `EventWarning` when an ask round was found but none of its questions parsed; this live path silently installs an empty `askPending` while still resting `SessionAwaiting`, so the same condition produces no diagnostic. Impact is observability only (state and pending set match restore), but a caller watching warnings will not learn that the pending-ask holds are inert after this boundary. Suggested fix: capture `isAskRound` and emit the same warning before publishing `s.askPending`.
