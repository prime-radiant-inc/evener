  **Problem**: Replacing an active generation only clears `loaded`; if the previous generation has a pending read, `hubLoading` remains `true`. ## Summary

The series adds a new framework-free, read-side transcript display defaults store (`appwire-client/typescript/transcriptDisplayStore.ts`) to the shared AppWire client, exports it, and hardens the ready-generation fence with an `awaitingFirstPayload` flag. The store reads per-layout confirmed defaults over `evener/settings/transcriptDisplay/get`, applies relayed `changed` notifications and external write-side changes behind a per-layout monotonic revision guard, and fences every await by generation/read-serial so replies landing after retirement, support loss, hub replacement, or a superseding read are dropped. The fence change makes the first authoritative payload of a new generation acceptable at any revision (a restarted hub's revision sequence can restart lower), while `applyHubDefaults` publishes both layouts and the `loaded`/`hubLoading` confirmation in one `setState` after `firstPayloadApplied()` so reentrant subscribers cannot observe `loaded` while a restarted revision would still be accepted. The accompanying tests (492 lines) exercise wire decoding, malformed/foreign notifications, first-payload atomicity, reentrant refresh, retirement/dispose/detach fencing, and restarted-revision behavior.

The final implementation matches the stated intent, and I found no logic, security, or regression defects in the changed code.

## Findings

- **Severity:** low
- **File:** `appwire-client/typescript/index.ts:485-494`
- **What goes wrong:** The new store's public action `applyHubChange(change: TranscriptDisplayChange)` is published through the exported `TranscriptDisplayStoreState`/`TranscriptDisplayStore`, and `applyHubChange`/`onNotification` consume `TranscriptDisplayChange`, but that interface (along with `TranscriptDisplayStoreFields` and `TranscriptDisplayStoreActions`) is not re-exported from the package root. Consumers importing `@evener/appwire-client` (the mandated import path per AGENTS.md) therefore cannot name the change type when they wire the store's action or annotate a handler; they are forced to derive it structurally (`ReturnType<typeof fromWireChange>`) or redeclare it. This is exactly the kind of reachable-but-unnamed API type that the export block was added to publish (`fromWireChange` is exported and returns it).
- **Suggested fix:** Add `TranscriptDisplayChange` (and, for symmetry with the other store interfaces, `TranscriptDisplayStoreFields`/`TranscriptDisplayStoreActions`) to the `export type { ... } from "./transcriptDisplayStore"` list.
