## Summary

The two commits address a retirement-timer race. On each `changed` notification, `RetirementController.Run` recomputed the remaining timeout from a `Now()` snapshot and called `timer.Reset(remaining)`. Because `Reset` anchors the duration at the moment of the call, if time advanced between the `Now()` snapshot and the `Reset` call, the timer's absolute deadline slid later. Commit `adb2e78` adds a gated fake-clock harness (`Now()` interception, timer `deadline`/`fired` bookkeeping, `assertNoArm`) plus `TestRetirementTimerAdvanceAfterEvaluationSnapshot`, which deterministically injects a 30-minute advancement between the snapshot and the reset. Commit `6704b48` changes `Run` to track the intended absolute `armedDeadline` and only call `Reset` when the deadline actually changes; an unchanged deadline now leaves the already-armed timer untouched. `armedDeadline` is cleared on `disarm()` and when a tick is consumed, so any genuinely un-armed timer still gets reset. The existing refusal test gains a `clk.Advance(time.Minute)` so the re-anchored `eligibleSince` produces a deadline distinct from the retained one.

I verified the surrounding logic: settling, disarm/re-arm, `TryClaim(false)` re-proving eligibility on each tick, timeout-zero handling, and all call sites of `arm`/`disarm`/`timer.Reset`. The `Equal` comparison is the correct semantic for `time.Time`, and every path where the timer may be stopped or expired clears `armedDeadline` first, so the early return cannot strand a fired or stopped timer.

  **Problem**: On a first or changed arm, `d` is derived from the earlier `Now` snapshot.
