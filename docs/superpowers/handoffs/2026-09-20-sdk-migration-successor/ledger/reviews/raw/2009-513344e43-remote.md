## Summary

The series adds a `generation: number | null` stamp to the keybindings draft. The shared `keybindingsStore` now:
- defines and exports a `KeybindingsDraft` type (`version`, `revision`, `rules`, `generation`),
- stamps a restored (generation-`null`) draft with the live ready generation the first time an authoritative payload is applied (`applyHubOverrides`),
- preserves an existing draft's stamp across `editDraft`/`saveDraft`, and
- re-stamps with the current generation on `rebaseDraft` (the user re-reviewing against the current revision),
- keeps `decodeKeybindingDraftFields` on its existing storage-only shape by stripping the stamp.

Tests were updated for the new field and new cases were added (restore→stamp, edit/save preservation, rebase re-stamp). The implementation is coherent with the ready-generation fence (`fence.generation` is `-1` when inactive, positive when begun), and the added tests exercise meaningful behavior rather than tautologies.

**Severity: low** — `appwire-client/typescript/keybindingsStore.ts:430-438`

`draftFieldsFrom` gained a `generation` parameter with a default, but no caller ever passes it: `restoreDraft` (line 733) and `decodeKeybindingDraftFields` (line 452) both call `draftFieldsFrom(checkpoint)`/`draftFieldsFrom(draftCheckpoint(value))` with one argument. The parameter's comment claims it "gives the live store its typed projection," yet the live store never supplies a generation through this helper — stamping happens later in `applyHubOverrides` (line 854). Rows only ever land with `generation: null` here.

What goes wrong if not fixed: this is dead surface that misrepresents where the generation is threaded. A future reader or refactor could reasonably assume `restoreDraft` participates in stamping and route generation through it, duplicating/diverging from the `applyHubOverrides`/`currentGeneration()` path (the two must not both write the stamp, or a restored draft could get stamped at restore time instead of on first authoritative apply, changing the documented "first authoritative payload stamps" contract).

Suggested fix: drop the parameter and hard-code `generation: null` in the returned draft, or, if a non-null projection is genuinely needed by a caller, add that caller rather than leaving the parameter unused.
