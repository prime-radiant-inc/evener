## Summary

The series makes the native Providers, Plugins, and Hub Settings screens survive a passive connection flap: it adds a `fatal` flag to `useHubConnection` (only a protocol close is fatal), extracts the wall/banner/none decision into `connectionDisplay.ts` (`useConnectionDisplay`, `useLiveReadiness`, `useRenderClient`, `whenReady`), keeps the screen trees mounted behind a `ConnectionStatus` banner during `reconnecting`, and gates every mutation/refresh/sign-in control on live readiness (including a pre-gate readiness check inside `runGatedMutation`). It adds unit tests for the display predicates/predicates and for the upgrade-confirmation path, and moves `ConnectionStatus` out of `screens.tsx` so tests can render it without the navigation graph. The overall implementation matches the stated goal.

---

**Severity: medium** — Screens kept mounted through a flap lose their reconnect refetch.

- `mobile-native/src/PluginsScreen.tsx:134-140` (`useEffect(..., [model])` only)
- `mobile-native/src/MarketplaceBrowser.tsx:78-84`
- `mobile-native/src/HubSettingsScreen.tsx:170-176` (`useFocusEffect` deps `[canUseConnection, model, upgrade]`)
- Claim it relies on: `mobile-native/src/connectionDisplay.ts:6-9`

The banner design keeps `Plugins`/`HubSettings` mounted across a passive `ready → reconnecting → ready` cycle. Their only load triggers are keyed on `model`/`canUseConnection` identity, and neither changes on such a cycle: the client object is unchanged (hubConnection's generation guard keeps it), the hub id is unchanged, and `useLiveReadiness`'s callback is memoized on `[scope, client]`, so `state` moving back to `"ready"` does not re-create it. Before this series the `state !== "ready"` wall unmounted these components, and remounting re-ran `fetchPlugins`/the focus effect. Now nothing does. The doc comment promises this is covered by "the store's own reconnect recovery", but native never calls `pluginsStore.connectionChanged(...)`/`marketplacesStore.connectionChanged(...)` (grep: only `credentialStore.ts` does), and `createHubOverviewStore` has no reconnect recovery at all.

Concrete harm: after the socket reconnects, the installed-plugin list, marketplace catalog, and hub overview can stay stale indefinitely (until the user pulls to refresh or navigates away and back), so plugin/provider changes made by another client while this phone was disconnected are silently missing. No added test exercises `Plugins`/`HubSettings` recovery (the new screen test only covers Providers, whose credential store already has `connectionChanged` wired).

Fix: in the `Plugins`/`MarketplaceBrowser` effects add `model.connectionChanged(client, connectionState)` (the lifecycle already re-reads a wanted list when a connection becomes ready), and refresh the hub overview on the `ready` transition — e.g. an effect keyed on `ready`/`state`, or add `state` to the focus effect's dependency list so it re-runs on the reconnect. A test that flaps state back to `"ready"` and asserts the store receives a second read would pin it.

---

**Severity: low** — A disconnected refusal is reported as "another change is still running".

- `mobile-native/src/pluginMutationGate.ts:85` (`if (!ready()) return "refused"`)
- `mobile-native/src/PluginsScreen.tsx:158-159` and `mobile-native/src/MarketplaceBrowser.tsx:122-123` (both render `PLUGIN_MUTATION_BUSY` for `"refused"`)

`runGatedMutation` now returns `"refused"` for two different situations: the mutation gate is busy, and the connection is not ready. Callers reduce every `"refused"` to `PLUGIN_MUTATION_BUSY` ("Another change is still running. Wait for it to finish."). This is reachable: `remove()`/`confirm()` check `canUseConnection()` before opening the native `Alert`, but the Alert's confirm button calls `act(...)` without re-checking, so if the connection drops while the dialog is open the user is told a write is still running when in fact they are offline.

Fix: give the not-ready case its own outcome (or re-check `canUseConnection()` in the caller before setting the error) and show a connectivity message instead of the busy copy.
