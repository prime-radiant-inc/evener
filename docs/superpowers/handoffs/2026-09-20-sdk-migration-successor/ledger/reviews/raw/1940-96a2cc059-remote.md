## Summary

The series reverses `RemoveMarketplace`'s destructive order: it now persists the unregister save **before** deleting the marketplace's clone from disk, so a save failure is a clean refusal (record and clone both intact) and a clone-removal failure is a distinct post‑apply outcome. That outcome is typed end‑to‑end: `plugins.ErrMarketplaceUnregisteredCloneRemains` in the manager, `appwire.ErrorMarketplaceUnregisteredCloneRemains` + `MarketplaceUnregisteredCloneRemainsData` (with `Applied` / `AppliedUnavailable`) at the RPC boundary, and a non‑zero, explicitly‑worded CLI error. Tests cover the manager's ordering (save failure leaves the clone), the retry‑after‑litter lookup miss, the lookup‑miss‑touches‑nothing security invariant, and both hub branches (reconcile read succeeds vs. fails). The manager also refuses to derive/stat an unvalidated caller name on a lookup miss, closing an `""`/`".."` traversal.

The reordering and typing are correct and well‑covered on the Go side. The gap is that the newly documented client contract ("clients should reconcile from Applied") is not implemented by any consumer.

---

**Severity: medium** — The shared TypeScript client / web UI treats the new applied‑with‑litter outcome as a plain failure, so a removal that actually landed is reported as failed.

`appwire/errors.go:59-66` documents `ErrorMarketplaceUnregisteredCloneRemains` as: "A client should reconcile from Applied instead of treating the removal as rejected." `cmd/evener-hub/app_plugins.go:289-303` now returns this as `CodeInternalError`. But no client parses it — `grep` for `marketplaceUnregisteredCloneRemains` outside Go tests returns nothing, and `appwire-client/typescript/state/extensions/marketplaces.ts` `removeMarketplace` (line 223) simply rejects on any RPC error. The web consumer catches that rejection and toasts a failure:

- `cmd/evener-hub/frontend/src/panes/settings/sections/marketplacesPlugins/MarketplaceSheet.tsx` `handleConfirmRemove` catch block: `toasts.push("error", \`Remove marketplace failed: ${errorText(err)}\`)`.

Concrete harm: when only the clone cleanup fails, the registry removal succeeds and the list eventually reconciles via the `evener/marketplace/updated` broadcast, but the user is told "Remove marketplace failed". A user who retries gets `ErrMarketplaceNotFound` (mapped to `InvalidParams`) — a second, more confusing error for an operation that already applied. Native has the same shape (`mobile-native/src/MarketplaceBrowser.tsx` `remove`).

Suggested fix: handle `evenerErrorInfo === "marketplaceUnregisteredCloneRemains"` in the marketplaces store (mirroring `keybindingsStore.ts`'s `rejectionPayload` use): read `applied` when `appliedUnavailable` is not set, update `marketplaces`/retire the catalog, and surface a "removed, but leftover files remain" message rather than a failure. Add a store-level test driving a rejection payload of that shape.

---

**Severity: low** — The success path still drops a post‑apply outcome back to a plain error.

`cmd/evener-hub/app_plugins.go:305` (`return c.listMarketplaces(ctx)`) runs after the manager has already saved the unregister. If that read fails, the handler returns a bare internal error, and a caller cannot tell the removal applied — exactly the failure mode the litter branch's comment says "must never" happen (`app_plugins.go:284-286`). The diff fixes this only for the clone‑litter branch, leaving the sibling path unclassified. Concrete harm: on a transient/corrupt read after a successful removal, clients report "remove failed" and a retry lands on not‑found. Suggested fix: on `listErr` here, return the same typed `ErrorMarketplaceUnregisteredCloneRemains`/`AppliedUnavailable` shape (or an equivalent post‑apply outcome) so the applied removal is never presented as rejected. This is pre‑existing behavior, but it is the same post‑apply classification this series is establishing, so it is worth aligning now.
