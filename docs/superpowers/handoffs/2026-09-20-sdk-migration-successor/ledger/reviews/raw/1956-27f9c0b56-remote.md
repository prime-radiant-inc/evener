## Summary

The series extracts the native draft storage backend into a shared, testable `rawStringDraftBackend` (replacing the inline `Storage`-backed backend), hardens the unreadable-record markers so they can no longer collide with legitimately stored JSON (symbol brands instead of string tags), adds `decodeKeybindingDraftFields`/`readDraftOutcomeWithValue`, and wires a provider-level recovery path: a probe effect that classifies the hub's keybindings draft independently of the model, `offlineDraftUnreadable`/`offlineStorageUnavailable` flags, and `discardUnreadableKeybindingsDraft()` (store-free discard plus a follow-up re-read and a live-model nudge). Tests cover the probe, offline discard, readable-replacement refusal, live reclassification, storage failure, and hub switching.

---

**Medium — `offlineDraftUnreadable` cannot be superseded by the live model as documented, and stays stale after a live discard**

File: `mobile-native/src/NativePreferencesProvider.tsx:45` (also the effect deps at line 124) and `mobile-native/src/nativePreferences.ts:144-163`.

The contract comment says the offline flag is "Superseded by `snapshot.keybindings.draftUnreadable` the moment a model publishes", but no such field exists. `keybindingsDomain()` in `nativePreferences.ts` projects only `support/loading/saving/confirmed/draft/error/conflict/writeUncertain/storageUnavailable` — it never copies `state.draftUnreadable` (which *does* exist on `KeybindingsStoreState`, `keybindingsStore.ts:149`). Compounding that, the probe effect only depends on `[hubId, state]`, so it never re-runs when the live store changes.

What goes wrong: once a model has published, the only remaining unreadable signal is `offlineDraftUnreadable`, and a connected consumer that keeps reading it (the only way to distinguish an unreadable record from a generic `storageUnavailable`) will keep showing the "Discard unreadable draft" notice after the record is gone. Concretely, if the user clears it through the existing connected screen's `model.discardKeybindingsDraft()` (`KeybindingPreferencesScreen.tsx:333` / `:302`), the store reclassifies and publishes, but `offlineDraftUnreadable` stays `true` (no state/hub change re-fires the probe), so the stale recovery action remains and its next invocation returns `"absent"`.

Suggested fix: project `draftUnreadable` into the keybindings domain (`keybindingsDomain` must add `draftUnreadable: state.draftUnreadable`), and either derive `offlineDraftUnreadable` from the model once one exists or subscribe to the bound model so a live reclassification clears the stale flag. Update the doc comment to match whichever source of truth is chosen.

---

**Low — `decodeKeybindingDraftFields` is added but has no runtime caller**

File: `appwire-client/typescript/keybindingsStore.ts:432` (exported at `index.ts:226`).

The commit "share draft classification and decoded fields" adds this export, but grep shows it is referenced only by `keybindingsStore.test.ts`; nothing in `mobile-native` (or any production file) calls it. `readDraftOutcomeWithValue` (`nativePreferenceDrafts.ts:195`) is likewise only consumed by `readDraftOutcome`, which throws its `value` away. The offline discard path therefore still re-reads storage (`readDraftOutcome`) and never decodes a readable replacement's fields, so the "share decoded fields" behavior is not actually wired anywhere. This is dead code today; either wire it into the provider (decode a readable replacement for the offline UI) or drop the export until a consumer exists.
