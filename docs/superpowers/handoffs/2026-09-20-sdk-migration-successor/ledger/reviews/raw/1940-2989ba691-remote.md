## Summary

The series restructures marketplace removal so the unregister metadata save lands *before* the clone is deleted on disk, then types the resulting "applied-but-clone-remains" outcome end to end:

- `internal/plugins.RemoveMarketplace` now saves `known_marketplaces.json` first; a save failure is a plain refusal that leaves the clone intact, and a subsequent clone-removal failure is `ErrMarketplaceUnregisteredCloneRemains` (registered metadata already gone).
- The lookup-miss path is kept ahead of any `marketplaceDir(name)` derivation, with a new test proving a miss (`""`, `".."`, `"../x"`, unknown) calls no removal primitive. The store lock's `migrateMarketplaceNames` already guarantees recorded names are valid, so a hit cannot carry a traversing name.
- `appwire` gains `ErrorMarketplaceUnregisteredCloneRemains` + `MarketplaceUnregisteredCloneRemainsData{Applied, AppliedUnavailable}`; the hub maps the sentinel to a typed `WireError` carrying the reconciled list, and falls back to `AppliedUnavailable=true` (keeping the typed shape) if re-listing fails.
- The CLI recognizes the sentinel, says the registry removal landed but clone files remain, and still exits non-zero.
- Tests cover the manager, hub, and CLI paths, plus path-scrubbing and the retry-after-litter case.

## Findings

**Medium** — The new typed outcome is never consumed by the repo's own AppWire clients, so a successful removal is surfaced to the user as a failure.

- `appwire/types.go:3578` / `appwire/errors.go:44` documents "Clients should reconcile from Applied", and `cmd/evener-hub/app_plugins.go:288-306` emits exactly that payload. But no TypeScript consumer reads `marketplaceUnregisteredCloneRemains`, `applied`, or `appliedUnavailable` (a repo-wide search returns no matches in `appwire-client/typescript` or `cmd/evener-hub/frontend/src`). `appwire-client/typescript/state/extensions/marketplaces.ts:223` routes `removeMarketplace` through `mutate`, whose `writeRevisioned` rethrows the rejection with no reconciliation (`state/extensions/listRevision.ts:163-165`), and `MarketplaceSheet.tsx:273` then reports `Remove marketplace failed: ...`.
- Concrete harm: when clone removal fails (e.g. a permission fault on the clone directory) the unregister has already applied and the marketplace is gone, but the requesting client shows a failure toast for a removal that succeeded. Before this series that clone failure was swallowed and reported as success, so this is a regression in the requesting client's feedback. The broadcast `evener/marketplace/updated` (via `saveMarketplaces` → `markStoreChanged`) eventually refreshes the list, leaving the user with contradictory signals.
- Suggested fix: in `removeMarketplace`'s mutation, catch the rejection and, when `evenerErrorInfo === "marketplaceUnregisteredCloneRemains"`, treat it as applied — publish the `data.applied` list (guarding on `data.appliedUnavailable`), and have `MarketplaceSheet` report the removal as landed-with-leftover-files rather than a hard failure. This mirrors `keybindingsStore.rejectionPayload`/`transcriptDisplay.postApplyDefault`. If client handling is deliberately deferred, the doc comments in `appwire/types.go` and `appwire/errors.go` should not claim clients reconcile from `Applied` until one does.
