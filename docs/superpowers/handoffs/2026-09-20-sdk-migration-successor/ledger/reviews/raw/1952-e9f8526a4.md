## Review Findings
- **Severity**: High
- **Location**: `mobile-native/src/HubSettingsScreen.tsx`, `mobile-native/src/PluginsScreen.tsx` (`lastClient` fallback) + `mobile-native/src/connectionDisplay.ts` (`useConnectionDisplay`)
- **Problem**: `lastClient` and `everReady` are per-mount, not per-hub. Switching hubs reuses the screen instance with new `route.params.hubId`/`activeProfile.id`: `client` is briefly `null` while the new hub connects, so `renderClient` falls back to the previous hub's closed client and `everReady=true` selects `banner` instead of `wall`. `HubSettings`/`Plugins` then issue requests for the new `hubId` over the old hub's connection (wrong-hub data under the new hub name).
- **Fix**: Scope both by hub, e.g. reset `lastClient`/`everReady` when `activeProfile.id` changes or key the screen/inner store by hub id before falling back.
---
- **Severity**: Medium
- **Location**: `mobile-native/src/PluginsScreen.tsx` inner `Plugins`, `mobile-native/src/HubSettingsScreen.tsx` inner `HubSettings`
- **Problem**: Banner keeps the screen mounted but nothing triggers a reconnect refetch. `PluginsStore` recovers only via `connectionChanged`, which the screen never calls (`model.start()` + `fetchPlugins()` on `[model]` only); `createHubOverviewStore` has no reconnect hook at all and only refreshes on focus/manual retry. After a flap the banner shows stale data indefinitely, contradicting the `connectionDisplay.ts` "auto-refreshing through the store's own reconnect recovery" comment. `ProvidersScreen` does rebind via `useCredentialStore`.
- **Fix**: Wire reconnect the way `useCredentialStore` does: forward `client`/`state` to `model.connectionChanged` where available, or explicitly `fetch`/`refresh` on `ready` transitions after `everReady`.
---
- **Severity**: Medium
- **Location**: `mobile-native/src/ProvidersScreen.tsx:onSignIn`
- **Problem**: `onSignIn` passes raw `client` to `flow.setConnection(client)` while the effect uses the guarded `state === "ready" ? client : null`. During a banner `client` is a closed client (flap) or `null` (manual-retry gap): the former makes `start()` race requests over a dead connection before the effect corrects it to `null`, the latter makes `start()` early-return with the sheet stuck and no error.
- **Fix**: Use the same guard in `onSignIn` (`state === "ready" ? client : null`) or disable sign-in while `display !== "none"`.
---
- **Severity**: Low
- **Location**: `mobile-native/src/connectionDisplay.ts:30-35`, `HubSettingsScreen.tsx` / `PluginsScreen.tsx` (`if (client) lastClient.current = client`)
- **Problem**: Mutating refs during render is unsafe under concurrent/StrictMode double render: an abandoned `ready` render still leaves `everReady=true`/`lastClient` updated, misclassifying a future wall as a banner.
- **Fix**: Move updates into effects (`useEffect`/`useLayoutEffect` on `[state]` / `[client]`) instead of writing refs during render.
## Summary
Keeps ready screens mounted behind a reconnect banner but leaks the prior hub's client across hub switches, skips reconnect refetch wiring on two screens, and mishandles sign-in during reconnects.

## Summary

The series adds connection-flap resilience to three "ready-only" native screens (`Providers`, `Plugins`, `HubSettings`). A new `fatal` flag is threaded from `useHubConnection` through `ConnectionProvider`, a `connectionDisplay` helper decides between wall / banner / none, and `ConnectionStatus` is extracted from `screens.tsx` into its own module so the screens can render it as a banner over content that stays mounted. `useHubOverview`-style stores are expected to recover after a reconnect. Tests were added for `connectionDisplay`, the `fatal` transitions in `useHubConnection`, and the banner/wall behavior of `ProvidersScreen`.

The intent is carried out for `ProvidersScreen` (its credential store is rebound on every connection transition), but the same mechanism is not actually wired for the other two screens, so their data can be stale after the flap.

---

**Severity: medium** — `PluginsScreen` and `HubSettingsScreen` keep their content mounted across a flap but never re-read it on reconnect.

- `mobile-native/src/PluginsScreen.tsx:80` renders the banner while `<Plugins>` stays mounted, and `mobile-native/src/PluginsScreen.tsx:101,123-124` only constructs/fetches the store on mount (keyed on `client`, which the connection layer deliberately keeps the same across a flap). The plugins store's own recovery (`createPluginsStore` → `storeLifecycle.connectionChanged`, `appwire-client/typescript/state/extensions/storeLifecycle.ts`, whose header states "the notification is not a recovery path and the reconnect is") is never driven from native — only `credentialStore.ts` calls `connectionChanged` (see `grep connectionChanged mobile-native`).
- Same for `mobile-native/src/HubSettingsScreen.tsx:142,160-164`: `createHubOverviewStore` is fetch-once with no connection awareness, and `refresh()`/`reconcileAfterReconnect()` only run from `useFocusEffect`, whose callback is memoized on `[model, upgrade]`; neither changes on a same-client flap/reconnect, so focus does not change and the effect does not re-run.

Concrete harm: a plugin installed (or a hub upgraded, or MCP servers changed) on the hub while this device was disconnected produces no notification the client was subscribed for. With the old `state !== "ready"` wall the screen unmounted and remounted, which re-issued the read; now the list stays mounted and never refreshes, so the user sees stale data indefinitely (until an unrelated notification, pull-to-refresh, or leaving the screen). This also contradicts the new doc claim in `mobile-native/src/connectionDisplay.ts:6-10` that content "auto-refresh[es] once ready again through the store's own reconnect recovery."

Suggested fix: like `useCredentialStore`, drive each screen's store from the connection: call `store.connectionChanged(client, state)` (plugins store) or add a `refresh()` on the ready transition (hub overview and `reconcileAfterReconnect()`), and add a Plugins/HubSettings test that flips `state` ready → reconnecting → ready and asserts a re-read is issued.

---

**Severity: low** — On a fatal (protocol) close the wall offers a `Reconnect` action that can never succeed and hides the explanatory error.

- `mobile-native/src/ProvidersScreen.tsx:70-75` (and the equivalent walls in `PluginsScreen.tsx` / `HubSettingsScreen.tsx`) render only "Connect to …" plus `<Action onPress={retry}>Reconnect</Action>`, with no `ErrorMessage`. `mobile-native/src/ConnectionStatus.tsx:30` is the only place the `error` text is rendered, and it is skipped when `display === "wall"`.
- The project already treats a protocol close as "a Retry that can never succeed" (see `appwire-client/typescript/client.test.ts:235-238`). The new `fatal` flag exists precisely to identify that case, yet it routes to the same wall whose only action is a doomed retry.

Concrete harm: a user hitting a version mismatch sees a generic connection message and a Reconnect button that loops, with no hint that "This app and hub need compatible versions. Update them together" (`connectionRecovery.ts`). Suggested fix: for `fatal`, render the `connectionFailure` message and suppress/replace the reconnect action (matching the web's "reload/update" affordance).
