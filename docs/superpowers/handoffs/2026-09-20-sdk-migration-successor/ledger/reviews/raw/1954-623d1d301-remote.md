## Summary

The series makes the marketplaces store reconcile a `marketplaceUnregisteredCloneRemains` rejection instead of treating it as a rollback. On the hub, that rejection means the unregister already applied and only the on-disk clone removal failed; the wire error carries the updated list in `data.applied` (or `appliedUnavailable` when the hub's follow-up list read also failed). The changes:

- `listRevision.ts`: `writeRevisioned` gains an optional `onFailure` that may return a state writer for an authoritative failure payload; when present it publishes under the request's own revision instead of retracting, then still rethrows.
- `marketplaces.ts`: adds `cloneLitterApplied` to safely parse `data.applied`, wires `removeMarketplace` to it, and adds `retireCatalogsAbsentFrom` so any accepted list (read success, write success, or applied-failure) retires cached browse catalogs for marketplaces no longer present.
- Tests cover reconciliation, `appliedUnavailable`/malformed payloads, reset/dispose fencing, and out-of-order read/write ordering.

I traced the new failure path against `createListRevision`'s state machine (held → later owner publishes or retracts), the generation fence, the `browses` revision side effects, and the Go payload shape (`applied.marketplaces` is always `[]` when empty, not omitted). The guards (`issuedIn !== generation` at writer creation, plus re-check at publish) correctly prevent a post-reset/dispose applied payload from landing, and the held-write-then-retract ordering behaves as the new tests assert.
