## Summary

The series restores offline recovery for an unreadable keybindings draft on the native client. It adds an independent storage probe in `NativePreferencesProvider` (`offlineDraftUnreadable`/`offlineStorageUnavailable`) that works before any model exists, a store-free discard (`discardUnreadableKeybindingsDraft`), retained-snapshot reconciliation when the bound client changes, and a "Discard unreadable draft" action in `KeybindingPreferencesScreen` wired through pure helpers in `keybindingOfflineRecovery.ts`. It also splits the keybindings projection's error sources (`draftError`/`hubError`/`loadError`) so a draft diagnostic and a hub diagnostic can be owned and cleared independently. The pure decisions and the main provider flows have focused tests.

---

**Severity: medium** — NativePreferencesProvider.tsx:228 (and the retained snapshot rendered at KeybindingPreferencesScreen.tsx:308)

`reconcileRetainedDraft`'s effect bails whenever `bound.client === client`, and the reconciliation guard repeats `previous.client === client`. A real network drop does *not* change the client object: `useHubConnection` keeps `connectedFor.current`/the core store's client and only flips `state` to `"closed"` (`hubConnection.ts`), so the provider sees the same `client` with `connected === false`. In that state the effect runs (the `state` dep changed) but returns early, so the retained `snapshot.keybindings` is never re-read from storage. The offline probe updates `offlineDraftUnreadable`, but the stale `domain` is still rendered. Two concrete consequences when a draft changes on disk while the app is offline:

- Readable → unreadable: the screen shows the new "A saved draft on this phone could not be read. Discard it…" notice **and**, because `domain.draft` is still the pre-disconnect draft, the "Changes saved on this phone" section with the stale rules (KeybindingPreferencesScreen.tsx:308). The user is told the draft is unreadable and also that it is intact.
- Unreadable → readable: `offlineDraftUnreadable` correctly goes false and the action disappears, but `ErrorMessage` still prefers the retained `domain?.error` ("Could not restore the saved shortcut draft…", KeybindingPreferencesScreen.tsx:180), so the stale diagnostic lingers with no in-place way to clear it.

The tests only exercise this reconciliation with a *replacement* client (`clientFixture({failed:true})`), where `bound.client !== client`, so the retained-client path is uncovered.

Suggested fix: reconcile on a connection-state transition even when the same client is bound (e.g. also rerun the projection when `state` leaves `"ready"`), or clear the stale projection in the disconnect branch and derive `ErrorMessage`/the draft section from the offline probe when `!preferences.connected` (mirroring `offlineAwareDraftUnreadable`).

---

**Severity: low** — keybindingOfflineRecovery.ts:47 and KeybindingPreferencesScreen.tsx:180

`offlineStorageErrorMessage` says "…Check current shortcuts to retry," but it is only surfaced when `!preferences.connected` (screen line 183), and "Check current shortcuts" is `disabled={!preferences.connected || …}` and `run()` short-circuits on `scope.connected`. So the message always points at a disabled/no-op control on the only path that renders it; the retry that actually re-probes storage is "Reconnect" (which changes `state` and reruns the probe). Harm is a user following an instruction that nothing happens on.

Suggested fix: reword the message to describe the failure and point at Reconnect (or allow the refresh action to run the probe when disconnected).
