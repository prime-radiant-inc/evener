## Summary

The series separates the *admitted interrupt boundary* from the *salvage explanation* that a cancelled round persists. Concretely:

- A new `SteeringKindInterruptedSalvage` (`events`, propagated to `STEERING_KINDS` in `types.gen.ts`) is used by `settleInterruptedRound` for the “This response was interrupted …” draft explanation, while the round loop's own interrupt marker stays `SteeringKindInterrupted`.
- The interrupt marker is now written through the durable `appendSteeringTurnDurablyForOwner` path (“durably admit before resolving asks”). Only an accepted marker clears `askPending`, settles `SessionIdle`, emits `EventSessionEnd(Interrupted=true)`, and opens the queued-input drain. A rejected marker leaves the ask pending and settles through the new `finishProcessingAtRestoredFailureBoundary`, which derives state exactly as restore does.
- `processOneInput`'s two early cancellation exits no longer settle the boundary themselves, deferring that decision (marker admission first) to the outer handler.
- `turnResolvesAskBoundary`/`deriveRestoredState`/`deriveAskQuestions.ts` treat only the admitted `interrupted` marker as resolving; the salvage kind is non-resolving, so an ask survives a rejected marker. Tests and a web label (“Interrupted draft”) cover the split.

The core Go changes are internally consistent (rejected-marker live state matches restore, and the drain gating is correctly tied to `markerAccepted`). I found two consumer/test gaps.

---

**Low** — `mobile-native/src/timeline.ts:8` and `:41` (`steeringNoticeLabel`, `isInterruptedNotice`)

The new kind has no mobile-native handling. `steeringNoticeLabel`'s switch has a `default: return undefined`, and `isInterruptedNotice` compares only to `"interrupted"`, so a salvaged-draft notice now renders with no label and is no longer classified as an interruption notice. Before this series that steer carried `interrupted` (both marker and salvage shared it), so it was labeled “Interrupted” and collapsed as an interruption notice; the web client was updated to label the new kind “Interrupted draft”, but the mobile client was not. Harm: the same wire kind is presented differently on the two clients, and mobile silently loses the label it previously showed until the marker arrives as a second, separate notice. Suggested fix: add `case "interrupted-salvage": return "Interrupted draft";` (and decide whether `isInterruptedNotice` should accept it) plus a timeline test case.

---

**Low** — `cmd/evener-tui/question_overlay_test.go:104` (`TestPendingAskQuestions_InterruptedSalvageKeepsContentAndDoesNotResolve`)

The test names the `interrupted-salvage` semantics but the message it builds is `{Kind: transcript.MsgSteering, Text: salvage}` with no kind field — `transcript.ChatMessage` (cmd/evener-tui/internal/transcript/types.go:117) has no `SteeringKind`, and `pendingAskQuestions` (cmd/evener-tui/question_overlay.go:114) never reads a kind at all (it only branches on `MsgUser` vs everything else). The assertion therefore passes for *any* steering text, including the admitted `interrupted` marker the daemon treats as resolving; it cannot detect a regression in how the TUI handles the salvage kind. Harm: false confidence that TUI cold-attach mirrors the daemon's “salvage does not resolve, admitted marker does” rule, when the TUI has no kind-aware path. Suggested fix: either drop the claim from the test's name/comment (it only pins that steering content stays visible and doesn't resolve), or add the kind field/plumbing required for the TUI projector to distinguish the marker from the salvage and assert both directions.
