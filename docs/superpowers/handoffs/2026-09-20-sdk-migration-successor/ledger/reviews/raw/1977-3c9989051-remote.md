## Summary

The four commits make pending `ask_user` resolution contingent on the user's reply being durably admitted to the transcript, instead of clearing the pending ask at `processOneInput` entry. Concretely:

- `processOneInput` now clears `askPending` at entry only for an answering *steering-carrier* identity (`carrierAnswersAsk && queuedIdentity.SteeringCarrier`).
- `acceptUserInputWithSkillSelection` clears the ask only after a touched admission point: after an already-incorporated transcript short-circuit, after a recovered client-start failure that actually recorded the user turn, after the claimed user turn's synced append, and after the direct user turn's durable (or durably preseeded) append.
- `appendUserInputTurnRefusingPoison` now goes through the shared `appendTurnAfterTranscriptWrite`/`writeTranscriptSyncedLocked` pair, adopting retained-unsynced lines, returning hard write failures instead of warn-and-continue, and reporting poisoned writers.
- The MaxTurns refusal settles through `finishProcessingAtFailureBoundary` (awaiting when an ask is still pending).

The new tests exercise MaxTurns, environment-append failure, transcript-append failure, closed transcript, retained-line adoption, recovered client-start admission (full/partial/no user record), and restore-equivalence for each. The changed regression tests correctly re-arm the fault injectors for the now-synced direct door. The production logic matches restore's `turnResolvesAskBoundary` (a recorded `TurnUserInput` resolves; an unrecorded one does not).

## Issues

**Low — Stale doc comment in `steeringCarrierClaimAnswersAsk` claims non-carriers still trigger the entry clear.**
`agent/session_tools_ask.go:112-114` (unchanged text, made stale by the diff at `agent/session_lifecycle.go:1820`).

The comment reads: "A non-carrier identity, or one with nothing to look up, answers by definition, preserving the entry clear's ordinary unconditional behavior for a genuine user reply." The caller now gates the clear on `&& queuedIdentity.SteeringCarrier`, so a non-carrier identity deliberately no longer clears `askPending` at entry — it clears only after `acceptUserInputWithSkillSelection` durably admits the turn. A future maintainer reading this doc could reintroduce entry-time clearing for ordinary replies (the exact bug this series fixes) or misjudge the restore/live alignment. Suggested fix: reword to say the return value is `true` for a non-carrier (an ordinary reply still resolves the ask), but the entry clear is now gated to carriers and a non-carrier clears only after durable admission.
