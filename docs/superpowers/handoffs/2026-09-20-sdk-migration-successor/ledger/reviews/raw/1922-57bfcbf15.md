## Summary

The series makes connection-loss behavior consistent across the native ready-only screens (Plugins, Providers, Hub Settings). It adds `fatal` (protocol-close) detection to `useHubConnection`/`ConnectionProvider`, and introduces `connectionDisplay.ts` with shared helpers: `connectionDisplay`/`useConnectionDisplay` (wall vs. banner vs. none, scoped per hub, with a `fatalRecovery` latch), `useRenderClient` (retain the last ready client through a manual-retry `null`/`connecting` gap but never adopt a replacement until it is ready), `useLiveReadiness`/`whenReady`/`isReady`, and `useReconnectRecovery` for stores without their own `connectionChanged`. `runGatedMutation` gains a live `ready` predicate and a distinct `"not-ready"` outcome, and every screen wires mutation/refresh affordances through it. The extracted `ConnectionStatus` gets its own module, and new tests cover the display state machine, reconnect reads, gated mutations, and fatal walls.

The intent is achieved: retained screens keep their data and drafts through a passive flap behind a banner, fatal closes still wall, and the replacement client is only adopted once ready. I found one gap.

---

**Severity: low** — `mobile-native/src/MarketplaceBrowser.tsx:95-96` (mount effect), with the same issue at line 121 (catalog browse on selection)

`MarketplaceBrowser` is conditionally mounted inside `Plugins` when the user switches to the Browse tab, and the mount effect issues `model.getState().fetchMarketplaces()` unconditionally. With this series, `PluginsScreen` now keeps `<Plugins>` mounted through a flap (`display === "banner"`), and the Installed/Browse tab `Action`s are not disabled. So a user can switch to Browse *while* the connection is `"reconnecting"`/`"connecting"`; `client.request` rejects immediately when the state is not `"ready"`, the store records `marketplacesError`, and the screen renders "Could not load marketplaces. Try again when connected." under the banner. Selecting a marketplace during the flap (`select()` → the `browseTarget` effect at line 121) does the same for the catalog. Every other read in this component is guarded (`onRefresh` checks `canUseConnection()`; the retry actions go through `whenReady`), so the mount/selection path is the odd one out. The store lifecycle does recover on the next `"ready"` (`wanted` latches off the error and refetches), so this is a transient, self-healing spurious error rather than a stuck state — but it tells the user something failed when the banner already explains the situation.

Suggested fix: gate the mount fetch on readiness (skip it when `!canUseConnection()`, letting the store's reconnect recovery perform the first read), or guard the `browseTarget` effect the same way, e.g.:

```ts
useEffect(() => {
  model.start();
  if (canUseConnection()) void model.getState().fetchMarketplaces();
  ...
}, [model]);
```

(With the `connectionChanged` effect declared first, the reconnect `"ready"` transition will still latch `wanted` and issue the read.)
