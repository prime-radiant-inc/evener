## Summary

The series refactors native keybindings draft handling so an offline/retained host can classify and discard an unreadable draft without a live store. It extracts `rawStringDraftBackend` (production and tests now share one parse/compare implementation), replaces the serializable `{kind: "..."}` sentinels with `unique symbol` brands so legitimate JSON can never collide with the unreadable/stored-null markers, adds `readDraftOutcomeWithValue`/`draftUnreadableAfterDiscard`/`decodeKeybindingDraftFields`, exposes `draftUnreadable`/`draftError`/`hubError`/`loadError` on the keybindings projection, and adds a `NativePreferencesProvider` reconcile path plus `offlineDraftUnreadable`/`offlineStorageUnavailable`/`discardUnreadableKeybindingsDraft`. The logic is heavily tested at the provider, store, and drafts layers.

---

**Medium — the new offline unreadable-draft recovery has no UI consumer, so the recovery action is unreachable**

The provider now exposes `offlineDraftUnreadable`, `offlineStorageUnavailable`, and `discardUnreadableKeybindingsDraft()` (`mobile-native/src/NativePreferencesProvider.tsx:44-65`, `:236`), but nothing in the app consumes them (grep across the repo finds only the provider and its tests). `KeybindingPreferencesScreen.tsx` renders its discard controls only inside `{domain?.draft && (` (`:245`) and `{domain?.confirmed && (` (`:354`). An unreadable record projects `draft: null` (`keybindingsStore.ts` `restoreDraft` unreadable branch) and, on a cold offline start, `snapshot` is `null` so the screen only renders the loading indicator. Result: the user cannot clear an unreadable keybindings draft online or offline, leaving the section permanently unusable, which is exactly the recovery `discardUnreadableKeybindingsDraft` and the `offlineDraftUnreadable` comment describe. The commit goal ("wire offline draft provider recovery") is therefore only achieved at the provider layer. Suggested fix: consume these fields in `KeybindingPreferencesScreen` (render a notice plus a discard action when `offlineDraftUnreadable` or `domain?.draftUnreadable`, invoking `preferences.discardUnreadableKeybindingsDraft()` when no model exists and `model.discardKeybindingsDraft()` otherwise).

---

**Low — the retained-snapshot reconcile drops the storage-failure diagnostic**

In `reconcileRetainedDraftProjection`, `case "storageUnavailable"` only sets `storageUnavailable = true` and leaves `draftError` untouched (`mobile-native/src/NativePreferencesProvider.tsx:91-93`). The live store's equivalent path sets `draftError = DRAFT_RESTORE_FAILED_MESSAGE` (`appwire-client/typescript/keybindingsStore.ts:736`). So a retained snapshot whose `draftError` was `null` (a previously readable draft) plus a failed storage read ends up with `storageUnavailable: true` but `error: null` (`keybindingsErrorMessage(null, null, null)`), whereas the live path shows the restore-failure message. Concrete harm: while reconnecting/offline the retained keybindings view shows a draft with disabled controls and no explanation. Suggested fix: set `draftError = DRAFT_RESTORE_FAILED_MESSAGE` in that branch to match `restoreDraft`, and assert `draftError`/`error` in the "marks only the retained draft projection unavailable" provider test so the divergence is covered.

---

**Low — the restore-failure message is duplicated instead of shared**

`NativePreferencesProvider.tsx:76` re-declares `DRAFT_RESTORE_FAILED_MESSAGE` with the same literal as the store's private constant (`appwire-client/typescript/keybindingsStore.ts:269`). Because the provider tests only assert `expect.any(String)` for this message (e.g. `NativePreferencesProvider.test.tsx:337`), a future rewording in the store would silently leave the retained/offline path showing the old copy for the same condition. Suggested fix: export the store's constant (or a shared helper) and import it in the provider, and assert the shared value rather than `expect.any(String)`.
