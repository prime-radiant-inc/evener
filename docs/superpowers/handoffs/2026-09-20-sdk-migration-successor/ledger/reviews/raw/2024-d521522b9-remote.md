## Summary

The commit fixes generation laundering in the checkpointed keybindings draft editor. When a local save fails (`storageUnavailable`), `refreshOverrides` previously re-read the draft via the ordinary `restoreDraft` path, which always stamps `generation: null`. A subsequent `applyHubOverrides` then stamped the *current* generation onto that draft, so a proposal composed under an older generation silently appeared current and could be saved against the wrong hub session. The change adds `DraftRepository.reload()`, which reports whether the on-disk record still matches the identity most recently classified (compared canonically), and `keybindingsStore.reloadDraft()` carries the in-memory generation forward only when it does. A replacement record (even with equal visible content) goes through the ordinary null-generation path. Tests cover the port-level identity report and both store-level outcomes.

## Issues

**Severity: low** — `appwire-client/typescript/draftCheckpointPort.test.ts:20-31`, `appwire-client/typescript/keybindingsStore.test.ts:678-702`

The central documented invariant — "Equal decoded fields are insufficient: a replacement can carry the same draft content while belonging to another writer" (`draftCheckpointPort.ts:112-115`) — is not actually pinned by either new test. Both replacements differ only in `id` (`d1` → `d2`; auto id → `"replacement"`), and `id` is itself a decoded field: `decode()` returns `{id, value}` / `draftCheckpoint()` returns `{id, baseRevision, rules, writeUncertain}`. An implementation that compared `decode(previous.raw)` against the new checkpoint instead of the raw canonical JSON would pass both tests unchanged, so the raw-identity-vs-decoded-content distinction this commit is built around has no coverage.

What goes wrong if unaddressed: a future "simplification" of `sameIdentity` to compare decoded checkpoints would silently break the documented behavior (a record rewritten with different raw bytes but the same decoded fields would be treated as the same identity and keep a stale generation) with no test failing.

Suggested fix: add a case where the two records decode identically but differ in raw bytes — e.g. load `{id: "d1", value: "a", futureField: 1}`, then have the external writer store `{id: "d1", value: "a"}` (or vice versa) and assert `sameIdentity: false`, mirroring the existing extra-field test at line 32.
