## Summary

The series fixes how the native preferences provider projects and reconciles a *retained* (stale) keybindings snapshot while a same-hub connection is still reconnecting. Previously the retained snapshot kept whatever draft classification the old client had last published. The changes:

- Add `draftError`, `hubError`, and `loadError` to the keybindings preference projection (and `draftUnreadable` to the shared `PreferenceState`), so the provider can distinguish draft-source diagnostics from hub-source diagnostics instead of collapsing them into one `error` string.
- Extract `keybindingsErrorMessage(draftError, hubError, loadError)` so the precedence is computed in one place.
- Add `reconcileRetainedDraftProjection`, a pure projector that re-classifies the retained snapshot from a fresh storage read (`storageUnavailable`/`absent`/`unreadable`/`readable`), recomputes `error`, and preserves hub/load diagnostics.
- Wire it into a new effect (when `bound.client !== client`, i.e. a new client is pending for the same hub) and into the store-free `discardUnreadableKeybindingsDraft` path (including its follow-up re-read).
- Add tests covering readable/absent/unreadable replacements, storage failures and recovery, and preservation/clearing of the different diagnostic sources.

I verified the new projector against the shared store's `restoreDraft`/`staleDraft` semantics (same conflict rule, same unreadable clearing of draft/writeUncertain/conflict, same preservation of `draftUnreadable` on genuine port failure), the exports used (`decodeKeybindingDraftFields`, `readDraftOutcomeWithValue`, `isReadableKeybindingDraft`) exist and are compatible, and the new snapshot fields don't leak raw hub error text to any UI (only the sanitized `error` is rendered).
