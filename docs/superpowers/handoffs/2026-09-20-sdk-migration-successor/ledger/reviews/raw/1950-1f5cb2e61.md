## Summary

This series advances the native offline-draft work by extracting shared draft helpers:

- `appwire-client`: `decodeKeybindingDraftFields` projects a stored checkpoint into the same `{ draft, writeUncertain }` fields `restoreDraft` publishes, with `draftFieldsFrom` shared by both, and it is re-exported from the package index.
- `mobile-native`: replaces the string-tagged `STORED_NULL_KIND`/`UNPARSEABLE_KIND` sentinels with `unique symbol` brands (so JSON can never forge them), extracts `RawStringStorage` + `rawStringDraftBackend` to centralize parsing/identity comparison, and adds `readDraftOutcomeWithValue` so a caller gets classification and the raw value from a single guarded `load()`. `readDraftOutcome` now delegates to it. Tests are refactored onto the shared backend and new collision/key-order cases are added.

The individual helpers are correct and the symbol-brand change is a genuine robustness improvement (symbols cannot round-trip through `JSON.parse`). The gap is that the "shared" backend is never adopted by the production native provider.

---

**Severity: medium** — `rawStringDraftBackend` is not what the production native backend runs, contradicting the new test's stated contract, and the production path keeps the behavior the shared helper was extracted to fix.

- `mobile-native/src/nativePreferenceDrafts.ts:142` defines `rawStringDraftBackend`, but the only callers are tests (grep: `nativePreferenceDrafts.test.ts`). Production still hand-rolls its own backend in `mobile-native/src/NativePreferencesProvider.tsx:32-57` and passes it to `nativeKeybindingDrafts`/`nativeTranscriptDrafts` (lines 90-115).
- The test refactor added at `mobile-native/src/nativePreferenceDrafts.test.ts:26-30` asserts "`rawStringDraftBackend` is the same function production calls over it, not a parallel reimplementation." That is false as of this tip; the same claim also appears in `mobile-native/src/draftBackend.testkit.ts:1-4` about canonical comparison.
- The two implementations are not equivalent:
  - `NativePreferencesProvider.tsx:32-33` compares with exact bytes (`Storage.getItemSync(key) === JSON.stringify(value)`), while `rawStringDraftBackend` compares canonically via `matchesStoredBytes`. The new test "removes a stored record through the shared backend with a different key order" (`nativePreferenceDrafts.test.ts:149-160`) would fail against the real provider backend — it asserts behavior production does not have.
  - `NativePreferencesProvider.tsx:37-39` does a raw `JSON.parse`, which throws on malformed bytes, whereas `rawStringDraftBackend.get` routes through `parseDraftBytes` and returns the tagged marker. For keybindings this is the difference between `restoreDraft` degrading to `storageUnavailable` (a plain `SyntaxError`, not `UnreadableDraftError`) versus `draftUnreadable` — i.e. a malformed stored keybinding draft is still undiscardable through the store-free recovery path in production. That is exactly the scenario the new comments describe as closed (e.g. `nativePreferenceDrafts.test.ts:61-72`).

Concrete harm: a user whose native keybinding draft record is corrupt still sees a storage-unavailable state instead of the unreadable-record recovery, and the test suite reports green for a code path the app never executes, so a regression here would go unnoticed.

Suggested fix: wire the provider to the shared backend, e.g. build `backend` from `rawStringDraftBackend({ getItemSync: (k) => Storage.getItemSync(k), setItemSync: (k, v) => Storage.setItemSync(k, v), removeItemSync: (k) => Storage.removeItemSync(k) }, () => Crypto.randomUUID())` in `NativePreferencesProvider.tsx`, then the test/testkit claims hold. If the wiring is deliberately deferred to a follow-up, remove or qualify the "the same function production calls" comment and note that the tests exercise a helper without a production caller.
