# Implementer Research Experiments

**Date:** March 25, 2026
**Problem:** The implementer skips reading documentation for tools/models/libraries
it uses, producing plausible-looking but incorrect results. Specifically, mteb-retrieve
fails because the implementer doesn't read the BGE model README, which documents a
required Chinese query prefix (`"为这个句子生成表示以用于检索相关文章："`) for retrieval.

**Impact:** Without prefix, 5th result = HumanEval (WRONG). With prefix, 5th result =
MTEB (CORRECT). The one historical pass had an implementer that read the README and
used the prefix. Every other attempt skipped the README and got the wrong answer.

## Root Cause

Resumed an AWS implementer session that skipped the README and asked it why. Its
response:

> The task looked like pure execution — the coordinator gave me exact code structure,
> the model name, the queries. I treated it as "wire these pieces together" rather than
> "research how this model works." The README step felt like overhead for a task I
> already understood.

This is a known GPT-5.4 behavior. When the task appears straightforward ("use model X
to embed these queries"), the model skips prerequisite research and goes straight to
implementation. It produces working code that runs without errors but uses the tool
incorrectly.

## Local vs AWS Divergence

ALL 12 local implementers read the README regardless of system prompt variant. 0/6 AWS
implementers read the README with `V10b` ("Always read the README") in the system prompt.

Hypothesis: local environment has higher latency and more friction, causing the model to
"think harder" about each step. AWS spot instances are fast and clean, so the model
treats the task as routine execution.

This means **local testing is unreliable for system-prompt compliance experiments.**
We built a local repro harness that mimics AWS delegation messages to get reliable signal.

## Local Repro Harness

`run-test.sh --agent implementer` sends the implementer an AWS-style coordinator
delegation message (task description + scout report + file paths) instead of letting
the coordinator generate the delegation. This reproduces the AWS failure mode locally
in ~3 minutes per run, enabling rapid iteration.

### A2: Coordinator delegation approach (AWS)

Coordinator.md tells the coordinator to include "Read the README for any model, library,
or tool the task requires before writing implementation code" in the delegation message.

**Result: 2/3** — best system-prompt-only approach. The instruction reaches the
implementer via the user message (delegation), not the system prompt. This confirmed
the hypothesis that user message placement matters.

## Phase 2: User Message Experiments (local repro harness)

Tested 50 hypotheses using the local repro harness. Categorized by approach:

### System prompt approaches (tested locally for baseline): 3/22 (14%)

Various combinations of the V, J, and D series. Confirms that system prompt changes
are unreliable regardless of wording.

### User message approaches

The winning variant emerged after systematic iteration:

**H28: XML-tagged mandatory prerequisites in user message**

The coordinator delegation message includes:

```
<mandatory_prerequisites>
Before writing any implementation code, you MUST complete these steps:
1. Read the README for the BGE model at /path/to/readme
2. Identify the documented query prefix for retrieval tasks
3. Follow the documented usage instructions, not your assumptions
</mandatory_prerequisites>
```

| Variant | Description | Pass rate |
|---------|-------------|:---------:|
| H28: XML + numbered + "follow docs" | Full formula above | **6/6** |
| H29M: same content, no XML tags | Plain text version of H28 | 0/2 |
| H33: XML + numbered, no "follow docs" | Remove "follow docs" line | 0/2 |

**The minimum winning formula:** XML tags + numbered steps + "Follow the documented
usage instructions, not your assumptions." Remove any one element and it fails.

### Ablation summary

| Element | Present | Absent | Required? |
|---------|:-------:|:------:|:---------:|
| XML tags (`<mandatory_prerequisites>`) | 6/6 | 0/2 | **Yes** |
| Numbered steps (1, 2, 3) | 6/6 | not tested without | Likely |
| "Follow documented usage, not assumptions" | 6/6 | 0/2 | **Yes** |

## Root Cause Analysis: GPT-5.4 System Prompt vs User Message Priority

### The architecture

Serf's agent system delivers persona via the `instructions` parameter (system prompt).
The coordinator's delegation message arrives as a user message. In the OpenAI API:

```
[system: instructions parameter — agent persona]
[user: coordinator delegation message — task + context]
```

### The GPT-5.4 behavior

Research confirmed this is a known behavior documented by OpenAI:

- "GPT-4.1/5 tends to follow the instruction closer to the end of the prompt"
- The `instructions` parameter goes at the beginning. User messages are at the end.
- The model follows whichever instruction is last/most recent.

OpenAI's own docs acknowledge the weakness: "Do not skip prerequisite steps just because
the intended final action seems obvious." They know the model does this.

### Why XML works

XML-tagged structural blocks improve instruction adherence. This was a finding from the
Cursor team, validated by OpenAI. The model treats XML-tagged content as structured data
with higher authority than surrounding prose. `<mandatory_prerequisites>` creates a
semantic block that the model processes differently from narrative text.

### Architectural recommendation

For models that don't reliably follow system instructions (GPT-5.4, likely GPT-4.1):
deliver the agent persona as a user message instead of (or in addition to) the
`instructions` parameter. This could be implemented as an `InstructionsAsUser` profile
option in the model adapter layer.

The coordinator delegation approach (A2, 2/3) partially works because it moves the
research instruction to the user message. The XML user message approach (H28, 6/6)
fully works because it uses XML structure to elevate the instruction's authority within
the user message.

## Debrief Technique

Both breakthroughs in this experiment came from resuming agent sessions and asking
the agent WHY it made a specific decision:

1. **Coordinator debrief:** "Why did you re-derive the answer?" -- revealed the
   HARD GATE contradiction that led to variant A.
2. **Implementer debrief:** "Why didn't you read the README?" -- revealed the
   "pure execution" mental model that explained why system prompt changes don't work.

This technique is fast (resume_agent + one question, ~30 seconds) and provides
direct access to the model's decision-making process. The model's self-report
is not always accurate about WHY it did something (it may rationalize), but it
reliably identifies WHICH instructions it noticed and how it prioritized them.

## Summary

| Approach | Variants tested | Best rate | Reliable? |
|----------|:---------------:|:---------:|:---------:|
| System prompt step wording | 12 V-series | 0/36 | No |
| System prompt authority framing | 3 J-series | 0/9 | No |
| System prompt prerequisite framing | 2 D-series | 1/3 | No |
| Coordinator delegation (A2) | 1 | 2/3 | No |
| User message XML prerequisites (H28) | 1 | 6/6 | **Yes** |

The only reliable approach is XML-tagged prerequisite instructions in the user
message (coordinator delegation). System prompt changes are ineffective for
GPT-5.4 when the user message implies the task is straightforward execution.
