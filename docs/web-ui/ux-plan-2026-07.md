# Web UI: what the study found, and what to do about it

Four participants used the current SPA and the older server-rendered htmx
UI side by side, against the same daemon, on the same tasks. Each was a
different persona; none was told which build was expected to win. This
is what came out, and the plan that follows from it.

The prompt for the study was a plain observation: the old UI "was more
usable and felt like it had better readability and information
architecture." That turned out to be true, and specific.

## The finding, in one sentence

**The current UI does not tell you about time, and it is quiet about
trouble.** Everything else the study surfaced is either an instance of
that or a straightforward bug.

## What all four participants found

Every participant, independently, on different tasks:

**Build B shows per-step wall-clock timestamps and durations with zero
clicks.** `12:10:18 AM · 38ms` on a tool call; `11s · ↑27674 ↓357 ·
~$0.16` on a turn. **Build A shows none of it, anywhere, even fully
expanded.** Aggregate stats exist but are two clicks deep behind
`⋯ → Details`.

This is the single most-repeated result in the study, and it is why the
old build "felt" more readable. It is not typography. Participant 2
measured the type and participant 3 corrected the measurement: both
builds use 16px/600 for the in-pane title, and the old build actually
has *more* size fragmentation (8-9 sizes, down to a 10px tier applied to
code content). The old build reads better despite worse typography,
because it answers questions the new one cannot.

## The three themes

### 1. Time is invisible

A reader cannot answer "how long did this take", "is it still moving",
or "what did that cost" without leaving the transcript. The data exists
— the Details panel proves it — but it is not where the reading happens.

- No per-step duration or timestamp in the transcript at all.
- Per-turn cost and tokens are two clicks deep.
- "Is it still making progress" is answerable only by watching.

### 2. Trouble is quiet

The rail is built to answer "which of these needs me", and it was
silent in exactly the cases where the answer mattered most.

- A `kill -9`'d session dropped out of LIVE and reappeared **visually
  identical to one that finished normally** (`zm6s`, fixed).
- A session blocked on a question showed a small dot and grey caption,
  where the old build showed a full-width amber banner (`zq7g`, fixed).
- A stalled session says "may be stalled" only after ~4.5 minutes
  (`3h2x`, open).
- Redirecting a turn leaves delegate subagents **running orphaned**
  (`znqk`, open) — and one bled into an unrelated session's tool-call
  display (`8525`, open, and the most serious thing still on the list).

### 3. Light theme is half-finished, on both builds

Measured, not eyeballed:

- Build A's secondary/status text — the "Wrote fizzbuzz.py" line that
  appears constantly — is **3.64:1** on white. Below AA (`rdry`).
- Build B's diff-added text is roughly **2:1** (`b05x`).

Neither build is "designed dark-first and abandoned"; both are real but
incomplete passes.

## The plan

Ordered by what a reader loses without it.

**P1 — Put time back in the transcript.** Per-step duration on every
tool call, and per-turn elapsed and cost, visible without expanding. The
data is already on the wire; this is a rendering and hierarchy problem.
Respect the existing preference (`roundTimings` defaults off) — the
question is what someone who turns it on is trying to learn, which is
"where did this turn go", not "here are nine raw durations". Kata `7zkv`
already reworked the raw dump; this is the next step from it.

**P2 — Make trouble loud, and make it arrive quickly.** `zm6s` and
`zq7g` are done. What remains: shorten the stall detection, and stop
orphaning delegates on redirect. `8525` — cross-session bleed — should
be treated as a correctness bug, not a UX one, and looked at first.

**P3 — Finish light theme against measured contrast.** Both failures
above are token-level and cheap. Verify with computed values, not by
eye; the layout guard's harness already renders real `tokens.css` and
can be pointed at contrast as easily as geometry.

**P4 — Cheap wins already filed.** `tbk8` (cold landing has no route
back to a running session — the old build has a one-click "Jump back
in"), `94yg` (the working-directory picker conflates browse-into with
select), `xak9`/`nqzh` (silent clipping in diff and traceback blocks).

## What we should not copy from the old build

It won on information architecture, not on craft.

- Its type scale is more fragmented, and its smallest tier carries the
  most important content.
- Its diff-add contrast is the worst number measured anywhere in the
  study.
- Its cold landing page shows no session state at all (`vw0p`).
- Its steering messages and turn dividers **vanish on reload** (`5pbg`).

The current build is better at 390px status labels, marks a failed step
before you expand it, and has a more disciplined type scale. The goal is
to add what the old build knew, not to return to it.

## Method notes worth keeping

- A one-shot `serf` CLI invocation never appears live in either hub — it
  exits first. Spawn through the hub's own UI, which keeps a managed
  subprocess. Two participants lost time to this.
- Participant 4 filed a kata and then **retracted it** after isolating
  the cause to its own automation tooling corrupting underscores. That
  retraction is worth as much as a finding.
- Personas were never told which build was expected to win, and the
  study contradicted its own prompt twice — on typography, and on 390px
  status labels. A study that only confirms is not measuring.
