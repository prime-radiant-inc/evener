What this costs, honestly

Watch details are not on appwire today. I checked: the only watch-adjacent fields that cross it are ParentWatchGranted on a delegate and SessionMeta.ObservedBy for observer subagents. Neither carries a watch id, note, cadence, or count. So the sidebar rows and the panel need a protocol addition either way — that is the feature, not the countdown.

“Next firing” is a second, separate cost. The runtime holds a time.NewTicker per watch — it never records a next-fire instant. It could be derived for timers from arm time plus interval, but a restarted daemon re-anchors the ticker, so the derived time would silently drift wrong. Making it truthful means storing the next-fire instant in the runtime and carrying it on the wire.

My recommendation: ship the watch projection without a countdown. Show cadence (every 10m) and state (armed), which is true of every watch kind. Add “next firing” later as its own change, for timers only, once the runtime records the instant. The countdown is shown above only so you can see the shape — the — is what a condition watch would honestly show.

Why the expanded block looks like this

  • The note as a sentence, not a field. A watch's note is written to be read aloud when it fires — so it is set as prose, at prose size, and it leads.
  • Facts as a sentence. every 10 seconds · armed 2h 12m · 214 deliveries, 8 dropped says the same thing a key: value grid said, in one pass, in reading order. No definition list.
  • The timeline is history, not forecast. Every mark is a delivery that happened, at the time it happened, with now marked. It makes no claim about when the next one is — which is exactly why it is safe to draw when a countdown is not.
  • A condition watch gets no timeline and says why in one line. Drawing one would imply a schedule that does not exist.
  • Jobs and delegates use the same composition — intent as a sentence, facts as a sentence — so the panel reads as one surface rather than three formats. Terminal output stays preformatted, because it is terminal output.
  • Kept from A: the count on the summary line, inline watch rows in the fold-out, neutral ink, the drawn clock, and no third rail fold.

Data each element needs

  • Row and summary line: watch id, note, cadence, state, delivery count — the existing live projection, once it crosses appwire.
  • Facts sentence: createdAt (exists), delivery counts (exists), last-delivery time (needs the timestamp DeliveryView currently drops).
  • Timeline: per-delivery timestamps and terminal state — durable in the event log today, needs projecting.
  • Runaway facts: RunawayDrops and MaxSelfInfluenceDepth (exist, durable-only).
  • Next firing: does not exist; see the opt-in note above.
