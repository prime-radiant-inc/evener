Mockup #15 — Connection & main-agent errors

Three things break in different ways, and the shipped UI shows them identically: a red row in the transcript. This page separates them so a glance answers the only question that matters — did Serf lose the agent, did the turn fail, or is the system just recovering?

What's wrong today (see crop-liveness.png): a transport drop renders as [error] stream failed: appwire unavailable — a red row inside the transcript, byte-identical to a failed tool, so you can't tell "Serf lost the agent" from "the agent's tool failed". A turn failure (provider/model error) gets no chrome-level promotion and no obvious Retry. And a transient retry / rate-limit renders red — or as a silent gap — a false stall or false failure.
Targets: transport → chrome (not a row) · turn failure → promoted + Retry · transient → neutral/amber, never red · human summary primary, raw [error] on expand.

red = broke (transport lost / turn failed / tool failed) amber = recovering / needs you (reconnecting, retrying) blue = live / the action to take (Retry) neutral = settled / a non-failure (cancelled)

AChrome reconnect banner + queued send

Transport failure leaves the transcript entirely and docks as a full-width banner under the top bar — amber while reconnecting (recovering, not broken), red only if it gives up. The composer flips to a queue: what you type is held and flushed on reconnect, so you're never typing into a dead socket. A turn failure is separate — an inline red end-cap with Retry. Connection is chrome; the turn is content. Tradeoff: a persistent banner steals vertical space and can feel alarming if reconnects are frequent; needs a quick-settle so a 1-second blip doesn't flash the whole banner.

BLiveness-bar takeover

The pinned liveness strip is already the always-reachable home for "is the agent alive?" — and connection state is exactly that question for Serf↔daemon. So put all connection state there: amber "Reconnecting…" on a drop, red "Connection lost" with a Retry if it gives up, and a neutral "retrying" for transient provider backoff. Nothing touches the transcript; the scroll stays pure conversation. Turn failures still get the inline end-cap (they're content). Tradeoff: the liveness bar is at the bottom; a user reading scrolled-up history may not notice the connection died. Pair with a one-shot toast or a top-bar dot for off-screen cases.

CTurn-level red end-cap + Retry

A provider/model error genuinely belongs to the turn, so keep it in the flow — but render it as an explicit end-cap that closes the failed turn: a sans human summary as the primary line, a blue Retry turn, and the raw [error] / request-id folded into mono detail on expand. It reads differently from a failed tool (a red rail mid-turn): the end-cap caps the whole turn. Transport still goes to the chrome; transient retries are a neutral inline chip, never red. Tradeoff: a turn that fails after useful partial work risks burying that work above the end-cap; the summary should name what completed ("112 of 240 shards done") so Retry resumes, not restarts.

DError taxonomy card + collapsed retry counter

One card whose headline is the classification: TRANSPORT (Serf↔daemon), PROVIDER (model/API), HARNESS (tool runner), or CANCELLED (you interrupted — neutral, not an error). Naming the kind makes the transport-vs-turn distinction explicit instead of leaving the user to infer it from a red row. Each kind carries the right action (Reconnect vs Retry turn) and folds its raw [error] + request-id on expand. A run of transient retries collapses to one counter line that only turns red when retries are exhausted. Tradeoff: a card is the heaviest device here — more chrome than a transport drop sometimes warrants; reserve the full card for genuine breakage and keep transient retries as the one-line counter.
