#16 — Blocking needs-you: permission/approval & agent question

These are the cases where the human is the bottleneck: the agent has stopped and wall-clock is bleeding until you act. Two shapes — a permission/approval prompt ("run rm -rf build/? Approve / Deny", with the exact action shown) and an agent free-text question ("which database should this migration target?"). The hard part is colour: a permission prompt is both interactive (a control to operate → blue) and needs-you (it blocks the agent → amber), and the four-colour system has no rule for which wins. And a free-text question, rendered as ordinary hero prose, looks like the agent thinking out loud — so it's missed and the session silently hangs.

What every alt must do: (1) make a blocking entry unmistakably "needs you," glyph-paired so it's colourblind-safe; (2) show the exact action / the literal question, never a paraphrase; (3) keep the resolve action a single obvious press; (4) never let the ask hang off-screen — each shows its scrolled-away fallback. The four alts differ only in how they balance amber (attention) against blue (the control).

The amber-vs-blue resolution carried across all four
  • Amber ◆ owns the container — the box / rail / dock that says this needs you. needs-you is the scarcer, louder meaning, so it claims the frame.
  • Blue owns the primary action — the one button you press to unblock (Approve / Send). interactive + primary is exactly the blue token's job.
  • Neutral owns the secondary — Deny / Later / a plain reply field. Denying is a normal choice, not an error, so it is never red.
◆ needs you / blocking (amber — owns the frame) interactive / primary (blue — owns the button) secondary / settled (neutral)
AAmber container + blue button

The split made literal: an amber-tinted box with a ◆ awaiting heading carries "this needs you"; inside, the primary action stays blue (Approve / Send) and Deny is a neutral outline. Amber labels the attention; blue labels the control — different layers, so they don't compete. The question variant puts the agent's literal question in the same amber box with an inline reply field, so it can never be mistaken for the agent thinking aloud. Tradeoff: two emphasis colours in one element asks the eye to parse a small hierarchy; if amber tint and blue fill are tuned wrong they can read as equally loud.

BAll-amber blocking

Attention wins outright. needs-you is the dominant meaning, so the whole block and its primary button are amber; blue retreats from blocking states entirely. The result is one loud, unambiguous colour — there is no second hue to arbitrate. The block uses an amber left rail (the one device) rather than a full tint, so it doesn't out-shout the agent's prose above it. Deny / secondary stays a neutral outline. Tradeoff: the amber button breaks the global rule that the primary action is always blue — users elsewhere learn "blue = press this," and a lone amber primary can read as a warning to avoid rather than the button to click.

CDocked approval / answer bar above the composer

The directly-targets-"don't let it hang off-screen" alt. The block still lands in the transcript (a quiet amber-rail marker you can scroll past), but the moment the agent blocks an amber bar docks above the composer — where your hands and eyes already are — carrying the summarized ask, the same blue primary / neutral deny, or a reply field for questions. Wherever you've scrolled, the ask is one glance from the input. It clears the instant you answer. Tradeoff: the dock is chrome real estate; with several blocked sessions it must collapse to "N awaiting → " and it duplicates the in-flow block (kept in sync, but two surfaces for one state).

DInline diff- / quick-reply-gated

Answer where the consequence is visible. A permission to edit shows the actual diff inline (amber-framed, desaturated +/−) so Approve means "approve this change," not an abstract yes. A question offers quick-reply chips for the likely answers — each a one-press blue action — plus a free field for anything else. Lowest friction: decide from full context without leaving the transcript. Tradeoff: richest to build and tallest in the flow; the chips need the agent to enumerate plausible answers (a model-side contract), and a long diff still needs the collapse/peek treatment from topic #6 so the approval prompt stays glanceable.

Recommendation

Resolve the colour clash with the split, not by picking one hue: amber owns the container, blue owns the primary action — needs-you is the scarce attention signal so it claims the frame, and the one button you press to unblock is interactive+primary, which is exactly blue's job. That is alt A, and it should be the base grammar for every blocking entry.

Ship A as the inline block, with C's docked bar layered on as the off-screen guarantee. A answers the colour question cleanly and reads correctly in flow; C is the part that keeps the ask from ever hanging off-screen and puts the resolve controls where the hands already are — together they cover "obvious in context" and "impossible to miss." D is the upgrade path: where the permission is an edit, render A's block with the inline diff, and where the question has enumerable answers, offer quick-reply chips — both strictly improve A without changing its colour rules. B (all-amber) is the one to reject: it's the simplest rule but it breaks blue = primary action everywhere else, and a lone amber button reads as a warning to avoid rather than the control to press — losing exactly the affordance a blocked user needs most.

Across all four: amber stays strictly needs-you and is always glyph-paired (◆ awaiting); Deny is neutral, never red (denying is a normal choice); the exact action / literal question is always shown verbatim in machine text; and a soft amber breathing dot on the wait timer is the only motion — honest liveness, not a reassuring spinner.
