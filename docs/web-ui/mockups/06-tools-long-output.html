#6 — Tool calls & long output

Four directions for how a tool cluster summarizes itself, how a long log collapses in two stages, and how the UI stays honest when the server truncated the output or it was never text at all. Each alternative renders the same four cases so they compare apples-to-apples.

Held constant across all four: the purpose leads (what the step was for, not the command); machine detail is demoted to a mono chip; one containment device (a neutral box) per output; done recedes (neutral), running draws the eye (blue), failure stands out (red). Never an "expand · N more" affordance over bytes that were actually dropped.
AMutating-step-first summary
The collapsed cluster headline is the one step that changed something ("Patched the eviction comparison"), with read-only recon folded into a quiet trailing "after 3 reads". You scan a column of clusters and see what the agent did, not how many times it did anything. Trade-off: needs the renderer to classify each call as mutating vs. read-only, and a pure-recon cluster falls back to a lede-less count.

CHead + tail · error-aware peek
Long output shows both ends — the first lines and the last lines, with an elided seam between (logs put the verdict at the bottom). For a failed run the peek is error-aware: it auto-scrolls the failing region into view and marks it with a thin red margin tick (no second box). Stage 2 expands the elided middle inline. Trade-off: two panes cost a little more vertical space than a pure head; the seam needs a real line count to be honest.

DPeek · Ride · Drop tri-state
A single honest status word states what actually happened to the bytes: PEEK (short, shown whole), RIDE (the whole output rode into the agent's context — scroll to read it), or DROP (bytes were truncated/too-big/binary and are gone). DROP never offers a fake "expand"; it offers a real action — re-fetch or download — or admits the data is unrecoverable. Trade-off: a third concept to learn; pays for itself by ending the "expand reveals nothing" lie.
