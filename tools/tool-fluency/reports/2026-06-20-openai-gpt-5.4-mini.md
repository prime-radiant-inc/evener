## Failures

### `job_watch.observer_callback`

Full run status: failed.

Evidence:

- Full run session: `01KVJZEGRP50AD0YJA33HM4MFM`
- Full run state: `/tmp/serf-fluency-openai-all-3/job_watch.observer_callback/rep-01/state`
- Calls: `delegate:1`, `job_watch:2`, `read_file:1`
- First `job_watch` attempt set `send.include_excerpt=true` for `target="caller"`, which is invalid because session-target frames already carry bounded event payloads.
- The second `job_watch` attempt repaired the arguments and installed the watch.

Cleaner targeted rerun after prompt changes:

- Targeted state: `/tmp/serf-fluency-openai-targeted-job_watch.observer_callback/job_watch.observer_callback/rep-01/state`
- Parent session: `01KVJZ323PGWXRQD1DAZP4BVJ2`
- Observer session: `01KVJZ3WV7SEVEH5JXZDMM0PB3`
- `serf-doctor watches` showed one matching delivery, delivered, with no self-loop.
- Observer transcript showed `communicate(await_reply=true, message="OBSERVER_READY")`, then receipt of the watch frame, then an interruption reminder. It never called `delegate_send`.

Root cause:

The model can create the observer and install the watch, and the runtime can
deliver the watch frame. The current noninteractive CLI harness closes the
session immediately after the parent yields, which cancels the watch-delivered
observer resume before it can call `delegate_send(to="caller")`. Full callback
verification needs a live-session or hub-backed runner that can drive the
follow-up `EntryNotification` turn. There is also an argument-fluency issue:
GPT-5.4-mini sometimes tries `include_excerpt` on a caller/session target before
repairing.

- Targeted rerun after adding explicit-tool positive prompting still skipped
  `web_fetch`: `/tmp/serf-fluency-openai-targeted-web_fetch-after-tool-rule`

Root cause:

GPT-5.4-mini answered the familiar `https://example.com` question from model
knowledge despite the prompt explicitly asking it to use `web_fetch` and despite
the tool description saying to call `web_fetch` for requested URL fetches. This
is a model/tool-selection fluency failure, not a runtime error.

## Fixes Made During This Pass

- Added `--fast-cheap-model` to noninteractive `serf` so `web_fetch` can avoid
  an unsupported default auxiliary OpenAI model in CLI runs.
- Added `--fast-cheap-model` passthrough to `serf-fluency`.
- Tightened `communicate` guidance around `await_reply` and the exact
  `output` envelope shape. This removed the earlier `communicate` schema repair
  failures in `read_file.happy_path` and `task_list.plan`.
- Added general positive prompting: when the user explicitly asks for a
  currently callable tool, call that tool before reporting.
- Added positive `web_fetch` tool-description guidance for explicit URL fetch
  requests.

## Recommended Next Work

1. Add a live-session or hub-backed harness to `serf-fluency` for observer
   sidecar probes.
2. Add reusable metrics for max tool calls and first tool call so noisy passes
   are visible without turning every noisy run into a failure.
3. Revisit OpenAI provider aliases for `glob`/`list_dir`; the current
   model-facing name makes two discovery concepts look like one tool.
4. Consider a stronger runtime/tool-choice affordance for explicit tool
   requests. Prompting alone did not make GPT-5.4-mini call `web_fetch`.
