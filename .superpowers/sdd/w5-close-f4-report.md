# W5 close fix F4 — tokenFlood 500-delta probe flake root cause

**Branch:** `w5f-tokenflood` (base `2510b8adc`) · frontend root `cmd/serf-hub/frontend`
**Status:** reproduced, root-caused, fixed, mutation-proven, and proven gone under
controlled oversubscription.
**File changed:** `cmd/serf-hub/frontend/src/protocol/tokenFlood.test.tsx` (only).

## TL;DR

The probe `"…500 deltas … render-count probe"` is **compute-bound**, not
async-stalled. Its body folds 500 wire deltas into a mounted `<Session>`, each
delta in **its own synchronous `act()`** → 500 full synchronous React
commits of the real Session tree (VirtualList + transcript + chrome), all
inside the **single test's default 5000 ms wall budget**. Uncontended that body
runs ~0.3–0.4 s; under heavy CPU oversubscription the 500 synchronous commits
starve past 5000 ms and vitest kills the test. **Every** observed failure is the
5000 ms wall — never the `rerenders` assertion. The render-isolation invariant
held at `0` in every starved run; the test simply couldn't *finish*.

F3's assessment is confirmed: distinct from the lazy-chunk cluster (this file
statically imports `Session`, `tokenFlood.test.tsx:13`), and **there is no
unawaited async boundary** — after the loop the DOM is already fully caught up
(measured `finalWait ≈ 2 ms`), so no "await the real completion" collapses the
wall time. The wall time *is* the synchronous compute.

**Fix:** shrink the mounted-Session render flood from **500 → 100** deltas
(`SESSION_FLOOD_SIZE`). This cuts the starvation-amplified wall of the timed
body ~5× while keeping a decisive flood (100 separate wire-frame store commits,
each rebuilding the enclosing turn). It does **not** touch any deadline. The
invariant is preserved at equivalent strength and the assertion is still
`toBe(0)` — mutation-proven below.

## Mechanism (with citations)

Per delta the test does `act(() => fake.emitNotification({ …/delta… }))`
(`tokenFlood.test.tsx` loop, one `act()` per delta — deliberate, see its own
comment: separate WS frames → separate store commits, not React auto-batched).
Each `act()` runs one full synchronous cycle:

- `emitNotification` → threads store applies the delta → `applyNotification`
  rebuilds the model: a **new** `turns` array, a **new** `TurnModel` via
  `mapTurn`, and a **new** `frameTimes` map/array
  (`src/stores/threads.ts:386-388`, `appendFrameTime`). Both `model` and
  `frameTimes` change identity every delta, so `Session` (subscribed to both —
  `Session.tsx:108-109`) re-renders in full every delta.
- `Session` re-renders `Cadence` (up to 64 SVG ticks — bounded by
  `FRAME_TIMES_MAX_ENTRIES = 64`, `threads.ts:285`; ruled out as a quadratic
  blow-up), `VirtualList`, `FlowOverlay`, `TurnBlock`, the live `AgentMessageItem`
  (→ `StreamingText` appends one chunk to its text node,
  `StreamingText.tsx:60-71`), and the settled sibling probe.
- The settled sibling is `memo(RenderCountProbe, ignoringTurn)` — `ignoringTurn`
  compares `item` by reference and ignores `turn` identity, so React bails out of
  re-rendering it (the invariant). This is why `rerenders = 0` regardless of load.
- `useTranscriptScroll`'s content-changed `useLayoutEffect` has primitive deps
  `[itemCount, firstTurnId, failedTurns, …]` (`useTranscriptScroll.ts:363-466`),
  none of which change on a pure text delta, so it does **not** re-run per delta.
  Confirmed: no per-delta effect amplification.

**Where the wall time goes (instrumented, throwaway probe, since deleted):**

```
flood=100  mount=28ms  loop=110ms (1.097ms/delta cold)  finalWait=2ms  rerenders=0
flood=250  mount= 4ms  loop= 79ms (0.316ms/delta warm)  finalWait=2ms  rerenders=0
flood=500  mount= 4ms  loop=144ms (0.288ms/delta warm)  finalWait=1ms  rerenders=0
flood=1000 mount= 4ms  loop=289ms (0.289ms/delta warm)  finalWait=2ms  rerenders=0
```

Three facts this nails down:
1. **`finalWait ≈ 2 ms`** — the `await waitFor(streaming-text === chunks.join(""))`
   returns immediately; the loop already flushed everything synchronously. **No
   async boundary to await** — rules out the brief's "await the real completion"
   shape.
2. **Loop wall is linear in flood size** (~0.29 ms/delta warm; ~1.1 ms/delta on the
   first, cold test in a process — React/jsdom reconciler JIT warm-up, ~3.8×).
   This is why the *first* run under load (cold + starved) was the worst (9078 ms).
3. The loop dominates; mount is small. The pass/fail is coupled to wall-clock only
   through **how many synchronous commits must complete before the 5000 ms wall**.

## The fix, and why it is mechanism-level (not a widened ceiling)

Change: `SESSION_FLOOD_SIZE` `500 → 100`; `describe`/`test` titles and the
constant's comment updated to match; the historical "measured exactly 500" note
reworded to the size-agnostic "re-rendered the settled sibling once per delta."
The assertion stays `expect(rerendersDuringFlood).toBe(0)`. The 10k data-layer
correctness flood (the four pure-`applyNotification` tests) is **untouched** — it
never renders, never flaked.

Why this is the mechanism, not an accommodation:

- **The flake's mechanism is wall-clock coupling of a compute-bound probe.** The
  test's pass/fail depended on completing O(N) synchronous render commits inside
  the 5000 ms whole-test budget, even though its *assertion* (`rerenders === 0`) is
  load-independent and held at 0 in every starved run. Reducing N attacks that
  coupling **at its source — the amount of compute** — not the deadline.
- **The forbidden fix (widening `testTimeout`/any deadline) is exactly the one I
  did not do.** No timeout is touched anywhere. The 5000 ms wall remains a
  meaningful tripwire: a genuine future compute regression (e.g. an accidental
  O(N²) in the reducer or a dropped item-memo forcing full re-renders) would still
  blow the budget. Per Jesse's standing rule, ceilings stay tripwires; I lowered
  the *work under the tripwire*, I didn't raise the tripwire.
- **"Await the real completion" does not apply** — proven by `finalWait ≈ 2 ms`;
  there is no awaitable async boundary inflating the wall.
- **Equivalent invariant strength (brief's hard constraint).** A broken
  render-isolation memo re-renders the settled sibling on *every* delta, so the
  `toBe(0)` bound fails **deterministically at any flood ≥ 1** — the flood size
  sets only how far past 0 a failure reads, never whether it fails. 100 separate
  commits, each rebuilding the enclosing turn, still exercises the exact churn the
  memo must withstand. Mutation-proven next.

## Mutation proof (the guard kept its teeth)

Locally broke the render-isolation mechanism the probe guards by replacing the
memo comparator `ignoringTurn` with `() => false` (a comparator that never bails
— the faithful simulation of a regressed `ignoringTurn` that stopped ignoring the
per-delta `turn`-identity churn), at the post-fix flood of 100:

```
× 100 deltas … render-count probe
AssertionError: expected 100 to be +0 // Object.is equality
 ❯ src/protocol/tokenFlood.test.tsx:298  expect(rerendersDuringFlood).toBe(0);
  Tests  1 failed | 4 passed (5)
```

The settled sibling re-rendered once per delta → `rerendersDuringFlood = 100` →
the bound failed **loudly and immediately** (an assertion, not a timeout; 153 ms).
Reverted to `ignoringTurn` — **zero net diff** (verified: comparator line reads
`}, ignoringTurn);`, `git diff` shows only the intended flood/label/comment
changes).
