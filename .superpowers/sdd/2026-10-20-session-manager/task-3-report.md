# Task 3 implementation report — 2026-10-22

## Result and actual API

Manager input now follows the hub's extracted human `(*sessionOperations).Start`, `Queue`, and `Steer` methods in `cmd/evener-hub/session_input.go`. The original AppWire human RPC closures call those methods. Manager dispatch calls them with a proof derived from the authenticated bound session in `cmd/evener-hub/session_tools.go`. The target runtime resolves that proof against its live binding; it never takes the actor from tool arguments or silently calls a human callback when the Manager callback is absent. The direct human methods remain and call the same retry-safe owner with `schema.SessionActor{Kind: "human"}`. The new methods are `(*Session).AcceptClientMutationStartAs`, `QueueAs`, `SteerAs`, and `ResolveSandboxEscalationAs`; their first durable acceptance fixes the actor for later retries, including a retry by the other actor.

`appwire.SessionOperationRequest.Control` holds the closed `SessionControlRequest{Approval *SandboxEscalationResolveParams}` union, and the response carries the matching empty result and authenticated actor. `(*sessionOperations).Control` calls the pre-existing approval owner; a stale decision fails rather than reporting success. `delegate_send(to=<canonical source-qualified ref>, input_mode=start|queue|steer, client_mutation_id, expected_instance_id, message|input)` supplies the corresponding typed human receipt. `session_control(action=approval, arguments={ref,escalationId,approve})` is available only with Manager enabled. Owned `delegate_send(to=dlg_...)` retains its original branch. No `ProcessInput` call or new question/approval ledger was added.

The actor persists in journal records, queued and steering input, pending mutations, user/steering turns, and approval notices. The strict forensic mutation reader in `agent/doctor/mutations.go` was extended to understand this persisted field without accepting unknown fields. The shared TypeScript transcript reducer preserves typed `actor` through hydration and merge. Web `UserMessageView`, also used by user steering, and native projected user rows label Manager messages with the Manager session ref while legacy human labels remain unchanged. `docs/daily-work.md` describes the new controls and current limits.

## 2026-10-22 fix round: actor must name the manager, not the worker

The earlier description of the Manager proof above is superseded here. Its `managerRef` incorrectly named the worker: `sessionInputProof` copied the calling runtime's binding ref into `Actor.ManagerRef`, then the target runtime compared that claimed label to its own binding ref. A real two-daemon `manager-origin` to `worker` input now persists and projects `local:manager-origin`, not the worker ref.

`SessionActorProof` now separates `CallerRef` (the authenticated `caller.Ref` from hub admission) from `BindingID` (the destination worker's live binding). Hub admission checks that its caller ref matches the binding of the Manager making the call. The local target source stamps the binding ID of the actual bound target connection before forwarding start, queue, steer or approval; the target runtime validates that ID against a valid live binding, checks the caller ref grammar, rejects a label equal to itself or a separately forged `Actor.ManagerRef`, and derives the persisted actor label exclusively from `CallerRef`. A worker does not need Manager enabled to accept an authorized Manager's input. The ordinary human input path still has no proof and is unchanged.

After the caller split and destination binding fix, it passed (`server 0.299s`, `hub 1.627s`); the real worker's on-disk journal contains the manager caller, and the shared transcript projector renders that same saved actor as the manager caller.
