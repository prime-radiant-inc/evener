# reconnect-button-source-hub: kill -9 mid-stream surfaces source=hub diagnostic with working Reconnect & retry button

**What this covers**: kata `0e7h`. The user-visible half of the e465
chain (commit `b46d0de`): when a `source=hub` diagnostic is rendered,
the diagnostic card must show a `Reconnect & retry` button (not
`Retry turn`), and clicking it must re-issue the last user turn —
which goes through the same `MethodTurnStart` auto-resume path that
`reconnect-auto-resume.md` exercises transparently. This is the
escape hatch for cases where the user already SAW a failure (because
the daemon died mid-stream) and is staring at a dead session.

The companion `reconnect-auto-resume.md` covers the silent server-
side path (Layer 3 in the mggf design). This scenario covers the
user-visible button (Layer 2).

## Pre-state

- Hub running on `0.0.0.0:9180` with `--serf` configured (so the
  spawner can launch fresh daemons on `MethodTurnStart`).
- Browser authorized for the hub (visit `/auth?token=<value>` once;
  token is in `/home/jesse/.serf/auth-token`).
- A fresh session whose daemon you can identify by PID. Spawn one:
  ```bash
  curl -sS -H "Authorization: Bearer <token>" \
       -H "Content-Type: application/json" \
       -X POST http://localhost:9180/api/spawn \
       -d '{"prompt": "Write a 5-paragraph essay about clouds, very slowly and verbosely.", "model": "anthropic/claude-haiku-4-5-20251001"}'
  ```
  Capture the returned `session_id`.
- The streaming-text prompt above matters — see Sharp edges. Killing
  mid-tool-call leaves the transcript with an orphaned `tool_use`
  and the retry surfaces a provider error from the next Anthropic
  call, which muddies the proof.

## Steps

1. Spawn the session as above. Get the daemon PID from the
   rendezvous file:
   ```bash
   jq -r 'select(.session_id == "<session_id>") | .pid' \
     /home/jesse/.serf/run/*.json
   ```
2. Navigate to `/s/<session_id>` in the browser. Confirm the page
   loads, the user message appears, and an assistant message starts
   streaming text.
3. Within 1-2 seconds of seeing assistant text begin streaming,
   `kill -9 <pid>` the daemon. Confirm the process is gone
   (`ps -p <pid>` returns no row).
4. Wait ~2-3 seconds for the page to react.
5. Read the diagnostic card(s) now in the conversation.
6. Confirm:
   - At least one card has class
     `diagnostic diagnostic-error diagnostic-source-hub`.
   - Its message text starts with `Local daemon unavailable: failed
     to WebSocket dial:` (the literal string is generated by the hub
     when `SubscribeThread`/`ReadThread` dials the dead rendezvous
     and gets ECONNREFUSED).
   - The card footer contains a button whose text is exactly
     `Reconnect & retry` (NOT `Retry turn`).
7. Click the `Reconnect & retry` button.
8. Within ~10 seconds:
   - A NEW daemon process appears with `--resume <session_id>` in its
     argv (e.g. `ps -ef | grep <session_id>`).
   - A new entry under `/home/jesse/.serf/run/` for the new PID.
   - The transcript grows: a fresh assistant message is generated
     by the resumed daemon (this is the retry succeeding through
     `MethodTurnStart` → `hubThreadResume` → `startTurn`).

## Expected

- After step 5: a diagnostic card with badge `Hub error`, source
  class `diagnostic-source-hub`, message including "websocket" or
  "WebSocket dial" verbiage. The classifier routes on `websocket`
  → `isHubFailure` (`cmd/serf-hub/assets/diagnostics.js`), and the
  renderer also hardcodes `source: "hub"` on the appendBanner call
  in `renderer.js:288` — both paths agree.
- After step 6: the button label is `Reconnect & retry`. The
  branch is in `renderer.js::buildDiagnosticActions`:
  ```
  const label = source === "hub" ? "Reconnect & retry" : "Retry turn";
  ```
- After step 8: the retry completes. A new assistant message
  appears with fresh content (the model regenerates; the killed
  partial response is NOT recovered — the resumed daemon starts
  the turn over from the user message).
- Falsification A: the button reads `Retry turn`. The diagnostic was
  classified as `source=provider`, not `source=hub` — the message
  or the classifier broke. Verify with the eval payload below.
- Falsification B: clicking the button surfaces
  `reconnect failed: appwire unavailable` or another inner error,
  and no new daemon spawns. The MethodTurnStart auto-resume path
  regressed (kata `e465` itself broke).
- Falsification C: the button does nothing (no new daemon, no new
  banner, no new assistant message). The onclick wiring in
  `makeRetryTurnHandler` broke.

## Cleanup

- Kill the respawned daemon if you don't want it lingering:
  ```bash
  ps -ef | grep "<session_id>" | grep -v grep | awk '{print $2}' | xargs -r kill
  ```
- The original killed daemon's stale `/home/jesse/.serf/run/<pid>.json`
  is left behind by `kill -9` (it skipped cleanup). Remove it:
  ```bash
  rm -f /home/jesse/.serf/run/<original-pid>.json
  ```
- The session itself stays on disk under
  `~/.local/state/serf/projects/<hash>/sessions/`. Safe to leave.

## Sharp edges

- **Kill mid-streaming-TEXT, not mid-TOOL-CALL.** A live recording
  showed: if you kill while a `bash` tool call is in flight, the
  transcript gets a `tool_use` block with no matching `tool_result`.
  After reconnect, the resumed daemon replays the transcript at
  Anthropic and gets `messages.X: tool_use ids were found without
  tool_result blocks immediately after` — a `source=provider` error
  card on TOP of the original `source=hub` card. The Reconnect button
  still works (it spawns a fresh daemon and re-issues the user
  text), but the next assistant turn ALSO fails, which muddies the
  proof that "reconnect succeeded". Use a long-running text-only
  prompt (like the cloud essay above) to get a clean E2E.
- **`kill -9` vs `kill -TERM`**: TERM gives the daemon time to flush
  state and remove its rendezvous file. The hub then sees no
  rendezvous → falls into `hubThreadResume` BEFORE the user is shown
  anything → invisible resume → no diagnostic card → no button to
  click. Only `kill -9` (or `kill -KILL`) leaves the rendezvous file
  in place pointing at a dead PID, which is what produces the
  "WebSocket dial: connection refused" message we need.
- **Timing window**: kill DURING the assistant stream — after the
  daemon has accepted `MethodTurnStart` and started writing
  notifications, but before it sends `turn.complete`. If you kill
  too early (before the relay even subscribed), the hub may
  auto-resume in `MethodTurnStart` itself (the `shouldResumeAfterTurnStartError`
  branch) without ever surfacing a diagnostic.
- **Multiple diagnostic cards**: it's common to see 2-3 duplicate
  hub-error cards. The relay tries to re-subscribe a couple of times
  before giving up, and each failed attempt emits a banner. This is
  expected; the test only requires AT LEAST ONE has the correct
  source class and button label.
- **Why `websocket` matches**: the classifier's `isHubFailure`
  pattern list is in `diagnostics.js`. The literal substring
  `websocket` (lowercased) appears in the underlying Go error from
  `nhooyr.io/websocket` when dialing a dead port: `failed to
  WebSocket dial: ...`. If the underlying client library is ever
  swapped (e.g. to gorilla), the error verbiage may change and this
  classifier path may silently regress to `source=serf` → reclassify
  to `source=provider` via the 96pr override (since
  `connection refused` doesn't match any provider pattern, it would
  fall back to `serf`). Either way, the button label changes — and
  this scenario catches it.
- **Why `reconnect-auto-resume.md` doesn't catch this**: that
  scenario kills the daemon BEFORE the user is viewing the session,
  so there is no live relay to fail. The hub's `MethodTurnStart`
  auto-resume fires on the very next user send and silently
  succeeds. This scenario specifically requires the user to be
  watching (a live relay open) when the daemon dies, which is the
  only path that surfaces a hub-source diagnostic to the UI.
